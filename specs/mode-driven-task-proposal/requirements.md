# 按 Run 选择的任务提案模式与独立 GoalPlan 需求

## 审批摘要

### 目标

普通 Run 直接依据用户请求执行；用户通过 `/plan` 为单个 Run 选择先提交提案、经审批再继续。Plan Prompt 要求 Agent 先提案，但 Runtime 不按 `isReadOnly` 在审批前额外屏蔽已授权业务 Tool，因此该顺序不是无副作用保证。GoalPlan 独立保存计划进度，可由明确获授权的模式通过 Tool 使用；Benchmark 使用普通 Run，评测条件只作为执行上下文或外部评分输入。

### 范围

- 包含：`/plan` 对单个 Run 的选择与恢复、普通模式直接执行、任务提案审批、GoalPlan 的按需创建与跨 Run 保留、单 Run 多 Todo、计划展示及完成判定。
- 不包含：实现其他新模式、向普通模式默认开放 GoalPlan 更新 Tool、审批 GoalPlan 内容、Todo 与 Run 一对一绑定或自动执行后续 Run。

### 核心行为

- 无参数 `/plan` 在持久化 `run_started` 提交前选择当前或下一 Run 的提案审批模式；命令本身不是用户任务消息，模式切换与 `run_started` 并发时按持久化提交顺序线性化，提交后拒绝切换。
- 普通模式不生成任务提案或任务审批等待点，可直接调用已授权 Tool；Tool Policy、Action 审批和完成证据仍适用。
- `/plan` 模式的 Agent Prompt 要求在调用业务 Tool 前先提交当前 Run 的提案；Runtime 不依据 `isReadOnly` 实施审批前 Tool 门控，所有业务 Tool 仍由既有 Tool 授权、Tool Policy 和 Action 审批规则控制。提案进入等待点后，用户响应前不得继续模型或 Tool 调用；反馈使旧提案失效，批准只对当前 Run 有效。
- GoalPlan 不依赖 `/plan` 存在；获授权模式可通过同一 Tool 创建和更新它。普通模式默认不能更新，但已存在的计划保留并可查看；GoalPlan 内容不授予执行权限，也不属于任务审批对象。
- 一个 Run 可顺序推进多个 Todo；将 Todo 标记完成必须引用当前 Run 已提交 Observation，旧 Run 或未提交证据无效。Run 满足自身任务完成条件后可以结束；未完成 Todo 保持原状态，不自动完成、取消或启动新 Run。
- Benchmark 不进入 Plan Run 或任务提案审批；`completionCriteria` 只作为执行上下文或外部评测输入，Run 完成仍受 Observation 证据约束，最终成功由 Benchmark 环境评分判定。

### 风险与待确认

- 风险等级：**high**；理由：改变提案审批与既有 Tool 授权的关系、Run 模式范围，以及 GoalPlan 与 Run 的持久化和完成语义。
- 关键操作：普通模式与 `/plan` 提案审批前均可能调用已通过既有授权规则的写入 Tool；本需求不授权运行真实外部副作用。
- 风险：Prompt 只能引导 Agent 先提案，不能形成 Runtime 级副作用隔离；旧的 Goal 级 Plan Mode、一个 Todo 对应一个 Run、Benchmark 自动批准提案等规则与本需求冲突。实现必须保持 Tool Policy、Action 审批、当前 Run 证据和恢复边界有效。
- 待确认：无。

## 引言

本功能把任务提案审批变为单个 Run 的显式选择，并让 GoalPlan 成为可由不同模式按授权使用的独立计划状态。普通执行无需先等待提案审批，计划进度也不决定 Run 是否可以完成。

## 需求

### 需求 1：为单个 Run 选择提案审批模式

**用户故事：** 作为用户，我希望用 `/plan` 只规划当前任务，以便后续任务默认恢复直接执行。

#### 验收标准

1. <a id="req-1-1"></a> 当用户在新 Goal 的任务输入前，或在已完成 Run 的下一次任务输入前提交无参数 `/plan` 时，系统必须把随后启动的一个 Run 设为提案审批模式；命令不得成为 Goal 消息或 Run Step。
2. <a id="req-1-2"></a> 当当前 Run 已创建且持久化 `run_started` 尚未提交时，用户提交无参数 `/plan` 必须使该 Run 进入提案审批模式；Coordinator 必须将模式选择与 `run_started` 提交串行化，使并发命令按提交顺序确定结果；同一 Run 重复提交不得产生第二次模式切换或审批请求。
3. <a id="req-1-3"></a> 当已选择 `/plan` 的 Run 结束后，后续新 Run 必须默认直接执行，不得沿用该 Run 的模式或任务审批结果；已接受但尚未用于启动 Run 的选择在已有 Goal 重启后必须仍只作用于下一 Run。
4. <a id="req-1-4"></a> 如果 `/plan` 带有参数、当前 Run 的持久化 `run_started` 已提交，或当前 Run 正在等待其他交互且尚未处于提案审批模式，系统必须拒绝本次切换，不得改写消息、模式、审批或 GoalPlan 状态。

### 需求 2：普通模式直接执行用户请求

**用户故事：** 作为普通模式使用者，我希望任务无需先提出并批准执行方案，以便直接推进已提交的请求。

#### 验收标准

1. <a id="req-2-1"></a> 当 TUI、CLI 或 Headless 入口以普通模式启动 Run 时，系统必须以该 Run 的用户请求作为执行目标，不得自动生成任务提案或进入任务审批等待点。
2. <a id="req-2-2"></a> 当普通 Run 请求业务 Tool 或完成任务时，系统不得仅因缺少已批准的任务提案而拒绝；Tool 授权、Action 审批以及当前 Run 的完成证据校验仍必须生效。
3. <a id="req-2-3"></a> 当普通 Run 缺少会实质影响范围、正确性或授权的用户信息时，Agent 仍可提问并等待回答；系统不得把该回答或模型自述冒充已提交的 Tool Observation 或用户批准的任务提案。
4. <a id="req-2-4"></a> 当普通 Run 的模型请求任务提案审批或未经授权更新 GoalPlan 时，系统必须拒绝该决策，且不得创建等待点或改变 GoalPlan。
5. <a id="req-2-5"></a> 当 Benchmark 入口启动 Run 时，系统必须使用普通模式且不得生成或自动批准任务提案；`completionCriteria` 只能作为执行上下文或外部评分输入，不得成为获批 Task 或 Runtime 完成门槛，Run 完成仍受当前 Run 的 Observation 证据规则约束，Benchmark 环境评分必须作为最终成功判定依据。

### 需求 3：`/plan` 模式审批当前任务

**用户故事：** 作为选择 `/plan` 的用户，我希望 Agent 按先提案再调用业务 Tool 的顺序工作，并可批准或反馈，以便明确本次任务范围。

#### 验收标准

1. <a id="req-3-1"></a> 当 `/plan` Run 尚无已批准提案时，Agent Prompt 必须要求先提交包含目标与可验证完成条件的提案，再调用业务 Tool；Runtime 不得仅因提案尚未批准或 Tool 的 `isReadOnly` 值而新增 Tool 门控，业务 Tool 仍须通过既有 Profile、Tool Policy 和 Action 审批；Run 不得宣称完成。
2. <a id="req-3-2"></a> 当 Agent 提交包含目标、可验证完成条件和审批请求的任务提案时，系统必须保存可恢复的审批等待点并向用户显示提案；在用户响应前不得继续调用模型或 Tool。
3. <a id="req-3-3"></a> 当用户批准与当前 Goal、Run 和请求 ID 匹配的提案时，系统必须将其固定为该 Run 的任务范围并继续执行；用户反馈时必须使旧提案失效，将反馈送回同一 Run 以重新提案。
4. <a id="req-3-4"></a> 当 GoalPlan 在提案审批前后发生变化时，系统不得把 Todo 视为审批内容或执行授权，也不得仅因 Todo 更新而要求重新批准任务提案。

### 需求 4：GoalPlan 独立供获授权模式使用

**用户故事：** 作为需要计划进度的使用者，我希望 GoalPlan 能随 Goal 保存，并由有权限的模式使用，以便计划不被某一个交互模式独占。

#### 验收标准

1. <a id="req-4-1"></a> 当用户仅提交 `/plan` 而尚无成功的 GoalPlan Tool 操作时，系统不得为该 Goal 创建空 GoalPlan；获授权模式首次成功创建或更新计划时，系统必须保存该 Goal 的唯一 GoalPlan。
2. <a id="req-4-2"></a> 当某个模式获得 GoalPlan Tool 使用权时，系统必须允许它对同一 GoalPlan 执行结构化增量操作；操作权限不得以当前 Run 是否由 `/plan` 启动作为唯一判断条件。
3. <a id="req-4-3"></a> 当普通模式未获得 GoalPlan Tool 使用权时，Agent 不得创建或更新 GoalPlan；如果 Goal 已保存 GoalPlan，普通 Run 及界面仍必须能读取其已提交状态，且不得因进入普通模式而删除它。
4. <a id="req-4-4"></a> 当 GoalPlan Tool 创建或更新 Todo 时，系统必须分配并保持稳定 ID，按当前 revision 原子提交合法状态变更；未知 ID、过期 revision 或非法变更必须整体拒绝，原计划保持不变。

### 需求 5：单个 Run 可推进多个 Todo

**用户故事：** 作为计划模式使用者，我希望在一个任务执行过程中连续更新多个 Todo，以便计划项代表步骤而非必须拆成多个 Run。

#### 验收标准

1. <a id="req-5-1"></a> 当 `/plan` Run 使用 GoalPlan 执行多个 Todo 时，系统必须允许这些 Todo 在同一个 Run 内按合法状态转换推进，不得因切换到下一个 Todo 而自动结束当前 Run 或创建新 Run。
2. <a id="req-5-2"></a> 当 Agent 请求更新 Todo 状态时，系统必须通过已授权的 GoalPlan 操作保存结构化计划事实；聊天文本、任务提案或 Run 状态变化不得被解析为 Todo 更新。
3. <a id="req-5-3"></a> 当当前 Run 的任务目标和完成条件已通过适用的证据校验时，即使 GoalPlan 尚有未完成 Todo，系统也必须允许该 Run 完成；未完成项必须保留原状态，不得自动标记完成或取消。
4. <a id="req-5-4"></a> 当 Run 结束而 GoalPlan 仍有未完成 Todo 时，系统不得仅凭这些 Todo 自动创建或推进后续 Run；下一次用户任务输入按新的 Run 模式处理。
5. <a id="req-5-5"></a> 当 Agent 将 Todo 标记为完成时，系统必须要求该操作引用当前 Run 已提交的 Observation；引用旧 Run Observation、未提交 Observation 或不存在的 Observation 时必须无副作用拒绝整个计划更新。

### 需求 6：计划与审批分别展示

**用户故事：** 作为会话使用者，我希望明确区分待批准的任务提案和可持续查看的计划进度，以便不会误以为 Todo 已获得执行批准。

#### 验收标准

1. <a id="req-6-1"></a> 当 `/plan` Run 等待任务批准时，界面必须展示当前提案及批准、反馈操作；普通 Run 不得显示不存在的任务审批等待点。
2. <a id="req-6-2"></a> 当 Goal 已有 GoalPlan 时，界面必须从最新已提交的 Goal 状态展示 Todo 及其状态，即使当前 Run 处于普通模式；GoalPlan 不存在时不得展示推测生成的计划。
3. <a id="req-6-3"></a> 当任务提案、用户反馈、GoalPlan 更新或执行 Observation 提交时，会话时间线必须保持原有顺序；恢复或迟到通知不得覆盖较新的审批状态和计划版本。

### 需求 7：模式、交互与计划可恢复

**用户故事：** 作为长任务使用者，我希望重启后回到同一个 Run 的正确模式和等待点，以便不会重复审批或错误执行。

#### 验收标准

1. <a id="req-7-1"></a> 当系统接受 `/plan` 选择、任务提案、批准、反馈或 GoalPlan 更新时，必须在继续模型或业务 Tool 前保存对应的 Run 身份、模式、交互和计划状态；重启后必须恢复最后一次已提交状态。
2. <a id="req-7-2"></a> 当用户提交的审批或反馈请求 ID 不属于当前 Goal 和 Run，或对应提案已失效时，系统必须无副作用拒绝，并保留当前有效等待点。
3. <a id="req-7-3"></a> 当保存失败、快照损坏或模式与交互状态不一致时，系统必须停在最后一次有效提交边界，不得猜测审批结果、调用副作用 Tool 或把未提交 Todo 标记为完成。
4. <a id="req-7-4"></a> 当 Run 在普通模式或 `/plan` 模式下完成时，系统必须继续按当前 Run 的已提交 Tool/Observation 核验完成声明；旧 Run 事实、用户回答和任务提案不得成为当前 Run 的完成证据。
