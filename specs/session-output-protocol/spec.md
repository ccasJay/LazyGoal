# 会话输出协议与正式消息 Spec

## 目标与范围

LazyGoal 将同一 Goal 的状态同步、输入结果、公开生成内容、正式消息、工具活动、人工交互和 Run 结算组织为一条类型化会话输出。消费者可以区分“正在生成”“候选待确认”“已保存消息”和“Run 已完成”，并按稳定身份将实时预览与持久化结果关联。

本次定义内部 Session 输出及 HTTP／SSE 映射，为真实对话增加稳定消息身份、来源和用途，支持最终答复候选预览、混合工具响应的正式过程消息、原生历史来源去重，以及有界消息查询和断线同步。最终答复仅在现有完成校验／审查接受并保存成功后成为正式消息；过程正文同样须由完整有效响应和 Runtime 提交产生。预览不授权工具、不代替审批、不作为证据。

本次依赖已批准的 streaming-session、model-output-streaming 及 human-interaction：分别复用会话受理／同步、模型块来源和规范交互视图，不另建队列、执行器或持久化 Session。action-approval-revision 保持自己的批准／修订规则，输出在其接入时忠实表达当前请求和实际执行版本。本次不提炼 SDK，不重做 Web 布局，不增加图片、MCP、子代理、思考公开、Provider 协议或分布式事件存储；不改变默认 Queue、显式 Steer／Interrupt、重启显式恢复、完成证据、授权或重试规则。

## 需求与验收标准

### 需求 1：单一且类型明确的会话输出

作为会话调用方，我希望通过同一协议观察完整过程，而不用从临时文本猜测执行状态。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当订阅一个 Goal 时，应复用基础会话的一致 `state_sync` 与长期订阅，输出该 Goal 跨 Run 的输入结果、公开生成、正式消息、工具活动、交互、运行状态、终态结果及流故障；同一 Run 结束不得关闭整个 Session。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当消费输出时，应能通过可辨识联合区分事件语义和其来源，携带必要 Goal／Run、输入、消息、模型调用／块、Action 或交互引用；不得把所有事件包装成聊天文本，也不依赖任意 `kind: string` 和未知 payload 猜测业务。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当收到已受理输入、生成结束、已保存消息或工具结果时，应分别表达对应事实；输入已受理不等于已应用，模型结束不等于正式消息或 Run 完成，实时工具返回不等于 Observation 已提交。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当通过内部无界面句柄或 Web 观察相同状态时，应获得一致的公开含义、身份和提交关联；wire 只做受授权的序列化与边界校验，不另推断 Runtime 状态或创建第二套输出事实。
- <a id="spec-req-1-5"></a>**验收标准 1.5**：当只消费完整结果、关闭自身订阅或遇到观察故障时，应沿用基础会话的结果查询与资源边界；不得为观察重启执行、自动回复交互、批准操作或取消其他连接及已受理工作。

### 需求 2：稳定且可查询的正式消息

作为用户，我希望保存后的消息刷新、重试或切换 Run 后仍可准确定位。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当真实用户或助手消息进入 Goal 时，应在其所属提交中保存稳定 `messageId`、Run 归属和必要来源；助手消息明确区分过程、最终答复及既有等待／失败等通知用途，保留当前 user／assistant 角色。不得用数组位置、正文哈希或当前选中 Run 代替身份。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当同一输入应用、模型正文或完成候选的提交重试时，应按来源关联原消息，不重复追加；同一来源出现不一致内容应明确失败。消息及其来源／提交关联与所属 Snapshot 变更共同保存，保存结果不明时先读取核对，不能用新消息身份绕过不确定提交。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当正式消息发布时，应在保存成功后发送带 `messageId` 和提交修订的通知，并关联对应预览来源；重复通知只更新同一条消息。已提交正文不可被后续分片修改，文本相同但来源不同的消息不得误合并。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当从存储重建、读取历史 Run 或分页时，应保持消息身份、来源、顺序和 Run 归属，继续满足既有 messageRange／上下文索引规则；队列项未应用及纯控制命令不伪装为用户对话消息。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当同步或消息通知只返回有界正文／最近消息时，应明确截断与范围，并提供同一权限边界下按稳定身份分页读取消息及正文的只读能力；不存在与读取失败不得混淆，不可把截断正文标为完整或声称历史已全部同步。

### 需求 3：最终答复候选的安全预览与结算

作为用户，我希望尽早阅读候选答案，同时清楚它是否已经通过审查并保存。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当本次 Decide 请求中已声明的 `system_complete_task` 产生可安全提取的 `summary` 时，应提供带稳定来源及候选身份的预览，并始终标明未确认；只有字段值可公开，不能把整个参数对象、Evidence、Memory Patch 或私有完成审查内容广播出去。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当 summary 字符串跨分片时，应正确处理 JSON 字符串转义、Unicode 和字段嵌套，按解码后的字段值提供有序增量；不得用正则、执行表达式、猜测缺失字符或扫描同名嵌套字段代替解析。工具身份或字段归属不能可靠判定时，应等待完整块再投影，不承诺所有供应商都逐字预览。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当完整候选完成生成但尚未接受时，应表达待确认状态；只有现有协议／语义／阶段／Evidence／完成审查全部满足，且对应 Runtime 消息已保存后，才以正式消息通知结算候选。中间阶段接受不能被标记为 Run 最终答复或终态。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当候选被确定性拒绝、审查拒绝、模型调用失败／取消、被 Runtime 因 Steer 等规则弃用或被新候选替代时，应明确作废相应预览，不写作正式答复或完成证据，不改变原有重试／修复预算；候选作废不等同于 Run 失败。新的调用或候选不得继续追加旧预览。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当保存已开始但结果不能确认时，应保持待核对状态并按最新 Snapshot 判断是否已提交；读取失败暴露同步故障，不提前作废或宣布正式成功。若增量解析出现歧义或预览与最终规范 summary 不一致，应作废该预览，不把预览重新标记为有效；正式消息仍以完整校验和真实提交为准，明确关联替换来源。
- <a id="spec-req-3-6"></a>**验收标准 3.6**：当仅有整块参数、宿主提供的完整阶段结果或不可增量提取的内容时，应仍能在可用时提供完整候选并走相同提交关联，不伪造打字增量或模型来源。预览处理故障只影响观察，不得修改候选、跳过校验、触发工具或改变执行结果。

### 需求 4：正式过程消息与模型历史去重

作为用户，我希望保留“先检查配置”等真实过程正文，但不让模型把同一段话重复读入上下文。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当同一模型响应包含公开正文和工具调用时，应在整次响应成功、通过现有阶段检查并由 Runtime 接受后，将普通正文块保存为有来源的过程消息；按块保留顺序，不保存 reasoning、结构化协议 JSON 或任意工具参数。响应未通过检查时只能保留临时预览。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当过程消息随被接受的请求进入提交时，应与其模型来源及当前执行边界一起保存，不因消息本身增加 Step、模型调用或工具执行；后续工具失败或等待审批不将已保存过程正文改写为工具成功。零工具正文继续沿用既有受理／修复行为，私有 Think 和完成审查不因此成为聊天消息。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当最终模型请求已经包含覆盖某过程消息来源的已结算原生交换时，应按来源省略重复对话正文；只有实际进入本次请求的同身份交换可以覆盖对应消息。不能按字符串相同删除用户消息、其他调用或独立答案，也不能删除原生调用／结果配对。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当原生交换尚未结算、被上下文预算淘汰、切换模型／协议身份或不存在时，应保留仍在对话预算范围内的正式过程消息；覆盖判定与最终预算、裁剪和请求渲染一致，不能因曾有原生来源而永久隐藏正文或在预算估算后临时拼出另一份请求。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：当重建并再次组装上下文时，应能从当前持久化消息来源和已提交轨迹恢复同样的去重判定，保留原始模型调用、结果和修订说明；不从诊断 Trace、浏览器文本、未提交 tail 或旧模型配置猜测来源。

### 需求 5：工具、交互与 Run 结果各自表达真实状态

作为宿主，我希望输出可以直接驱动状态呈现，而不混淆生成中的计划和已经发生的操作。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当模型仍在生成工具块时，只能报告生成状态与允许的安全摘要，不能报告工具已开始或产生可响应审批；待审批、执行尝试、重试、结果返回、Observation 已提交和结果未知均来自现有 Runtime／Tool 事实，并保留 Action／尝试来源。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当工具参数被用户修订或恢复重执行时，应沿实际可用的领域引用关联同一逻辑操作、实际执行版本及本次等待；不能用模型原始参数覆盖实际结果含义，也不将重执行描述为首次执行。PTC 子调用保留父程序与子操作身份，不凭空分配 Provider 调用块。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当输出问答、任务审批、工具审批或恢复请求时，应在完整等待保存后复用 human-interaction 的规范请求视图及当前引用；输入结算、请求失效和新等待各有准确关联。普通消息、过程正文和候选答复不代答或放行这些请求。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当 Run 进入 waiting 时，应报告等待／交互及其可恢复身份，不能发 completed 结果；当 Run 真正 completed、failed 或 cancelled 时，才报告对应结算及相关正式消息引用。Run ID 是该 Run 终态结果的稳定结算键，重发或同步不生成第二个结果。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当 Interrupt 被受理、执行收尾、流连接关闭或服务进程重启时，应分别表达队列／执行／连接状态，不用流 EOF、候选结束或生成取消代替 Run cancelled；不修改基础 Spec 的有限收尾、未知效果和显式恢复规则。

### 需求 6：重连、缺口与提交顺序

作为可能断线的消费者，我希望恢复后得到可信结果，而不把缺失片段拼成完整回答。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当建立或重建订阅时，应遵循 streaming-session 的注册／一致同步／缓冲交接规则，先同步最新提交修订、消息范围、队列／收据、当前等待及 Run 状态，再处理有效后续事件；同步不触发执行或回放旧候选。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当预览在重连前已生成部分内容时，应通过预览身份和增量位置识别缺失前缀，不把后半段当作从头生成；可以等待完整候选或正式消息，缺失／截断明确可见。旧调用、已作废候选和已被正式消息覆盖的增量不得重新显示为有效内容。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当 Snapshot 保存后通知丢失、重复或乱于相关实时活动到达时，应按持久化修订、消息及业务来源恢复和去重；末次通知缺失沿基础会话只读核对发现已提交消息／等待／终态，不依赖后续 token 到达。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当背压无法保留控制事件、发布失败、读取故障或 Publisher 重建时，应明确报告连接／同步问题并要求重新核对；不能撤销真实提交、伪造 Run 失败、自动重试输入或假称完整重放。实时 cursor 与持久化修订继续使用不同语义。
- <a id="spec-req-6-5"></a>**验收标准 6.5**：当多个句柄、多客户端或快速后继 Run 同时观察时，应保持同一 Goal 的来源和消息顺序，历史 Run 的迟到事件不能覆盖当前 Run；消息、交互和结果可按各自稳定身份归档，不依赖客户端重启后的内存计数。

### 需求 7：公开投影、有界查询与当前 Web 接入

作为本机用户，我希望宿主和 Web 共享可用输出，又不会看到不应公开的协议载荷。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当投影公开输出时，应保留现有授权及工具摘要白名单，排除 reasoning、私有阶段输出、签名、Provider metadata、原始参数／Observation 和系统提示词；summary 预览只公开本次声明允许的字段，不能由调用方提供任意 JSON 路径绕过过滤。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当输出预览、消息和查询结果时，应使用明确的正文／页大小上限与截断标记；预览超限只停止增加公开正文并标记截断，不取消生成或改写保存内容。模型和消息原文按源保留，wire 不将截断文本当作完整结果。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当通过 HTTP／SSE 读取统一输出、消息列表或正文时，应沿用精确 Host、同源 Origin、Bearer 和 Goal 访问边界，校验身份、分页与类型；错误脱敏，读取不调用模型／工具或写入授权。替换被取代的当前 wire 类型，不保留开发期旧事件双解析。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当现有 Web 接入新协议时，应最小迁移 API／Hook，使已提交消息、未确认预览、等待和真实终态仍可消费，避免正式文本与预览重复追加；不要求先实现后续内容块布局，但不能依赖第二条旧 SSE 输出通道维持页面。

### 需求 8：跨模块验收与契约交付

作为维护者，我希望正式消息、候选和上下文的关系有可复现证据，而不是只增加 DTO。

- <a id="spec-req-8-1"></a>**验收标准 8.1**：当验证候选与提交时，应以确定性分片、审查及存储屏障覆盖合法提升、审查拒绝、歧义 JSON、最终不一致、保存前后故障、结果不明和通知丢失；核对公开内容、实际 Snapshot、消息身份和真实执行计数。
- <a id="spec-req-8-2"></a>**验收标准 8.2**：当验证过程消息与原生历史时，应覆盖带工具／零工具正文、审批等待、工具失败、直接调用／PTC、原生交换未结算／已结算、预算淘汰、模型切换及文件存储重建；检查实际下一模型请求和已有证据／Step 规则。
- <a id="spec-req-8-3"></a>**验收标准 8.3**：当验证会话输出时，应通过正式无界面装配和真实 HTTP／SSE 消费同一协议，覆盖多客户端、快速跨 Run、缺失前缀、分页、背压和重连；使用真实 SDK／本地协议 fixture 与确定性工具，不调用付费 Provider，不凭类型导出认定交付。
- <a id="spec-req-8-4"></a>**验收标准 8.4**：当交付功能时，应迁移所有消息写入、克隆、编码、查询、模型视图与消费入口，同步公开中文 TSDoc、最小示例、所有者概览和语义表，通过类型、依赖、文档及受影响回归；当前 Schema 原位更新，不增加旧开发数据迁移、事件数据库或新的 SDK 包。

## 架构与核心决策

### 当前依据、依赖与职责

当前 [GoalMessage](../../packages/runtime/src/domain.ts) 和 [BrowserSessionMessage](../../packages/web-contracts/src/session.ts) 主要保存角色及正文，Browser 从消息数组区间推断 Run；[模型阶段执行器](../../packages/model-execution/src/llm-step-executor.ts) 在工具分支不把同次正文作为独立 Goal 消息。[Runner](../../packages/runtime/src/runner.ts) 在完成接受、等待或失败时追加决策文本，零工具正文也有单独提交路径。本次在这些既有写入路径增加身份与来源，不把公开事件作为状态写入入口。

[原生历史组装](../../packages/model-context/src/native-model-history.ts) 保留已结算交换，[请求渲染](../../packages/model-request/src/render.ts) 按 conversationPosition 将它们插入真实对话。目前没有按过程正文来源去重的规则，故仅保存更多正文会重复模型输入；本次同时扩展来源传递、预算组装和渲染，不能只改聊天 DTO。

### 会话输出与来源信封

下列名称定义语义分类，最终 TypeScript 名称在既有模块中统一；内部类型由 Runtime 所有，wire 通过显式投影共享含义。

| `state_sync` | 一致 Snapshot 的公开状态、提交修订、消息范围、输入／队列、当前等待、Run 状态和需显式恢复标志。 |
| `input_result` | 基础受理／拒绝／应用结果，关联 inputId；拒绝不伪装为已保存收据。 |
| `generation_event` | 公开过程正文或候选答复的开始、增量、完整候选、待确认、作废；临时来源而非正式消息。 |

### 正式消息与只读查询

真实对话仍存于 Goal Snapshot，消息正文不可变。每条保存 messageId、所属 runId、role、正文及来源；助手用途分为 process、answer、notice。用户消息来源指向基础输入，过程正文指向本次模型调用及块，最终答复指向获接受的完成候选。既有问答／审批反馈及 Runtime 通知保留真实来源，不把纯控制命令或预览补成聊天。无模型来源的宿主结果使用实际执行来源，不虚构 modelCallId 或 Provider 块。

每个连续公开正文块产生一条过程消息；最终 summary 产生独立答复消息。messageId 在所属 Runtime 提交边界分配并保存，来源关联用于提交重试核对，不由正文哈希推导。保存不明时先按来源和基础收据读取；相同来源已有消息就返回其原身份，不再创建第二条。现有消息数组位置和 messageRange 仍用于顺序／上下文区间，不能与 messageId 混用。

所有写入者包括创建、普通消息应用、Steer 应用、交互回复、零工具正文、工具响应正文、阶段／最终结果和通知，均遵守基础短提交协调。新的消息与已有事实／frame、Run 变更在所属 Snapshot 边界一起提交；输出发布在保存成功后，不另建 outbox 或预览数据库。已经接受并保存的过程正文可以先于工具真正执行存在，其含义只是模型已发送的过程说明。

Session 提供有界消息列表和正文读取，HTTP 映射为 `GET /api/goals/:goalId/messages` 和 `GET /api/goals/:goalId/messages/:messageId`。列表按消息顺序，以 afterMessageId 和首批确定的 throughMessageId 限定追加历史的读取区间，每页默认 50、最多 100 条；正文每次最多 64,000 UTF-16 code unit，返回实际范围、是否截断及后续读取位置，不拆断 Unicode 代理项。通知／列表正文同样标明截断，按 messageId 查询原文，不从预览补齐。未知／跨 Goal 引用明确不存在，读取失败不是空页。

完整 Snapshot 仍可能整文件读取，本次有界响应不承诺磁盘随机访问或固定读取成本。无界面查询和 wire 共用 Runtime 读规则，Browser 不持有另一份可变消息账本。分页不写状态或恢复执行，客户端恢复老历史可以继续按稳定范围读取。

### 候选投影与正式提交

候选引用由实际 Goal／Run、调用／块和允许字段来源关联，不等于 messageId；属于阶段还是 Run 的候选由当前请求及 Runtime 目标关联说明，不能单凭函数名判为最终答复。分片有解码后文本的位置，便于识别缺失前缀和同源合并。过程正文也使用有来源的临时预览；最终正式通知给出 messageId 和预览关联，消费者替换对应预览而非再次追加整份正文。相同文本的不同来源仍保留为不同消息。

安全提取器只在实际 Decide 请求声明包含 system_complete_task、生成来源可定位且工具身份可可靠确认时读取顶层 summary 字符串。处理 JSON 字符串状态、转义和 Unicode，不能扫描所有同名 key，也不把半个参数对象交给业务解码。元数据晚到、参数整块或来源不可靠时等待完整响应／块后再投影；这不是重新调用模型的理由。strict 文本协议若有完整合法完成决定，按其实际契约提供完整候选，不凭文本外观增量猜测。

该投影通过模型执行协调的受信调用级观察接入取得必要参数，不从全局诊断订阅、Trace 文件或浏览器读取原始响应。llm-core／Adapter 继续不理解 summary 的业务含义，通用事件 Core 不解析 JSON。投影错误与发布错误被隔离，只停止对应预览；完整候选仍由原有解码处理。歧义或不一致预览一经作废不重新标为有效，之后真正提交的正式消息显式替换它，不能宣称早先显示的内容已经获批。

```text
可公开增量 → 未确认预览 → 完整候选／待确认
                                  ├─ 拒绝、取消、失败或替代 → 作废预览
                                  └─ 原有检查／审查接受 → 保存 Snapshot
                                                         ├─ 成功 → 正式消息／真实状态
                                                         └─ 结果不明 → 读取核对
```

过程消息在相同响应被当前阶段接受时保存；混合完成候选的普通正文也须经过该候选适用的接受规则，拒绝候选不能先把其正文作为正式完成声明保存。阶段接受可以产生过程／通知，但只有 Runtime 真正结算当前 Run 的最终答复才标 answer。私有 Think、完成审查和 reasoning 不因正文为自然语言就公开。

预览仅存在于进程／连接的受控观察状态，不作为消息进入 Snapshot 或模型上下文。每条预览公开正文累计最多 64,000 UTF-16 code unit，超限标记截断并停止增加其公开正文；模型仍继续，最终保存使用真实完整内容。停止显示预览不会中断模型，用户 Interrupt 仍须走独立输入。

### 原生历史来源去重

消息来源元数据穿过 Conversation 投影、上下文选择和预算估算，最终只在“本次请求实际包含、协议身份匹配且已结算的原生交换”覆盖同一模型正文来源时省略该过程消息。覆盖以调用／块来源关联，不比较正文字符串；messageId 不进入 Provider 正文或伪装成工具调用 ID。

原生交换未结算或预算淘汰、身份切换时，仍在对话裁剪范围内的过程消息按原顺序进入请求；不额外恢复已经被预算淘汰的旧消息。去重参与现有预算与选择，而非在渲染后临时增删已计量内容。调用和 tool result 保持配对与相邻约束；不篡改原始参数、签名或 action-approval-revision 所要求的实际参数说明。

新增过程消息不等于新增 Step 或成功证据，也不改变先前工具／阶段事实的权威。来源关联必须落在当前消息和已提交 frame／轨迹中，不能靠可丢失的诊断记录恢复；不引入按正文 hash 的全局去重表或另一套长期模型历史。

### 同步、wire 迁移与边界

订阅建立沿用基础一致同步。重连丢弃旧临时预览，先呈现已提交消息、当前等待和真实状态；不重播前一进程的分片。若当前调用后续只到达非零位置的增量，标明预览不完整并等待完整候选／正式消息，不将缺失前缀后的文本拼成“完整回答”。完整候选的有界正文可以重新提供观察基准，正式消息始终由 Snapshot 核对。

已提交消息、等待和终态重复按各自身份归并，实时活动按来源 cursor／合并范围处理。基础只读核对复用一次，不另起新的每连接轮询或调度器；最后一次消息通知丢失也能由修订变化发现。读取故障仍是 stream_fault，不能据此将保存不明的候选作废。

Web 替换当前 BrowserGoalLiveEvent／消息 DTO 的被取代部分，使用同一条 Goal SSE 输出，并在现有 API／Hook 内做必要消费映射。当前页面可继续使用“尚未保存”等临时显示区域，不要求本次完成内容块布局、交互区域重做或动画；但不能把候选当成正式消息或重复追加。所有列表／详情和 SSE 沿当前访问控制及长度校验，普通输出不增加完整工具／Observation 或敏感元数据；需要详情仍使用既有授权读取。

## 曾考虑的备选方案

- **Snapshot 消息加稳定来源**：选择在真实消息中保存身份、用途和必要来源，继续由 Runtime 提交。备选独立消息数据库／事件 outbox 会增加跨库一致性，按数组位置或正文哈希识别又无法稳定重试和区分相同文本，不采用。
- **候选预览后正式提交**：按用户确认，允许早读 summary，但明确未确认及作废。备选仅保存后展示失去生成期反馈；把候选直接写正式消息会绕过审查和失败边界，均不采用。
- **保存过程正文并按来源去重**：按用户确认保留混合工具响应的公开正文。备选仅临时展示刷新后丢失过程说明；直接追加而不处理原生交换会重复模型输入，按文本相同去重会误删独立消息，均不采用。
- **请求契约限定的字段投影**：选择只提取允许的 summary，并在来源不确定时等待完整块。备选公开整个参数、任意 JSON 路径订阅或正则提取会扩大泄漏与解析歧义；拆分整块内容模拟实时输出也不提供真实能力，不采用。
- **类型化会话输出加有界查询**：选择当前 Session 与 HTTP／SSE 的显式联合和只读消息查询。备选所有内容变成聊天文本会混淆审批、工具和终态；持久化所有 token 并承诺完整重放会扩大恢复范围，均不采用。
- **最小 Web 接线、后续布局独立**：选择迁移当前 wire 和消费入口，正式内容块 UI 后续实现。备选保留第二条旧事件流会重复来源和状态；本次同时重做全部页面会越过本 Spec 的协议范围，均不采用。

## 风险与否定性保证

- **风险等级：high**。本次改变真实消息持久化、公开候选字段、模型上下文去重及恢复投影；错误关联可能泄漏私有内容、重复输入、遗失正式消息或提前宣称完成。验收须穿过真实提交、请求组装、协议 fixture 与 SSE，不以类型通过替代。
- **关键操作**：实现涉及当前消息 Schema、全部写入／克隆／编码、模型阶段结果来源、预算和历史渲染、Session 查询及当前 wire 替换。当前 Schema 原位更新，不自动迁移或删除开发期用户数据，不增加旧协议解析，不以设计批准授权真实付费调用、危险工具或 SDK 发布。
- **正式与临时不变量**：候选不能执行、批准或充当证据；完整响应、审查接受、Snapshot 保存和 Run 完成各有独立含义；保存不明先核对，已提交消息不可被迟到分片改写；同源重试不增消息，不同来源相同正文不合并。
- **历史与授权不变量**：正文来源去重不能破坏原生调用／结果配对、签名、预算或实际参数说明；公开过程正文不包含 reasoning；普通文本不解除交互；仅 Runtime 已提交等待可形成可响应请求；工具生成不等于工具执行。
- **恢复与资源不变量**：Snapshot／已提交轨迹继续权威，预览不持久化为恢复输入；连接、背压和观察错误不取消 Run，不自动重发输入或恢复执行；不承诺 token exactly-once、跨重启 cursor 续传或固定磁盘分页成本。
- **验证与边界**：覆盖 JSON 转义／歧义、候选拒绝、保存边界、通知缺失、多客户端、跨 Run、预算淘汰和身份切换；只用隔离数据与确定性本地调用。本阶段仅创建本 Spec，不改写四份已批准 Spec／Plan，不生成下游 Plan、不开始实现，也不写入项目记忆。
