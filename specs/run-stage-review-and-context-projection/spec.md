# Run 内阶段审查与上下文投影优化 Spec

## 目标与范围

让模型在同一 Run 中自主组织阶段目标，通过多个 Step 执行、审查和修正，再进入下一阶段。内部执行路线由模型决定；Runtime 保存足以恢复、审查和展示的阶段说明，不建立 Task 聚合、递归子 Goal 或独立 Planner。

Run 仍是用户操作开启的一次执行边界。模型不得因阶段切换、审查拒绝或执行失败自动新建 Run。waiting 的 resume 保留同一 Run；终态或中断后的用户续接沿用现有 Coordinator 规则。用户可见 Todo 保持 GoalPlan 语义，与内部阶段没有强制的一一对应关系。

本功能包含阶段说明及修订、阶段审查与最终交付审查、拒绝后的新 Step、Snapshot/Trajectory 恢复、模型输入去重、按阶段组装必要审查输入，以及 Web 阶段折叠展示。只扩展既有 context benchmark 和测试中证明这些行为所需的场景。

不修改现有格式纠错上限、传输重试、执行额度及其配置含义，不新增阶段数、审查拒绝次数或自动推进额度上限。不新增语义压缩模型、后台 Warm Sidecar、RAG、审查服务、工具发现策略、工具输入描述或沙箱能力；不开展整个 Prompt 的重写，也不修改全局模型配置。

## 需求与验收标准

### 需求 1：同一 Run 内的自主阶段

作为使用者，我希望 Agent 自主组织当前工作，同时保持用户请求和执行身份稳定。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当开始阶段工作时，模型应当声明非空阶段目标与完成条件；Runtime 应当分配阶段身份、保存当前修订及上一已接受阶段的结果引用，再允许该阶段的业务执行或完成候选。简单请求允许只有一个最终阶段，不要求固定阶段模板或详细路线。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当模型继续阶段内执行或切换到下一阶段时，系统应当保持 goalId、runId、执行额度累计值、已有授权与恢复边界；模型不得调用用户续接入口、伪造用户消息或重置预算。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当模型提交下一阶段说明时，前一阶段应当已有接受结果；若当前阶段尚未通过审查，系统应当拒绝跳过该阶段的转换，并允许通过合法修订调整同一阶段的工作。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当 Run 等待、失败、取消或用户继续时，系统应当沿用现有生命周期；阶段信息不得触发自动 Run 重试、自动用户续接或 Todo 状态同步。

### 需求 2：最小说明与可追溯修订

作为执行与审查组件，我希望阶段说明能够恢复和修订，而不会覆盖用户要求。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当阶段说明被接受时，系统应当持久化目标、完成条件、修订身份和上一阶段结果来源；系统不应当要求保存完整执行路线或思维过程。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当模型修订当前说明时，系统应当要求非空修订理由与当前修订引用，并记录前后内容；过期修订应当整体拒绝，不部分覆盖当前说明。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：若修订删除、改名或拆分了未完成条件，审查应当继续核对其对应的用户要求与历史拒绝缺口；模型自行降低完成条件不得构成任务完成依据。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当用户补充输入已经应用时，后续执行和审查应当使用最新有效用户要求；依据旧输入或旧阶段修订生成的未提交审查结果不得完成新版本阶段。

### 需求 3：阶段验收与最终交付

作为使用者，我希望局部工作有明确结果，而最终答复完整满足我的请求。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当提交阶段完成候选时，系统应当先校验协议、语义、授权相关规则、Memory Patch 及证据引用，再审查目标、条件、实际结果与关键事实支持；无效候选不得调用审查或提交完成。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当中间阶段审查接受时，系统应当提交阶段结果和证据来源，保持 Run 非终态；阶段结果不得伪装成用户最终答复、业务 Tool Observation 或 Goal 完成。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当提交 Run 最终交付候选时，系统应当在同一次审查中同时核对当前阶段及用户整体要求；所有局部阶段通过不应当自动使最终候选通过。接受前不得提交 Run 完成、最终回复或该候选 Memory Patch。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：若候选引用了前一阶段验证结果，但其后又修改了对应产物，审查应当识别验证与最终产物的不一致；仅有“阶段已通过”的记录不得证明最终版本正确。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当审查任务属于诊断失败原因时，系统应当允许依据失败操作完成充分诊断；当任务要求修复并验证通过时，同样的失败操作不得支持成功声明。无外部事实的简单请求不强制工具调用。

### 需求 4：审查拒绝后的继续执行

作为 Agent，我希望区分调用格式错误与需要继续完成的工作。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当合法候选被审查拒绝时，系统应当提交带具体缺口的阶段反馈及本次 Step 结果，保持当前阶段和 Run 执行中；下一 Step 应当收到反馈，可以调查、修改、验证、修订阶段说明或重写候选。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当发生审查语义拒绝时，系统不应当占用参数格式纠错预算；非法决策、非法阶段提议、非法 Memory Patch 和审查响应格式错误仍应当沿用对应现有阶段的三次纠错及既有请求重试机制，不改上限。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当拒绝后的工作继续时，系统应当正常累计 Step 和模型费用，保留原执行额度；额度耗尽、取消或执行异常应当沿现有规则停止，不通过切换阶段获取新额度。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：若审查因必要输入超预算或调用失败而未得出有效结论，系统应当记录实际错误，沿现有失败规则处理；不得计为语义拒绝、跳过审查、提交“未验证”的完成或静默丢弃候选 Patch。

### 需求 5：必要审查输入与模型上下文去重

作为上下文维护者，我希望减少重复输入，同时保留决定正确性所需的要求与证据。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当组装阶段审查请求时，系统应当提供阶段说明及修订、完整候选、用户有效要求、适用约束和必要已提交原始证据；最终审查还应当提供整体交付所需的历史来源，不默认重放完整会话。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当选择用户要求时，系统应当保留原始意图、当前 Run 的完整已应用用户输入、冻结 Profile 和适用的已批准范围；相关早期对话应当带来源补充。阶段说明或模型摘要不得替换这些权威输入，未选择的历史内容应当可定位，不得由模型自行宣称用户约束已失效。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当同一证据同时存在于工具完成记录和 Observation 时，系统应当只发送一次原始正文，并保留必要操作、来源身份和结果状态。失败输出、截断状态及来源范围不得因去重丢失；阶段结果、Think 和审查接受均不是外部事实证明。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当原生工具交换已完整纳入当前请求时，Hot 投影不应当重复发送对应动作参数与事件包装；若交换被预算移出、身份不匹配、尚未结算或缺少配对，语义投影应当保留必要内容。去重不得改变原始 Trajectory 或破坏调用与结果配对。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当原生 Tool 声明已携带完整 Schema 时，动态授权说明不应当再复制同一参数 Schema，但应当保留授权身份和必要使用指导；prompt_only 请求应当保留实际需要的契约说明。当前 runtime_feedback 仍应当位于请求末尾。
- <a id="spec-req-5-6"></a>**验收标准 5.6**：当去重后的必要固定输入仍超预算时，系统应当给出明确预算诊断；不得用有损证据摘要代替必要正文后放行。现有 Hot/Warm 确定性预算与来源边界保持有效。

### 需求 6：提交边界、恢复与 Web 展示

作为使用者，我希望重启后看到真实进度，且模型继续当前工作。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当提交阶段开始、修订、拒绝或接受时，系统应当通过现有 checkpoint 提交边界保存事实与恢复指针；重建进程后应当恢复相同 Run、当前阶段修订、最新拒绝缺口和已接受结果，未提交 tail 不得改变阶段状态。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：若审查已调用但结果未提交，恢复应当允许重新审查并记录实际费用；已提交接受不得重复完成同一阶段，已执行业务副作用不得因恢复审查而重放。审查不执行业务工具。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当 Web 展示 Run 活动时，系统应当按稳定阶段身份折叠显示目标、状态及已提交结果摘要，展开显示对应真实 Steps 和审查反馈；修订保持同一组，审批等待和参数重试仍归所属 Step，不制造虚构动作。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当刷新、重连、分页、搜索或查看原始轨迹时，阶段分组应当保持一致，并可定位修订与审查记录；阶段通过不得使 Run 标签提前完成。UI 不展示内部思维过程，不改写 Todo，也不以 SSE 临时状态作为恢复权威。

### 需求 7：行为回归与真实模型验收

作为维护者，我希望证明优化保留正确性并改善实际任务表现，而不只检查 Schema。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当验收本功能时，测试应当覆盖单阶段简单交付、多阶段同 Run、拒绝后补查、降低条件尝试、用户补充使候选失效、阶段通过但整体遗漏、旧验证结果失效、审查超预算、持久化故障、取消与进程恢复。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当执行真实 Docker 场景时，系统应当证明多阶段及拒绝修正在同一 Run 中发生；在现有 waiting 安全边界重建 Worker 后，应当继续同一阶段并通过实际产物与测试验收，不扩大为 executing 任意中途捕获。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当比较原输入与优化输入时，应当固定任务材料、模型配置和评分判据，保存双方请求、Schema、构建身份和逐次结果；固定审查正反案例各重复至少三次，记录误接受、误拒绝、未完成、调用量及输入计量单位。没有供应商 Token 时不得把字符数当作 Token。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当汇总验收时，应当分别报告协议合法、执行结束、实际产物正确和解释质量；Judge 高分不能覆盖确定性失败。当前实现的必需正反例、恢复、UI 与回归检查全部通过后才可交付；输入减少本身不构成质量通过，诊断对照不宣称统计显著或普遍成功率提升。

## 架构与核心决策

### 所有权与数据流

```text
用户输入 → 现有 Goal / Run 生命周期
  → 模型提交阶段说明 → Runtime 校验并提交
  → 多个 Step：执行、读取、修改、验证
  → 提交阶段候选 → 确定性校验 → 阶段审查
       拒绝：提交缺口 → 同一 Run 的下一 Step
       接受中间阶段：提交结果 → 同一 Run 的下一阶段
       接受最终交付：阶段与 Run 完成一起提交 → 用户答复
```

| 所有者 | 本功能职责 |
| --- | --- |
| Runtime | 阶段身份、修订和合法转换；已提交证据解析、Step/Run 推进、恢复与额度累计 |
| model-contracts | 阶段提议与候选的模型 JSON 契约、原生系统调用和 prompt_only 投影 |
| Agent | 当前阶段输入、原生历史去重、必要审查请求、响应解码与安全反馈；不拥有持久化 |
| Storage | 当前 Snapshot、Trajectory 的 DTO/Schema/Codec 与提交记录读取 |
| Web 边界与 Goal Board | 从已提交状态投影阶段组及详情；保留现有 HTTP/SSE 授权 |
| context benchmark | 固定场景、隔离环境、真实恢复、确定性判据、独立 Judge 和对照报告 |

### 阶段数据与转换

阶段是 Run 的附属执行记录，不是独立聚合、调度单元或用户任务授权。Snapshot 保存当前阶段及恢复所需来源指针，阶段历史和修订正文由 Trajectory 保存；不在两处复制完整历史。模型只能提出说明、修订和完成候选，Runtime 分配身份与事实序号。

最小记录包括阶段身份、修订、目标、完成条件、阶段状态、上一阶段结果引用；修订事实包含理由和前后内容。结果引用指向已提交结果及其证据，不复制原始工具输出。阶段状态表达执行中、待审查、已接受；审查拒绝回到执行中。Run 失败或取消保留当时阶段，展示服从 Run 终态，不另建一套失败调度。

阶段开始、修订与中间阶段完成是明确的模型提议操作，经过既有严格 Contract 与 Runtime 转换入口。它们不能替代 `complete` 的最终交付含义。最终 `complete` 关联当前阶段，以一次审查验证局部与整体；最后阶段接受和 Run 完成在同一提交边界处理。具体系统函数标识由 Plan 对齐现有命名，原生与 prompt_only 路径必须等价。

开始、修订、阶段候选结算均作为现有执行循环中的 Step 计量。有效审查拒绝是已结算的候选结果，提交原生调用交换、具体反馈与恢复事实，再推进下一 Step；不把语义拒绝作为当前参数校验异常循环。审查响应本身的格式错误仍走既有纠错，暂时请求失败仍走现有重试。

内部阶段没有冻结的完整路线。模型可根据新事实修订说明；Runtime 检查修订身份和转换，审查检查用户要求是否被满足，二者不假设结构合法就意味着语义正确。Todo 更新仍走独立 GoalPlan reducer，不新增自动映射。

### 审查输入与来源

审查候选绑定 Run、阶段修订、已应用用户输入边界和证据提交边界。恢复和 Steer 使用现有边界排除过期候选。审查仍使用当前 Decide 绑定模型，复用现有 accept/reject 契约，不新增服务或第三种模型输出；无法判定体现为调用或预算失败诊断。

固定输入保留原始意图、冻结 Profile、获批范围、当前 Run 的完整用户输入、完整候选和阶段条件。早期对话只按相关来源补入，例如用户明确沿用的旧答复；记录选择来源与边界，不依赖生成式摘要提取“有效要求”。模型原话和阶段结果作为背景，不能替代原始用户要求或证据。

Runtime 从 committed 来源解析候选引用和必要操作上下文；Agent 按阶段去重正文与封装。最终审查可读取同一 Run 已接受阶段引用的历史原始证据。保持既有跨 Run 证据门禁，不把前一 Run 的引用自动提升为当前完成证据。模型引用不充分由审查指出具体缺口，工具失败不伪装成功，完成审查不执行补查工具。

### 普通模型请求的去重

按当前请求实际保留的原生交换与对应 Action 来源去重，不按“这个事件曾出现过”永久删除。保留必要证据序号、失败与等待状态；交换移出窗口或模型身份切换后，确定性语义投影继续提供必要内容。原始事件、Snapshot、Working Memory 和合法的 protocolVersion 保持各自语义。

原生工具声明是当前参数 Schema 的请求权威；动态授权 Section 保留工具身份、描述和必要使用指导，不复制已声明 Schema。prompt_only 保留解码需要的形状说明。审查与普通决策分别计量最终请求，沿用既有预算策略及末尾 runtime_feedback。

### 持久化、展示与交付归属

复用现有 TrajectoryCheckpointCommitter、Snapshot 提交边界和只读恢复查询，不建立阶段侧文件或后台缓存。仅支持更新后的当前开发期 Schema，不为了旧试验 Goal 增加迁移或兼容分支，也不因实现变更单独增加协议版本。

Web 按阶段记录关联实际 Step 与审查事实，不从标题、模型自由文本或前端到达时间猜测分组。阶段开始前的既有控制活动保留在 Run 级，最终答复只来自接受后的 `complete`。产品新增文案使用英文，新增或扩展公共接口包含中文契约 TSDoc 与例子。

本 Spec 在实现交付时替换旧完成审查设计中的“拒绝共用格式纠错”“每次发送完整会话”等局部规则，不整体废弃来源门禁、恢复或上下文设计。因此不把包含其他有效能力的旧 Spec 标为整体 superseded。当前架构说明由各模块同步更新；Memory 维护另走精确预览审批。

## 曾考虑的备选方案

- **引入 Task 或递归 SubGoal**：可以聚合多个 Run 并独立验收。落选原因：用户要求内部阶段在同一 Run 执行，该方案增加重复生命周期和调度所有权。
- **每个阶段自动新建 Run**：可直接沿用 Run 分组。落选原因：改变用户开启 Run 的边界，并会重置执行预算、授权可见状态和证据范围。
- **阶段说明完全隐含，或保存详细路线**：前者省去字段，但恢复和审查无法稳定定位目标；后者限制模型自主调整且可能暴露思维过程。采用最小、可修订的阶段记录。
- **阶段条件固定不可修改**：审查基准简单，但无法合理适应新发现。采用修订 记录与用户要求共同约束，禁止以修订消除未完成义务。
- **仅审查 Run 最终答复，或沿用三次语义拒绝上限**：前者缺少用户要求的阶段验收，后者继续混淆参数纠错与调查工作。采用阶段审查和下一 Step 修正，不新增拒绝次数上限。
- **每次重放完整会话、跳过超预算审查或只看候选摘要**：完整重放成本随历史增长；另外两种丢失必要依据。采用必要原始要求与证据，超预算明确失败。
- **新增 LLM 压缩和 Warm Sidecar，或全量重写 Prompt**：尚无本功能需要的独立生产职责，会扩大成本和归因范围。采用确定性去重与必要阶段引导，保留现有上下文流水线。
- **阶段接受自动完成 Todo**：内部阶段与用户计划可能拆分、合并且没有一一对应关系，自动同步会误报用户进度。保留独立 Todo 契约。

## 风险与否定性保证

- **风险级别：medium**。变更跨 Runtime、模型协议、持久化、Agent 和 Web，影响审查、恢复及最终交付；不改变执行权限或引入外部发布。验证需覆盖集成、失效候选、提交故障和真实恢复。
- **迭代成本**：用户明确不新增阶段或拒绝上限。既有 `maxSteps=0` 仍表示不按 Step 终止，可能长时间循环；本功能不承诺新增总成本上界。阶段必须服务可交付目标，不能把每个工具动作机械拆成阶段。
- **审查误判与条件放宽**：模型既规划又提交候选，存在自设低门槛风险。始终保留用户要求，增加降低条件和整体遗漏反例；审查通过不保证模型普遍可靠。
- **必要输入仍可能超预算**：确定性去重和阶段范围不保证所有候选能装入上下文；不得以完成率为由跳过必要事实。相关诊断和已有产物保留。
- **证据时效与来源遗漏**：已接受阶段不是最终版本的证明，早期适用约束可能依赖关联对话；保留来源选择记录并覆盖旧测试失效、用户沿用历史要求和未提交 tail 场景。
- **费用与恢复**：未提交审查可重放并再次收费，不承诺审查 exactly-once；已提交业务副作用沿原恢复规则处理。
- **开发期数据**：新阶段契约可能使旧 Goal 或冻结检查点不再可读。验收使用对应当前构建重新制作、复核的材料，历史失败记录保持原样，不宣称其旧 Snapshot 可直接恢复。
- **否定性保证**：不自动创建 Run、不伪造用户输入、不静默丢弃非法 Patch、不放宽证据门槛、不重置预算、不以阶段通过提前完成 Run、不保存或展示内部思维过程、不以 Trace 或 UI 临时状态恢复执行。
