# two-stage-decision-pipeline 需求

## 审批摘要

### 目标

在 LazyGoal 中引入同模型双阶段决策流水线（Two-Stage Hybrid Decision Pipeline）：单步决策内先通过无约束提示词引导同一模型进行自由思考生成推理链（CoT），再将思考注入上下文并挂载原生严格模式（strict）提取结构化动作，兼顾深度推理能力、全量可观测复盘与 100% 格式合规率。

### 范围

- 包含：执行阶段（executing）与准备阶段（preparation）的同模型两阶段调度、思考链在事实轨迹（Trajectory）中的记录与 TUI/Inspector 复盘、两阶段上下文交接与 Token 预算防护、运行模式显式配置与既有单阶段兼容。
- 不包含：跨模型异构调度、流式打字机增量 UI 渲染、破坏现有 Contracts AST/Runtime 领域模型、应用层多轮重试修补。

### 核心行为

- 调度阶段先思后决：单个决策步内串行发起自由思考（Think）与严格抽取（Decide）两次请求，第一阶段思考作为第二阶段输入。
- 保证 100% 动作合法：第二阶段施加原生 strict 语法机约束，彻底杜绝转义与 JSON 格式错误。
- 轨迹全程可溯：思考链进入 Trajectory 持久化记录，终端用户可在 TUI / CLI 中复盘每一步思考逻辑。
- 预算与兼容可控：思考链交接纳入 Token 预算规划防溢出；保留既有单阶段模式向下兼容能力。

### 风险与待确认

- 风险等级：medium；理由：涉及 Agent 决策调度重构、LLM Adapter 协作与 Trajectory 事件流扩展，影响跨组件行为，但边界清晰可控。
- 关键操作：无
- 风险：两次 API 调用导致单步网络延迟增加，思考链过长可能挤占第二阶段输入窗口（已通过有界预算控制规避）。
- 待确认：无

## 引言

LazyGoal 当前依赖单次模型生成来完成决策，导致高强度的 strict 语法约束往往压制推理模型的思考发散能力，或在 prompt_only 下存在格式偶发异常与解析成本。本特性重构 Agent 单步决策执行逻辑，建立同模型双阶段机制：第一阶段释放模型长思考潜力捕获思考链，第二阶段凭借 strict 模式锁定强类型契约，实现高智商推理与工业级执行确定性的统一。

## 需求

### 需求 1：执行阶段同模型两阶段决策调度

**用户故事：** 作为 Agent 运行时调度器，我希望在 executing 阶段的单步决策中自动串联思考与严格决策提取，以便模型先推演行动再输出合规指令。

#### 验收标准

1. <a id="req-1-1"></a> 当运行时在 executing 阶段触发单步决策时，系统必须先发起无结构约束的自由思考请求，引导模型进行推演并获取纯文本思考链。
2. <a id="req-1-2"></a> 当自由思考请求成功返回后，系统必须将思考链内容作为上下文依据注入第二阶段，并在挂载原生严格 JSON Schema 条件下发起决策提取请求。
3. <a id="req-1-3"></a> 当第二阶段返回合规结构时，系统必须将其无损解析为领域可执行的 AgentDecision 动作并继续后续执行循环。
4. <a id="req-1-4"></a> 当任一阶段的请求被取消或发生网络/协议错误时，系统必须立即停止推进并向外抛出对应的执行异常，不得吞没错误。

### 需求 2：准备与规划阶段的双阶段支持

**用户故事：** 作为任务发起者，我希望在上下文收集和任务规划阶段同样应用先思考后提取机制，以便复杂规划问题获得更充分的前置推理。

#### 验收标准

1. <a id="req-2-1"></a> 当运行时处于 gathering_context 或 planning 阶段且启用两阶段模式时，系统必须在生成准备阶段动作时同样执行思考与严格提取成对调用。
2. <a id="req-2-2"></a> 当准备阶段第二阶段返回时，系统必须确保提取结果严格受限于当前阶段允许的契约分支（提问、就绪或任务提案）。

### 需求 3：思考链事实轨迹记录与可观测性

**用户故事：** 作为终端使用者，我希望能够在 TUI 检查器和 CLI 轨迹中查阅模型完整的思考链，以便复盘模型采取特定工具调用的逻辑动机。

#### 验收标准

1. <a id="req-3-1"></a> 当第一阶段生成思考链时，系统必须将其作为事实轨迹事件记录入轨，并持久化到当前 Goal 的轨迹存储中。
2. <a id="req-3-2"></a> 当用户在 TUI 轨迹检查器中查看具体执行步骤时，系统必须能够展示与该步决策对应的思考链内容。
3. <a id="req-3-3"></a> 当步骤因历史兼容或模型未生成思考链而缺失该字段时，系统必须正常渲染其余决策信息，不得发生崩溃。

### 需求 4：两阶段上下文交接与 Token 预算控制

**用户故事：** 作为资源管理者，我希望两阶段调用的 Token 开销得到受控管理，以便防止超长思考链挤占第二阶段决策提取的上下文窗口。

#### 验收标准

1. <a id="req-4-1"></a> 当将第一阶段产出的思考链组装入第二阶段请求时，系统必须将其计入 TokenBudgetPlanner 的动态输入预算。
2. <a id="req-4-2"></a> 如果第一阶段思考链文本超过预设的安全长度上限，系统必须在第二阶段前进行确定性尾部截断并注入截断标记。

### 需求 5：运行模式配置与平滑兼容

**用户故事：** 作为系统集成者，我希望通过配置显式启用两阶段模式，同时保留传统单阶段模式，以便在不同基准测试与交互场景中灵活适配。

#### 验收标准

1. <a id="req-5-1"></a> 当通过环境配置指定结构化输出模式为两阶段模式时，系统必须激活两阶段决策流水线。
2. <a id="req-5-2"></a> 当环境配置沿用既有的 strict 或 prompt_only 模式时，系统必须保持原有的单次调用流程，确保历史用例与基准脚本行为不变。
