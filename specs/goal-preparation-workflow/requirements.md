# Goal 准备工作流需求

## 引言

本功能让一个 Goal 在任务执行前持久化完成上下文问答、任务规划与用户批准，并在进入执行后尽可能连续运行；准备交互不属于 Step，真实会话与每轮派生的 Working Context 保持分离。

## 需求

### 需求 1：可恢复的准备阶段

**用户故事：** 作为 Agent 使用者，我希望 Goal 记录当前准备阶段，以便中断后能够从正确位置继续任务。

#### 验收标准

1. <a id="req-1-1"></a> 当使用初始意图创建新 Goal 时，系统必须将其置于 `gathering_context` 阶段，保存不可被后续准备操作改写的原始意图，并保持 Run 为 `created` 且 `stepCount` 为 0。
2. <a id="req-1-2"></a> 当 Goal 推进阶段时，系统必须只允许 `gathering_context → planning → executing` 的正向顺序。
3. <a id="req-1-3"></a> 当任一准备阶段的 Goal 被恢复时，系统必须恢复其阶段、PreparationState、原始意图、任务提案与会话消息的最新成功快照。
4. <a id="req-1-4"></a> 如果 Goal 没有经过用户批准的最终任务，系统必须拒绝进入 `executing`，且不得修改已有快照或启动 Run。

### 需求 2：上下文收集问答

**用户故事：** 作为 Agent 使用者，我希望 Agent 在执行前提出必要问题并记住回答，以便最终任务基于充分上下文形成。

#### 验收标准

1. <a id="req-2-1"></a> 当 `gathering_context` 阶段的 Agent 需要更多信息时，系统必须记录面向用户的问题，将 PreparationState 置为等待输入，并保持 Run 状态和 Step 计数不变。
2. <a id="req-2-2"></a> 当用户针对等待中的问题提交非空回答时，系统必须按时间顺序保存回答，并继续上下文收集。
3. <a id="req-2-3"></a> 当 Agent 给出结构化 `context_ready` 决策时，系统必须将 Goal 推进到 `planning` 并保存新阶段，且该决策不得产生 Step。

### 需求 3：任务提案与执行批准

**用户故事：** 作为 Agent 使用者，我希望在任务提案明确后批准或反馈修改，以便连续执行只基于我认可的任务开始。

#### 验收标准

1. <a id="req-3-1"></a> 当 `planning` 阶段形成任务提案时，系统必须保存可恢复的提案和面向用户的批准请求，并将 PreparationState 置为等待批准。
2. <a id="req-3-2"></a> 当用户批准当前任务提案时，系统必须将该提案固定为最终任务、完成 PreparationState，并将 Goal 推进到 `executing`。
3. <a id="req-3-3"></a> 当用户针对任务提案提交修改意见时，系统必须保存该反馈、保持 Goal 位于 `planning`，并允许产生新的任务提案；Run 仍须保持 `created` 且 `stepCount` 为 0。
4. <a id="req-3-4"></a> 如果 Goal 不在等待批准状态或不存在当前任务提案，系统必须拒绝批准操作，且不得修改快照或启动 Run。

### 需求 4：分阶段等待规则

**用户故事：** 作为 Agent 使用者，我希望不同阶段只能以匹配的原因等待，以便准备阶段充分交互而执行阶段尽量不中断。

#### 验收标准

1. <a id="req-4-1"></a> 当 Goal 位于 `gathering_context` 时，系统必须只接受 `question` 类型的交互等待。
2. <a id="req-4-2"></a> 当 Goal 位于 `planning` 时，系统必须只接受 `approval` 类型的交互等待。
3. <a id="req-4-3"></a> 当 Goal 位于 `executing` 时，系统必须只接受表示权限、破坏性操作、关键矛盾或外部依赖缺失的 `blocked` 等待。
4. <a id="req-4-4"></a> 当等待类型与当前阶段不匹配时，系统必须返回可识别的失败，不追加消息、不改变阶段或状态，也不继续后续处理。

### 需求 5：输入恢复与持久化顺序

**用户故事：** 作为 Runtime 调用方，我希望通过统一操作提交等待中的用户输入，以便会话更新和恢复执行保持一致。

#### 验收标准

1. <a id="req-5-1"></a> 当调用方对匹配的等待 Goal 提交非空用户输入时，系统必须在同一次恢复操作中追加输入、推进对应状态并保存完整 Goal。
2. <a id="req-5-2"></a> 当输入后的 Goal 尚未成功保存时，系统不得发起下一次准备交互或执行 Step。
3. <a id="req-5-3"></a> 如果 Goal 不存在、Run 标识不匹配、当前状态不等待输入或输入去除空白后为空，系统必须返回可识别的失败，且不得修改快照或调用后续执行依赖。
4. <a id="req-5-4"></a> 当保存输入或状态失败时，系统必须传播持久化错误并停止处理，使标准恢复仍只能看到最后一次成功保存的快照。

### 需求 6：真实会话与 Working Context 分离

**用户故事：** 作为恢复 Session 的使用者，我希望消息历史只表达真实交互，以便理解用户与 Agent 实际交换过的信息。

#### 验收标准

1. <a id="req-6-1"></a> 当用户回答、反馈或解除阻塞，或者 Agent 提问、请求批准或报告阻塞时，系统必须将面向对方的内容作为对应角色的真实消息按原顺序保存。
2. <a id="req-6-2"></a> 当系统为模型构造本轮 Working Context 时，必须从当前 Goal 的意图、阶段、任务与运行状态派生该上下文，且不得将生成的控制内容追加到会话消息。
3. <a id="req-6-3"></a> 当 Goal 保存并恢复后，真实会话的内容和顺序必须保持不变，后续模型请求必须能够使用这些已保存消息和最新派生上下文。

### 需求 7：执行阶段的 Step 边界

**用户故事：** 作为 Agent 使用者，我希望 Step 只统计已批准任务的实际执行，并能选择是否设置执行上限，以便前置问答不会影响任务执行且长任务可以持续推进。

#### 验收标准

1. <a id="req-7-1"></a> 当 Goal 位于 `gathering_context` 或 `planning` 时，任何模型交互都不得增加 `stepCount` 或计入配置的 `maxSteps` 上限。
2. <a id="req-7-2"></a> 当已批准任务的 Goal 首次进入 `executing` 时，系统必须先保存完整快照，再启动 Run 和第一个 Step。
3. <a id="req-7-3"></a> 当执行 Step 返回 `continue` 时，系统必须在保存该 Step 的状态与真实消息后自动执行下一 Step，无需用户确认。
4. <a id="req-7-4"></a> 当执行达到 `completed`、`failed`、`cancelled`、`blocked`，或者 `maxSteps` 为正数且 `stepCount` 达到该上限时，系统必须停止连续执行并保存对应最新状态；当 `maxSteps` 为 0 时，系统不得因 `stepCount` 增长而停止执行。

### 需求 8：快照协议升级

**用户故事：** 作为已有 Goal 的使用者，我希望升级后仍能恢复旧 Session，以便数据模型演进不会丢失已经保存的任务。

#### 验收标准

1. <a id="req-8-1"></a> 当系统恢复合法的 `schemaVersion: 1` 快照时，必须将其确定性转换为新协议：原任务同时形成稳定意图和最终任务，阶段为 `executing`，PreparationState 为已完成，Run 保持原状态。
2. <a id="req-8-2"></a> 当旧快照被转换时，系统必须原样保留已有消息的内容与顺序，不推断或删除其中可能存在的历史 Working Context。
3. <a id="req-8-3"></a> 当已转换的 Goal 下一次成功保存时，系统必须写入新协议版本；恢复操作本身不得改写原快照。
4. <a id="req-8-4"></a> 如果快照结构损坏或协议版本未知，系统必须返回可识别的协议错误，不修改持久化数据，也不启动任何准备交互或执行 Step。
