# 轨迹存储性能优化 需求

## 审批摘要

### 目标

测量并降低 `JsonFileTrajectoryStore` 的长轨迹读写开销:消除追加事件的 O(N²) 累计历史处理量,同时保持全部恢复边界与协议校验语义。

### 范围

- 包含:三档规模(100/1,000/10,000 事件)的性能基线与优化后对比;追加路径改为尾部反向扫描取最后序号;会话内按 Goal/Run 的序号缓存;读取路径全量校验保留。
- 不包含:跨进程锁、exactly-once、原子双写、偏移索引、增量读取、缓存持久化。

### 核心行为

- 追加单个事件的成本不随该 Run 已有事件数增长(消除累计 O(N²))。
- 同进程连续追加命中缓存不读取文件;进程重启或首次追加回退尾部扫描。
- 读取(范围查询、边界分类)的协议校验、序列单调性检查与 fail-closed 语义完全不变。
- `committedThroughSequence` 唯一恢复边界与未提交 tail 不自动 replay 不变。

### 风险与待确认

- 风险等级:medium;理由:触碰存储核心追加路径与恢复边界,但读取语义不变、变更局部可逆。
- 关键操作:无。
- 风险:追加不再提前发现历史文件中途损坏,损坏检测时机后移到读取时(读取时仍 fail-closed);压测数字受机器负载影响,以同机相对对比为准。
- 待确认:无。

## 引言

`JsonFileTrajectoryStore` 每次追加事件前都完整读取、解析并校验该 Run 的全部历史,只为计算下一个序号,长轨迹下累计处理量呈 O(N²)。本 Spec 定义追加路径的优化行为与性能验证方式,同时保持读取路径的全部既有语义。

## 需求

### 需求 1:性能基线与优化后对比可量化

**用户故事:** 作为评估轨迹存储优化收益的维护者,我希望有可重复运行的压测在优化前后产出同规模可比数据,以便用证据而非推测决定和验证优化。

#### 验收标准

1. <a id="req-1-1"></a> 当运行压测时,系统必须能输出 100/1,000/10,000 事件三档的累计追加耗时与范围读取耗时,且以可重复执行的测试形式提供。
2. <a id="req-1-2"></a> 优化后的同规模压测必须可以与基线直接对比,并显示 10,000 事件档的累计追加耗时显著下降、增长趋近线性。

### 需求 2:追加成本不随历史规模增长

**用户故事:** 作为长任务的执行方,我希望追加单个轨迹事件的耗时不随该 Run 已有事件数增长,以便长任务后期的持久化开销保持稳定。

#### 验收标准

1. <a id="req-2-1"></a> 当向一个 Run 追加事件时,系统必须仅通过会话内序号缓存或文件尾部扫描确定下一序号,不再读取、解析全部历史事件。
2. <a id="req-2-2"></a> 当进程重启后首次向已有轨迹的 Run 追加事件时,系统必须通过尾部扫描正确取得续接序号,行为与重启前一致。
3. <a id="req-2-3"></a> 当 JSONL 文件末行后没有换行符时,系统必须仍能正确识别最后的非空行并取得续接序号。

### 需求 3:读取与恢复语义完全不变

**用户故事:** 作为依赖轨迹恢复 Run 的 Runtime,我希望读取路径的行为在优化前后完全一致,以便恢复边界与协议校验不受优化影响。

#### 验收标准

1. <a id="req-3-1"></a> 当读取轨迹时,系统必须保持既有全量协议校验:非法 JSON、事件结构错误、Goal/Run 标识不匹配、序列非单调均按原语义抛出 `TrajectoryProtocolError`。
2. <a id="req-3-2"></a> 当按 `committedThroughSequence` 分类读取时,系统必须保持既有的 committed/tail 分类与查询语义不变。
3. <a id="req-3-3"></a> 当同一 Run 的事件追加与读取并发发生时,系统必须保持按 Run 串行追加的既有语义,不因缓存引入乱序或丢失。
