# Preparation 阶段移除与 AskUser 交互需求

## 审批摘要

### 目标

删除独立的 Preparation 生命周期，让 Goal 从创建开始使用统一执行流；保留任务提案批准护栏，并提供类似 Codex plan mode 的结构化 `ask_user` 交互。

### 范围

- 包含：统一 Goal 生命周期、任务提案批准、内置 `ask_user` Tool、选项/多选/自由输入 TUI、只读探查迁移、持久化恢复、单一瀑布时间线和证据边界。
- 不包含：取消任务批准或 Action 批准、让 YOLO 自动回答 `ask_user`、旧开发期 Preparation 快照迁移、重新设计流式 transcript 屏障或 TUI 视觉主题。

### 核心行为

- 新 Goal 不再进入 `gathering_context` 或 `planning`，而是进入统一执行生命周期；任务批准作为可恢复交互保留。
- Agent 可通过 `ask_user` 一次提出 1–3 个结构化问题；用户可单选、多选或填写 `Other`，答案按原请求恢复给 Agent。
- 任务批准前只允许只读 Tool；任务批准后沿用现有 Tool Policy、Action 批准和恢复规则。
- TUI 只保留一条 Session 瀑布时间线，`ask_user`、任务提案、Tool Observation 和普通步骤按产生顺序保留。
- 用户回答属于会话上下文，但不能替代 Tool Observation 作为完成证据。

### 风险与待确认

- 风险等级：**high**；理由：同时改变 Runtime 生命周期、模型输出协议、持久化快照、恢复语义、Tool 授权边界和 TUI 交互。
- 关键操作：任何任务批准前的副作用 Tool 执行，以及未完成 `ask_user`/任务提案交互的恢复。
- 风险：旧 Preparation 数据不迁移；协议、快照或 TUI 任一边界不一致都可能导致 Goal 无法恢复或错误放行 Tool。
- 待确认：无。

## 引言

本功能将 Preparation 的提问、只读探查、规划和任务批准能力并入统一执行生命周期，并新增可恢复的 `ask_user` Tool 与 TUI 交互面板，使 Agent 能在执行前后获取明确用户决策，同时不削弱副作用 Tool 的批准边界。

## 需求

### 需求 1：统一 Goal 生命周期

**用户故事：** 作为 Goal 使用者，我希望新任务从创建起就使用同一条执行流程，以便不再面对独立的 Preparation 阶段，同时保留必要的交互等待。

#### 验收标准

1. <a id="req-1-1"></a> 当系统创建新的 Goal 时，Goal 必须直接进入统一执行生命周期，不能再产生 `gathering_context`、`planning` 或独立 `preparation` 状态；Run 初始状态仍为 `created` 且 `stepCount` 为 0。
2. <a id="req-1-2"></a> 当 Agent 需要提问、提交任务提案、等待阻塞解除、调用 Tool、完成或报告失败时，系统必须通过同一条执行推进协议处理，不得要求调用方切换到 Preparation 专用入口。
3. <a id="req-1-3"></a> 当 Goal 等待 `ask_user`、任务批准或用户反馈时，系统必须保存可恢复的等待状态，且不得把交互本身计入执行 Step。
4. <a id="req-1-4"></a> 当 Goal 在任务批准后执行实际 Tool/Observation 或终态决策时，系统必须继续遵守现有 Step 计数、快照和终态不变量；任务批准前的只读探查不得增加 `stepCount`。

### 需求 2：任务提案批准门控

**用户故事：** 作为系统使用者，我希望 Agent 仍然先提交可审查的任务提案，以便未经我同意不会执行具有副作用的操作。

#### 验收标准

1. <a id="req-2-1"></a> 当 Agent 提交任务提案且当前任务尚未批准时，系统必须持久化完整提案并进入任务批准等待，同时拒绝任何副作用 Tool 的执行。
2. <a id="req-2-2"></a> 当用户批准当前任务提案时，系统必须将该提案固定为最终任务、清除待批准状态并继续统一执行流。
3. <a id="req-2-3"></a> 当用户提交任务提案反馈时，系统必须保存真实用户消息、使旧提案失效并继续请求新的任务提案；该反馈不得启动副作用 Tool 或增加执行 Step。
4. <a id="req-2-4"></a> 如果批准或反馈与当前 Goal、Run 或待批准提案不匹配，系统必须返回可识别失败，且不得修改快照、Run、提案或 Tool 状态。

### 需求 3：AskUser Tool 协议

**用户故事：** 作为 Agent，我希望通过结构化 `ask_user` Tool 提出关键选择，以便用户可以明确回答而不必解析散文式问题。

#### 验收标准

1. <a id="req-3-1"></a> 当 Agent 调用 `ask_user` 时，请求必须包含 1 至 3 个问题；每个问题必须包含非空标题、非空问题文本、2 至 3 个唯一选项，并明确是否允许多选。
2. <a id="req-3-2"></a> 当 `ask_user` 请求通过协议校验时，系统必须生成稳定请求 ID，按原问题顺序持久化待回答请求，并将 Goal 置于用户交互等待；该调用不得执行外部 Tool。
3. <a id="req-3-3"></a> 如果 `ask_user` 请求包含空文本、重复选项、非法数量、未知字段或不支持的多选结构，系统必须拒绝整个请求，且不得创建等待状态、追加答案或调用下游依赖。
4. <a id="req-3-4"></a> 当用户完成回答时，系统必须为每个问题生成一次规范化答案；单选只能包含一个选项或非空自由文本，多选必须包含至少一个选项或非空自由文本，答案随后只能提交一次。

### 需求 4：AskUser 前端交互

**用户故事：** 作为终端用户，我希望像 Codex plan mode 一样通过键盘选择或输入答案，以便快速完成 Agent 的计划确认。

#### 验收标准

1. <a id="req-4-1"></a> 当 Goal 等待 `ask_user` 时，TUI 必须在统一 Session 的底部活动抽屉显示问题标题、问题文本、选项说明和当前问题进度；上方已完成时间线必须保持不变。
2. <a id="req-4-2"></a> 当当前问题为单选时，用户必须能够使用方向键移动焦点并按 Enter 提交；当当前问题允许多选时，用户必须能够使用 Space 切换选项并按 Enter 提交。
3. <a id="req-4-3"></a> 当用户选择 `Other` 时，TUI 必须切换到文本输入，拒绝去除空白后为空的答案，并在验证失败时保留用户已输入内容。
4. <a id="req-4-4"></a> 当用户提交最后一个问题后，TUI 必须只派发一次结构化答案；提交成功后移除活动面板并恢复 Goal，提交失败或忙碌时不得重复派发。
5. <a id="req-4-5"></a> 当任务尚未批准时，TUI 必须将该交互标记为计划问题；任务批准后再次调用 `ask_user` 时，必须显示为执行期 Agent 问题，但使用同一套选择和自由输入行为。

### 需求 5：只读探查与副作用边界

**用户故事：** 作为系统所有者，我希望统一执行流仍能安全获取只读信息，以便移除 Preparation 后不会放宽工作区和外部环境的写入边界。

#### 验收标准

1. <a id="req-5-1"></a> 当最终任务尚未批准时，系统必须只允许声明 `isReadOnly: true` 的授权 Tool；任何写入工作区、配置或外部可变状态的 Tool 调用都必须在执行前被拒绝。
2. <a id="req-5-2"></a> 当只读 Tool 调用成功或失败时，系统必须按统一 Tool/Observation 规则提交可审计结果，并将其按顺序显示在统一瀑布时间线中；任务批准前的探查不得增加 `stepCount`，也不得保留隐藏的 Preparation 探查通道。
3. <a id="req-5-3"></a> 当最终任务已批准时，系统必须继续使用现有 Tool Policy、Action 批准和 Action 恢复规则；`ask_user` 仍必须等待真实用户回答，即使执行模式为 YOLO。

### 需求 6：交互持久化与恢复

**用户故事：** 作为长任务使用者，我希望进程重启后能够继续未完成的提问或任务批准，以便不会丢失计划上下文或重复执行操作。

#### 验收标准

1. <a id="req-6-1"></a> 当系统创建、更新或完成 `ask_user`/任务提案交互时，必须先成功保存 Goal 快照，再允许下一次模型调用、用户恢复或副作用 Tool 执行。
2. <a id="req-6-2"></a> 当恢复的 Goal 存在未完成 `ask_user` 请求或任务提案时，系统必须恢复完整问题/提案、请求 ID、Run 关联和已选模式，并在用户回答或批准前禁止继续模型和 Tool 推进。
3. <a id="req-6-3"></a> 如果用户提交的请求 ID、Goal ID、Run ID 或问题序号不匹配当前等待状态，系统必须无副作用拒绝该提交，并保留当前输入等待点。
4. <a id="req-6-4"></a> 当保存、协议解析或恢复校验失败时，系统必须传播可识别错误并停在最后一次成功快照，不得以猜测状态继续调用模型或 Tool。

### 需求 7：统一瀑布时间线

**用户故事：** 作为 TUI 使用者，我希望所有 Agent 活动都按一条时间线连续显示，以便不需要在 Preparation 页面和执行页面之间切换或重复查看步骤。

#### 验收标准

1. <a id="req-7-1"></a> 当 Goal 会话启动或恢复时，TUI 必须只显示统一 Session 页面，不得显示独立 Preparation 页面或 `Step 1: Preparation & Planning` 条目。
2. <a id="req-7-2"></a> 当消息、`ask_user` 结果、任务提案、只读 Observation、普通执行 Step 或流式 transcript 完成时，TUI 必须按提交顺序追加到同一条瀑布时间线，历史内容不得被覆盖或重复。
3. <a id="req-7-3"></a> 当用户从等待点返回或进程重启后恢复时，时间线必须保持与最新 Goal/Trajectory 快照一致，Screen 不得维护第二份可推进的领域状态。

### 需求 8：证据、协议与既有流式语义

**用户故事：** 作为 Runtime 维护者，我希望移除 Preparation 后仍保持证据和流式生命周期边界，以便统一流程不会产生虚假完成或丢失流式内容。

#### 验收标准

1. <a id="req-8-1"></a> 当 Agent 使用用户回答、任务提案或 `ask_user` 结果生成完成声明时，系统必须拒绝将这些内容当作完成证据；完成声明仍只能引用已提交的 Tool/Observation。
2. <a id="req-8-2"></a> 当创建或恢复当前协议 Goal 时，系统不得再生成或依赖 `preparation_input_recorded`、`preparation_result` 或 Preparation 阶段字段；不支持的历史开发期数据必须以可识别协议错误失败，不得自动迁移。
3. <a id="req-8-3"></a> 当流式 transcript 在交互切换、步骤切换或新流开始前被冲刷时，系统必须先完成当前活动流并提交未闭合尾部，再允许下一条流启动。
4. <a id="req-8-4"></a> 当上述任一协议、证据或流式边界校验失败时，系统不得追加伪造消息、完成声明、Tool Observation 或新的执行状态。
