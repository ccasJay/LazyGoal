# Runtime 独立组件提炼与 SDK 化准备 Spec

## 目标与范围

先将应用中耦合的执行装配、实例生命周期和调用接口提炼为可独立使用的组件，并由现有 `goal-server` 消费验证，为后续 SDK 化提供事实依据。本轮交付包括组件、按职责组织的目录、受检查的调用边界及真实接入，不是完整 SDK。

Runtime、Agent、Storage、工具和执行流已有各自职责；保留这些模块及领域行为。本轮聚焦 `goal-server` 组合根中的实际耦合：执行链与 HTTP 一起创建、关闭流程包含进程退出、调用方依赖整个 CompositionRoot。

交付场景：独立调用方提供已准备好的执行器、Profile、工具与存储 Port，即可组合执行能力；资源所有者可以单独构造关闭组件。`goal-server` 使用这些组件完成默认应用装配，仍提供原有 Web 服务。无界面调用可启动 Goal、到达等待点、关闭并重建实例，然后关联原 Goal 恢复执行。

首个生产消费者仅为 `goal-server`，Benchmark 本轮不迁移。不新建 `packages/sdk`，不设计完整公开 SDK 门面，不承诺 npm 发布、跨语言协议、多租户或多 Run 并发调度。子代理、通用 Hook 平台、文件回滚、持久化迁移和执行循环重写均不包含在本轮。

本 Spec 拥有执行装配与通用生命周期，不依赖 [Agent 拆包](../agent-component-extraction/spec.md) 或 [进程组件提炼](../process-runtime-extraction/spec.md) 先完成。模型执行通过现有 StepExecutor 注入；资源实现通过 ManagedResource 报告真实结算结果。后两份分别拥有模型能力内部拆分、真实进程句柄与日志结算修正，不将这些实现工作纳入本轮关闭核心。

## 需求与验收标准

### 需求 1：可独立调用的执行装配组件

作为组件调用方，我希望注入本组件职责所需的现有依赖即可推进 Goal，以便脱离应用入口验证和复用执行能力。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当调用方提供 StepExecutor、GoalStore、Profile Registry 和所需工具、轨迹等 Port 时，执行装配组件应连接现有 Launcher、Runner、Scheduler 和 Coordinator；调用方不应再次手工组合这些内部执行对象。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当导入或构造该组件时，不应解析应用配置、创建模型供应商、创建默认文件存储、启动 HTTP、注册进程信号或退出进程；准备外部依赖仍由调用方的装配层负责。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当组件装配完成时，Runner、Coordinator 和 Launcher 应使用同一组存储与轨迹边界，并共享需要一致的检查点提交器、工具和授权依赖；原有保存顺序、累计预算、协议及授权规则应保持不变。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：若无界面应用装配中途失败，应清理已创建的自有资源并保留初始故障；初始 Goal 未保存成功时不发起模型或工具执行，借用依赖不因装配失败被关闭。

### 需求 2：与进程退出无关的实例生命周期

作为资源所有者，我希望单独关闭执行实例并保留可恢复状态，同时继续运行宿主进程。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当首次调用实例 `close()` 时，组件应立即进入 closing，拒绝新执行与写控制，冻结新的检查点写入并中止实例活动；已进入保存边界的写入允许结算。关闭不应创建用户 Interrupt、失败或取消终态，也不伪造未提交 Observation。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当关闭实例时，应调用并结算由实例创建或明确交付关闭权的资源，包括自身订阅、worker 和进程会话；资源实现按 ManagedResource 契约确认自身释放，通用生命周期不另行管理其内部句柄。宿主借出的 Adapter、Registry、Policy、存储和信号不应因注入而自动转移所有权，宿主进程仍应继续运行。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当已受理的调用、写入与按 ManagedResource 契约报告的自有资源均完成结算时，关闭应报告成功；重复关闭共享同一结果。正常和强制清理阶段均应有界，资源拒绝、未结算或无法按契约确认活动停止时应报告类型化错误及原因，不得永久等待或静默报告成功。具体资源内部吞错或提前成功的实现修正由该资源所有者负责，不得用此限制吞掉生命周期已收到的错误。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当关闭成功后在相同持久化位置重建实例时，应可以读取原 Goal 并按既有规则恢复；若关闭超时仍有活动或写入未结算，则不保证立即重用同一持久化位置，不应声称未知工具副作用已回滚或可安全重放。

### 需求 3：按消费者需要提供控制与观察接口

作为组件调用方，我希望获得任务所需的操作和结果，而不依赖整个应用组合根。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当调用 `launch`、`advance`、`resume` 或 `continue` 时，组件应复用既有请求和结果，分别表达新建 Goal、推进已有 Run、回答当前等待及在终态后创建后继 Run；读取 Snapshot 不自动执行，等待也不被报告为完成。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当原实例等待后关闭、重建并提交匹配交互时，应继续同一 Run；关联身份失配、损坏数据或缺失所需实现时应沿用现有拒绝边界，不创建替代 Goal 或擅自替换冻结 Profile。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当通过控制接口提交 Steer、Interrupt、Plan Mode 或必要权限操作时，应由现有规则所有者处理。第二个冲突推进应明确拒绝；Steer、Interrupt、订阅和合法读取不应被长执行锁死，不增加任务队列或自动后继 Run。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当取消订阅、监听器异常或慢订阅者关闭时，不应取消 Run 或改变提交结果；恢复事实仍来自 Snapshot 与已提交 Trajectory，保存通知只在 Snapshot 成功写入后触发。

### 需求 4：由 goal-server 验证独立性与行为保持

作为现有 Web 用户，我希望服务使用提炼后的组件，执行和交互行为仍保持一致。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当构造应用内部的无界面运行时装配时，应能在不创建 HTTP 服务、绑定端口或注册进程信号的情况下完成构造、执行与关闭；原服务组合根应消费该装配结果，不保留第二套执行链。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当通过 `lazygoal web` 使用创建、消息、恢复、审批、Steer、Interrupt、Plan Mode、模型切换或权限控制时，HTTP/SSE 契约、busy 与稳定身份重试、状态拒绝和持久化结果应保持原有语义；现有模型目录、归档、终态删除、历史和指标查询仍按原边界工作。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当 HTTP 客户端或 SSE 断开时，已受理执行不应取消；当服务关闭时，应用应停止写命令受理、关闭运行时和 HTTP 等资源，并自行处理信号、异常与退出，保留 SIGINT 退出码 130。

### 需求 5：目录、真源和替换边界可验证

作为维护者，我希望目录能够说明组件职责，并由检查和行为证据约束这些边界，以便后续修改或替换组件时不重新耦合应用。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当提炼完成时，无界面装配与生命周期应各自位于明确的组件目录；目录外生产消费者通过约定入口调用，入口不将内部实现全集重新导出，不需要新增 SDK 包或 group 层级。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：若组件导入禁止的宿主模块、绕过入口访问内部实现，或直接使用禁止的进程退出/信号 API，依赖检查应失败并定位违规源；合法装配应通过同一检查。检查应覆盖本次边界中的 import、export、侧效导入及字面量动态导入，不能仅凭目录存在报告边界成立。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当目录变化后，新源码和测试应被现有类型检查、依赖门、文档及回归入口实际发现；在没有旧构建产物的源码树上仍可执行组件验证。本次组件与测试指向仓库源码，若改动涉及的组件或测试通过项目内路径导入 dist/lib/build 产物，检查应拒绝。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当调用方以符合现有契约的替身或已有替代实现替换 StepExecutor、Store 或工具依赖时，应通过同一组件入口运行，不修改组件内部；应验证约定的成功、失败与资源所有权行为，不要求新增 Provider 或插件机制。

## 架构与核心决策

### 提炼位置与组件责任

新增模块按当前角色聚合为独立目录，优先留在现有所有者内，不创建 SDK 包。以下名称描述本轮内部模块契约，不构成对外发布的稳定 API 承诺。

| 组件或装配层 | 建议位置 | 输入与职责 | 边界 |
| --- | --- | --- | --- |
| 执行装配 `createExecutionComponents` | `apps/goal-server/src/runtime/execution-composition.ts` | 接收现有 StepExecutor、Profile Registry、Store、工具和可选 Port，组合检查点提交器、Runner、InlineScheduler、Coordinator 与 Launcher。 | 仅依赖注入的 Port 与现有领域/工具契约，不创建具体模型或文件存储，不拥有借用依赖的关闭权，不复制领域规则。 |
| 实例生命周期 `RuntimeLifecycle` | `packages/runtime/src/lifecycle/`，从现有 shutdown 机制提取 | 协调实例信号、Checkpoint Gate、自有资源和已受理操作的结算，提供幂等有界关闭。 | 依赖 Runtime 内部存储边界及必要控制类型；不读取环境，不包含 Agent、Storage 实现、HTTP、ExitPort、进程信号或 process.exit。 |
| 无界面应用装配 `createRuntimeComposition` | `apps/goal-server/src/runtime/composition.ts` | 从现有组合根移出模型、存储、工具和上下文等应用默认装配，组合执行组件与生命周期，为服务提供所需能力。 | 可以使用应用配置与具体实现；不导入宿主入口或 HTTP/Browser 传输实现，不宣称这是通用 SDK。 |
| HTTP/进程宿主 | 现有 `composition-root.ts`、`cli.ts` 及必要的应用适配模块 | 构造 HTTP、挂载路由、浏览器访问控制、信号监听和退出决策，消费无界面装配结果。 | 不再自行创建 Runner、Coordinator 或另一套关闭算法。 |

```text
goal-server HTTP/进程宿主       独立测试调用方
             ↓                    ↓
        无界面应用装配      或直接注入现有 Port
             ↓                    ↓
         执行装配组件 ←→ 实例生命周期
             ↓
    现有 Runtime / Agent / Storage / 工具
```

执行装配暂留应用内部，因为本轮只有一个生产消费者；独立性通过组件入口调用和注入依赖证明。出现独立消费、依赖安装、运行环境或发布需求时，再决定是否提升为 package。Runtime 不导入 Agent、Storage、应用或未来 SDK；不按文件大小继续拆分 RunExecutor、状态转换或持久化规则。

### 目录与调用入口

```text
apps/goal-server/src/
  runtime/
    index.ts                  仅导出当前调用方需要的装配函数与类型
    composition.ts            应用默认依赖与实例装配
    execution-composition.ts  接收 Port 的执行链装配
  composition-root.ts         HTTP 服务组合
  cli.ts                      进程信号、浏览器入口与退出协调

packages/runtime/src/
  lifecycle/
    index.ts                  关闭与资源管理契约入口
    runtime-lifecycle.ts      操作受理、结算与关闭
    managed-resources.ts      从现有 shutdown 提取的资源管理
  checkpoint-gate.ts          保留既有检查点写入边界
  index.ts                    选择性导出生命周期契约
```

这是按职责组织的最小结构，不要求为每个类型或函数创建子目录。应用宿主及消费型测试通过 `runtime/index.ts` 进入；生命周期通过 `lifecycle/index.ts` 或 Runtime 包的选择性导出进入。组件内部可以直接引用同目录实现，针对内部实现的单元测试允许定向导入，但不能用其替代入口消费验证。

已有纯辅助模块仅在属于这些职责且迁移有益时移入；不增加统一 components 容器、可选资源空目录或独立构建配置。旧 shutdown 实现拆分后删除已迁移职责及陈旧导出，不留第二份关闭逻辑。

### 事实归属与机器约束

| 事实或材料 | 唯一权威归属 | 其他位置的使用方式 |
| --- | --- | --- |
| Goal 状态、授权规则及持久化协议 | 现有 Runtime、Permission、Storage 等规则所有者的源码与测试 | 装配调用原入口，不复制规则或引入 SDK DTO。 |
| 组件输入、结果、错误与资源所有权契约 | 对应组件公开类型与方法的 TSDoc | 目录入口导出，说明文档链接源码。 |
| 当前组件职责、目录与依赖方向 | 所属 goal-server/Runtime 的 overview 与 semantics | 根导航和读取者链接所有者；内部目录不另建一套包级文档。 |
| 本轮提议与验收 | 本 Spec；批准后的任务归 plan.md | 实现前不将拟议目录写成当前已支持能力。 |

Snapshot、运行时对象和模型投影可以有不同表示，转换与校验仍由原所有者负责。源码、Prompt 模板及资源保留当前真源位置；不复制生成结果作为第二份可编辑来源。

扩展现有 `scripts/check-dependencies.mjs` 的定向边界规则，而不引入新的通用架构框架：

- `goal-server/src/runtime/` 不得反向导入 `cli.ts`、外层 `composition-root.ts`，或 Browser、HTTP、Web wire 与 Node HTTP 服务实现；不得直接请求进程退出或注册进程信号。指标核心服务可按现有职责注入，HTTP 指标路由只在宿主装配。
- `execution-composition.ts` 只使用现有 Runtime、工具和执行控制等契约；具体 Agent/LLM、配置解析、文件存储和默认工具准备留在同目录的应用装配层。
- `runtime/src/lifecycle/` 不得依赖应用、模型或具体存储实现；生产代码跨入上述组件目录时通过入口，不穿透内部文件。入口本身及目录内部引用不受此穿透限制。
- 对上述组件和消费型测试，拒绝解析到项目内 dist/lib/build 的导入；第三方依赖自己的内部产物目录不在此限制内。

新增规则覆盖对应导入与导出形式，路径归一化后判断，防止通过重新导出绕过；用最小合法和违规工程样本验证检查行为。静态约束只承诺当前 TypeScript 代码及字面量模块引用，不作为任意动态加载或宿主代码的安全沙箱。

测试继续放在所属模块已有 `test/` 下，必要时使用子目录；不改为随意共置于 src 而让现有回归漏扫。沿用源码类型检查与 tsx 回归，显式核对新增位置被根回归、goal-server 类型检查和依赖扫描发现。未新增包，无需新建聚合构建或迁移 CI glob；文档检查覆盖所属模块的说明更新。独立产物消费与发布验证待存在真实需求时另行设计，不以产物验证替代源码验证。

### 依赖装配与控制接口

执行装配从当前 RunnerDependencies、LauncherDependencies 和 GoalCoordinatorDependencies 提取所需输入；相同依赖只注入一次，并在内部完成一致装配。生命周期所保护的 Store 与传给执行链的 Checkpoint Gate 必须是同一实例，不能分别包装出互不相识的写入边界。允许使用内存 Store、确定性 StepExecutor 和最小 Registry 验证，不要求测试创建供应商 Adapter 或整套应用配置。

返回值提供 `commands`，包含当前消费者需要的 `launch`、`advance`、`resume`、`continue`、`steer`、`interrupt`、`enterPlanMode` 及已有权限委派。优先复用现有方法签名与最小 Port 类型，不额外包装同义结果，不返回 Runner、提交器或整个 GoalCoordinator 实例。调用方提供的存储仍归调用方所有；组件不能通过隐藏其引用声称形成安全沙箱。

无界面应用装配提供上述控制 Port、只读恢复和已有服务所需的查询、保存通知与订阅能力；内部保留具体资源的装配引用，不将它们全部重新导出给每个调用方。Browser 继续接收其现有最小 Port；HTTP 受理回执、幂等命令与 wire 映射不下沉到执行组件。

模型目录、模型选择持久化与绑定对齐、权限模式、归档、删除和指标继续由现有所有者处理，只做本次分离必需的接线。服务不得为绕过组件而另起执行链，但本轮不要求把这些能力整合成 `models`、`permissions`、`goals`、`history`、`metrics` 等 SDK 操作组。

推进仍返回现有 LaunchResult/GoalProgressResult，并在等待或终态结算；领域拒绝不改为异常，基础设施故障仍拒绝 Promise。组件仅为冲突受理、生命周期不可用和清理不完整引入必要错误分类，服务适配到既有 busy 或关闭响应。

### 配置、操作受理与资源所有权

应用默认装配保留现有 Home、Profile、模型配置来源、优先级和持久化目录。工作区与解析后的环境通过装配参数传递，不修改进程环境或当前目录；凭据、函数、连接和句柄不进入 Goal Snapshot。适用配置属于应用实例、Goal 还是单次调用，继续按原有契约区分。

资源所有者创建实例级 AbortController、Checkpoint Gate 与受管资源集合，并明确交付给生命周期组件协调；宿主外部信号只作为中止来源，不因组件关闭而反向 abort 宿主共享控制器。借出的 Adapter、Registry、Store 或其他扩展不自动纳入清理，组件执行过程中自建的 worker、进程会话和监听器则纳入实例资源。

无界面装配的控制 Port 使用同一生命周期受理边界，记录未结算操作。单实例只允许一个活动推进；Steer、Interrupt 等控制不持有整个推进过程的排他锁。服务现有模型更新、权限写入、归档和删除等已受理写操作也必须纳入关闭结算，不能仅等待 GoalStore.save。保留现有业务校验，不新增多实例或跨进程锁承诺。

### 关闭组件与进程适配

从 `shutdown.ts` 提取唯一的关闭核心；ExitPort、ProcessExitPort、SIGINT 退出码和退出适配归 `goal-server`。现有 ShutdownCoordinator 的宿主职责迁到应用，由其调用关闭核心；更新实际调用方与测试，不保留兼容包装或两套关闭顺序。不能以注入空 ExitPort 代替分离。

`RuntimeLifecycle` 的状态为 open、closing、closed；关闭不完整时保持不可再受理的 closing，重复 close 返回同一失败结果。构造无 I/O；不引入与 Goal/Run 重叠的业务状态。

关闭顺序为停止受理与冻结新保存、发出实例中止、等待已受理操作及已进入保存结算、清理自有资源。正常和强制阶段各使用 `gracePeriodMs` 作为上限，默认各 2000ms；两个阶段均不得因不响应的依赖无限延长。所有相关 Promise 的迟到拒绝均需处理。

只有活动操作、写入和自有资源均已结算才能报告成功。超时或清理失败产生携带剩余操作类别与原因的类型化错误；保留原始执行或构造故障，不以清理错误覆盖它。失败不等于所有外部副作用已停止，确认停止前不得立即重用同一持久化位置。

ManagedResource 的成功返回必须表示该实现拥有的资源及必要写入已经结算，拒绝表示清理失败，未完成的 Promise 表示尚未确认结算；正常阶段未完成时可由外层请求 forceClose。资源注册表必须保留拒绝/未完成信息及强制升级资格，不能靠移除注册项伪造成功。通用生命周期只消费这个契约，不读取具体进程 Map、轮询 PID 或重写其输出等待算法。

HTTP 和浏览器连接不注册为 Runtime 自有资源。服务先停止新写命令受理，并在自己的关闭流程中处理 HTTP 与运行时关闭；无论运行时关闭是否报错，都继续尝试应用自有资源清理，最终由应用决定退出。正常退出与 SIGINT 路径共用同一实例关闭能力。

### 独立调用与恢复验证方式

低层验证直接构造执行装配和生命周期组件：提供内存或临时文件 Port、确定性 StepExecutor、Profile Registry 与最小工具，验证受理、推进、等待、故障和关闭，不创建整个应用。资源由测试中的明确所有者准备，组件不为无资源对象新增 close。

以下为低层组件的拟定调用草图；依赖由测试或调用方准备，示例不承诺完整应用默认配置：

```ts
import { createExecutionComponents } from "./runtime/index";

const { commands } = createExecutionComponents({
    store, executor: deterministicExecutor, profiles, toolRegistry,
});
const result = await commands.launch(request);
const saved = await store.restore(request.goalId);
```

完整接入验证通过 `createRuntimeComposition` 使用临时工作区和确定性 Adapter，覆盖“创建 → 等待 → close 成功 → 重建 → restore → resume 同一 Run”，并验证终态后 `continue` 创建新 Run。只读恢复不自动推进；不同等待类型仍提交匹配的 requestId/actionId，使用 Snapshot/Trajectory 核对恢复结果。

组件可独立调用与服务已实际消费，两者都是完成条件。仅移动代码、增加文件或保持一个必须创建 HTTP 的旧入口，均不能证明独立性。

替换验证沿同一入口注入确定性执行器、内存/文件 Store 和契约一致的工具替身，检查结果、错误及借用资源不被关闭；替换不需要修改组件源码，不添加只为测试存在的插件配置。组件角色按依赖与行为划分，不要求替换实现与原实现的内部结构相同。

### 与其它组件 Spec 的验收边界

| 负责的 Spec | 自身完成所需证据 | 不等待的其它实现 |
| --- | --- | --- |
| 本 Spec | 生命周期/注册表的真实状态与期限、符合契约的成功/拒绝/不响应资源、已受理写入、原 Goal 恢复及 goal-server 接入回归 | Agent 九包拆分、ProcessManager 内部竞态与日志结算修正 |
| 进程组件提炼 | 真实进程退出、启动/输出/终态写入结算及与生命周期的组合关闭 | 本 Spec 的 HTTP 拆分或其它控制功能全部交付 |
| Agent 拆包 | StepExecutor 内部组件独立消费及默认模型装配接入 | 本 Spec 关闭实现与进程组件迁移 |

本轮失败/超时机制以能明确拒绝、保持未完成或被强制释放的受控资源验证；已有进程工具的正常关闭回归仍执行。旧 ProcessManager 在输出写入、启动竞态或吞错分支中不满足资源契约的缺陷，明确由进程 Spec 修复并以真实进程验证，不能用本轮资源替身的通过宣称它们已解决，也不能为了通过原有回归跳过这些已存在测试。进程 Spec 不成为本轮验收的反向前置；跨组件的真实进程故障保证在进程 Spec 的组合验收通过后才能声明成立。

共同接入文件按职责修改：本 Spec 拥有无界面执行装配、生命周期与 HTTP/退出分离；Agent Spec 只修改当时实际装配中的模型执行器构造，进程 Spec 只修改进程管理器导入、创建和资源登记。三者均保留已存在的其它接线及依赖门规则，不覆盖整个组合根或回退检查器。共享文件造成的集成顺序不构成功能依赖，不在本文件定义分支编排。

## 曾考虑的备选方案

| 方案 | 未采用原因 |
| --- | --- |
| 首轮直接新增 packages/sdk 并承诺完整顶层 API | 会在组件边界未验证前固定统一配置与管理操作，扩大迁移范围；本轮先积累独立使用和真实消费证据。 |
| 在 Runtime 内装配默认 Agent 和文件存储 | 破坏现有依赖方向；具体实现由应用内部装配，Runtime 保留领域与基础生命周期责任。 |
| 立即将执行装配提升为 Runtime 公开工厂 | 注入 Port 的做法可行，但当前唯一生产消费者位于应用；先在内部验证输入与输出，避免过早固定包级契约。 |
| 为每类模型、工具和存储再建工厂或插件层 | 当前依赖已有类型化 Port，没有替换需求支持新增抽象；组件可直接使用这些依赖。 |
| 仅按文件大小切分组合根或执行循环 | 文件变小不保证可独立调用；本轮以构造依赖、副作用与消费者契约判定边界。 |
| 将组件文件继续平铺或只增加一个目录 | 前者难以表达成组职责，后者缺乏入口与约束；采用最小组件目录，并补针对性的依赖门和独立调用证据。 |
| 直接引入 packages/group/pkg、统一发布工具和每包覆盖率门槛 | 当前没有新增发布角色需求，且现有发现规则基于既有布局；保留当前包层级，仅补本次组件边界需要的检查。 |
| 整体重新导出 CompositionRoot | 仍要求调用方理解内部对象，并将 HTTP 和进程退出带入无界面调用。 |
| 保留 shutdown 全流程并注入空 ExitPort | 没有移除宿主退出职责，也没有明确关闭结算与失败后果。 |
| 等 Run 自然完成，或用取消订阅触发关闭 | 前者无法保证关闭有界，后者混淆观察、用户 Interrupt 与实例结束。 |
| 同时迁移 Benchmark | 增加环境与评分适配范围；本轮只由 goal-server 验证，后续按共同职责决定复用位置。 |

## 风险与否定性保证

- **风险等级仍为高。** 虽然取消完整 SDK 交付，检查点保护、关闭结算和权限调用仍跨模块调整；必须验证恢复与副作用边界。没有新增授权、删除范围、持久化格式或兼容迁移。
- **关键操作边界：** 实现验收使用临时目录、确定性模型替身和受控子进程。设计及后续测试不要求操作用户既有 Goal、真实模型或生产服务；既有终态删除仅保持原接线和范围。
- **领域不变量：** Runtime 保持唯一状态规则所有权；不重置累计预算、不吞存储错误、不绕过审批、不将临时活动当事实、不盲重放未知工具结果，不承诺外部文件回滚或 exactly-once。
- **使用限制：** 组件支持本次约定的 Node.js 同进程、串行推进场景，保留既有工具平台限制；不保证宿主借出对象的隔离，不允许多个实例同时写同一持久化命名空间。恢复需重新注入必要实现，不合成替代能力。
- **验证范围：** 独立组件覆盖依赖注入、相同 Port 装配、等待与恢复、关闭幂等、活动调用和在途写入、正常/强制期限、清理异常及未知结果；使用子进程验证关闭后宿主继续工作。goal-server 接入覆盖原 HTTP/SSE、模型与权限控制及查询行为，Benchmark 仅运行相关既有确定性回归，不执行迁移。
- **资源契约与验收归属：** 生命周期的有界等待和错误传播不证明一个内部吞错的具体资源已真实释放；该实现仍须由其所有者修复。本轮不依赖进程 Spec 完成，但也不提前宣称其真实进程故障保证成立。新增说明与 2.2/2.3 的验收边界修订需重新批准，已有功能测试不因职责分开而删除或弱化。
- **交付检查：** 实现阶段运行类型、依赖、文档、相关消费者回归及根确定性回归；增加边界检查的合法/违规样本并确认新增测试实际被发现，在无历史构建产物的源码树验证独立调用与替换。更新受影响模块的 overview、semantics 与公共契约 TSDoc。具体行为 TODO 与 Feature Verification 留待 Spec 批准后的 plan.md；独立组件完成不宣称完整 SDK 已交付。
