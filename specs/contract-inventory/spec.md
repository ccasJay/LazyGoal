# 全局数据契约盘点 Spec

## 目标与范围

建立可审阅的现状清单，为后续契约去重和 TS 迁移提供依据。覆盖项目生产数据边界：模型载荷、工具输入输出、Web DTO、持久化文件及 Snapshot，以及其他跨进程、外部接口和模型／工具 JSON 边界。盘点相关原生 TS 类型、Contract DSL/AST 和其他现有 Schema；不实现注册中心或迁移契约。

## 需求与验收标准

- <a id="spec-req-1-1"></a>**1.1 登记粒度**：当盘点生产数据边界时，应当为边界根及其可达的每个项目内具名 `interface`、`type` 和具名 Contract AST 节点各登记一条；同一声明只登记一次并记录引用关系。普通内部类型仅在被上述契约引用时纳入；测试、依赖和生成制品不作为独立定义登记。
- <a id="spec-req-1-2"></a>**1.2 记录来源**：当登记条目时，应当记录源码位置与声明名、边界类别、定义方式、所属模块、实际消费方及引用关系；分别标识 TS 类型、AST 节点或其他 Schema，避免把同源推导误记为独立定义。
- <a id="spec-req-1-3"></a>**1.3 身份与版本**：当现有契约声明协议身份或版本时，应当记录实际值及依据；未声明、无法确认和不适用须明确区分，不为现有协议虚构身份或版本。条目的源码定位键仅供清单引用，不作为新的协议身份。
- <a id="spec-req-1-4"></a>**1.4 生成目标**：当契约产生 Schema、Reader、Manifest 或其他投影时，应当记录实际产物、生成入口和消费位置；未生成、动态生成或无法确认须明确区分，不把未来目标当成现有事实。
- <a id="spec-req-1-5"></a>**1.5 动态契约**：当模型或工具契约由运行时授权集合、阶段或注册结果组合时，应当登记其具名组成部分、构造入口及影响组合的条件；不枚举全部运行时组合，也不声称最终 Schema 已在构建期固定。
- <a id="spec-req-1-6"></a>**1.6 可核查覆盖**：当完成盘点时，应当记录扫描范围、发现方法、各类边界入口及排除规则，并以源码和实际调用方核对；未能解析的引用、来源或消费方列为未知项及原因。清单须能据此复核遗漏，不以搜索结果数量或空白字段表示完整。
- <a id="spec-req-1-7"></a>**1.7 重复候选**：当发现名称或结构相似的定义时，应当记录候选及证据，并区分同源派生与独立定义；不能仅凭形状相同认定语义等价或确定合并方案。
- <a id="spec-req-1-8"></a>**1.8 独立交付**：当验收本步时，应当能够从清单定位至少一个模型、工具、Web 和持久化边界及其来源和消费者；运行文档检查并核对清单链接。生产代码、协议行为和既有生成制品保持不变。

## 架构与核心决策

清单是记录当前证据的文档，不是供 Runtime 或构建读取的 Catalog；数据定义和执行规则仍由各自所属模块维护。契约之间的语义等价与权威归属留待后续独立 Spec 决定。未知项是盘点结果，不能作为推断或删除的依据。

[已交付的模型列表响应](../ts-provider-models-contract/spec.md)记录现有 TS 及生成制品；[模型查询输入](../ts-provider-model-query-contract/spec.md)和 [Provider 测试结果](../ts-provider-profile-test-contract/spec.md)尚未实施，清单只描述实际源码，不预登记它们的未来产物。盘点与这两项迁移可以独立开展；合入前须根据实际源码复核盘点基线。

## 风险与否定性保证

风险等级：中。跨模块引用和动态组合可能造成漏项或错误归属；保留可复核来源和未知项，不将静态扫描结果视为运行时组合的完整证明。本步不改变数据或执行语义、不去重、不生成新制品、不删除 DSL 或 AST，也不引入兼容层。
