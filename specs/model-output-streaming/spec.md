# 模型输出流与有序内容块 Spec

## 目标与范围

LazyGoal 以供应商无关的有序内容块表达一次模型响应，使生成增量、完整结果及调用记录具有一致的内容与来源。模型调用期间可以观察正文和工具参数的生成过程；只有整个响应成功结束，才将完整结果交给现有阶段解码、Runtime 校验、审批和执行路径。

本次设计 `text`、`tool_call`、`reasoning` 三种内容块及其生命周期，统一 `LLMResponse` 与 `LLMStreamEvent`，补齐原生 OpenAI／OpenAI-compatible 和 Gemini 的流式调用，更新 pi-ai 映射、单次调用采集及当前消费方。保留 OpenAI Chat Completions、Gemini generateContent 和现有 pi-ai 接入；按实际协议能力提供增量或整块内容，不伪造分片。保留 strict／prompt_only、阶段 Adapter 装配、原生续接、现有权限和 Runtime 重试边界。

本次不提炼 SDK 包，不引入 Gemini Interactions、OpenAI Responses 或新供应商协议，不升级供应商 SDK；不改变 Session 输入、队列、Steer／Interrupt 收尾或 Run 完成规则。不设计正式会话消息协议、完成候选的 `summary` 预览、Web 内容块布局、图片／附件、MCP、子代理或提前执行工具。工具结果继续属于 Runtime Observation，供应商签名继续属于不透明续接信息；二者不是本次模型输出块。开发期旧数据不增加迁移或兼容分支，不删除用户 Goal。

## 需求与验收标准

### 需求 1：统一的有序内容块与完整响应

作为模型输出消费者，我希望增量和完整结果引用相同内容，以便准确解释一次生成而不维护两套正文。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当 Adapter 成功返回完整响应时，应以有序 `blocks` 作为正文、工具调用和公开 reasoning 内容的唯一权威；现有消费者所需的正文／工具列表／推理视图由块派生，不同时保存可独立修改的平行字段。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当响应含正文、工具调用或供应商实际返回的 reasoning 时，应分别表达为 `text`、`tool_call`、`reasoning` 块；文本显式区分普通文本与请求要求的结构化 JSON，工具块保留模型调用 ID、工具名和参数 JSON 文本。不得从字符串外观猜测业务决策，不得把系统完成函数的 `summary` 自动变成新块类型。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当供应商提供 Parts、内容索引或流中块归属时，应保留可证明的内容顺序和分离关系；未提供跨字段时序的完整响应按明确的协议映射排序，不声称重建未知时序。不得按 Markdown 段落拆块或把所有文本跨工具块合并为一个块。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当同一流产生完整响应时，其块索引、类型、顺序和内容应与已经完整结束的块一致；正文派生不得包含 reasoning，参数不得混入正文。发生不一致时应报告协议错误，不静默替换已经结束的块。
- <a id="spec-req-1-5"></a>**验收标准 1.5**：当通过 `generate` 或 `stream` 消费等价的确定性供应商响应时，应得到等价正文、工具参数、调用身份及续接语义；同一次流的最终结果与块内容必须一致，不要求两次独立生成具有相同内容、随机 ID 或分片边界。

### 需求 2：块身份与可判定的生命周期

作为观察者，我希望知道每个增量属于哪里、是否完整，以免把残缺内容当成有效请求。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当一次模型调用开始时，应分配独立 `modelCallId` 并用于输入记录、指标、诊断及实时来源；每个块具有本次响应内稳定且唯一的索引，所有块事件可由调用身份与索引定位。工具的模型调用 ID、块身份与 Runtime `actionId` 不得互相替代。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当块逐步生成时，应先开始、再接收有序类型化增量、最后完整结束；允许不同块的增量交错，但不得串接其内容。块结束后不可再追加，未知索引、重复开始／结束、类型冲突或成功结束后继续输出均应成为协议错误。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当文本或参数以完整块到达，或必须收齐才能归一化时，应明确表达整块交付；可直接开始并结束块，不要求伪造增量。工具名称及供应商调用 ID 晚到时，块索引保持不变，只有完整结束的工具块才要求这些最终字段齐备。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当中止、失败或非正常断流发生时，应结束本次调用的观察状态，并明确哪些块未完成；已经结束的块仅表示生成内容收齐，不表示响应整体成功、操作获批、工具执行或 Run 完成。不得用普通完整结束事件封口残缺工具参数。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当重试、协议修复或下一个阶段产生新调用时，应使用新的调用身份；迟到或缓存的旧调用分片不能归入新调用。事件合并键至少隔离调用、块及增量种类，不以整个 Run 或执行单元作为唯一拼接依据。

### 需求 3：现有供应商协议的真实流式映射

作为维护者，我希望三个现有适配器遵守同一契约，同时保留各协议真实能力。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当原生 OpenAI／OpenAI-compatible Adapter 进行流式调用时，应使用 Chat Completions 的真实流，正确累计文本、工具调用索引、分片名称／ID／参数及用量尾部；保留当前 tools、tool choice、strict 请求、取消和关闭 SDK 内部重试的设置，不改为 Responses API。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当 Gemini Adapter 进行流式调用时，应使用 generateContent 的流接口，按真实 Parts 分离正文、thought 和函数调用，保留续接 Parts 顺序及签名；完整到达的函数参数按整块交付，不开启当前协议不支持的参数分片能力，不迁移 Interactions API。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当 Gemini strict 结构化文本需要既有 Schema 逆向投影时，应在收齐所需内容并完成同一投影后交付规范块，明确为整块方式；`generate` 与 `stream` 共用归一化规则，已结束块不得被后续哨兵恢复或联合分支清理改写。普通文本仍按实际增量输出。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当 pi-ai 发出文本、thinking、tool call 的块边界和增量时，应保留其内容索引与归属，完整结果沿同一块组装；实际返回的 thinking 保持受限，不能因最终映射遗漏而与流结果矛盾。required 工具策略、prompt_only、既有取消／错误分类和缺省正式 usage 的规则保持。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当响应含不支持的多模态或其他非文本／函数 Part 时，应在供应商边界明确拒绝，不能静默删去后宣称成功；供应商未暴露的块边界、参数字节或推理不得凭空补造，缺失用量不以零或估算值代替。

### 需求 4：单次调用采集与完整响应后的执行边界

作为 Runtime 调用方，我希望流式观察不改变原有决策、授权与执行时机。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当工具块先于整个响应结束时，系统应允许观察生成过程，但不得提前把块送入 Runtime 审批、暂存 Action 或执行工具；整个响应成功结束后才交给现有阶段解码，继续遵守当前批次、PTC、完成审查和授权规则。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当采集流时，应要求恰好一个成功完成结果，检查块序列及最终结果一致性；缺少、重复、提前完成、未封口块或不完整结束标记均不得返回成功响应。采集器不以部分 JSON、空对象或先前调用的结果补齐。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当 Adapter 已产生完成候选但迭代器尚未正常结束时，调用方仍应等待结束并检查尾部；尾部异常或完成后的额外事件应使本次调用失败，不发布模型成功完成，也不交给执行器。用量等合法尾部信息应在最终完成结果之前汇总。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当注入只实现 `generate` 的确定性或宿主 Adapter 时，应继续支持同一内容块完整响应，调用开始时发布开始状态，返回后按整块方式观察；不得拆字模拟生成。已选择的流路径失败时不自动再调用 `generate` 或发起第二次请求。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：当记录调用时，应保持输入落盘失败阻止请求、指标及诊断失败隔离、当前 token 用量和耗时定义；每个真实调用只记录一次开始及其真实结束结果，不因块数量重复计费／计数，不把整块交付延迟伪装为逐 token 解码速率。

### 需求 5：取消、截断与错误传播

作为宿主，我希望中途失败可以被准确判断，不因已经看到文本就误认为成功。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当调用前或流消费期间中止时，应沿现有取消信号停止读取并关闭本次自有流／传输，传播取消错误；取消后的迟到分片不能继续发布或返回成功，不强行关闭借用 Adapter 或整个 Runtime。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当供应商报告长度截断、安全阻断、内容过滤、错误状态或无有效结束的 EOF 时，应明确拒绝成功完成，不因已出现完整文本或工具块而接受被截断的整个响应；没有可用业务结果的正常完整响应仍由既有阶段协议检查处理。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当流产生网络、鉴权、配额、协议或供应商异常时，应保留既有类型化原因和暂时故障分类，不在 Adapter／采集器内部重试、换协议或降级模型；Runtime 是否重试仍由既有预算与规则决定，每次新调用独立观察。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当失败发生在一个完整工具块之后或多个块之间时，应丢弃本次调用作为可执行响应的资格，已展示片段保持未提交含义，实际工具调用次数为零；错误不创建伪造 Observation、对话消息或成功完成证据。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当退出迭代、取消或错误清理时，应尝试释放本次拥有的迭代器和传输，观察清理异常并保留主失败原因；观察订阅背压或断开不应触发用户 Interrupt、阻塞模型采集或改变已完成的调用结果。

### 需求 6：观察事件、隐私与资源边界

作为公开观察者，我希望接收允许展示的生成状态，而不获得隐藏推理、任意参数或原始响应。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当发布内容块活动时，应保留 Goal／Run、可选执行单元及模型调用／块身份；普通正文、结构化 JSON、工具参数和 reasoning 分别执行明确可见性规则。完整响应含有受限内容时，不得借公共完成事件整体广播。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当默认订阅或现有 Web 接收输出时，应只得到既有允许的普通正文及安全生命周期摘要；原始结构化 JSON、工具名称以外的任意参数及完整工具块只供受保护诊断入口，reasoning 还须显式开启受限订阅。签名、凭据、原始 Provider metadata 和私有审查正文不进入公共事件。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当文本／参数增量合并或消费者缓慢时，应沿用现有有界订阅和关闭原因，同一块内保序、不同块不合并，控制边界不得静默丢弃；核心不得保存所有累积前缀或为每个分片写 Snapshot／Trajectory。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当事件发布失败或订阅消失时，应隔离观察故障，保持原模型响应、执行结果和持久化边界；允许事件缺口，不承诺每个分片送达、跨重启回放或实时事件 exactly-once。后续会话同步不能从残缺片段重建可执行结果。
- <a id="spec-req-6-5"></a>**验收标准 6.5**：当现有 Browser 继续消费模型活动时，应将新内部块事件投影到当前白名单活动 DTO，保留调用开始、正文和结束提示，不要求先实现新的 Session 输出或 Web 布局；公共 DTO 不因内部响应换形而获得 reasoning、完整参数或私有 JSON。

### 需求 7：当前消费方迁移与可验证交付

作为维护者，我希望新协议由真实调用链使用，而不是只增加未被消费的类型。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当切换内容块契约时，应迁移三个 Adapter、单次调用、诊断、指标、阶段解码、原生历史投影及实际测试／示例消费方；现有文本和工具语义通过唯一派生入口获取，删除旧平行输出字段和旧增量生产路径，不增加开发期双协议识别分支。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当已接受响应进入原生历史时，应由完整块派生现有 Assistant 消息，保留工具结果配对、原始调用参数及协议要求的 continuation；不把部分块、公开 UI 预览或 reasoning 展示状态写入 Goal 对话，不改变模型输入角色、历史裁剪或持久化权限语义。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当验证功能时，应使用确定性本地 HTTP／SSE fixture 穿过真实供应商 SDK，并通过实际阶段执行／Runtime 调用链检验正常、分片边界、交错块、晚到身份、取消、截断、异常尾部和阶段解码；完整块后失败必须零工具执行，私有内容不得出现在默认订阅或 Browser DTO。不得以真实付费模型或仅类型导出作为验收。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当交付新接口与职责时，应同步公开中文契约 TSDoc、最小示例、变化所有者的模块说明与语义表，通过适用类型、依赖和文档检查及受影响回归；本次不实现后续 Spec 的 Session 协议、候选答复预览或 Web 组件重做。

## 架构与核心决策

### 当前依据、所有者与相关 Spec

现有 [LLM 契约](../../packages/llm-core/src/types.ts) 分离正文、reasoning、工具列表，增量只包含 started／文本／推理／参数／completed；[pi-ai](../../packages/llm-pi-ai/src/pi-ai.ts) 已提供真实流，但丢失部分块边界。[OpenAI](../../packages/llm-openai/src/openai-compatible.ts) 和 [Gemini](../../packages/llm-google/src/gemini.ts) 当前使用非流式请求。[模型调用](../../packages/model-call/src/model-call.ts) 已分配 callId，却未把它带入全部实时增量，非流式开始事件还在完整响应返回后发布。本次统一这些生产与采集路径。

| 所有者 | 本次职责 | 不承担的职责 |
| --- | --- | --- |
| `llm-core` | 内容块、完整响应、增量与派生视图的供应商无关契约；无 I/O 的组装规则。 | 供应商 SDK、业务决策、授权、存储与 UI。 |
| `llm-openai`／`llm-google`／`llm-pi-ai` | 协议请求、真实分片与块边界映射、最终归一化、供应商错误与传输清理。 | Runtime 重试、Action 创建或执行、公开会话消息。 |
| `model-call` | 单次调用身份、消费与完整性检查、输入／指标／诊断、可见性受控的观察发布。 | 阶段业务解码、Goal 提交或执行调度。 |
| `model-response`／`model-execution` | 使用派生视图执行既有阶段解码及原生历史投影，只接收成功的完整响应。 | 根据部分块推测决策、提前审批或执行。 |
| `execution-stream`／`browser` | 保留旁路、背压和过滤，隔离调用／块合并键；将内部事件映射为当前公开活动。 | 持久化内容块、重放恢复或新 Web 布局。 |

[streaming-session](../streaming-session/spec.md#spec-req-7-1) 拥有 Goal 订阅、同步、输入收据和恢复，本 Spec 不依赖其尚未实现的 Session API，也不重复它的状态机；后续集成使用本次调用／块身份。[human-interaction](../human-interaction/spec.md#请求与响应协议) 及 [action-approval-revision](../action-approval-revision/spec.md#明确的决定分支与授权事务) 继续拥有已提交等待及批准，生成中的工具块不是这些请求。三份相关 Spec 均已有对话批准，本次不改写其文件或批准范围。

后续会话输出协议负责候选 `summary` 预览、正式消息身份和提交关联，Web 流式呈现负责内容块 UI。它们尚未形成获批文件，不作为本次可用依赖或额外交付条件。当前 Browser 的最小投影适配属于本次消费方迁移，不保留第二套内部增量协议。

### 内容块模型与派生视图

下表定义完整块的必要语义，最终 TypeScript 命名在实现时沿现有包边界落地：

| 块 | 内容 |
| --- | --- |
| `text` | 连续块索引、`format: plain \| json`、完整文本；format 来自本次请求的结构化输出契约，不扫描正文猜测。 |
| `reasoning` | 连续块索引、供应商实际提供的文本；保持受限，不与签名或最终答复混淆。 |
| `tool_call` | 连续块索引、完整模型调用 ID、工具名及原始或协议规范化的 `argumentsJson`。JSON／业务 Schema 是否可用由既有阶段解码判断。 |

`LLMResponse` 保存 `blocks`、可选 continuation 和诊断 metadata，不再继承带有可独立赋值正文／工具列表的响应形状。共享纯投影按顺序提取普通／结构化文本、reasoning 和工具调用，供现有解码及 `nativeResponseMessage` 使用；它们是读视图，不是第二套可变状态。文本按块内容直接连接，不隐式 trim 或插入换行；既有阶段的业务 trim 仍由阶段解码拥有。必要的供应商原生分隔语义在 Adapter 块映射处明确表达。

块索引是本次响应的稳定身份，供应商索引在适配器中映射为从零开始的连续顺序；交错增量仍指向原索引。`modelCallId` 沿用单次调用生成的 UUID，内部流索引以该调用作用域解释，观察信封使用二者组成块引用，不另生成持久化会话消息 ID。供应商工具 ID 若缺省，沿既有协议规则分配一次本地 ID；不得把该 ID 写回伪造原始 Gemini Part，重试也不得继承旧调用 ID。

完整响应只有规范化内容块这一正文来源；continuation 保留原生协议要求的 Parts／签名等不透明内容，不能从规范化块反向重建签名，也不能作为业务解码的第二来源。模型历史仍使用当前 `ModelConversationMessage` 角色与工具结果配对，必要的 response-to-message 转换显式完成。

### 流事件及成功边界

Adapter 的逻辑事件为响应开始、块开始、块增量、块完整结束、响应成功完成。块开始说明索引、类型及 `incremental`／`whole` 交付方式；增量按文本、reasoning 或工具参数区分，不能以任意 JSON merge 修改另一块。完整结束携带同一块的最终内容；成功完成携带完整响应，且必须是 Adapter 最后一个事件。完整工具身份可在结束时才齐备，不以推测名称或临时调用 ID 作执行依据。

采集器消费至正常 EOF 后，核验唯一完成、全部块封口与同源一致性，才发布成功结束并返回响应。异常和取消仍通过现有错误通道传播；`model-call` 在捕获处以同一调用身份尽力发布失败／取消终止摘要，使观察者知道未完成块已失效，但不制造成功响应。观察终止不是保证送达的持久化记录，进程崩溃时由会话同步读取权威状态。

```text
调用开始／分配身份
    → 输入记录成功 → 发起一个 Provider 请求
    → 块开始 → 真实增量或整块交付 → 块完整结束
    → 完成候选 → 正常 EOF 与完整性检查
    → 返回完整响应 → 既有阶段解码 → Runtime 校验／审批／执行
```

块完成后流仍可能失败，故不得提前创建待审批 Action。响应成功也不代表业务可用：空结果、非法参数、不可见工具及完成候选仍由原有解码／Runtime 检查拒绝。采集器检查跨事件顺序和供应商边界，不为同进程已经类型化的普通值重复增加不可信解析。

### 供应商归一化与能力差异

OpenAI Chat Completions 可能把工具名、ID 和参数分片发送，Adapter 在对应工具块内累计，终结时核验一致；用量尾部在响应完成前收齐。非流式协议只有分离字段而无相对时序时，明确按正文、公开 reasoning、工具数组的映射顺序输出，不声称与另一次流请求的分片边界相同。

Gemini 的 Part 顺序与签名保留，普通文本真实增量交付，完整函数参数整块交付。strict JSON 需要既有逆向投影时，Adapter 缓冲所需原文、完成同一归一化后交付规范 JSON 文本块；不将哨兵原文先作为公开规范文本发布。其 `generate` 与 `stream` 的投影规则必须共享，避免两条语义实现。

pi-ai 使用真实块索引和边界，将 thinking 与文本分开；有原始参数分片时保留其文本，SDK 最终只提供对象时核对解析后的参数语义，不因空白／键顺序不同改写已结束块。没有原始字节来源时才使用协议的稳定序列化形成完整参数，不把结果对象拆成虚构增量。整次调用被截断或阻断时，即使 SDK 留有工具对象也不能接受为成功。

无 `stream` 的宿主 Adapter 仍返回新的完整块契约；该能力缺省不是运行时流失败的兜底。`generate` 路径在网络前发布开始，结束后发布整块观察；输入或配置校验失败不发起请求。不会新增流失败重发、供应商 SDK 自动重试、Provider 切换或静默模型降级。

### 可见性、内存与现有消费方

块类型、正文格式和调用用途决定内部发布的可见性：普通可公开正文沿既有白名单，结构化 JSON 与工具参数为诊断，reasoning 为 restricted 且须显式选择；块开始／结束也执行相同过滤，不能仅保护 delta。公共模型结束只携带安全状态和身份，不附整个 `LLMResponse`。完成审查等当前未接入执行流的私有调用保持私有。

复用现有事件 Core，有意义的合并键包含调用／块／字段，只合并同一归属的相邻增量。增量、完整块和完整响应需要的内存随实际输出线性增长，不保留每个累计前缀；依赖现有输出 token 上限与有界订阅，不承诺常量内存，也不新增通用历史分片仓库或配额配置平台。

当前 Browser Adapter 直接读取新内部事件并输出当前活动 DTO；这是明确的读投影，不是检测旧／新响应的兼容分支。它不承担未来 `SessionOutput` 设计，也不把工具参数或 reasoning 加入现有页面。涉及序列化边界时更新当前校验；不改变 Snapshot 版本、不把未完成块持久化为 Goal 消息。

## 曾考虑的备选方案

- **有序块作为完整响应权威**：选择增量和完整结果共用块模型，再派生现有读视图。备选只扩展实时事件、保留独立正文和工具列表，会形成可失配的两套输出，且失去跨类型顺序，不采用。
- **整体成功后进入执行**：选择保留当前阶段和 Runtime 决策边界。备选块完成即审批／执行可重叠后续生成，但需要另外设计生成失败后的已发生效果、批次冲突和恢复事务，超出本次范围，按用户选择不采用。
- **供应商无关且按真实能力输出**：选择保留现有三个接入协议。备选直接暴露 SDK 原始事件会让消费者绑定供应商；迁移 Gemini Interactions 扩大协议与历史范围；拆分完整参数模拟实时输入会误导观察，均不采用。
- **仅三种输出块**：选择正文、工具调用和实际 reasoning。备选把 Observation、审批、最终 Run 结果、签名和每个 JSON 字段都做成模型块，会混淆 Runtime、传输与供应商续接所有权，不采用。
- **需要完整归一化的内容整块交付**：选择保留既有 Gemini strict 投影并标明交付方式。备选增量展示原始占位 JSON 后静默替换违反内容一致性；新增通用增量 JSON 逆向投影器没有本次必需价值，不采用。
- **最小迁移现有观察消费方**：选择保持 Browser 当前安全活动投影，后续 Spec 再设计完整会话输出和 Web 布局。备选本次完成全部消息／界面改造会与既有待实现 Spec 重叠；只新增类型不迁消费者则没有真实交付路径，均不采用。

## 风险与否定性保证

- **风险等级：high**。输出契约贯穿供应商、模型解码、原生历史与公开观察；块失配、受限内容泄漏或错误接受残缺工具调用可能影响后续实际操作。风险等级要求失败和隐私集成验证，不授权提前执行工具或改变权限。
- **关键操作**：实现需要替换当前 LLM 输出形状、供应商流消费、调用结束判定及现有读投影。保留输入角色、原生续接、Schema 投影、工具授权、Runtime 重试和当前持久化版本；只使用隔离本地服务、确定性模型／工具和临时数据，不以设计批准授权付费调用、用户数据删除、协议迁移或 SDK 发布。
- **内容与身份不变量**：完整块不可后改；最终响应与同一流一致；不同调用／块不得串文；签名不能重建或公开；部分 JSON 不能执行；完整块后失败也没有本次工具效果；模型成功结束不等于 Run 完成。
- **失败与观察不变量**：取消、截断、阻断和异常 EOF 不成功；错误不自动重发或降级；事件旁路失效不改变业务响应；慢观察者不阻塞执行，不承诺分片送达、持久化回放或外部效果 exactly-once。
- **验收重点**：真实 SDK 加本地 SSE fixture 覆盖碎片化参数、多个交错块、晚到身份、metadata 尾部、strict 归一化、失败／取消与续接；Runtime 屏障检查响应未完成时零工具调用；默认订阅和 Browser 检查无敏感载荷。分片与完整响应比对不以两次真实随机生成内容相同为前提。
- **规划写集**：本阶段仅生成本 Spec，不改写三份已批准 Spec／Plan，不生成下游 Plan，不开始实现，不记录已交付状态或写入项目记忆。后续若发现必须改变其他 Spec 的可观察契约，应先明确影响并取得对应修订批准。
