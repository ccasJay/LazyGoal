# 执行契约设计参考

> 本文保存双核心架构的执行契约职责与行为保证，作为[渐进迁移路线](../contract-migration/README.md)的参考，不再作为一个整体交付或审批单元。下文条目用于判断某个迁移接缝需要保留什么，不要求开发者同时重构全部执行接口。各步实施范围以当步独立 Spec 为准。

## 目标与范围

将 LazyGoal 的执行规则整理为与[数据契约](../data-contract-foundation/design.md)分离的稳定契约核心。执行契约定义类型化操作的前置条件、允许的状态转换、副作用、提交顺序、失败结果、恢复与所有权；Runtime 负责实施这些规则。数据读取成功只表示载荷合法，不代表命令已受理、动作已授权、工具执行成功或任务已完成。

接口、职责和表达的调整应当保留现有执行、授权、审批、恢复、重试及关闭的可观察语义。终态设计涉及 Goal/Run/Step、宿主输入、模型决定、工具与程序子调用、检查点、证据、取消和资源生命周期。六个内部维度及双核心归属见[数据契约参考的维度表](../data-contract-foundation/design.md#六个内部设计维度)。顶层“执行契约”包含完整生命周期；维度表中的“执行”特指操作准入与副作用。

不新增执行 DSL、通用工作流引擎、并行 Goal 调度、跨进程租约、分布式事务、通用置信度评分或新审批机制；不将宿主输入和模型决定重新设计成两套彼此独立的执行协议。发现必须改变行为的情况，应当明确修订对应验收规则后再实施。

## 需求与验收标准

### 需求 1：类型与行为分离

作为宿主、模型和工具集成者，我希望通过明确接口参与执行，而不依赖数据 Schema 或隐藏约定控制 Runtime。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当定义或修改执行入口时，应当使用原生 TS 接口和可辨识结果分支表达参数、成功、拒绝及基础设施失败；同一命令或状态的载荷类型应当复用唯一所有者的定义，不在执行层、数据层和适配器各复制一份。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当公开入口存在前置条件、持久化、副作用、取消或所有权限制时，其中文契约级 TSDoc 应当说明这些规则及最小用例；类型签名不得被视为时序、幂等或持久化保证的替代。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当边界读取器返回合法载荷时，Runtime 应当继续核对当前身份、状态与权限；数据诊断不得授予执行权、默认批准、推进任务或改变重试预算。同进程类型化调用不重复套用 JSON 读取器。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当模型、工具、Web 或存储适配器报告结果时，适配器应当只完成其协议转换及端口调用，不直接改写 Goal/Run、替 Runtime 裁决授权，或根据 Schema 分支推断动作已执行。

### 需求 2：状态所有权与输入受理

作为会话调用方，我希望状态由单一执行所有者推进，重复输入和竞争不会创建额外执行。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当应用状态转换时，应当由 Runtime 的领域行为执行；纯转换不做 I/O，非法转换返回原状态及明确拒绝，不产生副作用。Goal/Run/Step、阶段与路线各保留现有含义，不合并成一个通用 `status`。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当输入被受理时，应当先在现有短提交边界内保存输入身份、规范化载荷摘要及收据；相同身份和相同载荷重试返回原收据，相同身份但载荷不同明确拒绝。受理不等于已应用或已完成，提交结果不明时可按身份查询，不能盲目生成新输入重试。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当创建或只读连接 Session 时，创建应当在首次调用模型/工具之前保存初始 Goal、Run 和收据；只读连接不得推进任务、消费队列或自动恢复。实例的单活动 Goal 名额与 `BUSY` 行为保持不变，不新增隐式全局队列。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当普通消息、Steer、交互回应、显式恢复或队列控制并发到达时，应当保留当前种类区分、FIFO、目标 Run/请求/修订核对与原子消费规则。失败或用户中断后队列暂停，waiting 不自动出队，终态后的继续创建后继 Run，不原地重启失败 Run。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当模型返回期间输入、阶段或路线已改变时，Runtime 应当在接受与提交前核对请求绑定；过期结果不得应用到新的阶段或修订。Steer 与工具执行竞争时，已开始调用的真实结果先结算，再应用补充输入。

### 需求 3：执行准入与副作用边界

作为权限所有者，我希望任何工具执行都经过当前有效的准备、授权和提交路径。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当准备业务工具或程序内部子调用时，系统应当沿用冻结 Profile、Registry、当前 Run 暴露集合、输入准备、模式限制、Policy、Grant/审批及沙箱检查；父程序获准不授予子工具权限，工具发现和 Schema 暴露不授予执行权。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当 Plan Run 的任务尚未批准时，仅明确声明只读的已授权业务工具可以执行，该 Run 不得完成；普通 Run 与获批 Plan Run 保持现有准入差异，GoalPlan 的存在或写入不授予工具权限。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当合法输入经过数据提取及工具语义准备后，授权匹配、审批展示、执行参数和相关摘要应当使用同一个 canonical 执行版本；原始载荷及被剥离字段不得回流为执行参数。仅未知字段不同的载荷不得因这些字段产生不同的执行权限或副作用。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当允许一次工具执行时，应当先保存所需 Action 意图、批准/授权引用及恢复信息，再调用工具；提交失败不得启动对应副作用。流式片段不能代替最终 Observation，工具成功也不能直接将 Run 标记完成。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当外部工具已被调用但其响应校验失败、响应丢失或结果提交失败时，系统应当保留实际调用身份并按现有未知结果/执行故障路径处理；不得把数据错误解释为“没有执行过”，不得自动伪造成功结果或新增重试资格。

### 需求 4：审批与授权事实

作为审批者，我希望批准精确绑定当前等待和最终执行内容，并可在故障后核对其效力。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当接受批准、拒绝或交互回应时，Runtime 应当核对 Goal、Run、当前等待请求及对应 Action；旧请求、错误身份、已失效决定和不适用的回应分支不得解除等待或执行工具。问答整体回复和跳过不得被解释为批准。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当审批者修订首次尚未执行的 Action 参数时，应当保留同一工具及逻辑 Action，复用只读预检、最终参数与能力范围指纹；提交时重新准备并核对，不一致明确拒绝。批准后执行版本冻结，原模型请求和已保存事实不被覆盖。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当批准建立持续 Grant 时，应当保留决定身份及 pending→批准提交→active 的现有顺序和恢复核对；pending、revoked 或范围不匹配的 Grant 不得授权。YOLO 自动批准不创建持续 Grant，撤销与既有 scope 行为保持不变。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当操作结果未知并请求再次执行时，应当将决定绑定本次恢复身份及已批准执行版本，保留现有 `safe/manual` 恢复政策和显式重执行入口；不得把首次批准、旧恢复批准或新的参数版本当作再次执行许可，也不得宣称拒绝重执行已经回滚原副作用。

### 需求 5：提交与恢复权威

作为恢复实现者，我希望崩溃、提交错误和旁路丢失不会改变已确认事实或造成未经批准的重放。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当提交事实、Memory Patch 和状态时，应当复用现有共享提交端口，保持事实/accepted Patch、Snapshot 与 marker 的顺序及 Goal 修订推进；模型、工具或人工等待不得持有 Goal 的短提交 Gate。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当从持久化状态恢复时，Snapshot 的提交边界与恢复指针应当决定可见事实；marker、实时事件、诊断、指标和输入查看日志不得替代恢复权威。未提交 tail 不得被自动重放为已接受决定，既有独立持久化预算事实仍按其现有规则结算。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当恢复已开始但没有确认结果的工具或程序调用时，应当保留原身份、最终输入与回放匹配规则；程序和批次从现有恢复指针继续，不重复应用已提交子结果。恢复不得因更换数据引擎而重置重试次数、预算或授权范围。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当持久化数据通过结构读取但不满足内部一致性或执行支持范围时，应当在恢复前明确拒绝；宽容读取只容忍无害字段扩展，不修补缺失的执行事实、推断批准或迁移旧开发数据。

### 需求 6：失败、超时与重试

作为执行调用方，我希望每种失败保留真实含义，重试由执行所有者决定。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当出现数据错误、状态/权限拒绝、工具领域失败、暂时性模型/工具故障、取消或基础设施失败时，系统应当保留可辨识的结果分支与既有外层错误分类；未知异常不得自动标为可重试，观察到超时也不得宣称外部效果未发生。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当决定重试、退避、协议纠错或继续采样时，应当由 Runtime/对应执行所有者应用现有分类、次数、期限和持久化规则；数据读取器、Schema、工具元数据中的声明或单次 `retryable` 值均不能自行调度重试。协议纠错与不推进计数保持分离。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当取消或宿主关闭中止当前调用时，应当保留现有控制流与失败结算区别；不得将所有中止统一写成失败 Step，或因旁路未知字段诊断而消耗重试/纠错次数。

### 需求 7：可信结果与完成边界

作为结果消费者，我希望能够区分候选、工具结果、已提交证据与正式完成。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当模型声明阶段或 Run 完成时，应当先通过现有协议、语义、身份、阶段和已提交证据门禁，再进行必需的完成审查；只有审查接受并提交成功后才形成正式结果。工具 success、Schema 校验成功或模型自述均不能替代该过程。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当候选结果被预览、拒绝、替代或因输入变化而作废时，应当保持未确认语义及明确的失效通知；候选不成为恢复来源、完成证据或工具许可，正式消息继续保存稳定身份、来源和提交位置。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当核验证据时，应当保留当前 Run、已提交序列、允许来源与既有引用规则；用户问答、历史查询未命中、旁路进度和未提交结果不得被自动升级为可信完成证据。本次不引入通用 `confidence` 数值或新的自动采信阈值。

### 需求 8：中断、关闭与资源所有权

作为宿主，我希望停止执行与释放资源具有可核对的结果，且不会误伤借用资源。

- <a id="spec-req-8-1"></a>**验收标准 8.1**：当用户 Interrupt 被受理时，应当先持久化目标 Run 的中断、队列暂停与收据，再中止执行；停止受理后旧交互不能被批准，先前已提交的回应不能被回滚。已开始且效果未知的调用按现有规则记录并结算 cancelled，不再调用模型收尾或执行修复工具。
- <a id="spec-req-8-2"></a>**验收标准 8.2**：当宿主关闭 Runtime 时，应当保持 `open/closing/closed`、停止新受理、冻结提交入口、中止控制器及有界结算的既有顺序；关闭不创建用户 Interrupt，不将未确认停止伪造成取消终态，重复关闭复用同一过程。
- <a id="spec-req-8-3"></a>**验收标准 8.3**：当结算进程、订阅或宿主交互处理器时，应当只关闭本实例拥有的资源，保留借用关系和已有有界关闭/迟到结果规则；已发送终止信号或已写状态不是实际退出的证明，未完成清理应当以类型化原因报告，不扫描或重新控制历史 PID。

### 需求 9：行为验证与演进边界

作为框架维护者，我希望接口重构后能够证明执行语义保持，并与数据重构形成完整集成证据。

- <a id="spec-req-9-1"></a>**验收标准 9.1**：当验证新接口时，应当覆盖合法推进与拒绝、副作用前提交失败、过期审批、修订参数、未知结果、重复输入、Steer/Interrupt 竞争、恢复和不完整关闭；既有安全、审批、恢复及失败测试不得因换接口而删除其行为断言。
- <a id="spec-req-9-2"></a>**验收标准 9.2**：当两份参考 集成时，应当使用真实生成读取器验证“宽容读取→canonical 输入→授权/审批→持久化→执行/恢复”的路径，证明未知字段不影响权限、身份或重试，而非法已知字段不会启动副作用；仅使用读取替身不能证明此项通过。
- <a id="spec-req-9-3"></a>**验收标准 9.3**：当发布或恢复时，应当同时核对数据协议支持范围与执行所需的身份、状态和批准事实；数据 Schema 版本相同不能自动证明执行语义兼容。实现变化不自动新增版本、迁移器或全局执行版本字段。
- <a id="spec-req-9-4"></a>**验收标准 9.4**：当本参考 完成时，Runtime、权限、工具核心、执行控制及受影响适配器的说明、语义表和公共 TSDoc 应当指向各自权威契约；调用方不再通过遍历数据 AST、识别 DTO 字段存在或解析错误正文来推断执行权限与生命周期。

## 架构与核心决策

### 系统拓扑与所有权

执行契约采用现有类型化端口、纯领域转换和 Runtime 编排表达，不创建统一命令总线或新的规则解释器。宿主输入与模型提议有不同的来源及信任边界，但在进入执行后共用同一套状态、授权和提交规则。

| 所有者 | 权威职责 | 不拥有 |
| --- | --- | --- |
| Runtime 领域行为 | Goal/Run/Step、阶段与路线的合法转换、身份绑定和不变量。 | Provider wire 格式、文件存储实现。 |
| Session/Coordinator | 输入受理、队列、交互回应、显式恢复与持续授权决定的编排。 | 直接执行业务工具、复制另一条执行循环。 |
| RunExecutor/提交端口 | 决策接受、执行准入、事实与 Snapshot 提交、结果结算、恢复和证据门禁。 | 重新定义载荷结构或授权库的匹配算法。 |
| permission / sandbox | 依据调用方提供的事实判定权限与能力范围，实施真实资源限制。 | Goal 状态所有权、默认批准和执行调度。 |
| tool-core / 工具实现 | 类型化输入准备、无调度的工具语义校验、一次调用及失败分类声明。 | GoalStore、审批推进和 Runtime 重试循环。 |
| execution-control / 适配器 | 中止信号、可分类请求故障及传输转换。 | Run 状态、重试预算与提交决定。 |
| RuntimeLifecycle / 资源所有者 | 实例关闭边界、已受理工作结算、拥有资源的释放。 | 宿主进程退出、借用资源和历史 PID 的控制权。 |
| storage | 实现持久化 Port 和文件效果核对。 | 推断副作用是否发生、改变执行状态或裁决授权。 |

Runtime 仍依赖端口，组合根注入存储、模型、工具和权限实现。数据生成器不能成为 Runtime 的服务定位器。状态类型可被消息和快照引用，但状态转换规则只在其执行所有者维护。

执行接口保留现有入口的用途，按下列接缝清理载荷定义、实现依赖和契约说明，而不是增加一个总调度接口：

| 接缝 | 类型化边界与职责 | 对应验收 |
| --- | --- | --- |
| `Session.send` / 输入受理端口 | 接收 `SessionInput`，返回受理/拒绝和可查询收据；不等待 Run 完成。 | 需求 2、4。 |
| `StepExecutor` | `decide`、`think` 和 `reviewCompletion` 分别返回模型阶段结果；不写 GoalStore 或直接取得工具执行权。 | 需求 1、3、7。 |
| `ToolRegistration.prepare` / 已准备调用 | 绑定通过读取与语义准备的 canonical 输入及执行闭包；准备不执行，闭包仅由执行所有者在准入并提交后调用。 | 需求 3、6。 |
| `TrajectoryCheckpointCommitterPort` / 恢复读取端口 | 以已定义的提交顺序保存事实与状态，按权威边界读取；不裁决业务分支。 | 需求 5。 |
| `RuntimeLifecycle` / 受管资源 | 传递取消、关闭所有权与结算结果；不处理业务审批或重新取得历史资源控制权。 | 需求 8。 |

### 贯穿边界的执行路径

输入经过数据读取和必要的 wire→canonical 转换后进入类型化入口；Runtime 核对身份、状态和准入规则。工具路径在准备完成后，以同一最终输入解析真实资源、匹配权限或进入审批，持久化相应意图后执行，并提交实际 Observation。模型产生的身份、工具暴露和载荷形状均不能跳过任一门禁。

数据方向 的字段提取是本次明确的数据接受规则变化：自有固定对象的未知字段仅形成诊断，既有字段非法仍拒绝。执行侧只接收成功提取并准备后的数据，用该数据形成去重、审阅、授权和恢复所需摘要；未经提取的原始对象只在既有受控记录边界使用，不能作为后续参数来源。

业务拒绝、数据问题、暂时故障和结算不明是不同结果。公开方法按原有调用语义返回结果或抛出类型化基础设施错误，不强制将所有接口包装为同一种 `Result`。对外错误代码及可恢复身份保持稳定，库特有细节由边界适配隔离。

### 持久化、可信度与演进

Snapshot 和已提交事实持有恢复权威；事件流与诊断只提供观察。状态同步、工具输出预览、完成候选、正式消息及指标继续保留各自含义，不因统一契约术语而合并。证据类型可由数据契约生成，但其来源、提交有效性和采信决定由执行规则核验。

沿用当前开发期单版本策略，不迁移旧 Goal。对外发布的数据制品按数据方向 固定版本；执行接口的语义变更必须独立评估审批绑定、恢复与在途结果，不以“Schema 仍可读”宣称安全兼容。本次通过保留现有行为完成基础重构，不顺带定义新的可靠性等级或 exactly-once 承诺。

### 渐进实施边界及验证

执行侧依赖数据读取成功、拒绝问题及非阻断诊断的语义，不依赖生成器、Schema AST 或库特有类型。`DataReadResult<T>` 等接缝是终态设计候选，不要求首个局部迁移先建立全仓框架。状态、Policy、审批、恢复和资源接口由各自当前所有者维护，不反向要求数据层调用 Runtime。

每个小 Spec 只验证它实际触及的执行接缝。纯响应 DTO 迁移不需要重构 Runtime；工具输入迁移需要核对准备后的参数与真实授权/执行路径；持久化表示迁移需要核对恢复。类型化替身可用于局部验证，但不能代替该步真实消费者的集成证据。不得因为本文列出了完整生命周期而把全部执行重构附带到一次 AST 替换中。

本次的当前实现依据为[Runtime 概览](../../packages/runtime/notes/overview.md)、[纯状态转换](../../packages/runtime/src/transition.ts)、[会话输入](../../packages/runtime/src/session-input.ts)、[共享提交端口](../../packages/runtime/src/trajectory-checkpoint-committer.ts)、[审批与执行版本](../../packages/runtime/src/action-approval.ts)、[授权判断](../../packages/permission/notes/overview.md)、[执行控制](../../packages/execution-control/notes/overview.md)和[进程资源所有权](../../packages/process-runtime/notes/overview.md)。这些是行为基线；本参考 不把尚未落地的新接口表述为现有能力。

## 风险与否定性保证

- **风险等级：高。** 重构涉及权限、审批、副作用前提交、并发输入与恢复。关键操作是切换执行端口和工具准备接缝、调整授权/提交调用方及关闭编排。需以需求 9 的真实失败与竞争场景核验，类型检查通过不足以证明顺序正确。
- **主要风险。** 数据提取和审批展示使用不同版本会使批准与执行错配；接口拆分可能丢失提交前置条件或形成第二个状态所有者；故障分类变更可能错误重放副作用。对应保证分别由需求 3/4、2/5 和 6 约束。
- **否定性保证。** 不改变现有并发度、预算、退避策略、授权默认值、任务审批门、证据采信门和资源关闭期限；不把“数据合法”“已受理”“已批准”“已执行”“已提交”“已完成”互相替代。
- **故障边界。** 存储效果核对仍由具体 Store 负责，执行侧不声称跨进程互斥或分布式原子性。关闭不自行退出宿主；未知结果不宣称回滚；诊断丢失不改变执行事实。
