# 统一 Permission 需求

## 审批摘要

### 目标

让用户在浏览器与 TUI 中通过统一入口选择项目执行模式，审阅 Tool 操作和沙箱越界能力，并管理单次、当前 Goal 与当前项目的授权。

### 范围

- 包含：聊天框左下角的 Permission 入口、项目级 Default／YOLO 模式、Tool 与 Sandbox 审批、持续授权的复用和撤销，以及双端一致的等待、恢复和错误反馈。
- 不包含：新增通用允许／拒绝规则配置、改变 Seatbelt 的强制隔离范围、改变任务提案或 `ask_user` 的交互语义、无界面 Benchmark 的独立执行策略，以及首版 Linux／Windows 沙箱实现。

### 核心行为

- 浏览器与 TUI 的 Permission 入口同时提供模式选择和授权管理。模式属于当前项目，影响该项目现有及未来的本机交互 Goal，保存后在刷新、切换 Goal 和重启后仍有效；切换只影响后续尚未开始的 Tool 决策，不追认等待中的审批或重放已开始的操作。无界面 Benchmark 保留独立策略。
- Default 保留只读 Tool 的现有自动放行及其他 Tool 的审批；macOS 上处于默认沙箱范围内的 `bash` 自动执行。YOLO 仅沿用 Tool 自动批准语义，不创建持续授权，也不能越过 Tool Profile、输入或执行策略，更不能放宽 Sandbox 的文件、网络和受保护路径边界。
- 审批必须展示完整操作与能力、真实放行范围和期限，截断的输入须能展开审阅。用户可选择单次、当前 Goal 或当前项目；持续授权只复用匹配的操作及能力。不同 `bash` 命令不共用 Tool 授权；写入类 Tool 对同一路径的持续授权可覆盖后续不同内容；批准任意目标出站网络时必须明确展示其真实范围。
- 用户可在统一入口查看 Tool 与 Sandbox 授权的来源、范围、期限和状态并撤销。拒绝与失效原因应反馈给用户和后续模型决策；拒绝、撤销、失配、未提交或过期授权不能放行新操作。审批和模式切换必须校验当前项目、Goal、Run 与请求身份；结果不确定的操作仍需人工处理，不能因模式或授权变化自动重放。
- Browser 与 TUI 必须显示当前模式及沙箱保护状态，并区分 Tool 审批、Sandbox 能力审批、拒绝和故障；浏览器不得取得模型凭据。Linux／Windows 的本机交互 Goal 保留 Tool 策略和项目模式语义，同时明确显示没有 Seatbelt 保护。

### 风险与待确认

- 风险等级：high；理由：项目级 YOLO 可影响同时运行的多个 Goal，持续授权跨 Run／Goal 复用，错误匹配可能扩大文件或网络能力。
- 关键操作：实施后，项目外文件、受保护路径和联网能力仍须在有效授权范围内取得用户批准；当前仅编写需求，不执行这些操作。
- 风险：项目级模式切换可能使其他 Goal 的后续 Tool 无需逐项确认；过宽或错配的持续授权可能放行未审阅操作；并发切换、撤销和恢复若判断失序，可能绕过审批或重复执行。Design 必须界定一致的权限判断与提交时序。
- 关联 Spec：[既有 Tool 授权](../runtime-feedback-tool-approval/requirements.md) 曾排除浏览器 YOLO 开关，现有 TUI 模式只在会话界面内切换；本需求明确改为双端项目级模式。[macOS Seatbelt Sandbox](../macos-seatbelt-sandbox/requirements.md) 中重叠的审批、授权管理和 UI 职责需按本需求修订并重新审核，其强制隔离要求继续有效。
- 待确认：无需求决策待确认。

## 引言

本功能把项目模式、Tool 授权和沙箱越界能力放在同一用户操作面中；用户可以看清每次请求和持续授权的实际范围，Runtime 在执行前仍分别遵守 Tool 策略和沙箱边界。

## 需求

### 需求 1：项目级模式选择

**用户故事：** 作为同时使用多个 Goal 的项目使用者，我希望从聊天框左下角管理执行模式，以便清楚知道哪些后续 Tool 操作需要我逐项批准。

#### 验收标准

1. <a id="req-1-1"></a> 当用户在浏览器或 TUI 查看聊天输入区时，系统必须在左下角提供 Permission 入口；打开后必须能选择 Default／YOLO 模式并进入当前项目的授权管理。
2. <a id="req-1-2"></a> 当用户切换模式时，界面必须说明该选择影响当前项目所有现有及未来的本机交互 Goal，并在服务端确认后更新项目模式及各 Goal 可见状态；刷新、切换 Goal 或重启后必须显示已保存的选择。
3. <a id="req-1-3"></a> 当项目模式变化时，新模式必须只用于后续尚未开始的 Tool 决策；已提交的待审批请求不得被自动追认，已启动或结果不确定的操作不得因切换而重新执行。
4. <a id="req-1-4"></a> 当浏览器或 TUI 的模式切换请求来自过期页面、错误项目或与当前状态冲突时，系统必须拒绝该变更并显示服务端确认的当前模式，不得仅凭本地界面状态放行操作。

### 需求 2：Tool 策略与 Sandbox 边界

**用户故事：** 作为项目使用者，我希望自动执行模式仍受实际能力边界约束，以便切换 YOLO 不会意外开放宿主文件或网络。

#### 验收标准

1. <a id="req-2-1"></a> 当项目处于 Default 模式时，现有自动放行的 `read_file`、`grep` 继续无需逐次审批；其他需要 Tool 审批的操作在没有匹配授权时必须等待用户。macOS 上符合当前策略且处于默认 Seatbelt 范围内的 `bash` 无需逐次 Tool 审批。
2. <a id="req-2-2"></a> 当项目处于 YOLO 模式时，系统只能自动批准当前 Tool 策略允许的操作，不得因此生成当前 Goal 或项目的持续授权；每次操作仍须通过当前 Tool Profile、输入校验和执行策略。
3. <a id="req-2-3"></a> 当操作请求 macOS 沙箱默认范围之外的文件、受保护路径或联网能力时，无论项目模式或普通 Tool 授权为何，系统都必须重新核对该能力的有效授权；没有匹配授权时必须在执行前等待用户批准或拒绝。
4. <a id="req-2-4"></a> 当模型文本、Tool 输出或客户端请求声称某项能力已获准时，系统不得将该声明视作授权；任何默认模式或持续 Tool 授权都不得扩大 Seatbelt 的实际放行范围。

### 需求 3：可审阅的统一审批

**用户故事：** 作为审批者，我希望在批准前看清将执行的操作与实际获得的能力，以便按需要选择合适期限。

#### 验收标准

1. <a id="req-3-1"></a> 当 Tool 或 Sandbox 能力需要审批时，浏览器与 TUI 必须展示请求类别、当前命令或 Tool 操作、目标资源、读写或联网能力、实际放行范围，并提供单次、当前 Goal、当前项目三种期限。
2. <a id="req-3-2"></a> 当待批准的输入预览不完整时，界面必须允许查看完整操作；在完整内容可供审阅前，不得授予当前 Goal 或项目的持续授权。
3. <a id="req-3-3"></a> 当 Sandbox 联网能力实际允许命令及子进程访问任意出站目标时，审批界面必须明确展示这一范围，包括本机回环；模型提出的域名或用途说明不得被显示成强制的访问范围。
4. <a id="req-3-4"></a> 当用户批准或拒绝时，系统必须核对当前项目、Goal、Run 与待审请求身份；拒绝不得执行操作或产生授权，过期、重复冲突或错配的答复不得改变权限。

### 需求 4：持续授权的复用范围

**用户故事：** 作为经常重复操作的使用者，我希望已审阅的请求可以在限定范围内自动放行，以便减少重复审批而不扩大授权。

#### 验收标准

1. <a id="req-4-1"></a> 当用户选择单次授权时，该授权必须仅用于所批准的当前请求；选择当前 Goal 时，授权可供该 Goal 的后续 Run 使用；选择当前项目时，授权可供该项目的其他 Goal 使用，后二者在重启后仍保持原范围。
2. <a id="req-4-2"></a> 当后续 Tool 操作请求复用持续授权时，系统必须核对 Tool、规范化操作及项目或 Goal 范围；不同 `bash` 命令不得共用授权，`write_file` 或 `edit_file` 对同一路径的后续不同内容可在原批准的目标范围内复用。
3. <a id="req-4-3"></a> 当后续 Sandbox 请求复用持续授权时，系统必须核对当前命令、实际文件或网络能力、目标路径及读写方向、项目或 Goal 范围和撤销状态；超出任何已批准维度的请求必须重新审批。
4. <a id="req-4-4"></a> 当操作匹配已有持续授权时，系统仍必须执行当前 Profile、输入与执行策略检查，并遵守当前沙箱强制边界；授权来源不明、未可靠提交、已撤销或失配时不得自动放行。

### 需求 5：统一授权管理

**用户故事：** 作为项目维护者，我希望在一个界面中检查并撤销已有权限，以便了解未来哪些操作会自动执行。

#### 验收标准

1. <a id="req-5-1"></a> 当用户从浏览器或 TUI 的 Permission 入口查看授权时，系统必须展示当前 Goal 和当前项目的 Tool 与 Sandbox 持续授权，并明确标示授权来源、操作或资源、实际能力范围、期限及有效状态。
2. <a id="req-5-2"></a> 当用户撤销授权后，后续尚未开始的操作必须重新判定权限；撤销不得改写已提交结果，也不得被误称为已停止正在执行的命令。
3. <a id="req-5-3"></a> 当撤销来自过期页面、错误项目或不匹配的授权记录时，系统必须拒绝该操作并刷新可见状态，不得撤销其他项目的授权或留下界面上虚假的成功结果。

### 需求 6：等待与恢复时的权限一致性

**用户故事：** 作为长期 Goal 的使用者，我希望审批中断或程序重启后仍按真实授权状态继续，以便不重复执行有副作用的操作。

#### 验收标准

1. <a id="req-6-1"></a> 当审批、授权保存或执行之间发生中断时，恢复后的系统必须只承认已可靠提交且与当前请求匹配的模式和授权；待生效或损坏的记录不得放行操作。
2. <a id="req-6-2"></a> 当 Action 已开始但执行结果无法确认时，系统必须保留人工确认等待；项目模式切换、新增授权或撤销不得自动重放该 Action。
3. <a id="req-6-3"></a> 当授权被拒绝、撤销或不再匹配时，系统必须向用户及后续模型决策提供足以辨别原因的反馈；不得把拒绝转换为已批准操作或尝试绕过当前沙箱执行。
4. <a id="req-6-4"></a> 当多个 Goal 同时运行，或模式切换与授权撤销同时发生时，每个尚未开始的操作都必须依据当时已确认的项目模式和有效授权判断；旧页面、旧 Run 或其他项目的状态不得覆盖该判断。

### 需求 7：双端可见状态与平台边界

**用户故事：** 作为在浏览器和 TUI 之间切换的使用者，我希望看到一致的模式和审批状态，以便准确判断是否需要我介入。

#### 验收标准

1. <a id="req-7-1"></a> 当 Goal 运行或等待审批时，浏览器与 TUI 必须显示当前项目模式、是否启用命令沙箱，并区分 Tool 审批、Sandbox 能力审批、拒绝、结果不确定及沙箱故障。
2. <a id="req-7-2"></a> 当浏览器查看或提交 Permission 操作时，界面不得取得模型 API Key 或其他宿主凭据；展示的输入和诊断不得包含未获准文件的内容或私密环境值。
3. <a id="req-7-3"></a> 当本机交互 Goal 运行于 Linux 或 Windows 时，系统必须保留其 Tool 策略及本 Spec 的模式选择语义，并清楚标示命令未受 Seatbelt 保护；无界面 Benchmark 必须保留自身独立的执行策略，不得因同项目的模式选择而改变。
