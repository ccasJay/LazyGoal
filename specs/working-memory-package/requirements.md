# Working Memory 拆包需求

## 引言

将 Working Memory 的数据结构与纯计算核心拆为独立包，使其能够在不依赖 Runtime 的情况下使用，同时保持现有算法、恢复、持久化和模型接口行为。Goal/Run 恢复、证据判断和提交控制继续由 Runtime 负责；本 Spec 不新增 Static Memory、Subagent 或共享记忆能力。

## 需求

### 需求 1：独立使用记忆核心

**用户故事：** 作为维护者，我希望通过独立包使用记忆类型和算法，以便复用与验证记忆行为时无需启动 Runtime。

#### 验收标准

1. <a id="req-1-1"></a> 当调用方提供当前记忆、Patch 和必要的归约元数据时，独立包必须能够完成现有 Patch 校验、归一化、容量处理和确定性归约，无需创建 Goal、启动 Runner 或访问存储。
2. <a id="req-1-2"></a> 独立包不得依赖 Runtime 源码或通过 Runtime 的导出取得自身所需的记忆类型与算法。
3. <a id="req-1-3"></a> 拆包完成后，Goal/Run 恢复、证据资格判断和持久化提交控制必须继续由 Runtime 负责，独立包不得自行读取或修改这些执行状态。

### 需求 2：保持记忆算法行为

**用户故事：** 作为使用记忆核心的调用方，我希望拆包前后的处理结果一致，以便重构不改变已有事实和记忆条目的含义。

#### 验收标准

1. <a id="req-2-1"></a> 当当前记忆、Patch、限制和归约元数据相同时，拆包后的事实身份、规范化操作及归约结果必须与现有实现一致。
2. <a id="req-2-2"></a> 当 Patch 含有非法操作、字段、引用或条目转换时，系统必须整体拒绝该 Patch，不得返回部分成功结果或修改输入记忆。
3. <a id="req-2-3"></a> 当发生重复提议、证据更新或容量不足时，系统必须保持现有的抑制、事实强化、值替换和淘汰规则；重放已接受操作时不得重新执行当前准入或容量决策。
4. <a id="req-2-4"></a> 当应用条目状态变更或作用域清理时，系统必须保持现有 Fact、Hypothesis 和 Blocker 的生命周期结果。

### 需求 3：保持提交与恢复边界

**用户故事：** 作为恢复 Goal 的使用者，我希望拆包后记忆仍来自已提交事实，以便中断或保存失败不会使未提交记忆生效。

#### 验收标准

1. <a id="req-3-1"></a> 当恢复 Working Memory 时，系统必须只使用当前 Goal/Run 的 Snapshot 提交边界内、由所选 revision 链引用的已接受 Patch；未提交内容不得进入有效记忆。
2. <a id="req-3-2"></a> 当 Patch 已追加但对应 Snapshot 尚未保存成功时，该 Patch 不得成为恢复后或后续模型调用使用的有效记忆。
3. <a id="req-3-3"></a> 当恢复数据损坏、revision 链断裂或循环、身份不匹配或提交边界无效时，系统必须明确失败，不得以空记忆或部分归约结果继续执行。
4. <a id="req-3-4"></a> 拆包不得改变当前 Snapshot、Trajectory、记忆协议和 revision 的持久化数据格式。

### 需求 4：保持模型接口与控制边界

**用户故事：** 作为 Goal 的使用者，我希望模型仍获得相同的记忆上下文并遵循原有输出契约，以便拆包不改变模型行为或执行权限。

#### 验收标准

1. <a id="req-4-1"></a> 当已提交记忆与模型请求条件相同时，拆包后提供给模型的 Working Memory 投影内容必须与现有实现一致。
2. <a id="req-4-2"></a> 当模型提交 Memory Patch 时，其输出结构、协议版本和现有接受规则必须保持不变。
3. <a id="req-4-3"></a> Working Memory 及其 Patch 不得获得修改 Run 状态、审批、执行计数或其他 Runtime 控制字段的能力。

## 风险与待确认

- 风险等级：medium；理由：跨包公开类型与算法归属变化影响 Runtime、Agent 和现有测试，但不变更持久化格式或预期产品行为。
- 关键操作：无。
- 已知风险：类型或算法迁移遗漏可能造成接口不一致；提交与恢复边界受影响可能使未提交记忆可见；对阶段元数据的改写可能意外放宽现有校验。
- 待确认：无；拆包范围、算法、恢复与模型接口约束已在需求收集中确认。
