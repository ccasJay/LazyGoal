# Context Retrieval 独立包需求

## 审批摘要

### 目标

将现有历史上下文检索核心从 Runtime 拆为可独立调用的包，使 Runtime 专注于查询生命周期与安全边界，并保持默认检索行为不变。

### 范围

- 包含：检索文档模型、分词、倒排索引、BM25-lite 排序及可重建索引会话的独立化；Runtime 与 Storage 接线；可替换的检索实现边界；无需启动 Runtime 的固定语料评测。
- 不包含：向量或混合检索实现、外部检索服务、现有 `context_lookup` 协议变更、持久化格式迁移及旧开发数据兼容层。

### 核心行为

- 模型继续通过现有 `system_context_lookup` 系统函数查询历史；独立包不依赖 Runtime 领域状态或 Storage I/O，Runtime 继续控制已提交来源、查询事实、结果校验和完成证据，Storage 继续负责 Sidecar 文件存取。
- 默认实现对相同已提交输入维持当前文档、命中、排序、结果、缓存和恢复语义；损坏来源与无命中保持不同结果。
- 组合根能够选择符合现有历史查询契约的检索实现，默认仍使用 BM25-lite；替换实现不能扩大可读历史或绕过 Runtime 校验。
- 固定语料评测可直接调用独立包，报告检索质量与分词、查询耗时，并验证默认实现无质量回退。

### 风险与待确认

- 风险等级：medium；理由：跨包接口、Sidecar 类型归属与恢复接线改变，影响多个当前调用方。
- 关键操作：无。
- 风险：依赖环、来源边界或排序细节漂移可能导致错误命中及恢复不一致，需要覆盖集成与失败路径。
- 待确认：无。

## 引言

当前检索算法与索引会话位于 Runtime。本特性提取其可复用核心，保留现有历史查询协议和权威来源边界，并提供独立评测入口。

## 需求

### 需求 1：检索核心可以脱离 Runtime 使用

**用户故事：** 作为检索能力维护者，我希望直接使用独立检索包，以便调整和评测检索算法时无需实例化 Goal 状态机。

#### 验收标准

1. <a id="req-1-1"></a> 当调用方提供检索文档或明确的历史来源输入时，独立包必须能够完成文档建模、分词、索引构建和排序，而不要求创建 Goal、Run 或 Runtime 服务实例。
2. <a id="req-1-2"></a> 当构建检索包时，它不得依赖 Runtime 领域类型、Runtime 实现或 Storage 文件 I/O；Runtime 对检索包的依赖必须保持单向且通过仓库依赖检查。
3. <a id="req-1-3"></a> 当现有调用方使用检索文档、分词、索引和排序能力时，调用方必须改用独立包的公共入口；Runtime 不得保留第二份算法实现或仅为旧路径设置兼容转发入口。

### 需求 2：默认历史查询行为保持一致

**用户故事：** 作为正在恢复长任务的使用者，我希望包拆分前后的历史查询得到一致且可追溯的结果，以便原有决策和证据边界不受影响。

#### 验收标准

1. <a id="req-2-1"></a> 当默认实现对相同已提交语料执行相同请求时，文档范围、Token、字段命中、BM25-lite 分数、稳定排序、Top-K、相邻单元和结果预算行为必须与拆分前一致。
2. <a id="req-2-2"></a> 当检索 Conversation 或跨 Run 的 Trajectory 时，系统必须继续按各 Run 的 Snapshot 提交边界和完整 `(goalId, runId, sequence)` 来源读取，排除未提交 tail、内部程序事实与不应索引的 lookup 事实。
3. <a id="req-2-3"></a> 当查询完成时，系统必须继续区分 `found`、`not_found` 与 `lookup_error`，保留来源引用、历史标记和截断信息；旧 Run 命中不得成为当前 Run 的完成证据。
4. <a id="req-2-4"></a> 当 Sidecar 缺失、损坏、落后、超前或版本不匹配时，系统必须维持当前重建或增量更新规则；缓存写入失败不得改变查询结果，权威来源损坏不得降级为 `not_found`。

### 需求 3：允许替换检索实现但不放宽授权边界

**用户故事：** 作为运行时装配者，我希望选择符合统一契约的检索实现，以便以后调整召回算法时无需改动 Runner 的决策和恢复流程。

#### 验收标准

1. <a id="req-3-1"></a> 当组合根装配历史查询时，系统必须允许注入符合统一查询与结果契约的检索实现；未指定替换实现时继续使用当前 BM25-lite 实现。
2. <a id="req-3-2"></a> 当替换实现返回结果时，Runtime 必须在提交查询事实前按当前请求、Goal/Run 身份和提交边界校验结果，拒绝越界或无效来源。
3. <a id="req-3-3"></a> 当检索实现被替换时，模型请求、Tool 授权、Trajectory 提交、Snapshot 恢复和 Evidence Gate 的现有流程不得由该实现接管或绕过。

### 需求 4：检索质量可独立评测

**用户故事：** 作为检索算法维护者，我希望用固定语料直接评测包的质量与运行成本，以便发现拆分回归并为将来的算法比较建立基线。

#### 验收标准

1. <a id="req-4-1"></a> 当运行检索评测时，评测入口必须仅依赖独立包和固定语料即可完成索引与查询，不得启动 Goal、Runner 或完整应用组合根。
2. <a id="req-4-2"></a> 当评测固定语料时，结果必须报告 Recall@5、MRR、负查询判定，以及分词和查询耗时；语料、查询、预期命中和指标计算规则必须可复现。
3. <a id="req-4-3"></a> 当默认 BM25-lite 实现完成拆分后，固定语料的命中与排序必须保持确定性，质量指标不得低于同一语料在拆分前记录的基线；耗时作为观测指标报告，不以机器相关的固定阈值阻断验收。

### 需求 5：保持现有协议与存储所有权

**用户故事：** 作为系统维护者，我希望模块职责调整不改变持久化数据和协议，以便现有 Goal 的查询与恢复路径继续工作。

#### 验收标准

1. <a id="req-5-1"></a> 当模型通过 `system_context_lookup` 发起 `context_lookup` 时，Runtime 必须继续拥有请求协议校验、查询生命周期、已提交事实、结果校验和 Evidence Gate；系统不得为同一历史查询新增普通业务 Tool，检索包也不得直接修改 Goal、Snapshot 或 Trajectory。
2. <a id="req-5-2"></a> 当检索索引 Sidecar 被保存或恢复时，Storage 必须继续拥有文件 I/O 与持久化校验；Sidecar 仍只是可删除、可重建的派生数据。
3. <a id="req-5-3"></a> 当本次拆包完成时，不得仅因代码归属变化升级 `context_lookup`、Retrieval Index、Snapshot 或 Trajectory 协议版本，也不得新增旧开发数据迁移或兼容路径。
