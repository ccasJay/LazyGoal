# 进程会话组件提炼与生命周期收敛 Spec

## 目标与范围

新增私有包 `packages/process-runtime`，从 `tools` 迁入 `ProcessManager`，使宿主仅注入现有进程存储、宿主身份及可选资源注册接口，即可启动、观察、停止和清理自己拥有的后台进程，无需构造 Agent、工具注册表、Goal 执行器或 HTTP 服务。

本轮同时修正启动与关闭竞态、输出写入未结算、异步错误丢失及未确认退出却报告清理成功的问题。进程工具仍归 `tools`，持久化契约仍归 Runtime，JSON/轮转日志实现仍归 Storage，沙箱策略准备与授权仍按现有边界处理。

正常/强制关闭的时间上限与最终实例关闭判断由 [Runtime 组件提炼 Spec](../runtime-sdk-extraction/spec.md) 中 `RuntimeLifecycle` 统一协调。本组件提供可升级、幂等、如实结算的 `close`/`forceClose`，不复制一套实例关闭状态机或配置期限。goal-server 为本轮生产消费者；组合关闭验收只要求通用生命周期与资源注册契约已实现并验证，不要求 Runtime Spec 的 HTTP 拆分、其它控制功能或整份验收先完成。不能用当前会吞掉错误的旧注册表证明成功。

不新增进程工具协议或持久化状态，不迁移数据、不发布 npm 包、不引入任务队列、后台重启、PID 重连、跨进程配额或多租户能力。不拆分其它工具家族，不重构 Goal 归档/删除流程，不执行 Agent 拆包或 Benchmark 迁移。当前成功路径、工具 ID/Schema、沙箱权限、日志游标和重启后的 `interrupted` 投影保持。

### 依赖契约与验收归属

本 Spec 的唯一新增能力前置是 RuntimeLifecycle/资源注册表的关闭契约：正常/强制期限、错误不吞掉、未完成资源继续可辨识。现有 ProcessSessionStore 和 Sandbox 能力直接复用。不依赖 [Agent 拆包](../agent-component-extraction/spec.md)，不等待其包目录、默认装配工厂或模型实现出现。

真实句柄退出、在途启动、日志/终态写入以及这些故障与 RuntimeLifecycle 的组合，由本 Spec 独自验收；通用生命周期的状态机、期限与错误传播由 Runtime Spec 验收。本 Spec 可以在已验证的生命周期组件上完成组合验证，不等待 Runtime 整份交付；Runtime 的通用验收也不得反过来等待本 Spec。独立管理器验证不替代真实组合验收，不能用假的生命周期通过。

## 需求与验收标准

### 需求 1：进程管理可经独立包入口使用

作为宿主，我希望直接管理自己的进程会话，以便脱离工具和界面复用生命周期能力。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当经 `process-runtime/src/index.ts` 构造管理器并注入符合现有契约的 Store、hostInstanceId 和可选资源注册接口时，应能启动、等待输出、查询活跃数量、停止及关闭进程，不要求构造 Goal、Agent、ToolRegistry、默认文件 Store 或 HTTP 服务。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当以内存或当前文件 Store 替换存储时，应通过同一包入口运行并观察成功/失败结果，不修改组件内部；管理器不解析环境配置或选择数据目录，不取得注入 Store、注册表或宿主进程的关闭权。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当通过进程工具调用新包时，工具仍负责输入校验、可信 Goal 身份、沙箱计划匹配与执行选项准备；管理器只管理显式参数和当前实例拥有的句柄，不自行授予文件/网络权限、提交 Observation 或推进 Goal。

### 需求 2：启动受理、额度和所有权一致

作为资源所有者，我希望每次已受理启动都能被结算，避免关闭竞态留下无人管理的子进程。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当同一管理器并发受理启动时，已受理未结算启动与活跃进程应计入对应额度；现有每 Goal 4 个活跃进程、管理器所代表宿主的 16 个活跃进程及每 Goal 32 项会话上限保持，异步存储检查不能使并发请求绕过限制，拒绝不排队或创建进程。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当初始 `starting` 记录保存失败时，应拒绝启动且不创建 OS 进程；若保存后 spawn 失败，应尝试保存现有 `failed` 记录，保留原始故障与清理故障，不用后者覆盖前者。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当进程快速退出、发出异步启动错误，或保存 running/终态记录失败时，管理器应始终拥有对应启动、事件和结算结果；不得漏接退出、产生未处理拒绝、用迟到 running 覆盖终态，或因持久化失败放弃已有句柄的清理。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当关闭与已受理启动交错时，尚未 spawn 的启动应在后续异步边界重新检查关闭状态并拒绝；已经创建的进程必须纳入同一次清理。初始写入尚未完成也不能在关闭后逃逸成新活跃进程，已写记录仅使用现有状态如实结算。

### 需求 3：输出写入与等待有可观察的结算结果

作为日志消费者，我希望进程结束或关闭成功意味着已接收输出的写入已经结算，而不是仅移除了内存句柄。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当读取 stdout/stderr 时，现有按 Goal/process/channel 隔离、轮转、绝对字节游标、headCursor/gap、工具截断与等待上限应保持，不把通道合并或改为共享消费游标。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当进程输出、退出或关闭发生时，管理器应跟踪已接收的输出追加和终态写入，保持每通道接收顺序；写入失败必须进入可辨识的结算错误，不能被空 catch 丢弃，不能在仍有这些写入时报告关闭成功。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当等待输出期间发生输出结算、进程退出或管理器关闭时，应唤醒相应等待并清理本次定时器/监听器；等待结束不证明日志一定写入成功，也不改变进程或 Goal 状态，后续读取仍以 Store 为准。

### 需求 4：停止与资源关闭不制造成功

作为宿主，我希望明确知道哪些资源已停止、哪些写入失败，以及哪些结果仍未知。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当显式停止当前管理器拥有的进程时，应尝试终止其进程组并确认退出及最终记录结算，重复停止不重复终态或改变其它 Goal 的进程；现有单进程等待窗口到期却未确认退出时应返回失败，不能把已写 stopped 记录或已发送信号当作实际退出证明。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当首次调用 `close()` 时，应同步停止新启动受理，并跟踪已受理启动、当前句柄、输出和终态写入直到结算；重复调用复用同一次清理，不创建用户 Interrupt、Goal 失败/取消状态或虚假的工具 Observation。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当 `forceClose()` 在正常关闭仍等待时或直接被调用时，应停止受理并升级终止本实例仍拥有的进程组，不等待 Store 写入成功才发送终止信号；Store 不响应或抛错不能阻止对其它已拥有句柄的清理，迟到结果均被处理。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当发生已知输出/终态写入或进程清理失败时，应通过具有稳定分类、进程身份、失败阶段和原因的类型化错误报告；所有可继续的清理仍被尝试。只有启动、句柄、监听/定时器及已接收写入均完成结算且无未报告失败时才报告成功，不静默丢失错误或以超时删除活跃项冒充释放。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：当宿主通过 RuntimeLifecycle 关闭实例时，应在其现有正常/强制期限内得到成功或不完整结果，未确认停止或未结算写入不能被注册表吞掉；本管理器不自行退出宿主、不关闭借用资源，也不为同一批句柄建立多个相互竞争的清理所有者。

### 需求 5：现有消费者、权限与恢复保持

作为现有用户，我希望拆包只改变约定的生命周期缺陷，不改变工具授权和进程历史读取。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当使用 `process_start/read/stop` 或默认工具注册时，应保持现有 ID、Input Contract、成功输出结构、失败映射与 replayPolicy；跨 Goal 操作仍拒绝，跨 Run 读取同一 Goal 的会话仍可用，额度拒绝和关闭拒绝不扩大 Profile 或权限。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当 goal-server 装配或关闭时，应直接从新包取得单个管理器并将其自有资源纳入现有实例生命周期；正常、强制、启动中及持久化故障场景均通过同一管理器结算，服务端不重写杀进程或轮询算法，宿主退出仍由应用决定。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当以新 hostInstanceId 重建宿主读取旧会话时，原非终态记录仍由现有 Store 投影为 `interrupted`；读取不启动、重连或终止旧 PID，不改变磁盘协议或把会话记录当成 Goal 恢复/完成证据，manual 工具结果未知时沿用 Runtime 的确认规则。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当装配失败或注入依赖故障时，应清理本次实际创建的进程资源并保留原始错误；注册已关闭时不能留下刚 spawn 的无人管理进程，借用 Store/注册表与其它管理器拥有的进程保持原所有权。

### 需求 6：目录与边界受到验证

作为维护者，我希望独立入口、依赖和事实归属可以由检查及行为验证确认。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当迁移完成时，进程管理实现及其额度常量只在 `process-runtime` 定义；当前消费者经新包入口调用，`tools` 不保留管理器转导出或旧文件，工具、Runtime Port、Storage 和 Sandbox 的各自契约不复制为新真源。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当新增包出现禁止的工具/应用/Storage 实现依赖、Runtime 反向依赖、跨包内部穿透或宿主退出/信号监听时，依赖门应定位失败；覆盖普通/类型 import/export、import 类型表达式、侧效和字面量 dynamic import，合法 Node 子进程 API 与 Sandbox 能力调用不被误禁。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当新目录加入时，类型、测试、依赖与文档检查应实际覆盖新源码；无项目旧产物的源码副本能独立调用并替换 Store。新增/变更公共接口具有中文契约 TSDoc 与示例，模块文档和当前导航指向各自所有者，不以拆文件或测试总数替代行为证据。

## 架构与核心决策

### 角色、依赖与独立调用

| 所有者 | 职责 | 明确不拥有 |
| --- | --- | --- |
| `process-runtime` | ProcessManager、启动受理/额度、当前句柄、输出等待、进程组停止和自身结算 | Tool Schema、授权、Goal 推进、具体 Store、实例关闭期限与进程退出 |
| `tools` | 三个进程工具、输入校验、可信调用身份、沙箱计划匹配、工具结果映射与默认注册 | 进程管理实现或另一套关闭算法 |
| `runtime` | ProcessSessionStore/记录类型及 ManagedResource 契约、RuntimeLifecycle、Goal 恢复与重放决策 | 具体进程管理实现 |
| `storage` | JsonFileProcessSessionStore、Schema、轮转日志与旧宿主记录投影 | OS 进程句柄或杀进程决策 |
| `sandbox` | 当前受限 spawn、进程组信号及平台沙箱能力 | Goal 授权和会话持久化 |
| goal-server | 路径/Store/宿主身份装配、资源关闭权交付、HTTP/信号/退出 | 绕过组件直接清理它拥有的句柄 |

```text
goal-server → process-runtime → runtime（现有 Port 与资源契约）
     │               └──────→ sandbox（现有 spawn/终止能力）
     ├────→ tools → process-runtime
     ├────→ storage → runtime
     └────→ RuntimeLifecycle → 已注册的 ProcessManager
```

`process-runtime` 生产代码只允许依赖 `runtime` 和 `sandbox` 两个 LazyGoal 包及实际所需 Node 内置模块；不依赖 Agent、LLM、tool-core、tools、Storage 实现或应用。Runtime 不反向导入新包。tools 与 goal-server 增加对新包的直接依赖；Storage 不增加出站依赖。测试中的内存/文件 Port 替换经公共入口进行，生产入口约束与包内单测例外分别记录。

最小调用方提供 Store 和本次 hostInstanceId，构造管理器，传入明确的 goalId、command、cwd 和已有沙箱执行选项，调用现有 `startProcess`、`waitForOutput`、计数和 `stopProcess`；需要实例级有界关闭时，将该管理器交付给 RuntimeLifecycle。它不需要创建持久化 Goal；goalId 在这里是调用方提供的会话归属键，不授予业务权限。管理器不会替调用方准备或扩大沙箱权限。

### 目录与唯一事实归属

```text
packages/process-runtime/
  package.json
  src/
    index.ts              最小公开入口
    process-manager.ts    会话管理与自有进程生命周期
    errors.ts             本组件结算错误
  test/                   管理器独立调用、竞态与故障测试
  README.md
  notes/overview.md
  notes/semantics.md
```

仅在实际状态/异步职责需要时建立内部文件，不为启动、输出、配额或每个进程状态分别建包。迁移来源为当前 [process-manager.ts](../../packages/tools/src/process-manager.ts)；旧文件与 `tools/src/index.ts` 中管理器/额度常量导出删除，所有当前源码、测试和文档调用方直接迁移，不保留兼容路径。

当前 [process-session-store.ts](../../packages/runtime/src/process-session-store.ts) 保留 Port 和记录/日志类型；[JSON Store](../../packages/storage/src/json-file-process-session-store.ts) 保留磁盘 Schema、目录权限、轮转和 interrupted 投影；[进程工具](../../packages/tools/src/process-tools.ts) 保留模型交互协议；[受限进程能力](../../packages/sandbox/src/restricted-process.ts) 保留 spawn 与进程组信号机制。独立包不意味着零 Runtime 类型依赖，也不意味着独立发布。

### 启动受理与生命周期所有者

构造参数沿用 Store、hostInstanceId 和可选 resources。resources 仅要求现有 `register` 方法的最小类型面，可复用 `Pick<ManagedResourceRegistry, "register">`，不新增注册平台。构造不 spawn、不读取配置或注册进程信号；若资源注册失败，管理器不得取得后续启动资格。

管理器在第一次异步存储前同步受理并预留本次启动，关闭立即停止此受理。并发上限覆盖启动预留和活跃句柄，历史会话限制结合已存在记录与尚未落盘预留判定，不重复计数已经保存的同一会话；名额在失败或实际退出时按所属事实释放。额度仅保证单个管理器范围，当前 goal-server 为一宿主装配一个管理器，不承诺多个管理器或多个进程共享全局配额。

初始记录先于 spawn 保存。保存返回后若已 closing，拒绝继续创建 OS 进程，已建立记录用现有 `failed` 状态及原因结算；这是进程会话失败，不是 Goal/Run 终态。若已经 spawn，则立即取得句柄所有权并安装 error/输出/退出处理，再完成后续异步记录工作；快速退出不能落在监听空隙。running、终态和已知停止结果由同一会话所有者序列化结算，不能由多个异步回调互相覆盖。

当前注册管理器和每个子进程的双重清理路径收敛为一个所有者：资源注册表只持有管理器，管理器持有自己的全部句柄和启动预留。它不把尚未登记到 Map 的已受理启动排除在关闭之外，不在共享注册表进入关闭后再为子进程注册第二份清理。

### 输出、停止与错误结果

输出按通道串行追加并维护待结算任务，退出后的日志与终态写入仍属于管理器。输出追加失败被捕获并保留为结算失败，继续清理其它资源；不允许 EventEmitter 的 async 回调产生无人接收的拒绝。输出等待仅负责唤醒，不自行充当日志持久化证据。

显式 stop 只操作本实例实际拥有的句柄；没有活跃句柄的历史记录沿用现有读取语义，不据此重新获得 OS 控制权。仍使用现有进程组终止能力及显式停止的等待窗口；未确认退出时该次 stop 明确失败，已发出的停止信号不因返回失败而撤销。`stopped` 记录不能单独证明资源已经释放。实际退出后按自然退出或明确停止结果使用当前状态与退出字段结算，不新增持久化中间态。

管理器使用组件内统一的类型化生命周期错误报告已知失败，携带必要的 goalId/processId、启动/输出/终止/终态写入阶段、原始原因和仍未确认的类别。错误描述不额外复制命令、环境或输出正文；工具继续映射为既有 `PROCESS_START_FAILED`、`PROCESS_STOP_FAILED` 等失败结果。失败可发生于已产生副作用之后，不能由失败返回推断命令未运行，manual 恢复规则保持。

### 关闭、强制升级与 Runtime 前置条件

`close()` 首次调用同步进入 closing 并请求正常停止，后续调用复用同一次工作与结算结果。`forceClose()` 可在 close 等待期间或直接调用，立即进入 closing 并对仍拥有的进程组升级终止；它不被正常清理中的存储等待或错误阻塞。各清理任务的失败不妨碍其它句柄收到停止请求。

管理器跟踪真实进程退出、启动完成、输出和最终记录写入，以及自己创建的监听器与定时器。已知失败不得因 Map 清空而消失；未确认退出的句柄不能为了报告成功而移除。重复调用不重复写终态、重复注册或制造另一组监听/定时器。借用 Store、注册表和宿主共享信号不被关闭；工具或宿主准备的其它资源仍由其原所有者管理。

本包不提供独立的两阶段超时配置；资源方法等待实际结算，直接调用它们本身不承诺固定时间完成。需要有界关闭的独立宿主和 goal-server 均接入 RuntimeLifecycle：正常与强制阶段沿用其各 2000ms 默认上限及现有配置。Store 永不响应或无法确认进程停止时，外层按通用生命周期契约返回类型化不完整结果，组件继续处理迟到结果且不恢复受理；这不是关闭成功，也不保证可以立即重用存储位置或 hostInstanceId。

RuntimeLifecycle 与资源注册表必须保留该管理器的失败/未完成信息，不能吞错。本轮只消费上述契约，不在新包复制算法。组合关闭验收消费已落实的生命周期组件及其契约证据，该前置不是 Runtime Spec 所有任务或整份交付。跨 Spec 只保留“生命周期组件 → 本 Spec 组合接入”的单向依赖，不将通用关闭的验收回推为进程实现的责任。本 Spec 不自动授权执行或联合编排其它 Spec。

### 消费者接入、恢复与验证

goal-server 默认装配仍创建当前 JSON Store 与 hostInstanceId，改从新包导入管理器，并将单个管理器的关闭权交给实例资源集合。Tool 注册继续接受相同管理器/Store，三种工具继续通过可信 context、原沙箱策略和既有授权路径运行；不把沙箱准备、Tool Schema 或 Snapshot 提交移到进程包。

接入修改落在当时实际的应用装配位置：若 Runtime 的无界面装配已经存在，就在其中替换进程管理导入/创建/资源登记；否则只在现有组合根的进程段修改，不自行拆 HTTP 或模型装配。Runtime Spec 后续移动装配时保留该接线。共享依赖检查与导航只增量维护本包规则/条目，保留其它 Spec 已加入的规则，不回退文件。

文件恢复继续以 Store 的当前宿主身份进行只读 interrupted 投影，不保存可重连句柄、不遍历或误杀旧 PID，也不自动重新执行命令。Goal 历史/目录删除仍由原宿主与 Store 处理，本轮不新增按 Goal 关闭操作或改变其流程；进程记录不取得 Goal 完成证据地位。

验证使用公共入口、内存/临时文件 Store、受控 Node 子进程，以及可控存储 Promise/错误。正常路径覆盖多通道、快速退出、按 Goal 额度与归属、跨 Run 读取和旧宿主投影；竞态覆盖关闭发生于列表读取、初始保存、spawn 后 running 保存、输出写入和终态保存期间；故障覆盖 spawn/error、注册拒绝、追加/终态写入失败、不响应存储、重复停止及强制升级。没有旧 PID/用户进程作为测试目标，故障测试始终保留外部测试清理能力。

消费者验证沿现有 `packages/tools/test/process-tools.test.ts`、`packages/storage/test/process-session-store.test.ts` 和 `apps/goal-server/test/process-lifecycle.integration.test.ts` 扩展，独立管理器测试迁入新包。直接调用验证宿主仍能继续执行；RuntimeLifecycle 集成验证期限、失败分类、借用资源与无假关闭成功。用进程实际退出、终态记录及输出追加结算作为证据，不以 `stopped` 字段或资源数量为零单独判断。

依赖门登记新包及消费者，检查生产方向、入口、直接退出/进程信号监听和项目产物引用，并用正反例覆盖所有承诺静态引用形式；发送本组件拥有进程组的终止信号不属于禁止的宿主信号监听。新包保持当前扁平层级与源码消费方式，类型、测试发现、文档及 CI 实际覆盖新位置。在省略项目派生产物的临时源码副本验证独立调用，保留必要依赖而不清理用户目录。

当前说明分别归新包、Tools、Runtime Port、Storage 与 Sandbox；新增/变更公共契约补中文 TSDoc 与最小示例，根导航和布局同步。执行阶段运行类型、依赖、文档、上述消费者及根确定性回归；TODO 与 Feature Verification 执行结果记录在 Plan 的 Latest Result。

## 曾考虑的备选方案

- **只移动 ProcessManager、保留关闭缺陷**：迁移小，但独立调用仍无法知道写入/清理失败或已受理启动是否逃逸；本轮已明确包含这些生命周期修正。
- **在 tools 内仅建 process 目录**：可改善导航，但无法满足独立进程能力的包级消费和最小依赖要求。
- **同时拆出 process-tools 与 process-storage**：当前已有工具/Storage 所有者及真实接口，继续拆包会扩大迁移和维护面，本轮保留这些职责。
- **把存储契约迁入新包并令 Runtime 依赖它**：会把领域/资源基础包反向接到具体进程管理实现；保留现有 Port 可完成本轮独立注入，无需改写依赖方向。
- **管理器与子进程同时注册为资源**：容易重复停止、重复写入且在启动/关闭竞态中丢失所有权；以管理器作为唯一资源所有者。
- **在 process-runtime 再实现有界两阶段实例关闭**：重复 RuntimeLifecycle 的期限和错误汇总，容易产生不同关闭结果；本包只结算自己的资源，实例期限由既有生命周期统一负责。
- **存储写入失败就不再尝试杀进程，或到期直接清空活跃集合**：会留下失控副作用或虚假成功；终止尝试不受写入成功约束，未知结果如实上报。
- **重启时用历史 PID 重新连接或终止**：PID 可复用，记录无法证明当前所有权；维持 interrupted 投影，不新增后台服务或重启能力。

## 风险与否定性保证

- **风险等级：高。** 涉及 OS 进程副作用、关闭竞态及持久化结算。范围限定为本实例拥有的子进程，验证只用临时数据和受控子进程，不操作用户进程或真实任务。
- **行为修正范围。** 已确认的变化是额度/启动关闭竞态收敛、等待真实结算及错误不再丢失，原先可能返回成功的未结算/失败场景现在报告失败；成功路径、工具协议、文件 Schema、权限及 interrupted 规则保持。不以拆包为理由重写其它工具或存储实现。
- **所有权优先于记录。** Goal/process 身份与磁盘状态不构成当前 OS 句柄控制权；仅管理器实际创建并持有的句柄可被停止，不扫描系统 PID、重连或误杀旧宿主进程。
- **终止与持久化是两个事实。** 已退出但记录/日志写入失败仍是结算失败；已写 stopped 但尚未确认退出仍不能报告资源释放。不增加 exactly-once、外部副作用回滚或日志无损保证，已观察到的写入失败必须可辨识。
- **期限归属。** RuntimeLifecycle 的成功需要所有资源与操作结算；其超时只能界定等待，不能强制终结不合作的 Store Promise 或证明外部副作用停止。本 Spec 不另行定义通用关闭语义或重复期限配置，不吞掉管理器错误。
- **恢复不扩权。** 无新 Snapshot/进程状态版本、历史迁移、自动命令重放、跨宿主额度或多租户保证；Goal/Run、权限与 Action 结果未知的处理仍由 Runtime 拥有。
- **实施依赖与审批。** 三份 Spec 的审批状态分别管理，本 Spec 不声明其它能力已交付，也不替代其执行授权。本轮真实进程组合关闭只以前置生命周期组件及契约证据为条件，不等待 Runtime 整份交付，也不依赖 Agent 拆包。调整通用资源验收边界的 Runtime 修订需重新批准；正式多 Spec 编排须待参与 Spec/Plan 各自批准，不自动创建或覆盖其它编排。
