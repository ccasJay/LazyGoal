# 人机交互协议与 Web 表单重设计 Spec

## 目标与范围

LazyGoal 将模型澄清、任务批准、工具／沙箱批准与操作恢复请求呈现为可恢复的交互。用户可以逐题回答、用一段整体回复替代问卷、跳过问卷继续，或独立停止 Run；仓库内无界面宿主可以通过处理函数程序化决定，也可以等待真人。所有决定通过 Runtime 校验和提交，不由界面或回调直接推进状态。

本次整体替换现有 `AskUserForm`、`TaskApprovalForm` 和 `ActionApprovalForm`，重新设计问题卡片、审批布局、操作流程及提交状态；不是保留旧表单后仅添加按钮。新界面沿用 LazyGoal 白色薄荷绿主题、字体与现有工作区外壳，历史 Activity 和普通消息队列继续使用各自所有者的能力。

本 Spec 依赖已批准但尚未实现的 [streaming-session](../streaming-session/spec.md)。后者拥有输入受理、收据、提交协调、执行所有权、队列、订阅、Interrupt 和显式恢复；本次拥有交互请求与响应语义、宿主交互适配、模型可见回答及完整 Web 交互体验。实施和集成验证须先具备其契约，不把文件存在当作能力已交付。

本次不提炼 SDK 包、不迁移默认装配，不增加第二套持久化会话或交互队列。不包含修改工具参数后批准、重新设计授权匹配规则、拆分未知结果重执行命令、通用 Hooks、外部通知系统、图片、MCP、模型生成的选项预览、任意 HTML、通用表单搭建器、子代理、多活动 Goal 或终端 UI。操作恢复沿用现有命令及执行规则，但新界面必须准确说明再次执行的后果。

## 需求与验收标准

### 需求 1：具有明确语义的交互请求

作为用户或宿主，我希望知道当前需要回答问题、批准范围还是处理执行结果，以便作出对应决定。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当 Runtime 已提交问答、任务批准、工具／沙箱批准或未知结果等待时，应从当前 Snapshot 投影对应的交互种类、Goal／Run 身份及请求或 Action 身份；未提交的模型文本不得生成可操作表单。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当问答携带 Plan 路线扩展审批时，应明确展示审批性质、理由和完整候选路线，并保留既有批准选项身份；普通问答不能被展示成工具批准，问答回复也不能隐式批准任务或权限。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当同一请求通过初始同步、重复通知或重连再次出现时，应识别为同一交互；新请求、其他 Goal／Run 或新的等待类别不能继承旧表单草稿、处理函数结果或完整参数详情。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当输出公开交互视图时，应保留作出决定所需的安全说明及可用操作，并沿用有界投影与授权详情读取；默认事件不得携带任意完整工具参数、凭据、隐藏推理或原始 Provider 响应。只读详情查询不能批准或恢复执行。

### 需求 2：逐题回答、整体回复与跳过

作为被询问的用户，我希望能按选项回答，也能解释真实意图或跳过当前问卷，而不会被迫选择不合适的答案。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当提交逐题回答时，应沿用稳定问题／选项 ID、单选／多选及逐题 Other 文本规则，并完整校验当前问卷；缺题、重复、未知身份或不符合选择数量的回答应明确拒绝且保留等待。问题和选项数量沿用现有模型契约，不为模仿其他产品扩大限制。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当用户选择整体回复并提交非空文本时，应将其作为替代整份问卷的回答，在同一提交中结束当前问答并追加真实用户消息，随后允许同一 Run 按该回复继续；不创建后继 Run，不伪造逐题选择，不同时应用尚未提交的逐题草稿。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当用户显式跳过整份问卷时，应结束当前问答，提交“用户未回答、要求继续”的明确控制语义并继续同一 Run；不得填入默认选项、宣称已经回答或将 Run 标记为 cancelled。跳过不提供逐题省略能力。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当整体回复或跳过用于带路线扩展审批的问答时，应保留原已批准路线；只有既有规则要求的明确批准选项才能接受候选。整体回复中出现“批准”等字样也不构成结构化批准；任务或 Action 审批不能套用问答整体回复来绕过各自决定。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当回答、整体回复或跳过已受理时，应保存请求关联、响应种类和实际内容的已提交事实，使模型上下文与恢复后的历史一致；问答交互本身不增加业务 Step，不构造业务 Tool Observation。重复提交不得重复追加消息或再次恢复同一等待。

### 需求 3：停止 Run 与交互竞争

作为用户，我希望停止任务和跳过问题是不同的操作，且迟到回答不会让任务重新开始。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当用户在普通问答、任务审批或工具审批等待时选择停止 Run，应显式提交现有 Interrupt 输入，沿用中断意图与队列暂停的提交规则；不得通过跳过问卷、拒绝某个工具或解除句柄来冒充停止。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当回答／批准与 Interrupt 竞争时，应由 streaming-session 的同一 Goal 提交边界决定先后；Interrupt 先受理后，原任务的迟到回答或批准必须失效。回答先受理时，后续 Interrupt 仍按最新 Run 状态处理，不能以表单曾显示为由忽略已经发生的执行。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当停止涉及未知效果、必要收尾或收尾审批时，应继续展示实际收尾状态及当前有效请求，沿用既有预算和授权规则；再次点击停止不得绕过必要结算、重置预算或报告效果已回滚。旧交互失效不等于新收尾请求也失效。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当停止被受理、正在收尾或最终取消时，应分别展示对应状态；已受理的普通队列保持暂停，只有独立的继续队列操作才能解除。关闭卡片、离开页面或取消本地回调不能生成用户 Interrupt。

### 需求 4：可选的宿主交互处理函数

作为仓库内宿主开发者，我希望接收交互请求并返回决定，也能交由真人处理，而不实现第二套执行或恢复循环。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当无界面宿主显式连接交互处理器时，应可分别处理问答、任务批准、工具／沙箱批准和操作恢复，并程序化返回合法答案／决定；没有对应函数或显式返回不处理时保持等待。自动放行的工具不触发审批处理器，普通工具批准函数不得代答未知结果恢复请求。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当处理器开始调用宿主函数时，应提供已提交请求、稳定交互引用、取消信号及受同一访问边界保护的只读详情入口；函数在短提交 Gate 之外运行，不能阻塞其他读取、真人响应或 Interrupt。函数结果仍作为 Session `respond` 受理，不直接调用 Tool、修改 Goal 或写入 Grant。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当同一 Goal 已有一个活动自动处理器时，第二次连接应明确拒绝而不替换原处理器；其他句柄仍可观察及显式提交真人决定。同一处理器对同一待处理请求至多启动一次调用，不因重复事件或未处理结果反复调用。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当请求被其他客户端回答、被 Interrupt 取代、Run 结束、处理器解除连接或 Runtime 关闭时，应中止对应本地调用并阻止其迟到结果继续提交；不合作的 Promise 不得阻止解除连接和有界关闭。已经进入受理的结果仍按真实提交与收据结算，不能被本地取消撤销。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：当宿主函数抛错、决定被 Runtime 业务规则拒绝或提交结果不明时，应向宿主报告可定位请求的处理故障；结果不明时查询原输入收据以确定是否提交，尚未生成决定时不伪造收据。未提交时保留仍有效的等待，不默认批准／拒绝，不覆盖其他客户端已结算的状态，不无限重调函数。重试已产生的决定应复用原 `inputId` 和载荷。
- <a id="spec-req-4-6"></a>**验收标准 4.6**：当重新打开 Goal、重建 Runtime 或只注册处理器时，不得因此程序化回答历史等待、恢复模型或消费队列；宿主显式恢复并在仍需交互时才允许自动处理当前历史请求。真人显式提交匹配的 `respond` 仍按基础 Spec 只推进其目标等待，不代替继续队列。重新连接处理器可能再次投递尚未解决的请求，不能承诺跨进程回调 exactly-once。

### 需求 5：整体替换问答与审批界面

作为 Web 用户，我希望从当前任务上下文中理解并处理请求，而不是在几个不一致的旧表单之间切换。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当显示待处理交互时，应使用新设计的统一交互区域承载种类标题、请求内容、决定区及提交状态，整体替换三个旧表单及其原分支操作流程；不得仅给旧表单改名、换样式或增加按钮。其他 Goal info／授权管理面板和工作区外壳不随本次重写。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当显示问卷时，应提供可回看的问题导航、当前问题的完整文本与选项、明确单选／多选提示、逐题自由文本以及已答／未答状态；切换问题不提交答案，最终提交完整问卷前能审阅所有回答，单选自由文本与选项互斥，多选沿用现有组合规则。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当切换逐题回答与整体回复时，应保留当前请求的两份未提交草稿，并明确提示只提交当前选择的响应方式；跳过需通过独立且说明后果的操作，停止 Run 始终单独可达。问答区域的整体回复不得被发送为普通队列消息。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当显示任务或路线范围审批时，应在决定操作前展示任务目标、完成条件和完整有序候选阶段；任务批准保留明确批准与带非空反馈的重新规划两种操作，不把反馈当作批准。长内容可滚动阅读，但不得静默省略批准对象或以未展开的截断摘要作为完整范围。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当显示工具／沙箱审批时，应重新组织操作摘要、参数详情、申请的能力及授权期限，默认仅批准本次；持续授权受既有可用性与完整审阅限制，拒绝提供非空理由。结果未知时应明确说明此前可能已执行、再次执行可能产生重复效果，只提供既有单次恢复选择，不显示持续授权或参数编辑。
- <a id="spec-req-5-6"></a>**验收标准 5.6**：当普通任务队列与待处理交互同时存在时，应将后续任务输入明确标为排队用途，显示当前等待不会被其回答；接收其他普通消息不清除问答草稿。交互处理成功后，Activity 应可查已提交的请求及决定摘要，不能仅留下消失的卡片或伪造执行成功。
- <a id="spec-req-5-7"></a>**验收标准 5.7**：当使用键盘、屏幕阅读器或 320px 至桌面宽度的视口时，应能完整阅读内容、切换问题和响应方式、提交及停止；提供清晰焦点、字段错误关联与状态播报，保持页面可滚动且操作不被遮挡。文本框 Enter 不隐式批准、跳过或中断，Escape 不能被解释为已回答或停止；所有产品文案使用英文并沿用现有主题 token。

### 需求 6：提交结果、草稿与恢复体验

作为用户，我希望知道决定是否保存，并在网络故障或请求被其他人处理后仍能判断真实状态。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当用户提交任一交互决定时，应为本次决定冻结稳定 `inputId` 与载荷，区分编辑、提交中、结果待核验、已受理及请求失效；已受理只表示决定保存，不能显示工具已完成或 Run 已停止。相同决定重试复用原身份，修改后的新决定使用新身份。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当发生明确业务拒绝或可恢复读取错误时，应保留同一请求的草稿和有效选择，展示字段级或请求级原因；结果不明时先按原身份查询／重试，在核验前不能换身份重发或允许用户提交相矛盾的第二个决定。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当另一个客户端或宿主已结算当前交互时，应显示由最新状态确认的已处理／失效结果，禁用旧决定并切换到真实后续状态；不得把旧草稿应用到新请求。相同请求的常规状态刷新与暂时断线不应重置正在编辑的内容。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当刷新页面、重新连接或重启服务时，应从权威状态恢复当前请求、已提交决定及是否需要显式恢复；未提交草稿只要求在当前页面会话内保留，不承诺跨刷新恢复，不将答案或工具参数镜像到 localStorage。订阅缺口与末次通知丢失沿用基础 Spec 的同步机制。

### 需求 7：真实链路验证与职责文档

作为维护者，我希望新交互在 Web 和无界面宿主上遵守同一规则，并能通过确定性证据验证。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当验收问答链路时，应通过实际模型协议解码、Runtime 提交、存储重建和模型请求组装验证三种响应方式，检查真实用户消息及请求引用；同时验证路线扩展不会因整体回复或跳过被批准，不能只测试组件文本和类型导出。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当验收宿主与竞争行为时，应以确定性注入覆盖真人与回调竞争、Interrupt 两种提交先后、回调抛错与迟到、不合作的 Promise、保存后崩溃／响应丢失、重启后显式恢复和 busy；检查收据、Snapshot、轨迹和实际模型／工具调用次数，不依赖真实付费模型。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当验收新 Web 界面时，应通过真实服务和浏览器执行完整问卷、整体回复、跳过、等待时停止、任务批准／反馈、单次与持续工具批准、拒绝、未知结果提示、断线重连及多客户端失效流程，并检查移动布局、键盘与草稿保留；静态 HTML 快照不能替代行为验收。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当功能交付时，应更新变化所有者的概览、语义表、内部宿主使用示例及公开中文契约 TSDoc，并通过当前文档、依赖方向与类型检查；被替换的旧表单、旧交互命令分发和失效测试应移除或改为新契约，不并存两条可推进实现。

## 架构与核心决策

### 当前依据与依赖边界

当前 [问答契约](../../packages/model-contracts/src/model-output/canonical.ts) 已定义问题、选项 ID 和逐题 Other；[AskUser 系统工具声明](../../packages/model-contracts/src/model-output/system-tools.ts) 已将模型请求解码到 Runtime 交互。[Coordinator](../../packages/runtime/src/goal-coordinator.ts) 保存回答后继续当前 Run，并沿用批准先保存、Grant 后激活的授权事务。[旧表单](../../apps/goal-board/src/panels.tsx) 将浏览器会话和命令直接带入三套表单，其单一 busy 状态与 Browser 进程内交互去重不作为新协议的权威。

本次扩展 [streaming-session 的交互契约](../streaming-session/spec.md#spec-req-6-1) 和 [统一输入协议](../streaming-session/spec.md#session-接口与输入协议)：增加问答响应分支和处理器适配，保持其先提交、按身份去重、单活动 Goal、显式恢复及安全公开投影保证；不另定义 inbox、全局锁、收据或 HTTP 路由。依赖方未提供这些能力时，本次端到端验收不成立，不以旧 Browser 内存机制兜底。

[Permission](../permission/design.md) 继续拥有授权匹配与作用域；[Run 输入控制](../run-input-control/design.md) 继续拥有有限中断收尾。参数修改审批及未知结果命令拆分不是本次依赖，不引用尚不存在的审批 Spec；本次只准确展示现有恢复含义。现有已批准 `streaming-session/spec.md`、`plan.md` 不在本次写集内。

### 请求与响应协议

内部 `InteractionRequest` 是 `question`、`task_approval`、`action_approval`、`action_recovery` 的可辨识视图。`question` 可携带既有路线修订审批上下文；后两类继续区分工具／沙箱范围和 PTC 来源。请求引用包含 `goalId`、`runId`、种类及现有 `requestId` 或 `actionId`，不使用问题文本、展示标题或当前全局选中 Goal 作为身份。

所有决定仍是 `SessionInput.kind = "respond"`，带稳定 `inputId`、目标 Run 和对应请求引用。下表是领域语义，不另建独立 HTTP 命令族；具体字段在实现时复用现有联合。

| 响应 | 适用等待 | 结算后果 |
| --- | --- | --- |
| `answer_questions` | `question` | 完整逐题答案，沿用 `questionId`／`optionIds`／`otherText`。 |
| `reply_to_question` | `question` | 非空整体回复，互斥于逐题答案；解除问答并追加原文用户输入。 |
| `skip_question` | `question` | 不提供答案，提交跳过语义并继续；不等同于取消 Run。 |
| 既有任务批准／反馈 | `task_approval` | 明确批准固定任务，非空反馈使提案失效并重新规划。 |
| 既有 Action 批准／拒绝 | `action_approval` | 按原参数和现有授权范围批准；拒绝携带非空理由。 |
| 既有 Action 恢复选择 | `action_recovery` | 原有单次重新执行或拒绝规则；恢复批准不是“确认此前已成功”。 |

响应联合只接受当前种类合法的分支；问答整体回复在专用 `respond` 中表达，普通 `message` 仍排队。正文非空、长度沿用基础 Spec 的单条文本上限；逐题选项沿用现有契约，整体响应受现有 HTTP 正文总量限制。对逐题文本按字段校验，不自动裁剪用户正文来取得通过。空白判定与规范化遵循共享边界，不能改变重试载荷。

Coordinator 在统一短提交中读取最新等待、校验响应并提交：决定事实、真实消息、等待解除及输入收据共同跨越可恢复边界，再唤醒执行所有者。路线批准继续只认既有明确选项。拒绝和失败不得清除原等待；结算成功或 Interrupt 后旧引用不可复活。问答整体回复／跳过保留原请求来源，历史渲染可以据此查回问题；已回答后的完整内容不再作为一份可变 pending 正文保留。

模型可见输入明确区分问卷回答、整体回复与跳过，保留用户原文和来源。只有公开且已提交的事实进入上下文；不能把系统生成的“继续”描述为用户选择了某个选项，也不能把宿主处理器的程序化决定伪装为真人点击。来源标记由实际接入边界赋值，wire 不能自行声明宿主身份；它只区分本机宿主与显式客户端，不扩展为多用户身份认证或权限系统。

### 宿主处理函数与恢复

内部 Session 增加 `attachInteractionHandlers(handlers)`，返回可解除的处理器句柄；函数按请求种类分派，可分别提供 `onQuestion`、`onTaskApproval`、`onActionApproval`、`onActionRecovery`。结果是对应合法决定或显式 `unhandled`；函数也可返回等待真人的 Promise。此入口不承诺独立安装的公开 SDK API。

同一 Runtime／Goal 只允许一个自动处理器所有者，重复连接返回明确冲突；可以多个只读订阅及显式响应来源。处理器先接入一致同步，再核验当前请求是否允许投递；同一连接按请求引用去重，调用不占提交 Gate。解除后可显式重新连接并处理仍未结算请求，但这不提供跨连接、重启或宿主自身外部副作用的 exactly-once 保证。

每次调用创建局部取消信号。收到结果后先核验连接和请求仍有效，再冻结 `inputId` 与载荷，调用统一 `send`。其他响应或 Interrupt 先提交则本结果失效；本结果先进入提交后再解除连接，已受理决定不能回滚。处理函数异常与不合作 Promise 被隔离，释放本地资源不等待它永远完成；暂停或关闭处理器不取消 Goal。

处理器仅在当前实例正常产生的等待，或宿主已显式恢复的历史等待上自动调用。重启后打开／注册只展示；宿主显式 `resume` 发现仍需回答时并不代答，但允许已注册处理器处理该请求。恢复因 busy 或状态错误被拒绝不能开启自动投递。直接提交匹配的真人决定是显式交互指令，沿用基础 Spec 的推进规则；注册回调、读取详情和重新同步都不是该指令。回调未处理／失败后不自动循环重调，宿主可显式重连或提交决定。

宿主收到的是受信本机调用入口允许的安全投影及显式详情读取，不把任意完整参数广播给普通订阅。详情读取复用并按需扩展现有 Action 详情边界，以当前交互引用核验后读取完整问题／任务范围／工具参数；HTTP 适配继续受现有授权和大小限制保护。详情无法完整提供时明确报告限制，禁用依赖该完整范围的批准，不要求客户端从任意原始轨迹推测。`onActionRecovery` 必须单独注册，文档说明其批准会允许原操作再次执行；不得降级调用通用工具审批函数。宿主程序化批准仍受 Profile、发现、输入、权限、沙箱和已提交 Action 约束。类型化同进程处理函数不额外套不可信返回值解析；模型、wire、排队输入和持久化边界继续执行各自校验。

### 全新 Web 交互流程

新交互区域嵌入 Activity 下部，与当前对话正文对齐，保留历史可读；不使用每个请求自动弹出的阻塞模态框。旧 `WaitingInteraction` 下的三套表单由新的类型化视图和响应控制器替换，拆分仅服务上述行为，不建立可配置表单引擎。内部组件接收具体请求与编辑／提交状态，不依赖整个 `BrowserGoalSession` 来推断响应种类。

```text
交互种类 / 当前等待说明                       Stop run
请求正文 / 必要审批上下文
────────────────────────────────────────────────────
问答：问题导航与已答状态       回答当前问题 / 整体回复
      当前问题、选项与 Other  或整体回复编辑区
      回看与完整答案审阅
────────────────────────────────────────────────────
字段错误 / 提交状态      Skip and continue    Send answers

后续任务队列与输入区：Queue next task（明确不会回答当前请求）
```

这是信息与操作结构约束，不是继续复用旧表单的线框。任务审批用完整目标／验收／路线审阅区和批准／反馈决定区替换问答导航；工具审批用操作与能力详情区、期限选择和批准／拒绝决定区。未知结果使用独立恢复标题、已发生效果警示以及明确的 `Retry action`／拒绝操作文案，不把重执行写作普通 `Approve action`。字段、按钮和结果提示保持同一词汇。

问卷按问题导航编辑，允许回看；最终按钮只提交整份答案。整体回复是并列模式，不是给每题复制同一文本；切换模式保留各自草稿。跳过以独立次操作展开后果并要求显式确认，不能通过 Escape 或关闭编辑区域触发。停止 Run 沿用 Interrupt 状态显示，已经进入有限收尾时展示其真实限制，不添加“强制成功停止”入口。

默认授权范围为本次。任务／路线范围、完整参数未加载、持续授权不可用和结果未知使用不同说明；不靠颜色单独区分。执行对象或范围详情读取失败保留等待，不悄悄降为批准。长审批对象可在区域内滚动；现有有界投影若不足以完整审阅，显式详情读取后才能批准该范围，不把被截断文本当作完整内容。

继承 `style.css` 的白色、浅薄荷背景、深绿文本／边线、警示与错误 token 及 Avenir 字体体系；交互种类和后果通过内容层级、留白与分隔表达，不复制 Claude 品牌配色。桌面与窄屏均为一个当前交互区域；窄屏将导航和决定区纵向排列，阅读正文不会把停止或最终提交永久挤出可达范围。不引入新的外部字体或图像依赖。

编辑状态按 Goal／Run／请求引用隔离，常规刷新不重建草稿。提交时冻结载荷；结果不明只允许核验和原身份重试，不能允许一边核验一边编辑已冻结载荷后用同一身份重发。上述限制针对相互矛盾的交互决定，不以全局表单 busy 锁住独立 Interrupt；停止使用自己的输入身份，按最新可用 Run 状态与提交顺序受理。明确拒绝后可以回到编辑并产生新的提交身份。已受理后移除可操作表单，以已提交决定摘要及实际运行状态承接；下一请求使用全新编辑状态。网络同步失败显示仍可读的最后状态，但禁用依赖最新状态的新决定。

## 曾考虑的备选方案

- **整体替换现有表单**：选择重新组织问题导航、整体回复、范围审阅、决定与结果状态。备选为保留组件后追加按钮，不能满足用户明确选择的整体重做，也会继续混合跳过／停止和单一 busy 状态，故不采用；低层通用控件和主题 token 可复用。
- **持久化请求加 Session 响应**：选择现有 Goal 等待和统一收据为权威，回调只是消费适配。备选将挂起的回调 Promise 作为唯一状态，无法在进程退出或 Web 接手后可靠恢复；独立交互数据库又会与 Snapshot 产生双写，均不采用。
- **整体回复替代问卷**：选择显式响应分支解除本次问答，在原 Run 处理用户真实输入。备选只补充上下文却保留原问卷会让“先解释选项”被旧必填答案阻塞，与已确认行为冲突，故不采用。
- **稳定身份与响应联合**：选择 ID 关联和种类约束。备选以问题文本作为答案键，或从普通聊天中识别批准意图，无法可靠处理重复文案、旧请求和权限扩张，故不采用。
- **一个自动处理器与多个显式响应方**：选择同一 Goal 一个自动所有者，Runtime 决定真人／回调竞争。备选所有订阅者都自动执行处理函数会重复发起宿主外部交互；按连接持锁等待人工则阻塞 Interrupt，故不采用。
- **当前实例可自动处理、历史等待显式恢复**：选择复用恢复门禁后投递。备选注册函数即扫描并自动决定历史请求，会使只读打开产生执行效果；全部请求强制真人则不能满足程序化宿主需求，均不采用。
- **保留现有授权与恢复算法**：本次重做视图及接入，准确说明恢复批准的重执行后果。备选同步引入参数修订、授权规则扩展和恢复命令重构，会混合独立的执行事务变化，故留给后续审批 Spec。

## 风险与否定性保证

- **风险等级：high**。交互决定可能解锁模型和工具副作用；整体回复、回调自动批准、停止竞争及 UI 重写可能错误扩大授权或重复推进。验收必须覆盖权限、恢复、并发与真实浏览器行为，而不只验证表单渲染。
- **关键操作**：实现涉及当前问答响应／事实契约、等待结算、Session 处理器与 Web 主操作替换。Spec 批准不授权真实工具副作用、付费模型验收、删除用户 Goal、迁移本地开发数据或发布 SDK；确定性测试使用隔离存储与假模型／工具。
- **交互不变量**：普通消息不代答；问卷整体回复和跳过不批准范围；输入身份相同而载荷不同必须拒绝；同一等待只结算一次；失效回调不能复活原任务；已受理收据与模型可见回答必须一致。
- **权限不变量**：宿主函数没有绕过 Runtime 的执行权；未注册恢复处理器不能调用普通审批函数代办；持续授权保留既有事务和范围限制；未知效果不被描述为成功、回滚或未执行。
- **生命周期不变量**：连接、读状态、注册处理器和 UI 草稿恢复不自动启动历史任务；回调异常／断线不默认拒绝或取消；解除句柄不能撤销已提交决定；不合作的宿主 Promise 不能拖住有界关闭；Interrupted 队列仍须显式继续。
- **界面替换风险**：移除旧表单时必须逐项保留现有单选／多选、Other、任务路线、反馈、参数详情、授权期限与 PTC／恢复信息；新流程需真实浏览器验证焦点、键盘、长内容和窄屏。历史成熟行为由新契约覆盖，不用保留旧推进路径作为回退。
- **数据与文档边界**：按开发期政策原位更新当前 Schema，拒绝不支持的数据，不添加历史数据迁移或无需求的协议版本。实施时同步所有者文档；旧 Memory／Spec 的界面描述仅作背景，不作为保留旧表单的约束。本阶段只生成此 Spec，不生成 Plan、不修改已批准的依赖文件、不写入项目记忆。
