# 浏览器真实轨迹视图需求

## 审批摘要

### 目标

将已批准的 Harness 风格原型接入 LazyGoal 正式工作区，使用户能在 Goal 会话中查看当前和历史 Run 的真实执行轨迹。

### 范围

- 包含：用 Trajectory 替换 Details 的主要内容；三泳道概览、按 Step 分组的记录表、搜索、筛选、折叠、详情检查器、分页与提交后更新；在会话头部保留 Goal 信息及授权管理入口。
- 不包含：轨迹编辑、重放执行、Diagnostic Trace 浏览、持久化格式迁移，以及推测逐事件 Token 用量或模型调用耗时。

### 核心行为

- Run 列表与状态以正式 Snapshot 为准，当前和历史 Run 的事件均限定在各自 Snapshot 提交边界内；轨迹只读，不改变执行、授权或恢复状态。
- 按真实执行单元与 Step 身份分组，缺少 Step 身份的事件放在 Run 层级；按 Run 内序列排序，用 Action 身份关联工具输入与结果，不从单独的工具结束事件推断观察结果已确认。
- 沿用原型的三泳道概览、记录表和按需详情；支持时间与序列视图、范围拖选与清除、概览定位、Step 折叠及当前 Run 的完整轨迹搜索和分类筛选。
- 详情提供 Summary、适用的 Input／Result、Timing 和 Raw；Raw 对应选中事件的领域事实，不包含 Diagnostic Trace 或额外 Runtime 配置。工具计时只使用同一 Action 的真实起止记录；缺失、无效或未确认的信息明确标识，不伪造结果、用量或时长。
- 长轨迹分页读取与展示，不静默丢弃较早记录；历史未加载、载荷截断及读取限制明确提示。切换 Goal／Run 或关闭视图时，旧请求不能污染当前内容。
- 提交后读取新增事实，重连后补齐且不重复事件；上翻历史时不强制跳回末尾，断流不改变 Run 终态判断。空轨迹、无搜索结果、读取错误和授权失效分别给出可操作提示。
- 窄屏使用可关闭的详情抽屉，保留键盘操作与可见焦点；Activity、Plan、消息发送、Goal 信息与查看／撤销授权继续可用，产品界面文案保持英文。

### 风险与待确认

- 风险等级：medium；跨浏览器界面与只读 HTTP 数据接口，增加领域事实的可见范围，但不改变执行协议、持久化格式或既有授权机制。
- 关键操作：无；本范围不含修改轨迹、重放或迁移数据。
- 风险：详情可能包含工作区文件内容、工具参数和已记录思考，须受现有同源与能力令牌访问边界保护；缺失模型计时不能由决策时间代替。现有 Storage 范围读取仍解析完整文件，响应分页本身不保证磁盘读取或解析成本有界，长轨迹性能须实测。
- 待确认：无。

## 引言

本功能将已批准的轨迹原型替换为真实数据驱动的会话视图，使用户能按 Run 和 Step 浏览已提交的领域事实，并检查工具输入、结果和计时，同时保留现有 Goal 操作与访问边界。

## 需求

### 需求 1：浏览正式工作区的当前和历史轨迹

**用户故事：** 作为 LazyGoal 用户，我希望选择 Goal 内的真实 Run 查看轨迹，以便区分多次执行的事实与当前状态。

#### 验收标准

1. <a id="req-1-1"></a> 当用户打开 Goal 的 Trajectory 时，系统必须从正式工作区读取该 Goal 的当前和历史 Run，默认选择当前 Run，并以 Snapshot 显示 Run 状态，不使用模拟数据或 Benchmark 聚合目录的数据。
2. <a id="req-1-2"></a> 当用户选择一个 Run 时，系统必须只展示归属于该 Goal／Run 且位于其 Snapshot 提交边界以内的轨迹事件，不混入其他 Run 或未提交 tail。
3. <a id="req-1-3"></a> 当事件被读取、搜索或展示时，系统必须保持轨迹、Snapshot、执行与授权状态不变，不触发模型调用或工具执行。
4. <a id="req-1-4"></a> 如果 Goal 或所选 Run 不存在、读取数据损坏或底层读取失败，系统必须明确区分不存在与读取失败，不以空轨迹或其他 Run 的数据代替。

### 需求 2：保留执行顺序和真实身份

**用户故事：** 作为轨迹查看者，我希望看到真实步骤及其工具关联，以便追踪一次决策如何产生动作和观察结果。

#### 验收标准

1. <a id="req-2-1"></a> 当系统展示轨迹时，记录必须按 Run 内的真实 sequence 排序，并保留稳定事件身份；展示序号不得替代事件的原始序列。
2. <a id="req-2-2"></a> 当事件具有真实执行单元和 Step 身份时，系统必须按该身份分组；缺少 Step 身份的事件必须显示在 Run 层级，不按事件数量、位置或文本内容猜测 Step。
3. <a id="req-2-3"></a> 当用户查看工具输入、结果或计时时，系统必须按同一 Goal／Run 内的 Action 身份关联事实；分页边界不得导致错误关联，缺少对应事实时必须标记缺失。
4. <a id="req-2-4"></a> 如果只有工具结束记录而没有已提交的对应 Observation，系统必须保留该记录的事实含义并标识观察结果尚未确认，不据此宣称步骤成功完成；Run 状态仍以 Snapshot 为准。

### 需求 3：使用已批准的轨迹浏览布局

**用户故事：** 作为轨迹查看者，我希望在紧凑视图中定位执行阶段和记录，以便减少逐条展开的成本。

#### 验收标准

1. <a id="req-3-1"></a> 当 Trajectory 展示已提交事件时，界面必须沿用已批准原型的紧凑工具栏、Run／Agent／Tools 三泳道概览、索引／事件／内容记录表及按需打开的详情检查器；泳道中的事件类别不得与实际事实含义冲突。
2. <a id="req-3-2"></a> 当用户切换时间或序列视图、拖选范围或清除范围时，概览与记录表必须同步反映选择；Escape 或明确的清除操作必须恢复当前搜索与分类条件下的范围，时间视图不得伪造缺失时长。
3. <a id="req-3-3"></a> 当用户点击概览记录时，系统必须定位并选中对应记录，展开其 Step 并打开详情；当用户折叠或展开单个或全部 Step 时，不得修改事件事实。
4. <a id="req-3-4"></a> 当用户关闭详情或使用窄屏浏览时，系统必须保留可访问的记录表与详情关闭入口，并支持键盘操作、可见焦点及减少动画偏好；产品界面文案必须为英文。

### 需求 4：查看事实详情与可信计时

**用户故事：** 作为轨迹查看者，我希望检查记录的输入、结果和原始领域事实，以便判断实际执行内容而不是依赖摘要。

#### 验收标准

1. <a id="req-4-1"></a> 当用户选中事件时，详情必须展示该事件的 Summary、Timing 与 Raw，并在存在对应事实时提供 Input 和 Result；不存在或不适用的数据不得用零、空成功结果或估算值代替。
2. <a id="req-4-2"></a> 当用户查看或复制 Raw 时，系统必须提供选中事件的真实信封与领域载荷，保留原始身份、序列和时间；若载荷未完整读取、受到大小限制或展示被截断，界面必须明确提示，不能将不完整内容标为完整原始事件。该读取不得附带 Diagnostic Trace、凭据或领域事件之外的 Runtime 配置。
3. <a id="req-4-3"></a> 当同一 Action 的工具起止记录具有有效时间时，系统必须显示由这些记录得出的非负工具耗时；缺少端点、时间无效或起止顺序异常时必须显示计时不可用。决策事件时间不得被当作模型调用开始时间。
4. <a id="req-4-4"></a> 当记录缺少可信模型计时或逐事件用量时，系统必须保持这些信息不可用，不从相邻事件间隔、Run 汇总指标或临时活动猜测补齐；复制失败时必须反馈失败且不提示复制成功。

### 需求 5：搜索与分页浏览长轨迹

**用户故事：** 作为长任务的查看者，我希望找到较早事件及其完整详情，以便分析未出现在当前加载窗口中的执行记录。

#### 验收标准

1. <a id="req-5-1"></a> 当所选 Run 的轨迹较长时，系统必须分页读取和展示事件，并提供继续读取较早历史的操作或明确加载状态，不静默丢弃记录；概览必须明确其覆盖范围，不将部分加载窗口呈现为完整 Run。
2. <a id="req-5-2"></a> 当用户搜索或分类筛选时，查询必须覆盖所选 Run 的全部已提交轨迹，而非仅当前已加载记录；搜索覆盖事件类别、摘要及允许展示的领域内容，并与范围筛选一致。
3. <a id="req-5-3"></a> 当用户选择跨页记录、继续加载历史或查看超出列表摘要的内容时，系统必须保持排序与稳定选择，并按需读取详情；响应或载荷超过读取限制时必须明确提示，不返回伪造摘要或静默缺失结果。
4. <a id="req-5-4"></a> 当用户操作长轨迹时，分页、搜索与详情的加载过程必须有可见反馈，不因一次展示全部记录或重复叠加请求而阻断页面操作；验收必须覆盖长轨迹的实际响应和浏览表现，不能仅凭接口分页宣称读取成本有界。

### 需求 6：在提交与重连后安全更新

**用户故事：** 作为运行中 Goal 的查看者，我希望看到新增的已提交轨迹，同时保留我正在阅读的历史位置。

#### 验收标准

1. <a id="req-6-1"></a> 当当前 Goal 的提交刷新通知到达时，系统必须重新读取所选 Run 的已提交事实并更新概览与记录，不把临时文本或活动当作持久轨迹，不因新 Run 出现而混合或擅自替换用户已选的历史 Run。
2. <a id="req-6-2"></a> 当连接中断、发生事件缺口或重新连接时，系统必须重新对齐提交边界并补齐缺失记录，按稳定身份去重；传输故障或流结束不得被解释为 Run 完成、失败或取消。
3. <a id="req-6-3"></a> 当用户位于记录末尾时，新增事实必须可继续跟随；当用户上翻历史、选择范围或查看已有详情时，刷新必须保持阅读位置和选择，并提供返回最新记录的入口。
4. <a id="req-6-4"></a> 当用户切换 Goal／Run 或关闭轨迹视图时，系统必须取消该视图的旧请求和订阅；已经到达或迟到的旧响应不得覆盖新视图。后续读取失败时必须明确提示当前数据未更新，不能把保留内容标为最新。

### 需求 7：保留访问边界与既有会话操作

**用户故事：** 作为现有浏览器用户，我希望轨迹入口不会削弱本机访问控制或移除现有操作，以便继续管理 Goal。

#### 验收标准

1. <a id="req-7-1"></a> 当浏览器读取 Run、轨迹摘要、搜索结果或事件详情时，每次读取必须受既有能力令牌、精确 Host、同源和正式工作区边界保护；失效凭据必须显示重新打开正式浏览器入口的指引，不能回退为匿名读取。
2. <a id="req-7-2"></a> 当 Details 的主要内容替换为 Trajectory 时，Goal 信息和查看／撤销授权必须仍可从会话头部的独立入口访问，并继续使用原有授权操作约束。
3. <a id="req-7-3"></a> 当用户使用新轨迹视图时，Activity、Plan、普通消息发送和结构化交互必须保持现有行为；关闭浏览器或轨迹视图不得取消已受理的 Goal 执行。
4. <a id="req-7-4"></a> 如果没有已提交轨迹或搜索没有匹配记录，系统必须分别显示空轨迹和无匹配状态，并提供适用的刷新、继续加载或清除筛选操作；错误状态不得冒充空状态。
