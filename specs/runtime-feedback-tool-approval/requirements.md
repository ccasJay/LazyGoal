# Runtime 错误恢复与 Tool 授权审批需求

## 审批摘要

### 目标

让 LazyGoal 在可恢复错误后自动继续，同时让非 YOLO 模式下的用户决定具体 Tool 操作获准一次、在当前 Goal 会话内持续获准，或在当前项目内持续获准。

### 范围

- 包含：模型与可安全重放 Tool 的临时故障重试、模型输出和 Tool 输入纠错、现有 Action 审批的三档授权、授权查看与撤销、可恢复等待，以及浏览器和 TUI 的对应交互；所有行为纳入同一份 Spec。
- 不包含：改变 `read_file`、`grep` 的默认自动放行或现有 YOLO 自动批准语义；让授权绕过 Profile、Tool 输入校验或执行策略；自动重放结果不确定的 `manual` Tool；为浏览器增加 YOLO 开关。

### 核心行为

- 非 YOLO 模式下，需要审批的操作在执行前展示具体 Tool 和输入；单次授权只覆盖当前 Action，会话授权跨当前 Goal 的 Run，项目授权跨当前工作区的 Goal，后两者在恢复后仍有效，且可查看和撤销。持续授权只匹配相同操作或用户明确批准的有限范围；批准一条 `bash` 命令不会放行任意其他命令。
- 授权只能来自用户的有效审批，不能由模型、Tool 结果或 YOLO 自动批准生成。即使已有授权，每次新 Action 仍需通过当前 Profile、输入及执行策略检查；旧 Action 审批、项目错配或撤销后的授权不得放行后续操作。
- 网络、限流等临时模型故障由系统有限次重试；临时 Tool 故障只有在 Tool 可安全重放时由系统有限次重试。同一 Action 的安全重试沿用有效审批，不重复询问、不重复计 Step；取消立即停止后续尝试。
- 模型输出的解析、契约、可纠正语义、完成证据以及 Tool 选择或输入错误，必须转成有定位信息的反馈交给相应模型阶段重新生成；无效尝试不能成为有效决策或触发 Tool。已知 Tool 业务失败作为 Observation 交给模型，后续新 Action 仍需检查授权。
- 缺少用户资料、待审批或 Tool 结果不确定时等待用户；鉴权、配置、持久化损坏等不可纠正故障明确失败。自动尝试耗尽时保留每次原因并明确失败，不把无效原始输出当作最终回答。
- 恢复时保留已提交的 Think 与 Tool 结果；浏览器和 TUI 能区分自动重试、模型纠错、等待用户与最终失败。

### 风险与待确认

- 风险等级：high；理由：改变 Tool 权限及跨 Goal 持久授权、模型调用次数、外部副作用和中断恢复行为。
- 关键操作：当前阶段只编写需求，无需执行需另行确认的外部操作。
- 风险：过宽的持续授权可能放行未审阅输入；重试或恢复若丢失 Action 身份，可能重复执行有副作用的 Tool；模型纠错循环可能增加费用和延迟。Design 必须界定授权匹配、重试上限与恢复检查点，验证权限、取消及失败路径。
- 既有约束：仅在本需求定义的可纠正错误范围内，本 Spec 取代 [模型输出契约](../model-output-contracts/requirements.md) 与 [LLM 单步执行](../llm-step-executor/requirements.md) 中“无效输出不得修复重试”的限制；严格解析、授权和证据校验继续有效。普通的模型请求 Think 循环不因本功能新增次数预算。
- 待确认的需求决策：无。

## 引言

本功能将 Tool 审批与错误恢复纳入同一执行行为：先确认操作是否被当前权限允许，再根据故障性质选择系统重试、模型纠错、等待用户或明确失败；具体实现结构在 Design 阶段确定。

## 需求

### 需求 1：有限范围的 Tool 授权

**用户故事：** 作为项目使用者，我希望重复执行已批准的操作时不再反复确认，同时保留对不同操作的控制，以便自动纠错不会扩大授权。

#### 验收标准

1. <a id="req-1-1"></a> 当非 YOLO 模式下的 Action 需要审批且没有匹配的有效授权时，系统必须在执行 Tool 前等待用户；当前默认自动放行的 `read_file`、`grep` 仍无需首次审批。
2. <a id="req-1-2"></a> 当用户批准待执行 Action 时，系统必须允许选择仅当前 Action、当前 Goal 会话或当前项目三种期限；会话授权适用于该 Goal 的后续 Run，项目授权适用于同一工作区的后续 Goal，二者在进程恢复后仍须保持各自范围。
3. <a id="req-1-3"></a> 当后续 Action 请求使用持续授权时，系统必须只在 Tool 及规范化操作与已批准内容相同，或落入用户明确批准的有限范围内时放行；不同的 `bash` 命令不得因同一 Tool 的既有授权而自动放行。
4. <a id="req-1-4"></a> 当 Action 使用任何期限的授权时，系统仍必须重新执行当前 Profile 白名单、Tool 输入和执行策略检查；模型输出、Tool 结果及 YOLO 的自动批准都不得创建会话或项目授权。
5. <a id="req-1-5"></a> 当 Goal 或工作区身份与授权范围不匹配，或授权已被撤销时，系统必须将后续需审批的 Action 重新送入审批，不得跨项目沿用授权。

### 需求 2：可审阅、可撤销的审批

**用户故事：** 作为审批者，我希望在执行前看清本次操作和授权后果，并能撤销持续权限，以便知道哪些后续调用会自动执行。

#### 验收标准

1. <a id="req-2-1"></a> 当 Action 等待审批时，浏览器与 TUI 的非 YOLO 交互必须展示待执行 Tool、足以识别操作范围的输入及三种授权期限，并说明持续授权覆盖的后续操作。
2. <a id="req-2-2"></a> 当用户提交批准时，系统必须核对当前 Goal、Run 与 Action 身份，并在授权及该 Action 的批准可靠保存后才执行 Tool；过期、重复冲突或错配的审批不得授予权限或执行 Tool。
3. <a id="req-2-3"></a> 当用户拒绝 Action 时，系统不得执行 Tool 或产生授权，必须沿用可供模型判断后续方案的拒绝结果。
4. <a id="req-2-4"></a> 当用户查看当前会话或项目授权时，界面必须显示其 Tool、操作范围和期限；用户撤销授权后，后续 Action 必须立即按当前策略重新判定，已提交的 Tool 结果不得被撤销操作改写。

### 需求 3：临时故障的系统重试

**用户故事：** 作为 Goal 使用者，我希望短暂网络或服务故障自动恢复，以便无需为同一请求反复手动继续。

#### 验收标准

1. <a id="req-3-1"></a> 当模型请求遭遇可识别的限流、服务暂时不可用、连接或超时故障时，系统必须在有限尝试范围内自动重试，并遵守中止信号；鉴权、配置及请求协议错误不得归入此类。
2. <a id="req-3-2"></a> 当 Tool 遭遇可识别的临时故障时，系统只有在该 Tool 声明可安全重放且当前 Action 仍获准执行时才能自动重试；仅有失败结果标记可重试不得替代安全重放声明。
3. <a id="req-3-3"></a> 当同一已批准 Action 被安全重试时，系统必须沿用其 Action 身份和有效授权，不再次请求审批，也不得为重试重复增加 `stepCount`；结果不确定的 `manual` Tool 不得由系统自动重放。
4. <a id="req-3-4"></a> 当临时故障持续到尝试上限时，系统必须停止自动调用，保留各次失败原因并给出明确的最终失败；用户取消后不得继续发起尝试。

### 需求 4：模型可纠正错误的反馈

**用户故事：** 作为 Goal 使用者，我希望模型能根据准确的错误信息修正无效输出，以便可纠正问题不直接终止任务。

#### 验收标准

1. <a id="req-4-1"></a> 当模型输出无法解析、违反当前输出契约、包含可纠正的决策语义或完成证据错误，或选择、输入某个 Tool 的方式无效时，系统必须阻止该无效决策及其 Tool 副作用，并向对应阶段的模型提供可定位的错误码、问题位置和修复所需的有效约束。
2. <a id="req-4-2"></a> 当 Decide 需要纠错时，系统必须保留当前 Step 已提交的 Think 结果并重新请求 Decide；当 Think 输出违反其阶段契约时，系统必须保留原定 Think 目标并只重试该 Think。纠错反馈不得被当作新的真实用户消息或授权指令。
3. <a id="req-4-3"></a> 当模型收到纠错反馈后再次提交输出时，系统必须重新执行同一解析、授权与证据校验；仅有效结果可以推进 Step 或执行 Tool，不得因连续失败降级输出模式或放宽校验。
4. <a id="req-4-4"></a> 当模型纠错反复失败并达到有限尝试上限时，系统必须停止该纠错链，保留每次失败原因并明确标示最终失败；此上限不得替代正常 `request_think` 循环的既有规则。

### 需求 5：Tool 结果与人工等待的分流

**用户故事：** 作为 Goal 使用者，我希望已知的执行失败由模型尝试处理，而需要我判断的情况明确暂停，以便自动化不会猜测未知结果。

#### 验收标准

1. <a id="req-5-1"></a> 当 Tool 返回已知的业务失败结果时，系统必须将其作为 Observation 交给模型决定后续方案；模型发起新的 Action 时，仍须按当前授权范围检查，不能因先前 Action 获批就放行不同操作。
2. <a id="req-5-2"></a> 当模型纠正 Tool 选择或输入后发起新的 Action 时，系统必须再次验证 Tool 可用性、输入和授权；无效或未授权请求不得变成普通执行成功结果。
3. <a id="req-5-3"></a> 当继续执行需要缺失的用户资料、待审批的操作，或 `manual` Tool 的执行结果无法确认时，系统必须保存可恢复的等待状态，停止相关模型和 Tool 调用，直到收到匹配的用户交互。
4. <a id="req-5-4"></a> 当故障属于不可由模型纠正的鉴权、配置、持久化损坏或执行不变量问题时，系统必须明确失败，不得以模型纠错或自动重试掩盖该故障。

### 需求 6：恢复与执行计数一致

**用户故事：** 作为长期 Goal 的使用者，我希望审批和纠错在中断后仍按同一事实继续，以便不会重复执行或丢失权限边界。

#### 验收标准

1. <a id="req-6-1"></a> 当系统在审批、临时故障或模型纠错过程中中断并恢复时，必须依据已可靠提交的状态及尝试记录继续或明确失败；不得把未提交的授权、Think 输出、模型决策或 Tool 结果视为已生效。
2. <a id="req-6-2"></a> 当已有 Think 输出或 Tool Observation 已成功提交时，后续重试不得重新执行这些已完成阶段或 Tool Action；同一待执行 Action 的安全重放必须沿用其身份，结果不确定的 `manual` Action 保持人工等待。
3. <a id="req-6-3"></a> 当模型或 Tool 正在重试、纠错或等待审批时，系统不得为这些尝试重复增加 `stepCount`；仅有效决策及其已提交的执行结果按既有 Step 规则计数。
4. <a id="req-6-4"></a> 当会话授权或项目授权在重启后被读取时，系统必须验证其所属 Goal 或工作区、已批准操作范围及撤销状态；身份不明或记录损坏时不得自动放行 Tool。

### 需求 7：可理解的执行反馈

**用户故事：** 作为在浏览器或 TUI 中观察 Goal 的使用者，我希望知道系统正在自动处理错误还是等待我操作，以便及时提供必要输入并看懂最终结果。

#### 验收标准

1. <a id="req-7-1"></a> 当系统进行临时故障重试或模型纠错时，浏览器与 TUI 必须展示可区分的运行状态；等待审批、缺少用户资料和结果不确定时必须显示相应的人工等待原因。
2. <a id="req-7-2"></a> 当自动尝试耗尽或出现不可恢复故障时，浏览器与 TUI 必须显示可理解的最终原因，并允许查看与该故障相关的尝试记录；未通过校验的原始模型输出不得作为已完成回答展示。
3. <a id="req-7-3"></a> 当纠错最终成功时，界面必须以最终已提交的决策、Tool 结果和回复为准，不得将此前无效尝试混入已完成的步骤或最终回答。
