# Agent 完成判断与最终交付优化需求

## 审批摘要

用户已批准需求与设计，并明确请求实现完整方案。风险为 medium：每个完成候选通常新增一次模型调用，仍可能误放行或误拒绝。复用当前模型、输出模式、预算及 Decide 三次纠错机制，无待确认设计决策。任务范围不含并行 Agent、Goal 清理或 PTC 协议改造。

## 验收条件

### R1 完成门控

当普通 Run 或已批准 Plan Run 提交完成候选时，Runtime 应先执行现有协议、语义和证据引用校验，再独立审查实际交付与事实支持。未经接受，系统不得提交完成、最终回复或候选 Memory Patch。其他业务决策、Think 和上下文检查点应保持既有流程。审查不得替代授权、任务审批、引用校验或 Benchmark 环境评分。

### R2 审查职责与输入

系统应向当前 Decide 模型提供当前请求和相关约束、获批条件、完整候选及从当前 Run 提交边界解析的引用证据正文。审查应只返回接受或带非空具体缺口的拒绝，不执行工具、改写答案或泄漏内部分析。目录和规模统计、Think 和模型自述不得证明实现行为；有效的已提供源码可直接使用，简单请求允许简短答案。必要输入超预算时不得静默截断后放行。

### R3 纠错与恢复

当审查拒绝时，系统应提交有界 `origin: completion_review` 反馈并返回 Decide。协议错误与审查拒绝应共用现有三次纠错上限，传输失败应沿用请求重试。耗尽时应报告既有失败，不能绕过审查。取消、恢复和保存失败应保留最近提交边界；恢复复用已提交反馈，未完成审查允许重新生成候选并审查，无新增 Run 恢复字段。

### R4 最终交付

`summary` 应承载实际答案或成果说明，不能只描述“已完成分析”。Think 应保持内部分析职责，不能充当最终交付。接受后系统应原文保存和展示候选回复，不设置固定长度或章节门槛。

### R5 诊断与质量验证

审查调用应使用独立 callId 与 `completion_review` 输入记录标签，用量进入现有指标；审查文本和参数不得进入公开回复流、业务 Observation 或完成证据。相关公开接口须包含中文契约 TSDoc 和示例，当前架构说明同步更新，不新增开发数据兼容层。真实模型评测应固定正反场景并各重复三次，分别报告误放行、误拒绝、调用与令牌变化；未达标不得宣称修复完成。
