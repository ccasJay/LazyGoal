# Run 执行与持久化恢复职责拆分需求

## 引言

拆分 Run 执行、检查点提交与恢复的职责，同时保持现有 Goal/Run 生命周期、用户交互和跨进程恢复行为；新增可识别临时提交故障的安全重试。不包含 Steer、Queue、InstantInterrupt 或用户主动终止 Run 等新交互机制。

## 需求

### 需求 1：保持现有 Run 行为

**用户故事：** 作为 Runtime 调用方，我希望职责拆分后仍能按原有方式推进 Run，以便现有客户端和评测入口继续得到一致的结果。

#### 验收标准

1. <a id="req-1-1"></a> 当现有入口启动或推进普通 Run、Plan Run 时，系统必须保持既有状态转换、Step 计数、消息、审批和终态结果。
2. <a id="req-1-2"></a> 当 Run 进入用户交互、任务审批或 Action 审批等待点时，系统必须保持原有停止与恢复规则，不得因职责拆分创建额外 Run 或越过审批。
3. <a id="req-1-3"></a> 当客户端读取已提交的 Goal、Run 与 Trajectory 时，系统必须继续返回与现有提交边界一致的状态和事实。

### 需求 2：保持已提交边界的恢复语义

**用户故事：** 作为运行长任务的用户，我希望进程重启后继续原 Run 的已提交进度，以便不会丢失工作或误判工具结果。

#### 验收标准

1. <a id="req-2-1"></a> 当进程在 Run 未终结时退出并重新启动，系统必须从最近成功提交的 Goal 快照恢复同一 Run，不得将未提交的 Trajectory 尾部当作已完成进度。
2. <a id="req-2-2"></a> 当恢复点包含待处理 Action 时，系统必须保留现有安全重放与结果未知时人工确认的规则，不得重复执行已确认完成的 Action。
3. <a id="req-2-3"></a> 当进程关闭或调用级取消停止当前执行时，系统不得仅因该停止而将 Run 持久化为取消终态；再次启动时仍以已提交快照决定后续执行。
4. <a id="req-2-4"></a> 当仅执行恢复读取时，系统不得自动推进 Run、调用模型或工具，或改写恢复出的快照。

### 需求 3：安全重试临时提交故障

**用户故事：** 作为运行长任务的用户，我希望临时存储故障可以自动恢复，以便短暂写入失败不会立即中断 Run，也不会造成重复执行或错误恢复。

#### 验收标准

1. <a id="req-3-1"></a> 当事实、快照或提交标记写入遇到可识别的临时性存储故障时，系统必须进行有界重试；成功后才继续当前 Run 的后续执行。
2. <a id="req-3-2"></a> 当重试发生在部分提交成功之后，系统不得重复已提交事实、Step 或工具效果，也不得把未提交内容作为恢复依据。
3. <a id="req-3-3"></a> 当所需检查点尚未成功提交时，系统不得开始依赖该检查点的模型或工具调用；已发生的外部效果不得被报告为已回滚。
4. <a id="req-3-4"></a> 当临时故障的重试次数耗尽时，系统必须向调用方明确报告失败并停止当前推进；最近一次成功提交的快照仍是恢复依据。
5. <a id="req-3-5"></a> 当失败属于协议校验、数据损坏或其他确定性错误时，系统必须直接报告错误，不得把该错误作为临时故障重试。

## 风险与待确认

- 风险等级：high；理由：改动覆盖 Runtime 的执行与恢复路径，提交重试跨越事实、快照和标记写入，错误处理可能导致重复外部效果或错误恢复。
- 关键操作：无；本 Spec 不要求删除数据、迁移旧快照或执行其他不可逆维护操作。
- 已知风险：部分提交成功后重试必须识别已完成阶段；存储故障分类不准确可能导致无效重试或过早失败；现有存储不提供跨进程租约或 exactly-once 外部效果保证。
- 待确认：无。
