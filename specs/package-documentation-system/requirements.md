# 包内文档与语义表重构需求

## 引言

将 LazyGoal 的当前说明文档改为由所属包或独立模块就地维护，说明正文与该模块的语义表统一放入其 `notes/`，`README.md` 除外；读者通过各模块的语义表查找概念、归属与权威说明，并同步项目级文档规则和相关 Skills。范围覆盖核心包、应用、Benchmark 和 GEPA。现有 `specs/` 与 `project-memory/` 的内容、状态和引用保持原样，本次仅新增本功能的 Spec。

## 需求

### 需求 1：模块就地维护权威说明

**用户故事：** 作为项目开发者，我希望在所属模块内找到其当前说明，以便阅读代码时理解该模块，并随代码变化维护文档。

#### 验收标准

1. <a id="req-1-1"></a> 当读者查看核心包、应用、Benchmark 或 GEPA 等独立模块时，必须能够从该模块目录内找到其说明入口。
2. <a id="req-1-2"></a> 当读者阅读模块说明时，必须能够了解其职责、使用方式与当前限制；行为说明必须以当前实现为依据。
3. <a id="req-1-3"></a> 当多个模块涉及同一主题时，详细说明必须由负责该主题的模块维护，其他模块通过引用访问，不维护相互竞争的正文副本。

### 需求 2：说明正文统一归入模块内 notes/

**用户故事：** 作为文档维护者，我希望说明文档遵循一致的位置规则，以便直接判断文档归属和新增文档的位置。

#### 验收标准

1. <a id="req-2-1"></a> 当创建或迁移模块说明文档时，除 `README.md` 外，文档必须位于所属包或模块的 `notes/` 下。
2. <a id="req-2-2"></a> 当模块保留 `README.md` 时，该文件可以位于模块根目录，并必须能够引导读者找到该模块的说明正文。
3. <a id="req-2-3"></a> 当需要查询详细 API 契约时，模块说明必须指向源码中的权威契约，不通过本次重构将源码契约整体复制为另一份维护来源。

### 需求 3：各模块就地维护语义表

**用户故事：** 作为项目读者，我希望从各包或模块的语义表查找相关概念的含义、归属和说明入口，以便在阅读该模块时理解其语义与跨模块关系。

#### 验收标准

1. <a id="req-3-1"></a> 当读者查看任一纳入范围的包或独立模块时，必须能够从该模块的说明入口访问其在 `notes/` 内维护的语义表。
2. <a id="req-3-2"></a> 当语义表收录某个概念时，必须提供简明含义、负责的包或模块，以及可访问的权威说明入口。
3. <a id="req-3-3"></a> 当概念含义、归属或权威说明位置发生变化时，引用该概念的相关模块语义表必须同步更新；字段细节、状态转换和完整行为契约仍由所属模块或源码维护。

### 需求 4：迁移当前说明并移除旧入口

**用户故事：** 作为项目维护者，我希望迁移后只有新的说明体系承载当前文档，以便避免继续维护旧目录与新目录两套入口。

#### 验收标准

1. <a id="req-4-1"></a> 当现有架构说明迁移完成时，仍然适用的职责、所有权、数据流、生命周期、恢复语义和限制必须能够在所属模块的说明文档与语义表中找到。
2. <a id="req-4-2"></a> 当旧架构文档被新说明替代时，旧文档入口必须移除，不保留迁移提示页、跳转页或重复正文。
3. <a id="req-4-3"></a> 当读者使用迁移后的当前文档、README 和语义表时，其中的文档引用必须指向有效的新位置；现有 Specs 与 Memory 中的历史引用不属于此次修复范围。

### 需求 5：保护现有 Specs 与项目 Memory

**用户故事：** 作为项目负责人，我希望此次重构不改写历史 Spec 和项目 Memory，以便单独安排它们的后续维护。

#### 验收标准

1. <a id="req-5-1"></a> 当本功能被设计或实施时，本功能开始前已有的 `specs/` 文件必须保持内容、路径和任务状态不变；本功能的新 Spec 允许新增和维护。
2. <a id="req-5-2"></a> 当文档迁移、链接维护或验证发现 Memory 问题时，必须保持现有 `project-memory/` 文件及其内容、元数据、状态和生成索引不变，不顺带修复已知问题。
3. <a id="req-5-3"></a> 如果删除旧文档入口使现有 Specs 或 Memory 中的引用失效，必须将其作为已接受的迁移限制记录，不以修复这些历史引用为由扩大修改范围。

### 需求 6：同步项目文档 Skills 与规则

**用户故事：** 作为使用编码 Agent 的开发者，我希望项目文档 Skills 与新说明体系一致，以便后续新增、审查和更新文档时遵循同一规则。

#### 验收标准

1. <a id="req-6-1"></a> 当文档体系切换完成时，项目级 `lg-doc-standards`、`lg-prose-standard` 以及其他直接依赖旧文档归属规则的相关 Skills 必须与新体系一致。
2. <a id="req-6-2"></a> 当 Agent 根据相关 Skill 创建、审查或更新模块说明时，必须能够确定所属模块、`notes/` 位置、README 例外，以及语义表的包内归属和用途，不再要求以旧架构目录为当前说明来源。
3. <a id="req-6-3"></a> 当更新项目级文档约定时，`AGENTS.md`、`CLAUDE.md` 中与文档归属、导航和同步维护直接相关的规则必须同步更新，并保留现有 Specs 与 Memory 的范围边界。

## 风险与待确认

- 风险等级：medium。重构跨多个模块并影响文档导航与 Agent 的维护规则；改动可通过 Git 恢复，不改变产品接口或运行行为。
- 关键操作：迁移当前说明后移除旧架构文档入口。用户已确认采用直接移除的方案；本次请求仅设计 Spec，实施需另行授权。
- 已接受限制：现有 Specs 与 Memory 不修改，因此其中指向被删除文档的历史引用会失效。不会把这些历史链接纳入当前文档必须有效的验收范围。
- 已知风险：现有文档存在空文件、失效引用和行为漂移。迁移时必须核对当前源码，不能将旧说明直接视为已验证事实；现有 Memory 检查失败不通过本次重构修复。
- 待确认：无需求层面的未决事项。具体文档拆分、包内语义表的文件组织、迁移映射和验证方式在需求批准后的 Design 阶段确定。
