# 执行控制协议拆包需求

## 引言

将现有跨层执行控制协议移出 Runtime，消除 `@lazygoal/llm` 对 `@lazygoal/runtime` 的源码依赖，同时保持取消、模型请求重试和模型输出纠错的既有行为。本 Spec 不实现 Subagent 或新增执行能力。

## 需求

### 需求 1：消除模型适配层的反向依赖

**用户故事：** 作为维护者，我希望模型适配层使用独立的共享执行控制协议，以便 Runtime 与模型适配层保持清晰的依赖方向。

#### 验收标准

1. <a id="req-1-1"></a> 拆包完成后，`@lazygoal/llm` 的生产源码不得导入 `@lazygoal/runtime`。
2. <a id="req-1-2"></a> 当模型适配层再次导入 Runtime 源码时，依赖边界检查必须失败。
3. <a id="req-1-3"></a> 现有调用方必须能够共享同一套取消协议和暂时性模型请求故障类型，不得因拆包出现相互不兼容的重复定义。

### 需求 2：保持执行中止行为

**用户故事：** 作为运行中的 Goal 的使用者，我希望取消在各执行层保持一致，以便中止后不会继续调用或被误记为业务失败。

#### 验收标准

1. <a id="req-2-1"></a> 当模型、Agent、Tool 或 Runner 收到已中止的执行信号时，调用链必须继续识别并传播执行中止，停止后续相关调用。
2. <a id="req-2-2"></a> 当执行中止发生时，系统必须保持现有的 Goal 快照、Run 终态与退出语义，不得把中止转换为新的业务失败。

### 需求 3：保持模型故障处理边界

**用户故事：** 作为 Goal 的使用者，我希望拆包不改变模型请求失败时的处理方式，以便可恢复故障得到有限重试，其他错误仍按既有规则处理。

#### 验收标准

1. <a id="req-3-1"></a> 当适配器识别限流、暂时性服务故障、连接故障或超时时，Runner 必须保持现有的调用上限、退避、失败记录与中止响应；不得将 Provider 原始异常发给模型。
2. <a id="req-3-2"></a> 当模型响应的解析或决策校验失败且符合既有纠错条件时，Runtime 必须保持提交有界结构化反馈后重新调用模型的流程，且反馈不得包含原始模型输出。
3. <a id="req-3-3"></a> 当发生鉴权、配置、存储或未知请求错误时，系统不得因本次拆包赋予其自动重试资格，也不得将原始异常发送给模型。

## 风险与待确认

- 风险等级：medium；理由：跨包公开协议与依赖方向发生变化，影响多个现有调用方，但不改变持久化格式或预期运行行为。
- 关键操作：无。
- 已知风险：若迁移后存在两个运行时错误类定义，基于错误身份的中止或重试判断可能失效；跨包导入调整也可能遗漏非生产入口。
- 待确认：无；本次范围和错误处理规则已在需求收集中确认。
