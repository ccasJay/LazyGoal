# ALFWorld TextWorld 评测接入需求

## 引言

本 Spec 为 LazyGoal 增加可重复、可选启用的 ALFWorld TextWorld 端到端评测。评测使用独立 Conda 环境运行 ALFWorld，通过专用环境 Tool 驱动任务并收集机器可读结果；本 Spec 不覆盖 THOR 视觉环境、跨进程环境恢复或生产运行时对 ALFWorld 的强制依赖。

## 需求

### 需求 1：独立评测环境可准备

**用户故事：** 作为评测维护者，我希望用独立的 Conda 环境准备 ALFWorld，以便评测依赖不会污染 LazyGoal 的 Node/TypeScript 运行时。

#### 验收标准

1. <a id="req-1-1"></a> 当评测环境初始化时，系统必须使用项目声明的 Conda 环境准备 Python、ALFWorld 及其 TextWorld 依赖。
2. <a id="req-1-2"></a> 当目标平台需要指定 Python 包架构时，环境准备说明必须提供可执行的架构选择方式，并明确 TextWorld 与视觉环境的范围差异。
3. <a id="req-1-3"></a> 当 ALFWorld 数据尚未准备或数据路径不可用时，初始化必须报告可识别的配置错误，不得开始模型评测。
4. <a id="req-1-4"></a> 当普通 LazyGoal 测试未显式启用 ALFWorld 评测时，测试运行不得创建或要求该 Conda 环境。

### 需求 2：TextWorld 任务生命周期可驱动

**用户故事：** 作为评测运行器，我希望创建、推进和关闭一个 TextWorld 任务会话，以便每个 LazyGoal Goal 都能对应一个可控的环境实例。

#### 验收标准

1. <a id="req-2-1"></a> 当评测开始一个任务时，系统必须返回初始观察、任务标识和当前可用命令集合。
2. <a id="req-2-2"></a> 当 Agent 请求执行一个环境命令时，系统必须只推进一次环境步，并返回新的观察、任务是否结束、任务是否成功和目标完成率。
3. <a id="req-2-3"></a> 当任务结束、评测中止或评测发生错误时，系统必须释放该任务会话，且不得继续接受该会话的环境步请求。
4. <a id="req-2-4"></a> 当同一任务会话收到并发或重复的未完成步请求时，系统必须拒绝其中的冲突请求，不得隐式推进多步。

### 需求 3：Agent 只能通过专用环境 Tool 交互

**用户故事：** 作为 Agent 评测维护者，我希望模型通过明确的 ALFWorld Tool 与环境交互，以便评测结果反映 AgentDecision 和 Action/Observation 协议，而不是 Bash 脚本行为。

#### 验收标准

1. <a id="req-3-1"></a> 当 ALFWorld 评测 Profile 生效时，模型必须只能看到经授权的 ALFWorld 环境 Tool，且这些 Tool 必须支持初始化、单步推进和关闭任务会话。
2. <a id="req-3-2"></a> 当模型请求环境步时，系统必须将请求中的一条文本命令传给环境，并把环境返回的观察作为唯一可信结果交给下一轮 Agent 决策。
3. <a id="req-3-3"></a> 当 ALFWorld 专用 Tool 已授权且能表达当前环境操作时，评测流程不得要求模型使用通用 Bash 代替该 Tool。
4. <a id="req-3-4"></a> 当模型声明完成但环境尚未报告任务成功时，评测结果必须保留为未成功，不能仅依据模型的 `complete` 判定成功。

### 需求 4：任务集合和运行配置可复现

**用户故事：** 作为回归测试维护者，我希望明确固定本次评测使用的任务和运行配置，以便不同提交之间可以比较结果。

#### 验收标准

1. <a id="req-4-1"></a> 当运行固定任务集评测时，系统必须按照任务清单确定数据切分、任务顺序和任务数量，不得在测试过程中无提示地替换任务。
2. <a id="req-4-2"></a> 当评测使用随机种子、环境配置或 Prompt/Profile 配置时，系统必须在结果中记录这些配置的可追溯标识。
3. <a id="req-4-3"></a> 当同一任务因环境错误需要重试时，系统必须区分原始尝试与重试结果，不得覆盖原始失败记录。

### 需求 5：评测结果可验证并可机器读取

**用户故事：** 作为项目维护者，我希望评测输出包含足够的环境事实和汇总指标，以便在 CI 或本地比较 Agent 表现。

#### 验收标准

1. <a id="req-5-1"></a> 当一个任务完成或失败时，系统必须记录任务标识、最终 `won`、结束状态、步数、目标完成率和失败类别（如有）。
2. <a id="req-5-2"></a> 当一组任务评测结束时，系统必须输出总任务数、成功数、成功率、平均步数以及按类别汇总的失败数量。
3. <a id="req-5-3"></a> 当调用方配置成功率或其他回归阈值时，系统必须在未达到阈值时以非零结果结束，并保留完整机器可读报告。
4. <a id="req-5-4"></a> 当评测输出包含环境观察或模型文本时，系统必须保证报告格式仍可被机器解析，且单个异常任务不得破坏整份报告的结构。

### 需求 6：环境和协议故障具有稳定语义

**用户故事：** 作为测试维护者，我希望区分环境不可用、命令非法、超时和协议错误，以便快速定位失败来源。

#### 验收标准

1. <a id="req-6-1"></a> 当 Python、ALFWorld 数据或环境连接无法启动时，评测必须报告环境初始化失败，并且不得伪装成 Agent 任务失败。
2. <a id="req-6-2"></a> 当环境拒绝 Agent 命令时，系统必须返回可识别的领域失败结果，并允许后续 Agent 决策使用该观察继续或终止任务。
3. <a id="req-6-3"></a> 当环境调用超时、环境连接意外中断或响应无法解析时，系统必须终止当前任务会话并报告基础设施错误。
4. <a id="req-6-4"></a> 当评测中止发生时，系统必须停止后续环境调用并完成会话清理，不得写入虚假的成功 Observation。

### 需求 7：现有 LazyGoal 行为保持兼容

**用户故事：** 作为 LazyGoal 维护者，我希望新增 ALFWorld 评测只影响显式评测入口，以便现有 Goal、Tool、Snapshot 和测试流程保持稳定。

#### 验收标准

1. <a id="req-7-1"></a> 当普通 LazyGoal CLI 或现有测试运行时，系统必须保持原有 Tool Registry、Profile 授权和 Runner 行为，不自动加载 ALFWorld。
2. <a id="req-7-2"></a> 当 ALFWorld 评测结束时，系统不得修改现有 Goal Snapshot、AgentDecision、Action/Observation 或 replay 协议的结构。
3. <a id="req-7-3"></a> 当现有测试套件在未安装 ALFWorld 的机器上运行时，除显式启用的 ALFWorld 测试外，其余测试必须继续执行并保持原有结果。
