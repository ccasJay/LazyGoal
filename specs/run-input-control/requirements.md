# Run 输入与主动终止需求

## 引言

以已获批的 [Run 执行与持久化恢复职责拆分 Spec](../run-execution-persistence-separation/requirements.md) 为前置依赖，为同一 Goal 提供 Steer、Queue 和 Interrupt：Steer 调整当前 Run 的后续执行，Queue 在当前页面保存后续 Run 的输入，Interrupt 主动终止当前 Run。本 Spec 包含 Web 交互，不包含 Steer 抢占当前模型调用的 InstantInterrupt。

## 需求

### 需求 1：运行中调整当前任务

**用户故事：** 作为运行任务的用户，我希望通过 Steer 补充或修正要求，以便当前 Run 的后续执行反映我的新意图。

#### 验收标准

1. <a id="req-1-1"></a> 当 Run 正在执行且用户提交 Steer 时，系统必须将受理的消息用于同一 Run，不得因此创建新 Run。
2. <a id="req-1-2"></a> 当当前 Run 即将发起下一次模型调用时，系统必须先将此前受理且尚未生效的 Steer 消息按接收顺序纳入该调用的用户消息。
3. <a id="req-1-3"></a> 当系统受理 Steer 时，系统不得仅为使该消息提前生效而中止当前模型调用或正在执行的工具；正在执行的工具结束后，消息仍须在下一次模型调用前生效。

### 需求 2：可靠受理与恢复 Steer

**用户故事：** 作为运行长任务的用户，我希望已受理的修正不会因重启或完成竞态而丢失，以便明确知道哪些要求会由当前 Run 处理。

#### 验收标准

1. <a id="req-2-1"></a> 当系统向用户确认 Steer 已受理后，后端重启不得丢失该消息；恢复原 Run 时必须保留其接收顺序。
2. <a id="req-2-2"></a> 当消息受理或恢复发生重试时，系统不得重复注入同一条已受理的 Steer。
3. <a id="req-2-3"></a> 当 Steer 提交与 Run 完成同时发生时，系统必须明确报告受理结果；受理成功的消息必须由原 Run 处理，不得在其尚未被处理时将该 Run 正常完成。
4. <a id="req-2-4"></a> 当 Steer 未被受理时，界面必须保留该输入供用户重新发送，不得静默丢弃或自动改为下一 Run 的输入。

### 需求 3：排队执行后续任务

**用户故事：** 作为需要连续执行多个任务的用户，我希望通过 Queue 暂存后续输入，以便当前任务完成后依次执行。

#### 验收标准

1. <a id="req-3-1"></a> 当用户选择 Queue 时，界面必须将该消息加入当前页面的队列，不得将其作为 Steer 注入当前 Run。
2. <a id="req-3-2"></a> 当当前 Run 正常完成且队列未暂停时，系统必须在同一 Goal 中按入队顺序，为每条排队消息分别创建并执行一个新 Run。
3. <a id="req-3-3"></a> 当同一条消息的提交发生重试时，系统不得因此重复入队或创建额外 Run。
4. <a id="req-3-4"></a> 当页面刷新或关闭时，未执行的 Queue 消息可以丢失；系统不承诺在后端重启或页面重建后恢复队列。

### 需求 4：在等待和异常结束时控制队列

**用户故事：** 作为管理连续任务的用户，我希望当前任务遇到等待、失败或主动终止时队列停止推进，以便先处理当前情况再决定是否继续。

#### 验收标准

1. <a id="req-4-1"></a> 当当前 Run 等待审批或用户回答时，系统不得取出 Queue 消息并启动后续 Run。
2. <a id="req-4-2"></a> 当当前 Run 失败或被手动终止时，界面必须暂停 Queue 自动执行，并保留当前页面中的剩余消息。
3. <a id="req-4-3"></a> 当 Queue 已因失败或主动终止暂停后，系统必须等待用户明确继续，才可启动下一条排队消息。

### 需求 5：主动终止当前 Run

**用户故事：** 作为运行任务的用户，我希望通过工作按钮主动终止当前 Run，以便停止后续执行并在需要时开始新任务。

#### 验收标准

1. <a id="req-5-1"></a> 当用户点击运行中的工作按钮以终止 Run 时，界面必须立即显示正在停止，系统必须停止原任务的正常推进；后续调用仅允许用于需求 6 定义的自动收尾。
2. <a id="req-5-2"></a> 当系统处理 Interrupt 时，系统必须中止当前模型调用，并请求正在执行的工具停止；该操作仅作用于目标 Run，后端服务必须继续运行。
3. <a id="req-5-3"></a> 当当前执行资源停止，且必要的自动核查和纠错完成或达到上限后，系统必须将该 Run 结算为 cancelled，保留 Goal、已提交消息、轨迹与工作结果，不得声称已发生的效果被回滚。
4. <a id="req-5-4"></a> 当 Run 已进入 cancelled 终态后，用户必须能够在同一 Goal 中提交新消息并启动新 Run。

### 需求 6：自动处理终止时未知的工具结果

**用户故事：** 作为需要保护已有工作结果的用户，我希望终止时出现的未知工具结果由当前 Run 自动核查和纠错，以便结束任务时保留真实结果并避免直接重复操作。

#### 验收标准

1. <a id="req-6-1"></a> 当 Interrupt 发生且工具可能已写入文件或产生其他效果，但结果无法确认时，系统必须将带有结果未知标识的中断错误写入轨迹，保留操作身份，并交给同一 Run 的模型自动核查和纠错，不以用户核查确认作为收尾前提。
2. <a id="req-6-2"></a> 当自动核查和纠错需要工具调用时，系统必须仅允许确认或修复被中断操作结果所需的调用，沿用现有授权、审批与沙箱规则，不得恢复原任务的正常推进。
3. <a id="req-6-3"></a> 当系统处理未知工具结果时，系统不得仅因结果未知而直接重复原操作，也不得将未知效果报告为确定成功、确定失败或已回滚。
4. <a id="req-6-4"></a> 当自动核查和纠错完成或达到有界次数上限时，系统必须保留真实的错误、核查、修复与尚未解决的未知结果记录，并结算为 cancelled；耗尽后不得继续自动纠错或转为必须人工确认的等待。

### 需求 7：恢复已受理的终止意图

**用户故事：** 作为运行长任务的用户，我希望已受理的终止请求在后端重启后仍生效，以便任务不会因重启重新开始执行。

#### 验收标准

1. <a id="req-7-1"></a> 当系统确认 Interrupt 已受理后，后端重启不得丢失该终止请求。
2. <a id="req-7-2"></a> 当恢复带有已受理终止请求的 Run 时，系统必须仅继续需求 6 定义的有限自动收尾与取消结算，不得重新推进原任务。
3. <a id="req-7-3"></a> 当普通服务关闭或调用级中止停止当前执行时，系统不得将其视为用户 Interrupt；后续仍须按基础 Spec 的已提交快照恢复规则处理。

### 需求 8：在原按钮位置选择发送或终止

**用户故事：** 作为 Web 用户，我希望根据输入内容在原按钮位置选择调整、排队或终止，以便在运行期间直接控制当前任务。

#### 验收标准

1. <a id="req-8-1"></a> 当 Run 正在执行时，消息输入框必须保持可编辑，允许用户准备 Steer 或 Queue 输入。
2. <a id="req-8-2"></a> 当输入为空时，原发送按钮位置必须显示带旋转动画的工作按钮；再次点击该按钮必须请求终止当前 Run。
3. <a id="req-8-3"></a> 当输入非空且用户发起发送时，原按钮位置必须展示 Steer、Queue 两个选项，用户选择后才按对应方式提交；同一位置随输入切换，不新增独立终止按钮。
4. <a id="req-8-4"></a> 当存在尚待生效的 Steer 或 Queue 消息时，界面必须展示其所属发送方式和顺序，使用户能够区分调整当前 Run 的消息与后续任务。

## 风险与待确认

- 风险等级：high；理由：运行中输入和主动终止跨越模型调用、工具效果、检查点提交与重启恢复，受理或结算顺序错误可能丢失用户要求、重复执行或误判外部效果。
- 关键操作：无；本 Spec 不要求删除现有 Goal、迁移旧快照或修改权限。
- 已知风险：Steer 与完成提交存在竞态；中止工具不保证已产生效果被回滚，自动核查和修复可能产生额外工具效果，必须受收尾范围、次数上限及现有授权约束；自动收尾后结果仍可能未知，此事实必须保留；Queue 只保存在当前页面，刷新或关闭可能丢失剩余消息；基础 Spec 的职责拆分是前置依赖，不能将其拟议结构视为当前实现。
- 待确认：无；本 Spec 范围为 Steer、Queue、Interrupt，InstantInterrupt 留待后续。
