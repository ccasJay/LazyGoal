# Prompt Cache Alignment 需求

## 引言

本特性基于“Goal-stable → Epoch-stable → Step-dynamic”三层上下文拓扑重构向大语言模型发送决策请求时的消息布局与编码方式，将长生命周期的任务契约与 Epoch 边界基线固定为逐字节严格不变的确定性前缀，并将微观水位监控下沉至运行时，使尾部控制消息收敛为纯动态推进增量。在保持纯函数无状态与完全可恢复的前提下，透明对齐现代大语言模型供应商的前缀缓存（Prefix Caching）机制，大幅降低交互冗余、Token 消耗与首字推理延迟。

## 需求

### 需求 1：三层上下文拓扑与严格前缀有序性

**用户故事：** 作为上下文组装与缓存对齐引擎，我希望请求消息严格按照生命周期稳定性自顶向下组织，以便最大化命中大语言模型供应商的最长公共前缀缓存。

#### 验收标准

1. <a id="req-1-1"></a> 当系统生成任意阶段的模型决策请求时，消息拓扑必须严格遵循自顶向下的三层物理顺序：`Goal-stable` 根前缀、`Epoch-stable` 中间前缀、`Step-dynamic` 尾部增量。
2. <a id="req-1-2"></a> 当下层动态内容发生变化时，系统必须保证上层稳定前缀的序列化文本在字节级别完全不变，不得产生前向字节污染。

### 需求 2：Goal-stable 根前缀的确定性固化

**用户故事：** 作为长任务运行系统，我希望在整个 Goal 执行生命周期内共享完全不变的任务基线，以便跨 Epoch 仍能复用最高层级的前缀缓存。

#### 验收标准

1. <a id="req-2-1"></a> 当 Goal 处于 Executing 阶段推进时，系统组装的 `Goal-stable` 前缀必须包含 Global Overview、当前 Agent Profile（系统提示与指令）、已授权 Tool 定义的完整 JSON Schema，以及经过审批的 GoalTask（Objective 与 Completion Criteria）。
2. <a id="req-2-2"></a> 当任务进入 Executing 阶段后，系统不得在后续任何下层消息中重复全量序列化已在 `Goal-stable` 中声明的任务目标与完成标准。
3. <a id="req-2-3"></a> 在同一个 Goal 的生命周期内，只要未发生用户显式干预或重新协商，`Goal-stable` 前缀必须保持 100% 逐字相同。

### 需求 3：Epoch-stable 中间前缀的生命周期锁定

**用户故事：** 作为长上下文管理者，我希望单个 Context Epoch 内部的几十步连续执行共享稳定的 Epoch 前缀，以便在 Epoch 窗口期内实现逼近 100% 的缓存命中率。

#### 验收标准

1. <a id="req-3-1"></a> 当系统处于同一个 Context Epoch 推进执行时，`Epoch-stable` 前缀必须仅包含该 Epoch 的静态标识（`epochNumber`、`openedAtSequence`）以及当前 Epoch 固定的对话历史基线（`view.conversation`）。
2. <a id="req-3-2"></a> 系统必须将动态波动的微观 Token 计数（`inputTokens`、`remainingTokens`）彻底从 `Epoch-stable` 前缀中剥离，保留在 Runtime 本地状态机内部，不得作为前缀字段输出给模型。
3. <a id="req-3-3"></a> 在同一个 Epoch 持续的全部步骤推进中，`Epoch-stable` 前缀的序列化文本必须保持完全一致；当且仅当发生 Epoch 边界关闭并开启新 Epoch 时，该前缀才允许更新一次。

### 需求 4：Step-dynamic 尾部控制消息的纯增量收敛

**用户故事：** 作为系统维护者与使用者，我希望每轮决策请求的尾部控制消息仅包含当前步骤真正演进的状态增量，以便减少单次请求的数据传输体积与上下文干扰。

#### 验收标准

1. <a id="req-4-1"></a> 当系统生成每轮 Executing 控制消息时，该消息必须仅包含步骤计数（`stepCount`）、上一轮执行结果（`previousStep`，包含最新环境 Observation 与候选动作集）、Hot 轨迹热窗口以及当前即时 Memory 状态。
2. <a id="req-4-2"></a> 当 Runtime 判定当前 Token 预算达到检查点警戒线时，系统必须在尾部动态消息中以离散控制信号呈现 `checkpoint_required`，在未达警戒线时不得携带波动的水位数值。
3. <a id="req-4-3"></a> 当本轮不需要更新 Working Memory 时，控制消息中不得携带未使用的空结构或非法占位字段。

### 需求 5：保持无状态纯函数与任意快照断点恢复

**用户故事：** 作为任务恢复与调试者，我希望三层请求优化不依赖任何连接级会话状态，以便系统能从任意已保存的 Snapshot 无缝恢复执行。

#### 验收标准

1. <a id="req-5-1"></a> 当系统从已持久化的 Goal Snapshot 恢复执行时，系统组装的首次决策请求必须仅基于当前 Snapshot 与 Trajectory 提交边界生成，不得依赖任何外部服务端会话缓存或连接状态。
2. <a id="req-5-2"></a> 当模型供应商不支持或未命中前缀缓存时，系统发送的完整三层消息列表必须依然包含模型做出正确决策所需的全部上下文，任务推进行为与决策判定必须保持完全一致。
3. <a id="req-5-3"></a> 如果系统执行过程中发生进程重启或网络重试，重新生成的模型请求必须与中断前同一步骤生成的请求内容完全幂等。

### 需求 6：严格保持 AgentDecision 协议与证据闭环

**用户故事：** 作为安全与执行审计者，我希望三层结构重组不改变决策验证与完成验收的标准，以便维持系统事实安全边界。

#### 验收标准

1. <a id="req-6-1"></a> 当模型基于三层结构上下文返回决策时，系统必须继续按现有严格的结构化 AgentDecision 协议（tool_call、complete、wait、fail、context_lookup）进行校验，拒绝非法或漂移的响应。
2. <a id="req-6-2"></a> 当模型提交 complete 完成决策时，系统必须继续强制校验其引用的已提交观察证据序列号，不得因任务元数据提升至 Goal-stable 前缀而放宽完成标准。
