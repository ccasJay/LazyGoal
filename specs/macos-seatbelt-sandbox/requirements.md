# macOS Seatbelt 项目沙箱需求

## 审批摘要

### 目标

让 macOS 上的日常 Goal 命令在项目范围内自主执行。模型需要访问网络或项目外文件时，可以提出明确请求；命令只能在统一 Permission 已核准实际能力后越过默认边界。

### 范围

- 包含：独立的 `@lazygoal/sandbox` package、现有文件工具路径边界的迁入、macOS Seatbelt 命令沙箱、网络与项目外文件的实际能力范围、受限启动和失败反馈。
- 不包含：Tool／Sandbox 授权账本、审批与撤销 UI、项目执行模式管理、首版 Linux／Windows 沙箱后端、Benchmark 容器运行时改造，以及独立 `web_fetch` Tool 的网络实现变更；授权与 UI 由 [Permission Spec](../permission/requirements.md) 负责。

### 核心行为

- macOS 上，符合 Tool Profile 与输入策略、且未请求额外能力的 `bash` Action 无需逐次 Tool 审批，直接在 Seatbelt 内执行。`bash` 及其子进程默认仅能读写当前项目，并读取运行所必需的系统工具及依赖；默认不能联网。文件工具继续拒绝越界路径，并与命令使用一致的项目身份。
- 模型可以为具体命令提出联网目标或项目外路径，但请求本身不授予能力。Sandbox 必须给出可强制的实际范围，且仅按 Permission 核准的范围受限启动；普通 Tool 授权与 YOLO 不能扩大该范围。首版联网放行仅支持明确展示的任意目标出站能力，包含本机回环。
- 子进程不得继承 LazyGoal 的模型凭据；LazyGoal 内部状态不可开放，项目 Git 元数据的写入须另有针对该目标的有效批准。重启后不得信任旧的内存执行计划，结果不确定的命令不能自动重放。
- macOS 上 Seatbelt 不可用或启动失败时，该命令明确失败，不能改为无沙箱执行。Linux／Windows 首版维持现有命令执行行为，但必须准确报告未启用 Seatbelt，并保留后续平台接入点。

### 风险与待确认

- 风险等级：high；理由：改变命令及子进程的文件和网络强制边界，错误策略可能暴露宿主文件或凭据。
- 关键操作：实施阶段对项目外文件、受保护元数据或网络放行时，必须取得 Permission 核准的实际能力；当前文档阶段无外部操作。
- 风险：沙箱内自动执行的命令仍可修改或删除项目普通文件；系统 `/usr/bin/sandbox-exec` 已标记 deprecated，且可能因宿主环境或嵌套沙箱无法启动；严格默认范围可能使依赖项目外缓存或网络的开发命令先进入审批。
- 关联 Spec：本需求只定义可强制范围与执行结果；[Permission Spec](../permission/requirements.md) 定义用户授权、持久 Grant、项目模式和 Browser／TUI 审批。
- 待确认的需求决策：无。

## 引言

本功能为 macOS 本机 Goal 增加可强制执行的命令边界：默认沙箱内的 `bash` 无需逐次 Tool 审批，网络及项目外文件只按 Permission 已核准的能力放行；其他平台保持当前命令执行行为并准确报告保护状态。

## 需求

### 需求 1：独立 package 与统一项目边界

**用户故事：** 作为 LazyGoal 维护者，我希望文件工具和本机命令从同一独立沙箱能力取得项目边界，以便权限规则可以一致地演进。

#### 验收标准

1. <a id="req-1-1"></a> 当构建 LazyGoal 工作区时，系统必须提供独立的 `@lazygoal/sandbox` package；`read_file`、`write_file`、`edit_file`、`grep` 的项目路径约束必须由该 package 提供，迁入后既有拒绝条件、错误码和中止行为保持有效。
2. <a id="req-1-2"></a> 当 macOS 上的 `bash` Action 进入执行时，系统必须通过 Seatbelt 启动命令，使该命令启动的子进程继承相同文件和网络限制；仅设置工作目录不得被视为已启用沙箱。
3. <a id="req-1-3"></a> 当 macOS 上的 `bash` Action 符合当前 Tool Profile、输入及执行策略且未请求额外沙箱能力时，系统必须跳过逐次 Tool 审批并在默认 Seatbelt 内执行；其他 Tool 的现有审批规则继续生效，任何 Tool Grant 都不得自动放宽沙箱能力。

### 需求 2：默认文件访问范围

**用户故事：** 作为项目使用者，我希望命令默认只处理本项目文件，以便在运行构建和测试时不会读取或修改无关的宿主资料。

#### 验收标准

1. <a id="req-2-1"></a> 当 macOS 命令未获得额外文件权限时，系统必须只允许其读写当前项目范围，以及只读运行该命令所必需的系统工具和依赖；项目外的普通用户文件不得被读取或写入。
2. <a id="req-2-2"></a> 当命令通过绝对路径、父目录、符号链接或子进程访问项目外目标时，系统必须在实际文件访问边界拒绝该操作；文件工具的路径校验也必须继续拒绝相应越界输入。
3. <a id="req-2-3"></a> 当命令需要临时文件时，系统必须为其提供受限的临时工作范围，不得因此获得对宿主临时目录中其他数据的通用访问权。
4. <a id="req-2-4"></a> 当目标是 LazyGoal 内部状态、模型凭据或项目版本控制元数据时，普通项目写权限不得自动覆盖这些保护；项目版本控制元数据仅在 Permission 已核准具体目标后可按该范围写入，内部状态和模型凭据不得通过授权向命令开放。

### 需求 3：默认断网与模型发起的联网请求

**用户故事：** 作为项目使用者，我希望模型在必要时能主动提出联网需求，同时只有获准的命令能够真正联网，以便日常任务保持自主且网络权限可控。

#### 验收标准

1. <a id="req-3-1"></a> 当 macOS 命令没有有效网络能力时，该命令及其子进程的外向连接和回环连接必须被沙箱阻止；现有独立 `web_fetch` Tool 仍走自身的 Tool 授权路径。
2. <a id="req-3-2"></a> 当模型认为某个命令需要联网时，它必须能够提出包含当前命令、目标网络范围和用途的请求；模型提出请求本身不得授予网络能力。
3. <a id="req-3-3"></a> 当命令请求联网时，系统必须把沙箱实际可强制的网络范围交给 Permission 判断；没有对应核准结果时不得启动联网命令，模型提供的域名或用途说明不得自行形成网络规则。
4. <a id="req-3-4"></a> 当 Permission 核准联网能力时，首版沙箱只能按已明确展示的任意目标出站范围放行该命令及子进程，包含本机回环但不开放入站监听；若实际范围无法与核准范围一致，必须拒绝启动。

### 需求 4：项目外文件的实际能力范围

**用户故事：** 作为项目使用者，我希望命令访问项目外缓存或相邻目录时按具体范围受限，以便授权不意外覆盖其他文件。

#### 验收标准

1. <a id="req-4-1"></a> 当模型需要项目外的非系统文件时，它必须为当前命令提出具体路径与读写操作；未获 Permission 核准时，普通 Tool 授权、YOLO 或模型说明不得代替该文件能力。
2. <a id="req-4-2"></a> 当请求涉及项目外文件或受保护元数据时，系统必须规范化实际路径、文件或目录子树范围及读写方向，并将可强制范围交给 Permission；目录子树的递归范围不得被误表示为单个文件。
3. <a id="req-4-3"></a> 当 Permission 核准项目外文件能力后，命令及子进程只能在该次执行计划所列路径、范围和读写方向内访问；旧计划、其他命令的授权或更宽的模型原文不得扩大该计划。

### 需求 5：凭据与审批边界

**用户故事：** 作为 LazyGoal 使用者，我希望本机命令只得到执行所需的环境与权限，以便模型、Tool 结果或自动批准模式不能获取我的宿主凭据。

#### 验收标准

1. <a id="req-5-1"></a> 当启动沙箱命令时，子进程不得继承 LazyGoal 持有的模型 API Key、访问令牌或其他宿主私密环境值；执行所需的环境变量必须经过明确筛选。
2. <a id="req-5-2"></a> 当 Tool Grant 已匹配或 YOLO 自动批准当前 Action 时，系统仍必须强制默认或经 Permission 核准的沙箱边界；模型文本、Tool 输出和普通 Tool 授权不得生成或扩大网络及项目外文件能力。
3. <a id="req-5-3"></a> 当沙箱拒绝原因或执行诊断交给 Runtime 时，信息必须足以区分边界拒绝与启动故障，同时不得包含模型凭据及未获准文件的内容。

### 需求 6：故障、恢复与执行次数

**用户故事：** 作为长期 Goal 的使用者，我希望审批和沙箱故障不会绕过保护或重复执行命令，以便中断恢复后的权限仍可信。

#### 验收标准

1. <a id="req-6-1"></a> 如果 macOS 上 Seatbelt 不可用、策略无法建立或受限进程无法启动，系统必须停止当前命令并明确报告沙箱故障，不得改为无沙箱执行。
2. <a id="req-6-2"></a> 当受限命令因文件或网络边界而失败时，系统必须区分可请求权限的拒绝与其他执行故障，并向模型或用户反馈有限且安全的原因；不得仅凭命令失败就自动重跑一个可能已产生副作用的 Action。
3. <a id="req-6-3"></a> 当 Goal 在审批中断或重启后恢复时，系统必须根据当前 Permission 核准结果重新构建沙箱执行计划；不得把旧的内存计划、待生效、错配或已撤销能力作为新命令的执行凭据。
4. <a id="req-6-4"></a> 当命令是否已执行无法确认时，系统必须保留当前 Action 的结果不确定等待，不得因获得新的沙箱能力而自动重放该命令或重复增加 Step。

### 需求 7：平台与沙箱状态

**用户故事：** 作为跨平台使用者，我希望明确知道当前 Goal 是否受沙箱保护，以便正确理解命令的权限和失败原因。

#### 验收标准

1. <a id="req-7-1"></a> 当 macOS 受限命令进入执行、被边界拒绝或启动失败时，系统必须分别产生可区分的保护状态和失败原因，供 Permission 界面准确展示，不得把未启动命令标成已受保护执行。
2. <a id="req-7-2"></a> 当在 Linux 或 Windows 上运行首版功能时，既有本机命令执行行为必须保持，系统必须准确报告未启用 Seatbelt，并保留后续平台实现的明确接入点。
3. <a id="req-7-3"></a> 当运行 Benchmark 容器任务或独立 `web_fetch` Tool 时，本功能不得声称其由 macOS 命令 Seatbelt 保护，也不得改变其现有隔离及 Tool 授权行为。
