# 统一 Agent Step 流与默认工作模式需求

## 审批摘要

### 目标

删除任务批准前的 `planProbe` 特殊执行层，让 Agent 对环境的读取使用与普通 Tool 相同的可恢复 `Action/Observation` 流程，并通过统一 System Prompt 引导模型自主选择读取、提问、任务提案和执行动作。

### 范围

- 包含：只读环境读取的普通 Step 语义、统一默认工作模式 Prompt、任务批准前的只读权限门控、Observation 上下文反馈、Step 计数与恢复、统一 TUI 时间线以及 `planProbe` 专用协议面的移除。
- 不包含：取消任务提案批准、放宽副作用 Tool 权限、重做 `ask_user` 或 Context Retrieval、旧开发期 `planProbe` 数据迁移以及新的 Prompt 兼容层。

### 核心行为

- 任务尚未批准时，模型可以在需要时读取授权环境；每次读取都必须作为普通 Step 持久化、计数、展示并进入下一轮模型上下文。
- System Prompt 引导模型先减少关键不确定性，再选择最小可验证下一步；Prompt 只提供行为指导，Runtime 仍强制执行授权、审批、证据和恢复边界。
- 任务批准前仍禁止所有非只读 Tool；任务批准后沿用现有普通 Action/Observation、Policy 和恢复规则。
- 系统不再产生或消费 `planProbe`、`observe_probe`、`probeCount` 或专用探查进度协议；旧开发期数据按当前协议失败，不自动迁移。

### 风险与待确认

- 风险等级：**high**；理由：改变任务批准前的 Tool 执行路径、持久化快照不变量、Step 预算、模型上下文和跨包协议。
- 关键操作：切换任务未批准状态下的 Tool 提交与恢复语义，并拒绝旧开发期 `planProbe` 快照或事件。
- 风险：读取被计入统一 Step 后可能更快消耗执行预算；任一层仍保留特殊分支都可能造成重复执行、上下文丢失或恢复不一致。
- 待确认：无。

## 引言

本功能把 Agent 的环境读取纳入唯一的 Action/Observation 执行闭环。模型通过统一 System Prompt 自主决定何时读取环境、何时向用户提问或提交任务提案；Runtime 继续以硬性规则限制未批准任务的副作用，并保证每个读取结果可审计、可恢复且可用于下一轮决策。

## 需求

### 需求 1：只读环境读取使用普通 Step

**用户故事：** 作为 Goal 使用者，我希望 Agent 读取环境时也产生普通执行进度，以便每一次读取都能被计数、审计和恢复。

#### 验收标准

1. <a id="req-1-1"></a> 当任务尚未批准且模型请求已授权的只读 Tool 时，系统必须使用与普通 Tool 相同的 Action/Observation 生命周期处理该请求，并为其增加一个 `stepCount`。
2. <a id="req-1-2"></a> 当只读 Tool 成功或失败时，系统必须将对应的 Action、Tool 结果和 Observation 作为一个完整普通 Step 提交到当前 Goal 的执行轨迹。
3. <a id="req-1-3"></a> 当一个只读 Step 已提交时，系统必须更新与普通 Step 相同的 `lastStep`、提交边界和进度状态，不得为该读取保留隐藏的非 Step 结果。

### 需求 2：统一 System Prompt 引导默认工作模式

**用户故事：** 作为 Agent 使用者，我希望模型遵循稳定的默认工作方式，以便它能自主调查、澄清和推进任务，而不依赖 Runtime 为读取环境安排特殊流程。

#### 验收标准

1. <a id="req-2-1"></a> 当 Agent 请求模型决策时，系统必须提供统一的执行工作模式说明，要求模型阅读当前目标和已提交事实，在需要时选择最小可验证下一步，并等待 Observation 后再继续判断。
2. <a id="req-2-2"></a> 当当前任务尚未批准时，System Prompt 必须引导模型在只读环境读取、必要的用户提问和任务提案之间自主收敛，不得把读取结果或模型自述当作完成证据。
3. <a id="req-2-3"></a> 当当前任务已经批准时，System Prompt 必须引导模型围绕完成条件执行、验证并在证据充分时结束，不得再次生成任务提案。
4. <a id="req-2-4"></a> 如果当前 Observation 已经包含回答某个环境问题所需的事实，模型必须被引导优先使用该事实推进，而不是无理由重复相同读取或停留在创建 Goal 的等待状态。

### 需求 3：任务批准前的副作用边界

**用户故事：** 作为系统所有者，我希望统一 Step 流不会放宽任务批准护栏，以便删除 `planProbe` 后仍然不会提前修改工作区或外部状态。

#### 验收标准

1. <a id="req-3-1"></a> 当任务尚未批准且模型请求非只读 Tool 时，系统必须在调用该 Tool 前拒绝请求，并且不得产生工作区、配置或外部可变状态的副作用。
2. <a id="req-3-2"></a> 当任务尚未批准且模型请求未授权或不存在的 Tool 时，系统必须在调用该 Tool 前拒绝请求，并保留可识别的协议或授权失败。
3. <a id="req-3-3"></a> 当任务已经批准时，系统必须继续使用现有 Tool Policy、Action 批准、重放和失败处理规则，不得因读取曾经发生在批准前而改变后续普通执行边界。

### 需求 4：Observation 驱动的连续推进

**用户故事：** 作为 Goal 使用者，我希望每次环境读取都能影响下一轮决策，以便 Agent 不会重复读取或在 `creating goal...` 状态中自旋。

#### 验收标准

1. <a id="req-4-1"></a> 当只读 Tool 的 Observation 成功提交后，下一次模型请求必须能够获得该 Observation 的 Tool 标识、结果状态和受限输出内容。
2. <a id="req-4-2"></a> 当只读 Tool 返回失败 Observation 时，下一次模型请求必须能够获得失败原因，并允许模型选择修正读取、提问、任务提案或其他合法决策。
3. <a id="req-4-3"></a> 当模型已收到本轮只读 Observation 时，Runtime 必须结束本轮 Tool 执行并进入下一轮决策，不得依赖隐藏的 Probe 回调或在同一状态上无限自旋。

### 需求 5：统一 Step 计数、预算与恢复

**用户故事：** 作为长任务使用者，我希望前置读取与执行读取拥有相同的持久化和预算语义，以便进程重启或达到预算后仍能得到可预测结果。

#### 验收标准

1. <a id="req-5-1"></a> 当普通只读 Action 通过授权和输入校验后，系统必须先保存对应的待执行状态，再允许 Tool 调用；保存失败时不得调用 Tool。
2. <a id="req-5-2"></a> 当只读 Tool 返回结果且 Observation 保存成功时，系统必须只增加一次 `stepCount`，并清除对应待执行状态；保存失败时必须保留可恢复的最后成功状态。
3. <a id="req-5-3"></a> 当 Goal 在没有最终任务时已经完成一个或多个只读 Step，系统重启恢复后必须保留其 Step 数、最后 Step、轨迹提交边界和下一轮模型可见的 Observation。
4. <a id="req-5-4"></a> 当统一执行预算达到上限时，前置只读 Step 必须与其他普通 Step 使用相同的停止、等待或失败语义，不得通过独立 `probeCount` 绕过预算。

### 需求 6：统一时间线与运行时可见性

**用户故事：** 作为 TUI 使用者，我希望环境读取看起来就是普通执行步骤，以便不需要理解隐藏的计划探查阶段。

#### 验收标准

1. <a id="req-6-1"></a> 当只读 Tool 完成并提交 Observation 时，TUI 必须将其按普通 Step 追加到当前 Session 时间线，并显示工具标识、结果状态和可用摘要。
2. <a id="req-6-2"></a> 当 Goal 等待读取结果、用户交互或任务批准时，TUI 必须继续使用统一 Session 页面和已有活动抽屉，不得创建或切换到 Probe 专用页面。
3. <a id="req-6-3"></a> 当 Goal 从快照恢复时，TUI 必须仅依据已提交的普通 Step 和当前等待状态重建读取进度，不得依赖独立探查进度事件或 UI 私有状态。

### 需求 7：移除专用 Probe 协议面

**用户故事：** 作为 Runtime 维护者，我希望系统只有一套 Tool/Observation 协议，以便新增 Tool、恢复和上下文组装不再维护计划探查例外。

#### 验收标准

1. <a id="req-7-1"></a> 当当前协议处理任何环境读取时，系统必须使用普通 `tool_call`、Action、Tool Observation 和 Step 事件，不得产生 `planProbe` 或 `observe_probe` 专用事件。
2. <a id="req-7-2"></a> 当 Agent 组装下一轮模型上下文时，系统必须使用普通执行单元投影已提交的只读 Action/Observation，不得依据缺少 `action_staged`、`probeCount` 或其他 Probe 标记识别读取结果。
3. <a id="req-7-3"></a> 当系统恢复包含旧开发期 Probe 字段、事件或不完整提交边界的数据时，系统必须以可识别的当前协议错误失败，不得猜测、迁移或继续调用模型和 Tool。

### 需求 8：事实与完成证据边界

**用户故事：** 作为系统所有者，我希望 Prompt 简化只影响模型选择而不削弱事实校验，以便统一执行流仍然不能虚构环境状态或完成结果。

#### 验收标准

1. <a id="req-8-1"></a> 当模型引用环境事实或声明完成时，系统必须只接受当前 Goal/Run 已提交的允许 Tool/Observation 作为对应证据。
2. <a id="req-8-2"></a> 当模型输出与当前任务门控、Tool 授权、输入契约或证据范围不匹配时，系统必须拒绝该决策并且不得执行副作用 Tool 或推进错误状态。
3. <a id="req-8-3"></a> 当 System Prompt 与 Runtime 强校验的判断不一致时，系统必须以 Runtime 校验结果为准，并保留可诊断的协议失败，而不是依赖模型自行纠正安全边界。
