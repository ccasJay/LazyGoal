# GitMutex 空闲键回收

## 目标与范围

`GitMutex` 在同一仓库键的最后一个回调结算时回收锁记录，保持进程内按键排队。Git 写操作继续按 `commonDir` 共享锁。

## 用户故事

- **S1** 作为 Git 写操作调用方，我希望同一仓库的回调按入队顺序执行，并在队列清空时回收锁记录，以便长期访问多个仓库时只保留仍有操作的键。

## 验收标准

| ID | 故事 | 类型 | 当 | 系统应 | 验证 |
|---|---|---|---|---|---|
| R1.1 | S1 | 状态 | 同一键有回调正在执行，后续回调依次入队 | 按入队顺序逐一执行，同一时刻最多运行一个回调。 | 用可控 Promise 挂起首个回调，依次排入后续回调，逐项放行并断言进入顺序和无重叠。 |
| R1.2 | S1 | 事件 | 某键的回调挂起时提交另一键的回调 | 允许另一键独立执行和结算。 | 挂起 A，断言 B 在 A 放行前已结算，且只删除 B 的记录。 |
| R1.3 | S1 | 异常 | 回调拒绝且同键仍有等待者 | 向原调用方返回原拒绝原因，并释放后续回调的等待。 | 排入后续回调后让首个回调拒绝，核对错误对象身份和后续成功结果。 |
| R1.4 | S1 | 事件 | 当前回调结算时，同键已登记更新的队尾 | 保留较新的队尾。此后加入的同键回调仍排在现有队尾之后。 | A 后排入 B。结算 A 并挂起 B，核对登记的队尾仍为 B，再提交 C，断言 C 只能在 B 结算后进入。 |
| R1.5 | S1 | 事件 | 某键的队尾回调成功或失败，且没有后续登记 | `withLock` 结算时该键已从 Map 删除。同一键可重新入队并再次回收。 | 分别运行无等待者的成功和拒绝回调，直接核对目标键已删除，再复用该键核对执行和清理。 |
| R1.6 | S1 | 普遍 | Git 写入和 worktree 工具通过既有执行入口运行 | 保持仓库锁键、授权检查、命令执行与工具结果语义。 | 核对写入入口继续使用 `commonDir`。运行现有 Git 写入、worktree 和 Runtime Git 授权回归。 |

组合：在 `packages/sandbox/test/git-mutex.test.ts` 用可控 Promise 验证 R1.1–R1.5，直接断言 Map 条目。运行 `npm test` 覆盖 R1.1–R1.6 与全量回归。

## 决策

| 决策 | 理由 | 放弃 |
|---|---|---|
| [GitMutex](../../packages/sandbox/src/git-runner.ts#L25) 将 `currentLock.then(() => nextLock)` 的结果保存在局部变量并写入 Map。`finally` 保留现有释放顺序，释放 `nextLock` 后，仅在 Map 仍指向本次写入的队尾 Promise 时删除键。 | 现有 Map 已记录每个键的队尾。用实际写入的对象核对身份可保留较新的等待者并回收空闲键。 | 无 |
| 回归直接观测测试中的 Map 键和队尾身份，生产端继续使用现有 `GitMutex.withLock` 和 [Git 写入入口](../../packages/sandbox/src/git-runner.ts#L681)。 | 能捕获回调结果正确但锁记录仍残留的回归。 | 无 |

## 风险与否定性保证

| 等级 | 理由 | 关键操作 |
|---|---|---|
