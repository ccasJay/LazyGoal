# Tool Core 拆包需求

## 引言

将通用 Tool 定义、注册、输入准备和单次执行契约拆为独立 Tool Core，使其能够在不依赖 Runtime 的情况下使用。Profile 授权、Tool Policy、Action 审批、持久化与重放决策继续由 Runtime 负责；本次拆分保持现有工具、模型接口和执行行为，不新增工具能力。

## 需求

### 需求 1：独立使用通用工具核心

**用户故事：** 作为工具开发者，我希望独立定义、注册和准备工具，以便无需创建 Goal 或启动 Runner 就能复用和测试工具实现。

#### 验收标准

1. <a id="req-1-1"></a> 当调用方提供 Tool 实现、输入 Contract 和必要执行参数时，Tool Core 必须支持现有工具的定义、注册、查找、输入准备和单次调用，无需创建 Goal、启动 Runner 或访问 GoalStore。
2. <a id="req-1-2"></a> Tool Core 不得导入 Runtime 源码，也不得通过 Runtime 的转发导出取得自身所需的类型或行为。
3. <a id="req-1-3"></a> 拆包后，现有 Tool 实现、Runtime、Agent 和 Benchmark 调用方必须能够使用同一套工具核心定义，保持既有描述、请求、准备结果和执行结果的字段及含义。

### 需求 2：保持注册与单次输入准备

**用户故事：** 作为工具调用方，我希望工具仍在执行前完成严格、确定的输入准备，以便非法输入不会触发工具副作用，合法输入不会被重复解析或隐式修改。

#### 验收标准

1. <a id="req-2-1"></a> 当注册工具或建立 Registry 时，系统必须保持对非法输入 Contract、空 Tool ID 和重复 Tool ID 的现有拒绝行为。
2. <a id="req-2-2"></a> 当准备一次工具调用时，系统必须保持 Input Contract 作为唯一结构事实源，完成一次结构解析后再执行工具语义校验；不得新增 trim、coerce 或补充默认值等输入转换。
3. <a id="req-2-3"></a> 当结构解析或语义校验失败时，系统必须保持现有输入失败结果与诊断语义，不得启动工具、执行沙箱内业务操作或产生工具外部副作用。
4. <a id="req-2-4"></a> 当输入准备成功时，沙箱能力派生及后续执行必须使用已解析的同一 canonical 输入，不再接收原始输入重新解析；等待审批或中断恢复后仍按 Runtime 的现有规则重新准备持久化 Action。

### 需求 3：保持执行结果、流与故障语义

**用户故事：** 作为工具调用方，我希望拆包后的工具调用保持现有执行和错误协议，以便 Runtime 能继续正确处理结果、中止与可重试故障。

#### 验收标准

1. <a id="req-3-1"></a> 当执行已准备的工具调用时，系统必须保持现有 Action 身份、可信执行上下文和沙箱计划的传递方式，以及成功或领域失败 Observation 的结构与含义。
2. <a id="req-3-2"></a> 当使用现有流式执行能力时，系统必须保持输出分片和最终结算协议；单次入口调用不得同时启动流式与非流式执行，也不得在 Tool Core 内自动重试。
3. <a id="req-3-3"></a> 当准备、沙箱能力派生或执行链中发生中止时，系统必须按现有规则传递共享信号并传播执行中止，不得将中止伪装为普通失败 Observation。
4. <a id="req-3-4"></a> 当工具显式报告暂时性基础设施故障或抛出其他异常时，系统必须保持现有故障类别、错误字段与传播规则；不得因拆包把未知异常或 failure.retryable 结果转换为自动重放资格。

### 需求 4：保持 Runtime 授权与恢复边界

**用户故事：** 作为 Goal 的使用者，我希望工具核心拆分不改变工具可见性、授权和恢复规则，以便独立工具接口不会绕过现有执行控制。

#### 验收标准

1. <a id="req-4-1"></a> 当 Runtime 发现、暴露或调用工具时，必须保持当前 Profile、Registry、Run 可见工具集合、Tool Policy、审批与沙箱检查的执行结果；工具描述或 Schema 可见性不得单独授予执行权。
2. <a id="req-4-2"></a> 当 Runtime 调度直接 Tool 调用或程序中的子调用时，必须继续注入可信身份并执行原有授权流程；Tool Core 不得决定 Goal/Run 状态、审批结果或工具授权范围。
3. <a id="req-4-3"></a> 当 Runtime 决定重试或恢复 Action 时，必须保持 safe/manual 重放声明、有效批准、尝试记录和不确定结果等待的现有约束；这些决策不得转入 Tool Core。
4. <a id="req-4-4"></a> 拆包不得改变模型消费的 Tool 描述与输入 Schema、模型工具调用契约，以及当前 Action、Observation 和 Snapshot 的持久化数据格式。

## 风险与待确认

- 风险等级：medium；理由：公开工具契约和多个调用方的依赖方向变化，必须验证授权与恢复集成，但目标不改变权限语义或持久化格式。
- 关键操作：无。
- 已知风险：迁移遗漏或出现重复错误类可能破坏调用与故障识别；输入准备顺序变化可能重复解析或提前产生副作用；共享 JSON、Observation、诊断与取消类型若继续引用 Runtime，会使拆包边界失效。
- 当前源码中的取消原语仍位于 Runtime，Design 阶段需明确共享取消协议的承接方式与前置关系。
- 需求阶段待确认：无；本文件为待审核草稿，公开导入路径与具体迁移方式由 Design 阶段确定。
