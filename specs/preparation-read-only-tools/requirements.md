# Feature Requirements: 准备阶段声明式只读工具与流式瀑布

## 审批摘要

### 目标
让 Agent 在执行前的两个准备阶段（`gathering_context` 需求澄清与 `planning` 方案制定）拥有声明式、可扩展的只读探测能力（覆盖本地代码与 WebSearch），并在 TUI 终端中以一致的流式瀑布效果（Waterfall Timeline）实时透明呈现调查过程，彻底消除“面对只读信息盲问用户”与“准备过程黑盒”的体验缺陷。

### 范围

#### 包含
- 从当前 Goal 绑定的工具列表与 `ToolRegistry` 中，动态依据只读能力属性（`isReadOnly`）自动筛选准备阶段可用工具集，不硬编码特定工具名；
- 允许只读工具集支持本地文件/代码检索（`read_file`、`grep`）与外部信息检索工具（`web_search` 或等价只读网络查询）；
- 在 Preparation 流程中支持有限轮次的只读探查循环（`tool_call` -> `observation` -> 继续探查或给出问答/任务提案）；
- 为准备阶段工具调用设置安全轮次上限（默认最大 5 轮），防止死循环消耗 Token；
- TUI 在准备阶段（`PreparationScreen`）与执行阶段保持一致的流式瀑布体验，使用 Ink `<Static>` 追加输出并固化历史步骤，底部保留问题输入或提案审批抽屉。

#### 不包含
- 准备阶段严禁开放或执行任何带有写入副作用的工具（`write_file`、`edit_file` 以及任何修改性命令一律严格拦截）；
- 不改变“必须经由用户显式批准 Task Proposal 后方可进入 Executing”的核心安全门控；
- 不改变 Executing 阶段既有的全功能 Action/Observation 循环、审批门控与单步快照不变量。

### 核心行为
1. 当进入 `gathering_context` 或 `planning` 阶段时，系统通过 `ToolRegistry` 动态过滤出当前 Goal 授权且声明为 `isReadOnly: true` 的工具列表，注入准备阶段 Prompt 中；
2. 模型可自主发起只读工具调用；Runtime 执行工具并将观察结果作为下一轮提示输入，支持连续多次只读探查直至信息充分；
3. 当模型在准备阶段尝试调用非只读工具时，系统直接以安全违规拒绝并终止非法操作，保证本地工作区零修改；
4. TUI 准备页面将每一个已完成的只读步骤以 `✔ [toolId] ...` 瀑布流输出并向上累积，先前步骤不被擦除，底部紧凑抽屉呈现当前状态或交互输入。

### 风险与待确认
- **已知风险**：跨子系统协议升级（涉及 `@lazygoal/contracts` 扩展 Preparation 结果契约、`@lazygoal/runtime` 准备循环引擎改造、`@lazygoal/agent` Prompt 模板扩展、以及 `@lazygoal/tui` 准备屏幕渲染重构），初始风险等级定为 **High**；
- **待确认项**：无未决重大决策。方案已明确采用基于元数据的动态只读过滤、严格写拦截与 TUI 流式瀑布方案。

## 引言

LazyGoal 当前将所有工具执行循环与可视化流完全绑定在 `executing` 阶段，而在前置的 `gathering_context` 与 `planning` 阶段，Agent 既无法查看工作区代码、git 提交历史，也无法执行网络搜索，导致面对只读需求时退化为反复向用户索取信息的盲目交互。本功能通过在准备阶段建立声明式只读工具探针机制与 TUI 流式瀑布呈现，让 Agent 能够安全自主搜集事实并透明展示过程，最终生成高质量的任务提案。

## 需求列表

### 需求 1：从可用工具列表中声明式解析只读工具集

**用户故事：** 作为 Agent 开发者，我希望系统能够依据工具的只读元数据自动将只读工具开放给准备阶段，以便随时扩展诸如 `web_search` 等新工具而无需修改核心引擎代码。

#### 验收标准
1. <a id="req-1-1"></a> 当构建准备阶段（`gathering_context` 或 `planning`）的模型提示词时，系统必须从当前 Goal 绑定的授权工具中，动态筛选出所有声明了 `isReadOnly: true` 的工具定义注入模型上下文。
2. <a id="req-1-2"></a> 当系统中注册了支持外部文档与网络查询的只读工具（如 `web_search`）且在 Goal 的授权列表中时，系统必须将其自动纳入准备阶段可用工具集。
3. <a id="req-1-3"></a> 系统不得在准备阶段通过硬编码工具名称列表（如仅硬编码 `read_file` 与 `grep`）进行静态限制，新增的只读工具只要具备合法声明即可被准备阶段自动识别。

### 需求 2：准备阶段支持受控的多轮只读探查循环

**用户故事：** 作为终端用户，我希望 Agent 在澄清需求或制定计划时能够自主查看代码库与网络文档，以便直接理解上下文并给出精准方案，而不需要我手动复制粘贴。

#### 验收标准
1. <a id="req-2-1"></a> 当 Agent 在 `gathering_context` 阶段需要获取上下文时，系统必须允许模型产出合法的只读 `tool_call` 决策，并在 Runtime 执行后将观测结果返回给下一轮模型推理。
2. <a id="req-2-2"></a> 当 Agent 在 `planning` 阶段需要调研依赖或验证代码结构以完善计划时，系统必须允许模型发起只读探查，并在探查完毕后产出最终的 `task_proposal`。
3. <a id="req-2-3"></a> 当准备阶段的连续只读探查步数达到预设阈值（默认 5 步）时，系统必须强制终止探查循环并提示模型基于当前已知信息给出提问或任务提案，防止无休止消耗 Token。

### 需求 3：严格拦截写操作与环境副作用

**用户故事：** 作为系统所有者，我希望在任务计划未经我确认批准之前，任何工具调用都不能修改工作区文件、配置或外部可变状态，同时允许 Runtime 持久化恢复与审计所需的内部状态。

#### 验收标准
1. <a id="req-3-1"></a> 当准备阶段的模型尝试发起非只读工具（如 `write_file`、`edit_file` 或具有破坏性写入的命令）调用时，系统必须在执行前直接拒绝该动作并不产生任何副作用。
2. <a id="req-3-2"></a> 在用户正式批准 `planning` 阶段产出的 Task 提案之前，Preparation 工具不得修改工作区文件、配置或外部可变状态；LazyGoal 可以写入 Goal Snapshot、Trajectory 与诊断记录等自身恢复和审计状态。

### 需求 4：TUI 准备阶段实现一致的流式瀑布效果

**用户故事：** 作为终端用户，我希望在准备阶段也能像执行阶段一样看到一步步工具调用的瀑布流向上滚动，以便实时了解 Agent 正在看什么代码、查什么资料。

#### 验收标准
1. <a id="req-4-1"></a> 当 Agent 在准备阶段完成每一次只读工具调用时，TUI 必须使用 Ink `<Static>` 将该步骤以紧凑单行格式（包含工具标识、关键参数与摘要）追加固化到终端历史中，不得原地擦除覆盖。
2. <a id="req-4-2"></a> 当 Agent 正在执行某项只读探查时，TUI 必须在底部活动抽屉展示进行中的 Spinner 与当前操作说明（如 `Searching git log...`）。
3. <a id="req-4-3"></a> 当 Agent 结束探查进入提问（`question`）或提案审批（`approval`）时，TUI 必须在下方动态活动抽屉整洁渲染输入框或确认面板，且上方完整保留先前的探查步骤瀑布流。
