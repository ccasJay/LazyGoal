# Context Epoch 工作窗口需求

## 简介

本草稿覆盖三项工作：落实已确认的 Epoch 容量、计量、阈值和超窗恢复行为，增加阈值触发后的单次模型提炼，以及按 Goal 重组存储目录。验收同时关注任务连续性、成本和性能。

本期的模型提炼仅用于压缩当前 Goal 的工作上下文。Working Memory 沿用现有行为。记忆机制、经验总结和独立的 Epoch 交接记录留待单独设计。

## 需求

### 需求 1：统一适用范围

**用户故事：** 作为 LazyGoal 用户，我希望所有 Goal 和模型使用统一的 Epoch 机制，以便以一致的方式管理长任务上下文。

#### 验收标准

1. 当 Goal 使用任意受支持的模型执行时，系统应使用本功能定义的 Context Epoch 机制管理其工作上下文。
2. 当设计和验证该机制时，应同时考虑长任务连续性、成本和性能。

### 需求 2：窗口容量与配置

**用户故事：** 作为 LazyGoal 用户，我希望窗口容量与模型能力关联，并可设置容量和整理阈值，以便控制工作上下文的使用。

#### 验收标准

1. 当模型的最大上下文容量已知时，Epoch 容量默认应设置为该模型的最大上下文容量。
2. 系统应允许用户将 Epoch 容量设置为小于该模型最大上下文容量的值。
3. 系统应允许用户设置以 Epoch 容量为基数的整理阈值。
4. 当设置的整理阈值为 80% 时，调用结束后的 Epoch 大小超过 Epoch 容量的 80% 应触发整理。
5. 当模型的最大上下文容量未知且用户未配置 Epoch 容量上限时，系统应在发送模型请求前拒绝调用，并提示用户配置 Epoch 容量上限。
6. 当模型的最大上下文容量未知但用户已配置 Epoch 容量上限时，系统应以该上限作为 Epoch 容量和整理阈值的计算基数。

### 需求 3：当前窗口计量

**用户故事：** 作为 LazyGoal 用户，我希望 Epoch 大小反映模型当前窗口占用，以便基于实际工作上下文判断是否整理。

#### 验收标准

1. 当一次模型调用结束时，系统应根据该次模型输入与输出的窗口占用判断 Epoch 大小和整理阈值。
2. 当后续请求再次包含此前已发送的历史时，系统不得通过累加各次请求用量重复计算这些历史的当前窗口占用。
3. 当上下文内容变化并构造后续请求时，系统应按实际保留的上下文重新计量其窗口占用。
4. 当模型未返回可靠用量时，系统应允许使用当前上下文的 token 估算值判断阈值，并在界面标记该值为估算。
5. 当缺少 Epoch 容量或无法获得实际或估算占用时，界面应显示不可用图标。

### 需求 4：超窗恢复

**用户故事：** 作为 LazyGoal 用户，我希望模型因上下文超窗拒绝请求后任务能够继续，以便不因单次超窗中断长任务。

#### 验收标准

1. 当完整请求被供应商以超出上下文窗口为由拒绝时，系统应自动整理上下文并重试。
2. 超窗恢复的具体整理方式、重试限制和失败处理须在后续讨论中确定。

### 需求 5：阈值触发后提炼

**用户故事：** 作为 LazyGoal 用户，我希望每次因超过阈值整理 Epoch 时，模型都检查将要移出的历史，以便把仍需用于接续任务的信息带入下一 Epoch。

#### 验收标准

1. 当 Epoch 占用超过阈值并触发整理时，正常整理流程应额外调用一次模型，检查候选移出历史并提炼接续当前 Goal 所需的信息。
2. 即使现有上下文已经包含接续任务所需的信息，正常整理流程仍应执行这次模型调用。
3. 构造提炼请求时，应以本次候选移出窗口的历史为提炼对象，并附上当前任务接续状态及判断旧信息是否仍有用所需的近期线索。保留在下一窗口的历史只按需提供必要片段。
4. 切换到下一 Epoch 时，Runtime 应将仍生效的用户要求和当前任务状态带入模型工作上下文。模型提炼应保留与任务接续仍相关的已验证发现、未解决问题、关键决策理由及其来源，供下一 Epoch 使用。
5. 提炼结果应作为压缩后的历史参与下一 Epoch 的模型上下文组装。该流程不新增 Working Memory 的写入行为。
6. 当提炼成功时，Runtime 应将压缩后的历史作为 Epoch 切换事件的载荷写入当前 Run 的轨迹，再提交包含新 Epoch、该事件的恢复指针和新轨迹提交水位的 Goal 快照。快照只保存恢复指针，不复制压缩正文。
7. Epoch 切换应以 Goal 快照的显式提交为准。进程在快照提交前退出时，系统应恢复旧 Epoch 并忽略未提交的压缩历史。快照提交后，系统应根据其中的指针和提交水位加载压缩历史，恢复新 Epoch。系统不得根据轨迹尾部、临时文件或内存标志推断 Epoch 是否已经切换。

### 需求 6：按 Goal 组织存储

**用户故事：** 作为 LazyGoal 用户，我希望一个 Goal 专属的持久化内容集中在同一目录，以便按会话定位和管理这些内容。

#### 验收标准

1. 当系统持久化某个 Goal 的快照、轨迹、Epoch 整理产物及专属衍生文件时，应将它们写入该 Goal 的目录。
2. 每个 Run 应有独立的 `runs/<runId>/` 子目录。该 Run 的轨迹及其索引、模型请求记录、用量指标和诊断日志应存放在该子目录。
3. Goal 目录应保留最新快照。完整对话继续保存在快照中，跨 Run 共享的载荷和 Goal 级检索索引分别位于 Goal 层的 `blobs/` 和 `indexes/`。
4. 对采用新布局的 Goal，系统应支持打开、续写、恢复和历史查询。恢复应以最新 Goal 快照及其中记录的轨迹提交边界为准。
5. 当一个 Goal 的 Run 数量超过 Trajectory 面板 Run 列表的一页时，用户应能翻页选中较早的 Run，分页查看其事件并打开模型输入详情。读取所选 Run 的轨迹页时，系统应只访问该 Run 的轨迹及其索引。
6. 切换到新布局时，应删除旧布局下的全部本地 Goal 及其专属持久化内容，不迁移旧 Goal。切换后创建的 Goal 统一使用新布局。

#### 目录布局

```text
goals/<goalId>/
├── snapshot.json
├── runs/<runId>/
│   ├── trajectory.jsonl
│   ├── trajectory.index.db
│   ├── model-inputs.jsonl
│   ├── metrics.jsonl
│   └── trace.jsonl
├── blobs/
└── indexes/
```

## 待讨论

- 模型容量未知但用户已配置上限时，界面如何标明该上限的来源。
- 超窗自动整理的重试限制、整理失败和多次超窗时的行为。
- 模型切换、运行中断或恢复时的窗口和 Epoch 行为。
- 容量与阈值设置的作用域、默认阈值、有效范围及变更生效时机。
