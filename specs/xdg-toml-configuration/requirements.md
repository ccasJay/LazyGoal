# xdg-toml-configuration 需求

## 审批摘要

### 目标

将 LazyGoal 的配置架构从“项目级 `.env` + 环境变量注入”彻底重构为符合 **XDG 基础目录规范（XDG Base Directory Specification）** 的 **TOML 声明式用户级应用配置体系**，建立“内置默认值 → `config.toml` → `profiles/<profile>.toml` → CLI 临时参数”的严格四层加载链，实现跨项目零重复配置、环境隔离与安全权限管控。

### 范围

- 包含：XDG 基础目录发现与路径绑定、`~/.config/lazygoal/config.toml` 与用户级 `profiles/<profile>.toml` 的 TOML 解析与语义校验、四层配置优先级合并引擎、CLI 临时单向覆盖机制、敏感文件权限安全保障、彻底移除 `bin/lazygoal.cjs` 中的 `.env` 与 `--env-file` 自动注入。
- 不包含：工作区本地的 `goals` 和 `trajectories` 持久化数据迁移、系统钥匙串（Keychain）密码锁集成、对当前工作区 `.env` 文件的保留嗅探。

### 核心行为

- 遵循 XDG 标准：优先读取 `$XDG_CONFIG_HOME/lazygoal`（默认 `~/.config/lazygoal`），集中管理配置文件与 Profile。
- TOML 严格校验：以 TOML 作为唯一声明式配置格式，语法错误或非法字段时快速失败，精准报告文件名、行号与键名。
- 四层覆盖链：严格遵循“内置默认值 → 全局配置 → Profile 配置 → CLI 参数”逐层覆盖，CLI 参数仅在内存生效且绝不回写磁盘。
- 剥离项目级 .env：完全剔除项目目录 `.env` 自动加载逻辑，消除多重配置真理来源。

### 风险与待确认

- 风险等级：medium；理由：重构了 CLI 入口参数装配、配置加载链路与 Profile 查找路径，影响所有启动流程，但逻辑边界清晰，提供平滑迁移说明。
- 关键操作：无
- 风险：若用户初次启动未创建任何配置文件，需提供清晰可读的初始化引导与缺失提示。
- 待确认：无

## 引言

LazyGoal 当前严重依赖工作区根目录下的 `.env` 文件以及必须手动创建的 `.lazygoal/profiles/default.json`，不仅在切换多个工程目录时体验割裂，还容易造成密钥散落与配置冲突。本特性引入 XDG 基础目录规范与 TOML 声明式配置，建立集中、类型清晰且安全的配置体系，使开发者在任何新工作区均可开箱即用。

## 需求

### 需求 1：XDG 基础目录发现与结构管理

**用户故事：** 作为跨平台命令行用户，我希望 LazyGoal 自动根据 XDG 规范定位用户级配置目录，以便全局统一管理模型凭据与 Profile。

#### 验收标准

1. <a id="req-1-1"></a> 当系统初始化配置路径时，系统必须优先检测 `$XDG_CONFIG_HOME` 环境变量；若未设置，则默认使用 `$HOME/.config`。
2. <a id="req-1-2"></a> 当解析配置资源位置时，系统必须将主配置文件绑定至 `$XDG_CONFIG_HOME/lazygoal/config.toml`，并将用户 Profile 目录绑定至 `$XDG_CONFIG_HOME/lazygoal/profiles/`。
3. <a id="req-1-3"></a> 当用户或系统需要创建配置目录时，系统在 POSIX 环境下必须使用 `0700` 目录权限创建，防止非授权用户读取。

### 需求 2：TOML 声明式配置解析与语义校验

**用户故事：** 作为开发者，我希望通过直观的 TOML 文件声明模型、工作区与 TUI 偏好，并在编写错误时得到明确的定位提示。

#### 验收标准

1. <a id="req-2-1"></a> 当读取 `config.toml` 时，系统必须支持解析 `[llm]`、`[workspace]`、`[profile]` 及 `[tui]` 结构化配置小节。
2. <a id="req-2-2"></a> 如果 TOML 文件存在语法错误或包含未定义字段，系统必须快速失败退出，并在错误信息中准确报告文件路径、行号与错误描述。
3. <a id="req-2-3"></a> 当写入包含 API Key 的配置文件时，系统必须确保该文件在 POSIX 环境下的权限设置为 `0600`。

### 需求 3：四层配置覆盖优先级

**用户故事：** 作为操作者，我希望系统按照清晰的优先级合并多层配置，并支持通过 CLI 参数进行单次临时覆盖。

#### 验收标准

1. <a id="req-3-1"></a> 当生成最终运行时配置时，系统必须严格按照“内置默认值 → `config.toml` → `profiles/<profile>.toml` → CLI 命令行参数”顺序逐层覆盖。
2. <a id="req-3-2"></a> 当通过命令行传入临时覆盖参数（如 `--model`、`--provider`）时，系统必须将该参数值应用至当前进程内存，严禁回写磁盘文件。
3. <a id="req-3-3"></a> 如果必填配置（如模型名称或 API 凭据）在所有配置层级合并后依然缺失，系统必须在启动阶段终止并输出具体缺失字段及配置引导。

### 需求 4：用户级 Profile 管理与切换

**用户故事：** 作为在不同场景使用不同模型策略的用户，我希望在全局目录下管理多套 Profile，并能随时无缝切换。

#### 验收标准

1. <a id="req-4-1"></a> 当 `config.toml` 中设置 `profile.active = "name"` 或 CLI 传入 `--profile name` 时，系统必须从 `~/.config/lazygoal/profiles/name.toml` 加载该 Profile。
2. <a id="req-4-2"></a> 如果激活的 Profile 文件不存在，系统必须报错并输出当前 Profile 目录下的可用选项。

### 需求 5：移除项目级 .env 自动注入

**用户故事：** 作为追求整洁工作区的开发者，我希望运行 CLI 时不再受到当前工作区旧 `.env` 文件的隐式干扰。

#### 验收标准

1. <a id="req-5-1"></a> 当通过 `bin/lazygoal.cjs` 启动进程时，系统不得探测当前工作区的 `.env` 文件，也不得向子进程注入 `--env-file` 参数。
2. <a id="req-5-2"></a> 当在没有任何 `.env` 或本地 `.lazygoal` 目录的全新工作区启动时，系统必须凭借全局 XDG 配置成功完成启动。
