# TUI 瀑布式步骤流渲染 需求

## 审批摘要

### 目标

将 LazyGoal 终端交互界面从“原地擦除覆盖的单步仪表盘”重构为“沉浸式瀑布时间线（Waterfall Timeline）”，让 Agent 每次完成的工具调用与观察结果在终端历史中清晰累积与滚动，同时保持底部正在运行步骤与交互面板的紧凑动态展示。

### 范围

- 包含：CLI 运行时实时提交通知装配、SessionController 对已提交步骤历史流的 ViewModel 派生、Ink `<Static>` 驱动的步骤瀑布流渲染与超长输出安全折叠、底部正在运行动作抽屉与等待面板的动态衔接。
- 不包含：Runtime 领域模型与快照存储协议变更（`Goal.state.run.lastStep` 仍为有界最新快照）、多 Goal 并发调度、终端上下翻页富文本交互控件。

### 核心行为

- 实时步骤事件连通：CLI 启动执行时正确装配带有提交通知能力的 GoalStore，确保连续多步执行期间的每个 step 都能实时投射到 TUI。
- 步骤时间线有序累积：SessionController 随着每个 step 的提交，在 ViewModel 中维护单调递增的已完成步骤时间线列表。
- 瀑布流固化到终端历史：已完成的步骤项通过 Ink `<Static>` 渲染，沉淀为终端 scrollback，用户可随时向上滚动回溯执行链路。
- 紧凑呈现与安全折叠：单步输出采用紧凑单行格式，大输出自动折叠并标明省略字数，杜绝超长内容刷屏破坏终端可读性。
- 动态活动抽屉分层：底部动态重绘区仅展示当前正在执行中的 step（带 Spinner）或等待用户交互的操作面板（审批/输入/终态），新 step 完成后自动移入上方瀑布。

### 风险与待确认

- 风险等级：medium；理由：涉及 TUI 包内数据流装配、ViewModel 字段扩展与 Ink 渲染层布局调整，但完全封装在 `packages/tui` 内，不影响 Runtime 领域状态机与持久化契约。
- 关键操作：无
- 风险：`<Static>` 输出后在当前终端会话不可撤销，若截断阈值过大可能导致长日志污染终端。
- 待确认：无

## 引言

LazyGoal 当前在Executing 阶段的终端渲染仅展示单个最新 Step，并在每次状态更新时就地擦除覆盖，导致用户无法感知多步执行的过程链路，如同面对静态仪表盘。本功能通过在 TUI 层打通实时提交通知管道并重构 Ink 组件布局，将已完成步骤以瀑布式时间线推入终端历史，提供沉浸透明的 Agent 执行体验。

## 需求

### 需求 1：CLI 实时步骤提交通知装配

**用户故事：** 作为终端用户，我希望在 Goal 连续执行多个步骤时能实时看到每一帧的推进，以便掌握 Agent 的即时工作动态。

#### 验收标准

1. <a id="req-1-1"></a> 当 CLI 组合根初始化 TUI 与 Controller 时，系统必须通过 `NotifyingGoalStore` 包装存储实例并将通知能力提供给 `SessionController`。
2. <a id="req-1-2"></a> 当 Runtime 完成一个 Step 并将最新快照保存到 Store 时，系统必须实时触发 Controller 的提交通知回调，不得延后到整个 run loop 退出。
3. <a id="req-1-3"></a> 如果 Controller 已处于关闭（shutting down）状态，系统必须丢弃到来的通知，不得触发界面重绘。

### 需求 2：SessionController 步骤时间线投影

**用户故事：** 作为前端渲染层，我希望从 ViewModel 中直接获取有序的已完成步骤列表，以便以声明式方式渲染时间线。

#### 验收标准

1. <a id="req-2-1"></a> 当 Controller 接收到带有新 Step 的 Goal 提交事件时，系统必须基于 `stepCount` 单调递增将该 Step 的结构化摘要追加到 ViewModel 的步骤时间线中。
2. <a id="req-2-2"></a> 如果到来的 Goal 提交事件中的 `stepCount` 小于或等于已处理的最大步骤数，系统必须拒绝重复追加，保证步骤时间线严格去重。
3. <a id="req-2-3"></a> 当用户通过已有 Goal 快照恢复 Session 时，系统必须初始化步骤列表并包含快照中的最近一个已提交 Step（若存在）。

### 需求 3：Ink Static 步骤瀑布流与安全折叠渲染

**用户故事：** 作为终端用户，我希望看到已完成的步骤像日志流水一样向下追加并保留在终端滚动条中，以便回溯执行链路且不被超长日志刷屏。

#### 验收标准

1. <a id="req-3-1"></a> 当渲染 Session 界面时，系统必须使用 Ink `<Static>` 渲染所有已完成的步骤条目，确保其被提交到终端 scrollback 历史中。
2. <a id="req-3-2"></a> 每个已完成步骤条目必须清晰展示步骤序号、工具标识、关键输入摘要以及执行结果状态（成功或失败）。
3. <a id="req-3-3"></a> 当工具的输入或输出文本长度超过预设阈值时，系统必须在展示层进行单行安全截断并附带省略提示，不得破坏终端排版。

### 需求 4：动态活动抽屉与交互面板无缝衔接

**用户故事：** 作为终端用户，我希望底部的当前工作区只显示当前正在做的事情或等待我操作的面板，以便视觉焦点清晰明确。

#### 验收标准

1. <a id="req-4-1"></a> 当 Agent 正在执行某一个 Step 或调用模型决策时，系统必须在底部动态区域展示 `StatusSpinner` 与当前步骤的进行中文案。
2. <a id="req-4-2"></a> 当 Agent 进入 `action_approval` 或 `action_recovery` 等待点时，系统必须在底部动态区域展示待审批 Action 详情与确认面板，且上方保留已提交步骤流。
3. <a id="req-4-3"></a> 当 Goal 达到 `completed` 或 `failed` 终态时，系统必须展示终态摘要面板，并保留完整的步骤时间线供用户查阅。
