# Runtime 阶段、程序批次与恢复导航一致性

## 目标与范围

落实 RC03–RC05：最终审查拒绝后可在原 Plan Run 修正，批次内的程序调用按模型顺序推进，恢复后的模型导航只消费各 Run 提交水位内的事实。
沿用当前 Snapshot、Trajectory、模型协议及授权契约。范围限于阶段重开、程序 Action 的批次推进和工作导航重建。

## 用户故事

- **S1** 作为批准 Plan 的用户，我希望最终审查指出缺口后可继续修正原阶段，以便保留已完成的工作与批准范围。
- **S2** 作为发出多工具调用的模型，我希望程序调用及其余 Action 按顺序执行，以便等待和恢复后仍从正确的位置继续。
- **S3** 作为恢复 Run 的宿主，我希望模型使用与权威 Snapshot 一致的工作导航，以便继续执行时依据可核验的阶段结果和重要信息。

| R2.1 | S2 | 事件 | 无需父级审批的 `execute_program` 是新批次队首、持久批次的后续成员或最后一项 | 开始程序时同一检查点保存父 Action 的程序状态和消费队首后的剩余批次。批次身份与剩余顺序稳定，末项消费后清除游标。程序结算后从下一项继续，已消费的程序不会重新入队。 | 以 `[程序, B, C]`、`[A, 程序, C]` 和程序位于末尾覆盖新建、切片与清空。核对实际调用顺序、每项结算次数、持久指针和中间无额外 Decide。 |
| R2.2 | S2 | 状态 | 批次中的父程序需审批，或程序子工具等待审批、未知结果决定或宿主重启 | 父级等待检查点已经消费当前批次项，批准启动程序时保留其余项。子工具沿用暴露范围、最终获批参数与恢复身份校验。父程序仍未结算时后继项不执行，成功结算后按原顺序继续；取消和失败沿用现有结算规则。 | 覆盖父级审批、子调用审批与重启，观察指针未二次推进。使用真实 PTC worker 验证越权拒绝、未知写入无自动重试、取消与后继顺序。 |
| R2.3 | S2 | 异常 | 程序开始检查点保存失败，或已保存但 worker 尚未启动便中断 | 保存前失败不启动本次程序，已保存批次仍按原位置恢复。保存成功时以同一检查点的父程序身份、子调用位置和剩余批次为准，沿用现有恢复门禁。 | 注入开始检查点保存前故障及保存后 worker 启动前中断，重开文件 Snapshot／Trajectory。核对程序 ID、剩余 Action 和受控副作用次数。 |
| R3.1 | S3 | 状态 | 从 Snapshot 为当前 Run 及归档 Run 恢复历史阶段和 Context Notes | 以每个 `(goalId, runId)` 各自的 `committedThroughSequence` 选取可见事实。事实追加后保存失败留下的接受记录和 note 修订不进入导航。Snapshot 已保存时，缺失 marker 不降低其可见水位。 | 为当前和归档 Run 构造不同水位及重叠序列号，注入保存失败和 marker 失败。通过实际模型输入投影确认边界内事实可见，边界外阶段和 notes 均不可见。 |
| R3.2 | S3 | 异常 | 导航读取遇到 I/O／协议错误，或启用 Trajectory 的 Run 声明非零水位但缺少该提交边界 | 返回保留 Goal／Run 身份和原错误的恢复失败，停止本次依赖该导航的模型推进。确实无历史的空结果与未配置 Trajectory 的受支持入口沿用既有语义。 | 分别注入当前和归档 Run 的读错误、坏记录、缺失水位及零水位空历史，捕获诊断和模型调用次数。 |
| R3.3 | S3 | 事件 | 正常执行期间阶段重开、重新接受或 note 修订后，以相同 Snapshot 重建导航 | 实时推进与冷恢复提供相同的历史接受结果和有效 note 版本。重开的当前阶段显示执行中，历史条目保留最近一次已提交的接受结果及其版本，直到重新接受。旧 Run 历史仍只能用于导航，当前完成 Evidence 继续受本 Run 校验。 | 对比同一水位的实时和重建模型输入。覆盖同一阶段重开、修订与再次接受，note 修订、跨 Run 重名阶段，以及用旧 Run 事实提交完成证据被拒绝。 |

组合：用文件 Snapshot 和 Trajectory 串联 Plan 拒绝、恢复及重新接受。经正式 Decide 多调用解码和 macOS Seatbelt PTC worker 验证批次、审批及恢复，并在实际模型请求组装处核对导航。运行 `npm test` 和 `npm run check:docs`。

## 决策

| 决策 | 理由 | 放弃 |
|---|---|---|
| 在现有 [Plan 路线所有者](../../packages/runtime/src/run-plan.ts) 表达末阶段重开，由 [Runner](../../packages/runtime/src/runner.ts) 与现有阶段拒绝转换合成一次提交。重开是阶段结算，保留已批准路线内容及版本。 | `currentStage` 与路线游标必须同时满足正式 Storage 跨字段约束。 | 无 |
| 程序首次暂存复用 Runner 的 `pendingBatchPatch`，在保存 `pendingProgram` 的检查点同步写入。审批入口沿用等待提交时的批次消费及 [RC06 的执行与恢复交接](../runtime-stop-and-approved-action-handoff/spec.md)。 | 同一队首只有一个推进时点，程序开始与剩余批次可从同一 Snapshot 恢复。 | 无 |
| 通过 [RunRecoveryReader](../../packages/runtime/src/run-recovery-reader.ts) 读取各 Run 的提交视图。Runtime 维护瞬时导航投影的增量与重建语义，`model-context` 消费投影。 | Snapshot 持有可见水位，Trajectory 持有事实，导航无需另存历史副本。 | 无 |

## 风险与否定性保证

| 等级 | 理由 | 关键操作 |
|---|---|---|
| high | 批次恢复点控制工具调用顺序和副作用；阶段与导航参与后续模型决策和证据核验。 | 验收使用临时存储、可控模型和隔离工具。 |

PTC 活动时间预留继续按既有恢复规则计费，导航的提交过滤仅适用于导航来源。保留现有 Storage 校验、审批及未知结果恢复门禁。
