# Goal 看板前端架构重构 需求

## 引言

本需求旨在对 LazyGoal 浏览器前端应用（`@lazygoal/goal-board`）的 `main.tsx` 进行模块化架构重构，消除承担过多职责的上帝文件（God File）与上帝组件，将杂糅的内联子组件物理剥离为单职责模块，将 SSE 实时流、快照同步、命令交互与排队调度等副作用抽离为独立领域 Hooks。重构严格坚持现有功能与交互行为 100% 等价保真，优先基于 React 原生能力治理状态流，全程依托单元测试与 E2E 浏览器自动化测试保障安全演进，并在完成后同步更新模块架构文档与语义表。范围不涉及后端 HTTP/SSE 协议变更及底层数据模型调整。

## 需求

### 需求 1：功能与交互行为 100% 等价保真

**用户故事：** 作为使用 Web 看板交互的最终用户与开发者，我希望重构后的前端在所有交互功能与视觉呈现上保持完全一致，以便在享受更稳定系统架构的同时不改变任何已有使用习惯和交互体验。

#### 验收标准

1. <a id="req-1-1"></a> 当用户在 Goal 看板进行会话选择、搜索过滤、归档切换、新建 Goal 及删除等操作时，系统的视图响应、状态更新与视觉布局必须与重构前完全一致。
2. <a id="req-1-2"></a> 当活动 Run 产生流式输出、工具执行状态变更或完成提交时，系统的文本逐字追加、实时活动提示标签及完成态收敛行为必须保持严格等价。
3. <a id="req-1-3"></a> 当用户触发 Steer 输入引导、Interrupt 中断、Resume 恢复或交互审批指令时，系统的控制按钮使能禁用逻辑、忙碌状态展示及错误回退处理必须与重构前完全一致。
4. <a id="req-1-4"></a> 当用户在会话中切换至 Trajectory 标签页或在活动记录中点击特定执行单元时，系统的轨迹聚焦定位与历史复盘联动行为必须保持完全保真。

### 需求 2：顶层主入口收敛与视图组件物理剥离

**用户故事：** 作为前端代码维护人员，我希望 `main.tsx` 仅承担顶层装配与路由组合职责，以便清晰理解系统组件树拓扑并消除 2000 行的巨型上帝文件。

#### 验收标准

1. <a id="req-2-1"></a> 系统必须将原本内联定义在 `main.tsx` 中的子组件（包括但不限于 GoalCard、ModelPicker、MessageComposer、PermissionControl 及 WorkspaceContext）物理剥离至独立的单职责源码文件中。
2. <a id="req-2-2"></a> 系统必须将看板列表主视图（BoardView）与会话主视口（SessionView）拆分为独立的业务组件模块。
3. <a id="req-2-3"></a> 重构后的 `main.tsx` 必须仅保留根应用挂载、全局上下文提供以及顶层视图布局装配逻辑，其代码体量必须收敛至 200 行以内。
4. <a id="req-2-4"></a> 剥离后的所有视图组件必须严格保留现有的 DOM 结构层级与 CSS 类名定义，严禁引入改变几何排版的不必要嵌套标签。

### 需求 3：运行时状态与网络流抽离为自治领域 Hooks

**用户故事：** 作为系统架构师，我希望将散落在 UI 中的异步流与状态机封装为内聚的业务 Hooks，以便实现视图层与领域控制层的彻底解耦，提升逻辑的可测试性。

#### 验收标准

1. <a id="req-3-1"></a> 系统必须提供独立的 SSE 事件流 Hook，负责连接生命周期维护、断线重连重试以及实时生成文本和活动状态的缓冲聚合。
2. <a id="req-3-2"></a> 系统必须提供独立的会话快照 Hook，负责管理活动 Goal 的 Snapshot 加载、只读刷新请求以及草稿态会话的临时维护。
3. <a id="req-3-3"></a> 系统必须提供独立的消息队列控制 Hook，负责管理客户端输入排队列表、当前 Run 状态与入队消费的有限状态机流转，并具备严格的单飞锁（In-flight Lock）防重机制。
4. <a id="req-3-4"></a> 系统必须提供独立的命令分发 Hook，负责承载 Steer、Interrupt、Resume 及 Interaction 调用的统一忙碌标记与错误降级。

### 需求 4：优先原生轻量状态治理与依赖边界

**用户故事：** 作为项目维护者，我希望前端架构遵循轻量化与高内聚原则，以便避免过度设计和无谓的打包体积膨胀。

#### 验收标准

1. <a id="req-4-1"></a> 系统的跨组件状态通信必须优先基于 React 原生能力（自定义 Hooks、`useReducer` 状态机及局部 `Context`）组织，严禁为了重构引入 Redux 等笨重状态库。
2. <a id="req-4-2"></a> 如果重构设计与验证表明原生状态跨层共享存在极端繁琐度，系统仅允许在充分评估后引入极简状态库（如 Zustand），严禁引入其他未授权的第三方运行时依赖。
3. <a id="req-4-3"></a> 系统的领域状态共享必须采用按职责切分的局部 Context 隔离范围，严禁将所有正交状态全部提升至单一大 Context 造成全树重复渲染。

### 需求 5：渐进式重构验证与测试安全网保全

**用户故事：** 作为质量保证工程师，我希望重构过程具备持续、可验证的安全防护网，以便在任何阶段都能即时捕获潜在的回归缺陷。

#### 验收标准

1. <a id="req-5-1"></a> 重构方案必须划分为小步渐进的实施阶段，且在实施任何重构代码改动前，现有的单元测试与 E2E 浏览器自动化测试必须确认为全绿基线。
2. <a id="req-5-2"></a> 在每个重构阶段完成物理迁移或 Hook 抽离后，系统必须成功执行已有的所有自动化测试（包括 `e2e/board.test.mjs` 与 `e2e/runtime.test.mjs`），不得跳过、删减或弱化现有测试用例。
3. <a id="req-5-3"></a> 当任何阶段的测试出现选择器断言或布局几何误差时，系统必须立即在当前阶段修复，严禁将破坏性变更带入下一阶段。

### 需求 6：架构文档与语义契约同步更新

**用户故事：** 作为后续维护 LazyGoal 的贡献者，我希望前端模块的文档与当前最新架构实现保持高度同步，以便清晰理解各模块的设计边界与职责分工。

#### 验收标准

1. <a id="req-6-1"></a> 在代码拆分与状态下沉全部完成后，系统必须同步更新 `apps/goal-board/README.md`，准确说明重构后的分层目录结构与入口职责。
2. <a id="req-6-2"></a> 系统必须同步更新 `apps/goal-board/notes/overview.md` 和 `notes/semantics.md`，完整记录新增组件与领域 Hooks 的职责归属、数据流向和权威概念定义。
3. <a id="req-6-3"></a> 系统在完成文档修订后必须通过 `npm run check:docs` 校验，确保所有跨模块引用链接有效且格式规范。

## 风险与待确认

- 风险等级：medium；理由：虽然重构属于不改变外部网络契约的前端内部调整，但由于涉及核心上帝文件 `main.tsx` 2000 行代码的彻底解耦，且 E2E 测试对 DOM 结构与流式时序极其敏感，需要依赖严格的分阶段验证策略控制风险。
- 关键操作：无
- 风险：
  - 子组件抽取时若无意添加额外父级包裹元素，可能破坏现有 E2E 测试中的 DOM 层级与尺寸断言。
  - 队列调度（Queue）与 SSE 事件流从主组件解耦时若状态同步机制不当，可能在高频并发下出现出队竞态。
- 待确认：无
