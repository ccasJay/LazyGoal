# 文本流式会话完整接入 Spec

## 目标与范围

LazyGoal 提供长期开放的文本 Session：宿主持续提交输入，同时异步消费执行事件；一个 Session 对应一个持久化 Goal，并跨越多个 Run。现有无界面运行时与 Web 共享受理、队列、调度、交互与恢复规则，不再依赖浏览器保持在线来执行已受理的后续任务。

本次在现有 Node.js／TypeScript Runtime 与应用装配中实现单条和异步流输入、持久化消息队列、显式 Steer／Interrupt、可恢复问答与审批、跨 Run 输出订阅、重连同步、单消息封装，以及 Web 端完整接入。普通消息默认进入下一 Run，只有显式 Steer 修正当前 Run；进程重启后先恢复和展示状态，必须由用户或宿主显式恢复执行。

支持单进程内多个 Session 句柄连接同一 Goal，同一 Runtime 实例最多执行一个活动 Goal。等待人工交互的 Goal 可保留状态而释放活动执行名额。内部会话入口复用现有模型、工具、权限、上下文、指标和实例生命周期；不改变普通 Run、Plan Run、阶段审查或完成证据规则。

本次不提炼 SDK 包，不新增 `packages/sdk`，不将应用默认装配迁入新包，也不承诺通用对外 SDK API。图片、附件、音视频、MCP 接入、工具热更新、子代理、多活动 Goal 并行、跨进程租约、分布式任务队列、浏览器内执行模型、终端交互界面和 npm 公共发布均不包含在内。不迁移既有开发期 Snapshot，不自动删除本地 Goal。CLI 保持启动宿主和无头命令职责，不恢复已退役的 TUI。

## 需求与验收标准

### 需求 1：现有运行时中的长期 Session

作为宿主开发者，我希望通过现有无界面装配获得稳定 Goal 句柄，以便提交输入和观察活动而不启动 HTTP 服务。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当通过内部会话入口创建 Session 并提供首条文本、稳定 Goal／输入身份及执行配置时，系统应先持久化 Goal、首条用户消息、Run 和受理收据，再返回句柄并启动执行；返回不得等待 Run 完成，首次保存失败不得调用模型或工具。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当连接已有 Goal 时，系统应返回同一 Goal 的 Session 和最新可见状态，不创建替代 Goal、不调用模型或工具、不自动消费队列；不存在、数据损坏或配置无法解析时应明确失败。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当一个 Run 到达 waiting、completed、failed 或 cancelled 时，Session 应保持开放并报告真实状态；只有显式解除连接、订阅结束或 Runtime 关闭才结束对应连接，不能将 Run 结束等同于整个会话结束。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当仓库内无界面调用方通过现有 `apps/goal-server/src/runtime/index.ts` 装配入口，使用默认依赖或注入符合契约的执行器、工具与存储时，应能完成创建、流式交互、审批、关闭和重建恢复，无需启动 HTTP、绑定端口、注册进程信号或手动组合 Runner；不要求独立安装的 SDK 包。
- <a id="spec-req-1-5"></a>**验收标准 1.5**：当重试创建请求而目标 Goal 已存在时，应核验原创建身份和载荷后连接原 Goal；即使首条输入尚未完成，也不得将创建重试当作重启后的执行恢复指令。

### 需求 2：单条与异步流输入共享受理语义

作为输入生产者，我希望知道消息是否已保存，并能在执行期间继续发送控制命令。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当调用 `send(input)` 时，系统应在该输入及收据提交后返回类型化受理结果；受理成功仅表示输入已保存，不表示消息已应用、工具已停止或 Run 已完成。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当 `consume(inputs)` 消费 `AsyncIterable<SessionInput>` 时，应逐条等待受理结果后读取下一项，不等待业务执行结束；每项均走与 `send` 相同的规则，模型或工具等待期间合法 Steer／Interrupt 仍可受理。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当同一 Goal 内重复提交同一 `inputId` 和规范化载荷时，应返回原收据，不重复入队、应用消息、批准 Action 或创建 Run；同一身份携带不同种类或载荷时应返回身份冲突，且不得改写原记录。去重判定先于过期 Run 等状态拒绝。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当输入不满足当前状态、队列容量、权限或关联身份时，应报告稳定的拒绝原因且不报告已受理；输入流中的业务拒绝应作为对应输入结果输出，并继续读取后续项。保存或受理基础设施失败时，应停止该输入消费者，不预取后续项，并报告可按原身份核验和重试的错误。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当输入源正常结束时，只应结束该来源的消费，已受理输入继续处理，Session 和输出保持开放；当输入源抛出异常或消费被主动停止时，应保留原始原因、停止读取该来源并保留已受理工作，不伪造 Goal 失败或取消，也不关闭其他来源。

### 需求 3：默认排队并在 Runtime 持久化

作为连续提交任务的用户，我希望关闭页面后已受理消息仍可按顺序执行。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当 Goal 正在执行或等待交互时收到普通消息，应按受理顺序保存为该 Goal 的后续队列，不改写当前 Run 的模型输入或批准等待；Goal 处于可启动的终态且无恢复或队列暂停约束时，应为队首消息创建后继 Run。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当当前 Run 正常完成且队列未暂停、执行所有权仍有效时，应按 FIFO 为每条普通消息分别创建一个后继 Run；用户消息追加、新 Run 创建及队列项绑定应在同一 Snapshot 提交边界完成，崩溃或响应丢失不得形成重复 Run。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当 Run 等待问答、任务批准、工具批准或未知结果处理时，队列不得替代当前交互或启动后继 Run；当 Run 失败或 Interrupt 被受理时，应持久化暂停队列并保留尚未应用的消息，只有显式继续队列才解除暂停。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当暂停后收到新的普通消息时，应保留暂停状态并将新项追加到队尾；当显式继续队列时，应从原队首启动，不能跳过旧项。显式清空队列只能清除尚未应用的普通消息，保留收据、真实对话和正在执行的 Run。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当浏览器刷新、连接断开或进程关闭时，已确认受理的队列顺序、暂停状态和输入身份应由持久化恢复；前端不得使用本地队列重新提交一份已受理任务。请求结果不明时，应先按原身份查询或重试。
- <a id="spec-req-3-6"></a>**验收标准 3.6**：当单条文本超过 64,000 个 UTF-16 code unit，或普通消息与 Steer 的未应用项合计超过 128 项、正文合计超过 1,048,576 个 UTF-16 code unit 时，应拒绝新增项而不丢弃旧项；重复请求不重复占用额度，Interrupt、审批回答、恢复和队列清空不受文本队列额度阻塞。

### 需求 4：显式 Steer 修正当前 Run

作为用户，我希望补充要求能够作用于当前任务，同时知道它何时真正生效。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当收到关联当前 running Run 的合法 Steer 时，应保存同一 Run 的待应用输入，不创建后继 Run、不取消在途模型或工具调用，并分别报告已受理和已应用状态；非 running、旧 Run 或已进入 Interrupt 的新请求应明确拒绝。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当执行器到达既有模型安全边界时，应按受理顺序应用待处理 Steer，提交真实用户消息及应用位置，再重建后续请求；正在进行的工具先按既有规则结算，失效的 Think／纠错指针不能继续用于新输入。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当 Steer 受理与完成提交竞争时，先受理的 Steer 应阻止旧输入产生的正常完成越过它；完成先提交则新 Steer 明确拒绝，不能静默改为普通队列消息。被替代且尚未执行的旧决策不能触发新的 Action 或终态。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当 Steer 被拒绝或结果不明时，Web 应保留草稿或可核验的提交身份；当进程重启后恢复同一 Run 时，应保留已受理 Steer 的身份、顺序及应用位置，不重复追加用户消息。

### 需求 5：显式 Interrupt 与可观察的有限收尾

作为用户，我希望主动停止当前任务，并准确了解工具是否已经停止及是否仍存在未知效果。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当收到带目标 Run 和稳定输入身份的 Interrupt 时，应在相同提交边界保存中断意图并暂停队列，然后确认受理、停止原任务的正常调用准入、中止原模型调用并请求工具或 worker 停止；该操作不得中止其他 Goal 或整个 Runtime。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当已启动操作的效果未知时，应沿用现有 Interrupt 的同一 Run 有限核查、修复、审批与预算规则；不能仅因未知而重复原操作，不能恢复原任务的正常推进，不能声称效果已回滚或伪造成功的工具返回。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当中断进行时，无界面会话调用方和 Web 应区分持久化受理、停止／收尾、等待必要审批与最终 cancelled，并展示未解决的未知结果；只有资源停止并按既有规则完成或耗尽有限收尾后才报告取消完成，收尾等待不能被误报为已取消。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当 Interrupt 受理后重启时，应保留原中断身份、阶段和已消耗预算；显式恢复只能继续剩余收尾及取消结算，不恢复原任务，不能重置预算。取消后新任务仍须通过显式继续队列或合法的新输入处理暂停约束。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当多个 Interrupt、Steer、终态提交或关闭竞争时，应返回可核验的同一中断收据或稳定拒绝；不能正常完成仍未结算的已受理中断，普通关闭或连接断开不得生成用户 Interrupt。

### 需求 6：可恢复的问答、审批和安全控制

作为交互式宿主，我希望通过事件接收请求并用准确身份回答，而不依赖悬挂的进程内回调。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当 Run 需要问答、Plan 任务批准、Action／沙箱批准或既有恢复选择时，应先保存完整等待及关联身份，再向 Session 输出安全投影；关闭连接或重建实例后仍能查询和回答同一等待。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当提交交互回答时，应核验 Goal、Run、请求及必要 Action 身份，并通过既有 Coordinator／权限规则应用；旧请求、重复但载荷不同的回答或普通文本不得解除等待、扩展授权或重复执行已结算 Action。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当通过现有无界面控制入口或 Web 切换模型、选择 Plan 模式、查看或撤销权限时，应保持既有安全点和规则所有者；新 Run 启动前从最新 Goal 对齐模型 Binding，不能继承另一个 Goal 的进程绑定。排队消息的受理不冻结未来模型选择，实际应用时的选择必须可查询。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当宿主注入现有自定义工具或执行器时，应经相同发现、授权、校验、审批、执行与恢复路径使用；工具可见不等于已经授权，公开接口不得提供绕过规则的直接 Action 执行入口。

### 需求 7：跨 Run 输出、重连与背压

作为输出消费者，我希望持续观察同一 Goal，并在连接异常后恢复可信状态。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当创建订阅时，应先建立观察边界并输出一致的 `state_sync`，随后输出该 Goal 的输入结果、Run／Step／Tool 活动、公开模型文本、交互等待与终态事件；后继 Run 切换不关闭订阅、不遗漏开始事件，事件须携带真实 Goal／Run 及必要调用身份。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当读取初始状态与发布活动并发时，应通过一致快照与缓冲交接保证已提交变化能由同步状态或后续通知观察到；不能把读取前的旧增量重放为当前回复，也不能把模型或工具分片当作已提交结果。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当连接重建或出现事件缺口时，应重新同步最新 Snapshot、输入收据、队列和等待状态，并丢弃失效的临时文本；历史 Run 和已提交事实通过只读查询按需读取，不承诺重放断线期间的每个实时分片。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当消费者速度不足时，应沿用有界队列和相邻增量合并；无法保留控制事件时应明确关闭该订阅并报告 `backpressure`，不得静默丢弃控制结果、无限缓冲或让慢消费者阻塞状态提交和执行。
- <a id="spec-req-7-5"></a>**验收标准 7.5**：当退出输出迭代、监听器抛错或取消某个订阅时，应仅释放该订阅资源，其他订阅、输入消费者及已受理执行保持有效；默认事件不包含隐藏推理、密钥、原始 Provider 响应或任意完整工具参数／输出。
- <a id="spec-req-7-6"></a>**验收标准 7.6**：当末次提交通知丢失且没有后续实时事件时，健康订阅和等待结果的单消息调用仍应通过只读状态核对发现已提交的等待或终态，不能无限停留在旧状态；核对读取失败应明确报告同步故障，不伪造业务结果。

### 需求 8：重启恢复、并发与资源生命周期

作为运行时所有者，我希望恢复与关闭的后果明确，避免失联任务自动产生副作用。

- <a id="spec-req-8-1"></a>**验收标准 8.1**：当进程重建、连接已有 Goal 或只读查询时，不得自动执行活动 Run、中断收尾或已受理队列；应展示无执行所有者的可恢复状态。普通消息可以继续受理到该 Goal 的队列，但不能隐式解除已有恢复或暂停约束。
- <a id="spec-req-8-2"></a>**验收标准 8.2**：当用户或宿主提交匹配最新 Run 与提交修订的显式恢复命令时，应按 Snapshot 恢复当前 Run 或已受理队首；有待回答／审批时应报告所需交互并保持等待，恢复不得代答。因失败或 Interrupt 暂停的队列仍须显式继续。
- <a id="spec-req-8-3"></a>**验收标准 8.3**：当多个客户端对同一 Goal 提交输入或控制时，应使用同一个短提交边界确定受理顺序、身份和状态；同一 Run 只能有一个执行所有者，Snapshot 更新不得覆盖并发受理的队列、Steer、中断或模型选择。
- <a id="spec-req-8-4"></a>**验收标准 8.4**：当一个 Goal 占用实例活动执行名额时，其他 Goal 的新执行、交互推进或输入受理应明确返回 busy 且不偷偷进入全局调度队列；活动 Goal 的合法输入、Interrupt、读取和订阅不得被长调用锁住。名额释放后的执行必须重新对齐目标 Goal 的 Binding。
- <a id="spec-req-8-5"></a>**验收标准 8.5**：当 Session 解除连接时，应停止该句柄的输入消费和订阅并拒绝后续句柄调用，但不删除 Goal、不取消执行、不暂停已受理队列；当 Runtime 关闭时，应由既有生命周期停止受理、结算已受理写入、执行任务和自有资源，关闭不创建用户取消终态。
- <a id="spec-req-8-6"></a>**验收标准 8.6**：当关闭未能完整结算时，应保留类型化错误及真实未确认结果，不能报告安全关闭或立即重用存储；当归档或删除 Goal 时，应拒绝活动、未完成收尾或仍有待处理输入的 Goal，要求先明确处理或清空队列，不自动丢弃已受理工作。

### 需求 9：无界面运行时、Web 和单消息调用完整接入

作为维护者，我希望各入口使用一套实现并有可重复的交付证据。

- <a id="spec-req-9-1"></a>**验收标准 9.1**：当 Web 发送文本时，应走统一 Session 受理入口；运行中默认排队，并提供显式 Steer 与 Interrupt；界面应分别展示草稿、正在提交、已受理队列、待应用 Steer、当前消息和停止阶段。拒绝不得清空草稿，结果不明不得用新身份重复发送。
- <a id="spec-req-9-2"></a>**验收标准 9.2**：当 Web 刷新、切换页面或多标签连接时，应从 Runtime 同步队列、暂停、收据及等待状态，不依赖 `localStorage` 或前端 effect 调度后继 Run；迁移后删除旧队列的自动提交和第二套执行预约职责，不导入旧本地队列作为任务。
- <a id="spec-req-9-3"></a>**验收标准 9.3**：当提供单消息封装时，应复用同一 Session 执行链，并在指定 Run 完成、失败、取消或等待交互后返回对应结果及可恢复身份；封装自己的订阅应被释放，调用结束不能关闭借用 Runtime，也不能假装等待已成功完成。
- <a id="spec-req-9-4"></a>**验收标准 9.4**：当现有 CLI 启动 Web 或无头入口执行任务时，应保留宿主信号、进程退出和各 Benchmark 的环境／预算语义；迁移范围仅为会话受理与观察入口，现有默认装配保留在应用目录，不重写 Benchmark 评分器或引入交互式终端。
- <a id="spec-req-9-5"></a>**验收标准 9.5**：当功能交付时，应提供通过现有无界面装配入口执行的仓库内调用示例，以及真实 Web 服务的文本发送、队列、Steer、Interrupt、审批、断线和重启恢复验收；应以确定性故障注入验证保存后崩溃、受理响应丢失、完成竞争、多客户端和慢消费者，不能仅凭类型导出或目录存在认定完成。
- <a id="spec-req-9-6"></a>**验收标准 9.6**：当模块导出接口、持久化字段或职责变化时，应同步中文契约 TSDoc、最小示例、所属模块说明与语义表，并通过适用的类型检查、依赖门、文档检查和受影响回归；Runtime 会话模块不得反向依赖 apps，现有无界面装配不得依赖 Browser／HTTP 或进程退出实现。

## 架构与核心决策

### 当前依据与功能边界

当前 [执行装配](../../apps/goal-server/src/runtime/execution-composition.ts) 已组合 Launcher、Runner、InlineScheduler 和 Coordinator；[无界面装配](../../apps/goal-server/src/runtime/composition.ts) 与 HTTP 宿主分开，但仍属于应用内部。`launch`／`continue` 等执行命令等待运行到等待点或终态；[Browser 命令服务](../../packages/browser/src/browser-goal-command-service.ts) 持有后台任务、单活动 Goal 预约和内存受理去重。[前端队列](../../apps/goal-board/src/hooks/useQueue.ts) 由页面状态与 `localStorage` 驱动，不是 Runtime 的持久化输入。

[执行流](../../packages/execution-stream/notes/overview.md) 当前按 Goal／Run 发布进程内有界事件，没有历史重放；[Runtime](../../packages/runtime/notes/overview.md) 和 [Storage](../../packages/storage/notes/overview.md) 持有执行与持久化规则。本 Spec 将受理、队列及执行所有权收回 Runtime，并在上层提供 Session。

本 Spec 延伸 [Runtime SDK 化准备](../runtime-sdk-extraction/spec.md)：继续复用其执行、无界面装配和关闭边界，不新增 SDK 包；本次增加该规范原范围外的持久化队列与自动后继 Run，装配位置保持不变。[Run 输入控制](../run-input-control/design.md) 继续拥有 Steer 和有限 Interrupt 收尾；本次替换其页面 Queue 所有权与发送默认值，扩展统一受理及观察接口，不重新设计收尾算法。[Web 后端分离](../web-backend-separation/design.md) 的同源访问控制与 [Permission](../permission/design.md) 的授权规则保留。

继续使用现有 `createRuntimeComposition` 和执行组件的注入入口传递工作区、Home／数据位置及现有执行器、工具和持久化 Port，不新增通用 `createRuntime` 工厂。默认值沿用当前配置优先级，不通过切换进程工作目录隔离实例。凭据、函数、连接和进程句柄不写入 Goal。装配创建的资源由现有生命周期结算，宿主借出的依赖仍归宿主关闭；不把注入对象自动登记为自有资源。

### Session 接口与输入协议

下表规定仓库内部会话契约。`sessions` 表示现有无界面装配返回的会话操作，`session` 表示其中的 Goal 句柄；它们不构成独立安装或对外稳定的 SDK。类型声明在实现时复用现有契约并补齐中文 TSDoc。

| 操作 | 输入及结果 | 生命周期语义 |
| --- | --- | --- |
| `sessions.create(...)` | 稳定 `goalId`、首条 `{ inputId, content }`、Profile／模式及必要初始选择；返回已受理的 Session 和首条收据。 | 创建并启动首个 Run；同身份同载荷重试关联同一 Goal，冲突明确拒绝。 |
| `sessions.open(goalId)` | 已存在 Goal；返回新的轻量句柄。 | 只读连接，不推进。多个句柄共享 Runtime 所有者，不各自启动执行器。 |
| `session.send(input)` | 一条 `SessionInput`；返回受理收据或稳定业务拒绝。 | 等待持久化受理，不等待 Run。调用方保留 `inputId` 以核验响应丢失。 |
| `session.consume(inputs)` | `AsyncIterable<SessionInput>`；返回来源结束或异常。 | 顺序读取并复用 `send`；业务拒绝由输入结果事件报告，基础设施失败停止读取。消费控制只停止该来源。 |
| `session.events()` | 返回独立、单消费者的异步订阅。 | 调用时建立订阅，不延迟到首次 `next()` 才建立；首项是 `state_sync`，Run 结束不关闭。 |
| `session.read()`／`session.getInput(inputId)` | 最新状态或持久化收据。 | 只读、不推进；用于重连和不确定受理结果核验。 |
| `session.detach()` | 无。 | 幂等释放该句柄的订阅与输入源；不接管共享 Runtime 关闭权。 |
| `sessions.query(createRequest)` | 与创建 Session 相同的稳定创建请求；返回首个 Run 的完成、失败、取消或等待及关联身份。 | 是一次任务的内部便捷封装，创建／连接 Session 并等待对应首个 Run，不另建执行循环；复用原身份查询结果不隐式恢复旧任务。 |
| `lifecycle.close()` | 现有实例关闭选项。 | 沿用装配返回的 `RuntimeLifecycle`，停止受理并结算活动；不退出宿主进程。 |

`SessionInput` 使用可辨识联合：普通 `message`、`steer`、`interrupt`、`respond`、`resume` 和 `queue_control`；每项都有 Goal 内稳定 `inputId`。`steer`／`interrupt` 必须带目标 `runId`；`respond` 带当前交互及必要 Action 身份；`resume` 带最新 Run 和提交修订；`queue_control` 支持继续与清空，带被观察到的队列修订以拒绝失配操作。正文只接受非空文本，不提供隐式消息种类猜测。

普通消息面向 Goal，不固定绑定发送时的旧 Run；受理顺序决定它在队列的位置，应用收据给出唯一实际 Run。Steer 和控制请求面向明确的 Run。恢复、继续队列与审批都是显式输入，不从 `sessions.open`、`state_sync` 或输入流 EOF 推断执行授权。

输入原始身份、种类和规范化载荷摘要组成去重键的判定内容；仅按有契约定义的字段规范化，不改写用户正文。首次调用方必须保存身份，不能在网络重试时生成新身份。业务拒绝不写为已受理收据，必要时仍发布本次输入结果；实时通知缺失时，以 `getInput` 结果为准。

输入源由宿主拥有。停止消费或解除句柄后，即使尚未结束的 `next()` 迟到返回，也不能继续受理该项；会话模块尝试调用迭代器的 `return()` 释放来源，但不将任意宿主 Promise 视为可强制取消的资源。宿主负责让自定义输入源响应其取消信号，会话与实例关闭不能永久等待不合作的来源。

### Web 传输映射

| HTTP／SSE 入口 | 映射 |
| --- | --- |
| `POST /api/goals` | 创建首条输入与 Session，增加稳定首条 `inputId`，保存成功后返回 Goal／Run 和收据。 |
| `POST /api/goals/:goalId/inputs` | 接收 `SessionInput` 联合；新受理返回 202，既有同载荷收据返回 200；拒绝明确区分字段错误、身份／状态冲突、busy 和关闭，不返回成功收据。 |
| `GET /api/goals/:goalId/inputs/:inputId` | 查询持久化收据及应用关联；未找到明确返回不存在，读取失败不能伪装为不存在。 |
| `GET /api/goals/:goalId` | 返回安全会话投影，包含队列、输入状态、暂停、交互、提交修订及是否需要显式恢复。 |
| `GET /api/goals/:goalId/events` | 订阅整个 Goal，输出 `state_sync` 后持续覆盖后继 Run，不再要求客户端绑定单一当前 Run。 |

Web 的消息、Steer、Interrupt、交互和恢复调用迁入统一 inputs 入口，删除被替代的独立控制路由及旧 DTO；不为开发期旧 wire 增加兼容分支。模型、权限、Provider、只读历史与管理接口保持各自入口，但写操作委派同一 Runtime 规则与提交边界。所有入口沿用现有精确 Host、同源 Origin、Bearer 与长度校验；SSE 默认只发送公开白名单，错误响应脱敏。

### 持久化与提交顺序

Goal Snapshot 是队列、收据及当前状态的唯一权威，新增最小会话状态如下：

| 数据 | 用途 |
| --- | --- |
| Goal 级单调提交修订 | 标识同一 Goal 的每次成功状态变更，跨 Run 保持递增；用于恢复命令、状态同步和竞态判定，不复用 Run 内 Trajectory sequence。 |
| 单调输入受理序号与输入账本 | 保存 `inputId`、种类、载荷摘要、受理序号及 pending／applied／cleared 状态；应用后保留对应 Run、消息或控制记录引用。 |
| 待处理普通消息及队列修订／暂停原因 | 保存尚未应用的正文和 FIFO；暂停原因区分失败与用户中断，队列变更更新修订。 |
| 现有 Run 内 Steer／Interrupt／交互状态 | 继续由执行器拥有，账本指向对应执行记录；应用后的正文来自真实 Conversation，不重复维护一份可变正文。 |

统一受理账本承接 Browser 内存去重和后继 Run 重试的受理判定；既有 continuation 等记录仅保留仍被执行历史需要的关联，不另持一套互相竞争的去重结果。收据长期保留，不在去重保证仍有效时静默截断；大 Goal 的账本增长属于明确成本，本次不增加压缩或归档协议。

每个 Goal 复用并扩展现有短暂 mutation／call Gate。受理、Steer 应用、终态、后继 Run、模型选择及管理写入都读取最新状态后提交；Gate 不跨越模型、工具或人工等待。所有 Snapshot 写路径共同维护提交修订，不能通过裸 `store.save` 绕开当前边界。

受理流程是：查询既有收据 → 核验状态与容量 → 追加事实并提交 Snapshot → 返回收据／发布通知 → 唤醒执行所有者。跨 Run 消费在一次 Snapshot 中归档旧 Run、将队首标为已应用、追加用户消息并创建新 Run；只有提交成功后才执行新 Run。保留先追加事实、保存 Snapshot、再发布成功通知的既有顺序；未纳入提交边界的 Trajectory tail 不重放。

保存成功后、唤醒前崩溃时，输入仍可查询且需要显式恢复；唤醒或运行失败不得撤销已经确认的收据。存储错误若无法证明提交未发生，调用方必须使用原身份核验，不能断言消息不存在。该协议避免重复受理和重复创建 Run，不承诺外部工具副作用 exactly-once。

### 执行所有权、恢复与控制

Runtime 会话模块持有一个活动执行名额、按 Goal 的短提交序列及被生命周期追踪的后台执行 Promise。受理 Promise 与执行 Promise 分离；任务异常必须被观察、转为可查询的真实执行／恢复状态，不能形成未处理的 Promise rejection。无界面装配只接线并暴露操作，Browser 不另起任务或持有第二个执行锁。

活动 Goal 正常完成后，同一执行所有者可以继续消费其队列；没有后续消息或进入等待时释放名额。其他 Goal 不在后台等待名额或自动获得调度。本次不承诺跨 Goal 公平性、多个 Runtime 写同一目录或跨进程独占；宿主必须为同一存储位置使用唯一写入实例。

恢复状态由最新 Snapshot 和当前实例是否持有执行所有者共同投影，不伪造持久化的 running／cancelled 转换。重建实例后的旧活动 Run、待收尾中断或尚未消费的队列必须显式 `resume`；已暂停队列还需 `queue_control` 继续。无待恢复工作的终态 Goal 收到新消息属于新的执行指令，可以正常启动后继 Run。审批回答只推进其匹配等待；普通消息既不恢复旧 Run，也不代替回答。

Steer 与 Interrupt 委派既有控制路径。Interrupt 受理和队列暂停共同提交后，请求中止原调用；收尾继续遵守原有有界模型调用次数、工具授权和未知结果规则，不新增“无限等待工具”或“仅由用户核查才能取消”的规则。Session 的输入源错误、订阅断开与实例关闭是不同控制原因，不能转换成用户 Interrupt。

### 输出一致性与恢复来源

扩展现有事件 Core 支持 Goal 范围观察，Run 仍是每条执行事件的来源身份；不通过轮询旧 Run 结束后再订阅新 Run，避免开始事件遗漏。公开输出采用类型化联合，包含同步状态、输入受理／拒绝／应用结果、执行活动、交互等待、终态及流故障；输入结果按 `inputId` 关联，实时活动保留模型调用或 Action 身份。

订阅建立时先注册缓冲，再在同一 Goal 提交协调边界读取一致 Snapshot，记录 Goal 提交修订并首先输出 `state_sync`，随后交接缓冲。已由同步状态覆盖的旧提交通知去重；旧执行单元的暂时增量丢弃；需要保留的当前调用增量按来源顺序交接，缓冲不足明确报告缺口并要求同步，不能声称得到完整文本。后续成功提交携带相同修订关联，发现缺口时重新读取状态。

实时 cursor 只在当前 Publisher 生命周期有效；提交修订属于持久化 Goal。公开订阅不提供跨重启实时 cursor 续传承诺，也不持久化每个分片。已提交对话、收据和等待可由 Snapshot 恢复，历史执行事实由 Trajectory 的已提交边界查询；输出流既不替代这些来源，也不将事件流整体重放到 Runtime。

实时发布是旁路，发布失败不得改变已提交结果；因此宿主不能仅凭曾观察到事件证明所有收据都已送达。重连、背压和缺口走状态同步，未确认输入主动查询收据。存在订阅或单消息结果等待者时，会话模块复用提交通知，并以不超过一秒的间隔合并核对所观察 Goal 的最新提交修订，弥补最后一次通知丢失；没有观察者时不启动核对任务，核对只读不调度。读取故障作为同步错误暴露，恢复后重新同步，不将故障当作 Run 终态。单消息封装等待指定 Run 的结果，以最新持久化状态复核；遇到等待交互立即返回可恢复身份，不永久挂起等宿主尚未实现的回答。

## 曾考虑的备选方案

- **长期会话与单次请求共用 Session**：选择 Goal 作为持久化聚合、Session 作为连接句柄。备选是另建持久化 Session 与第二套状态机；它会重复 Goal 的消息、等待和恢复所有权，故不采用。
- **默认排队、显式 Steer**：按已确认行为，让每条普通任务有清晰的后继 Run 边界。备选默认修正当前 Run 会改变正在执行任务的目标，且难以表达连续独立任务，故不采用。
- **Snapshot 内的持久化输入账本**：队列与 Run 创建使用现有提交边界。备选为独立队列文件、消息中间件或 Outbox；当前单进程目标不需要额外事务和一致性协议，故不采用。
- **短受理边界与被追踪的后台执行**：复用现有 Runner，分离已受理与业务完成。备选让 `send` 等待 Run 结束会阻止同一输入流继续递交控制；无追踪的后台 Promise 又无法正确关闭和恢复，均不采用。
- **显式恢复**：进程重启和连接只读取状态。备选启动时自动恢复会在没有本次恢复指令时产生工具效果，与已确认策略冲突，故不采用。
- **状态同步加有界实时流**：保留 Snapshot／Trajectory 权威和事件旁路。备选持久化所有分片并保证事件总线 exactly-once 会扩大存储和调度协议，也不能保证工具效果 exactly-once，故不采用。
- **在现有模块实现流式会话**：Runtime 拥有会话规则，应用现有无界面目录继续装配；以仓库内调用和 Web 接入验证。备选立即新建 SDK 包并迁移默认装配，会将当前目标扩大为安装、导出和包边界提炼，现阶段按用户要求不采用；保留内部会话契约不等于承诺对外 SDK。
- **HTTP 输入与 SSE 输出**：Web 复用当前传输并映射统一 Session 协议。备选强制 WebSocket 并不会自动解决受理、去重或恢复问题，本次无新增传输需求，故不采用。

## 风险与否定性保证

- **风险等级：high**。持久化队列、运行中控制和恢复跨越模型调用、工具副作用、授权与 Snapshot 提交；竞态可能丢失已受理输入、重复执行任务或误报停止。取消 SDK 包提炼收窄了模块迁移范围，但不降低执行与恢复风险，不改变 Spec → Plan 的审批顺序。
- **关键操作**：实现涉及当前 Snapshot／Trajectory 契约原位更新、现有装配接线、队列调度所有权迁移及后台执行关闭；不得自动迁移或删除用户旧 Goal、启动真实付费模型验收、发布 npm 或修改现有权限。此类外部操作不由本 Spec 的设计批准自动授权。
- **恢复与并发验证**：必须控制受理／完成的两种提交先后顺序，覆盖 Snapshot 提交后崩溃、受理响应丢失、重复输入、后继 Run 创建中断、重启后显式恢复及多客户端竞争；实际检查清单和证据由获批后的 `plan.md` 记录，不在本阶段生成下游任务。
- **中断与授权验证**：覆盖模型、普通工具、PTC、已有未知结果处理、必要收尾审批、预算耗尽及宿主关闭；保持原中断修复范围，不把 cancelled 等同于文件回滚，不凭推测报告成功。
- **输出与资源验证**：覆盖注册订阅与读取状态竞争、快速跨 Run、断线、慢消费者、输入源异常、迭代退出、多个句柄与 Runtime 关闭超时；证明观察者不能改变执行结果，无界面装配调用不启动 HTTP 或退出宿主。
- **兼容边界**：按项目开发期政策更新当前 Schema 和测试数据，不增加旧数据解析、自动升级或无需求的版本分支；不支持的数据明确拒绝。只删除本次测试生成的数据，不以兼容性理由清空用户持久化目录。
- **否定性保证**：受理成功不能仅存在于浏览器或内存；未提交输入不得触发执行；同一输入不得重复创建 Run；新 Run 不继承旧 Run 的完成证据；队列不能代答审批；慢订阅者和客户端断开不能取消任务；重建实例不能自动产生工具调用；缺失模型 Binding 不能回退另一 Goal 的配置；未知效果不能被包装为已回滚；关闭未确认结算不能报告成功。
- **范围保证**：本次不新增 SDK 包、不迁移默认装配到新包，也不扩展为通用对外 SDK；图片与 MCP 分别另立 Spec。不引入终端 UI、通用 Hook 平台、跨进程写入支持或多活动 Goal 调度。产品可见文案保持英文，本文和新增公开契约 TSDoc 使用中文。
