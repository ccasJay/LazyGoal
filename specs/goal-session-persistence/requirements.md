# Goal Session 持久化需求

## 引言

本功能将单个 Goal 作为完整、可恢复的 Session 聚合进行持久化，以 `goalId` 定位其最新快照，同时保留独立 `runId` 与现有 Run 生命周期语义，使进程重启后仍能恢复任务定义、冻结 Profile、消息历史和当前执行进度并继续运行。

## 需求

### 需求 1：保存完整 Goal 聚合

**用户故事：** 作为 Runtime 调用方，我希望完整保存一个 Goal 的任务与执行上下文，以便后续恢复时无需重新构造已存在的信息。

#### 验收标准

1. <a id="req-1-1"></a> 当系统保存一个 Goal 时，持久化结果必须包含其 `goalId`、metadata、任务定义、冻结 Profile、全部 messages 和当前 Run 状态。
2. <a id="req-1-2"></a> 当 Goal 被保存和恢复时，其 `goalId` 必须保持不变，并作为该 Goal 聚合的唯一持久化标识。
3. <a id="req-1-3"></a> 当 Goal 包含当前 Run 时，该 Run 的 `runId` 必须与 `goalId` 分别保存且保持不变。
4. <a id="req-1-4"></a> Goal 的持久化数据必须能够完成 JSON 序列化与反序列化，不得依赖函数、连接、Adapter 或其他进程内对象才能恢复。

### 需求 2：只保留最新完整快照

**用户故事：** 作为 Runtime 作者，我希望每个 Goal 只恢复最近一次成功保存的完整状态，以便持久化语义保持简单且确定。

#### 验收标准

1. <a id="req-2-1"></a> 当同一 `goalId` 首次保存时，系统必须持久化该 Goal 的完整当前快照。
2. <a id="req-2-2"></a> 当同一 `goalId` 再次保存时，系统必须以新的完整快照替换先前快照。
3. <a id="req-2-3"></a> 当同一 `goalId` 已成功保存多个版本时，标准恢复操作必须只返回最近一次成功保存的快照，不提供旧快照或事件历史。
4. <a id="req-2-4"></a> 当快照中的 Profile 或 messages 被恢复时，系统必须保持 Profile 内容以及 messages 的内容和顺序，不得改用当前 Registry 中的 Profile 或重新生成历史。

### 需求 3：跨进程恢复 Goal

**用户故事：** 作为 Runtime 调用方，我希望在进程重启后通过 `goalId` 恢复 Goal，以便长时间任务不会因进程退出而丢失上下文。

#### 验收标准

1. <a id="req-3-1"></a> 当 Goal 已成功持久化且原进程结束后，新进程必须能够通过相同 `goalId` 恢复其最新完整快照。
2. <a id="req-3-2"></a> 当恢复成功时，返回的 metadata、任务定义、冻结 Profile、messages 和当前 Run 状态必须与最近一次成功保存的快照一致。
3. <a id="req-3-3"></a> 当指定 `goalId` 不存在时，系统必须返回可区分的未找到结果，不得创建或返回伪造的 Goal。
4. <a id="req-3-4"></a> 当恢复操作发生时，系统不得自行推进 Run、调用 StepExecutor、追加 message 或改变恢复出的快照。

### 需求 4：保持现有 Run 语义

**用户故事：** 作为 Runtime 作者，我希望 Goal 持久化不会改变现有 Run 的身份和状态转换行为，以便已有执行流程继续成立。

#### 验收标准

1. <a id="req-4-1"></a> 当 Goal 包含一个 Run 时，系统必须继续使用独立 `runId` 标识该次执行，不得以 `goalId` 替代其执行身份。
2. <a id="req-4-2"></a> 当 Goal 被恢复时，Run 的 `status`、`stepCount` 和可选 `lastResult` 必须与最近一次成功保存的值一致。
3. <a id="req-4-3"></a> 当恢复后的 Run 接收现有合法输入时，系统必须继续产生与既有状态转换规则一致的下一状态和 Step 计数。
4. <a id="req-4-4"></a> 当恢复后的 Run 接收现有非法输入时，系统必须继续返回可识别的非法转换结果，并保持当前状态不变。

### 需求 5：从恢复点继续执行

**用户故事：** 作为 Agent 调用方，我希望恢复后的 Goal 能从已保存的 Run 进度继续执行，以便不会重复已完成的 Step 或丢失累计约束。

#### 验收标准

1. <a id="req-5-1"></a> 当恢复出的 Run 状态为 `created` 或 `running` 时，现有执行流程必须能够从该状态继续运行，且不得重置 `stepCount`、messages 或冻结 Profile。
2. <a id="req-5-2"></a> 当恢复出的 Run 状态为 `waiting` 时，系统必须继续要求显式恢复输入后才能执行下一 Step。
3. <a id="req-5-3"></a> 当恢复出的 Run 已处于 `completed`、`failed` 或 `cancelled` 时，系统不得再次调用 StepExecutor 或改变该终态。
4. <a id="req-5-4"></a> 当恢复后的 Run 成功完成下一次状态变化时，系统必须在继续后续 Step 前保存包含新 Run 状态和新增 messages 的最新完整 Goal 快照。

### 需求 6：明确处理持久化故障

**用户故事：** 作为 Runtime 调用方，我希望保存或恢复失败能够被明确报告，以便系统不会基于未持久化或不完整的状态继续执行。

#### 验收标准

1. <a id="req-6-1"></a> 当 Goal 保存失败时，系统必须停止依赖该次保存的后续执行，并将持久化错误交给调用方。
2. <a id="req-6-2"></a> 当 Goal 恢复因底层持久化故障而失败时，系统必须将该错误交给调用方，不得改写为未找到结果。
3. <a id="req-6-3"></a> 当保存或恢复失败时，系统不得返回声称已成功持久化或完整恢复的结果。
