# 在线模型列表响应改用 TS 类型 Spec

## 目标与范围

将 `/api/providers/models` 的成功响应 `BrowserProviderModels` 从 AST 定义改为原生 TS 类型，连同运行时读取及真实浏览器消费一起替换，建立后续可复用的最小生成路径。

本步只涉及成功信封 `{ ok: true, models: [{ id, name }] }` 及其条目；删除 `browserProviderModelsContract`、`browserProviderModelContract` 对应的两个 AST 节点和推导依赖。不迁移查询输入 `BrowserProviderModelQuery`、Provider 设置/错误响应、其他 Web DTO、模型决策、工具、存储或 Runtime；不先建立完整契约平台。

本 Spec 自身包含本步全部行为要求。整体方向见[迁移路线](../contract-migration/README.md)，无需先完成两份架构参考中的其他条目。

## 需求与验收标准

### 需求 1：用原生类型定义这一个响应

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当维护在线模型列表响应时，所属模块应当仅在原生 TS 中定义成功信封与条目；`ok` 固定为 `true`，`models` 为数组，条目的 `id` 为含非空白字符的字符串，`name` 为字符串。空列表与空 `name` 继续合法，不自动 trim 或更改返回值。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当生成本响应的 Schema 和校验制品时，系统应当从同一 TS 定义及 `id` 的 JSDoc 模式约束生成；不得另写字段 Schema、字段提取白名单或转换成旧 AST。拼错或不支持的契约约束注解应当生成失败。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当完成本步时，对应两个 AST 节点、`InferContract` 引用与旧登记项应当删除；该契约的生产消费链不再调用 AST `safeParse`。未迁移契约保持原实现与现有检查，不因本步全包切换。

### 需求 2：返回提取后的数据

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当收到合法响应及根对象/模型条目上的额外字段时，读取器应当成功返回仅含 `ok`、`models`、`id`、`name` 的独立数据，并提供定位未知字段的诊断；原始对象不得修改，结果的数组和条目不得与输入共享可变引用。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当缺少必需字段、`ok` 不为 `true`、列表或条目类型错误、`id` 为空白或已知字段为错误类型时，读取器应当失败，不返回部分数据；不得转换类型、补默认值或通过删除非法已知字段使其通过。读取对象必须是 JSON 数据。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当浏览器实际调用 `fetchProviderModels` 时，API 应当返回读取器提取的结果，不能只检查布尔 guard 后继续返回原始响应。未知字段诊断应当通过现有浏览器开发诊断方式有界记录契约身份及路径，不记录字段值或响应正文；诊断记录失败不影响合法请求。

### 需求 3：保持链路可用且可重复生成

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当从干净检出运行现有开发、测试或浏览器构建入口时，应当直接消费已提交的本响应生成制品，不在请求中编译、不依赖 TS transformer 或 `dist/lib/build`；同样输入重复生成应当一致，类型或约束变更未更新制品时检查应当失败。制品应当固定本契约身份、版本、真实 Schema 方言与来源摘要，不增加消息信封。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当验证真实 API 消费链时，应当证明未知根字段与未知条目字段被提取且产生诊断，非法已知字段导致既有 `invalid_api_response`，非 2xx HTTP 错误和取消保持现状；生成读取器应当通过 Node 样本与实际浏览器构建/消费验证，其他 Provider 端点及旧契约检查保持通过。

## 架构与核心决策

### 最小闭环

类型仍归 `web-contracts` 所有。公开的 `BrowserProviderModels` 改为原生声明，条目可定义为同模块类型；公共接口补充中文契约级 TSDoc。生成入口只登记这一个根类型及身份，不引入全仓注册中心或新的定义语言。

复用已调查的 `ts-json-schema-generator` → Ajv standalone → 普通 ESM 路线，只支持本步实际需要的固定对象、数组、布尔字面量、字符串和 `pattern`。生成代码放在本模块 `src/generated/` 并提交；编译器及打包依赖仅用于生成，不进入浏览器请求路径。Schema 按生成器真实的 draft-07 方言标记，版本/来源记录随本响应制品固定，不建立全局发布或协商系统。

本步不存在联合类型。可在 JSON 输入的独立副本上使用 Ajv 的额外字段清理，并关闭类型强制转换与默认值补充；清理前后的键差用于生成未知字段诊断，不维护第二份字段列表。只有校验成功才暴露提取后的数据。此策略仅用于本步无联合的形状；后续联合、递归或开放字典必须在各自小 Spec 验证，不能直接沿用本步结论。

读取入口返回成功数据/诊断或拒绝问题，保持为本契约的简单类型化函数，不要求先实现全仓 `DataReader` 框架。`isProviderModels` 若无其他真实消费者则随旧路径删除；不得为保留无消费者 API 额外增加兼容包装。

### 真实消费者与渐进共存

当前[响应定义](../../packages/web-contracts/src/contracts/provider.ts)、[类型导出](../../packages/web-contracts/src/provider-settings.ts)、[布尔 guard](../../packages/web-contracts/src/validation.ts)和[浏览器 API](../../apps/goal-board/src/api.ts)构成此契约的接缝。当前 `requestJson` 验证后返回原对象；本步必须使这一端点消费提取结果。复用原有鉴权、请求、取消与 HTTP 错误处理，只在接收结果的接缝增加读取能力，不迁移其他端点。

已迁移的响应走新生成路径，其他 Provider 契约继续使用原 AST。两种引擎服务不同契约，不构成同一载荷的双读或失败回退。旧 AST 完整性检查去掉已删除节点后仍覆盖其余节点；新契约通过生成一致性与实际读取检查覆盖。

文档只需更新所属模块对这一例外及职责的说明和语义链接，不提前把整个 `contracts` 或 `web-contracts` 描述为已迁移。该闭环交付后，再选择下一契约族扩展生成能力。

## 风险与否定性保证

- **风险等级：中。** 新增生成链并调整浏览器 API 读取方式，影响限定为一个只读查询的成功响应。关键接缝是 API 返回提取数据而非原对象；需验证实际消费路径，不能只测试生成函数。
- **工具链限制。** 当前已验证的基础生成路线尚未完成本响应的仓库集成；生成器与仓库 TS 版本差异、浏览器打包及约束生效必须在本步证明。不借此先支持全部高级 TS 类型或写新的通用 Parser。
- **否定性保证。** 不改变 Provider 查询输入、凭据获取与保存、模型能力判断、HTTP 状态处理、重试或 Runtime 执行；未知字段只进入有界诊断，不进入结果数据。首步不包含联合歧义策略、审批状态重构或持久化迁移。
