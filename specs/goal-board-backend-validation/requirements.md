# Goal 看板单会话后端验证需求

## 审批摘要

### 目标

以已合入 `dev` 的 Goal 看板原型为界面参照，让用户在浏览器中完成一条由真实 LazyGoal 后端驱动的 Goal 会话，并据此验证执行、交互与恢复行为。

### 范围

- 包含：保留原型主要看板与会话布局；当前工作区的真实 Goal 列表、创建与选择；单个活动会话的已提交记录和实时进展；提问、任务提案和工具动作的等待交互；后续输入；刷新页面及服务重启后的恢复；可重复的浏览器验收。
- 不包含：多 Goal 并行执行、项目管理、设置持久化、Profile 切换、Benchmark 控制台，以及为看板填充虚构的运行数据。

### 核心行为

- 看板和会话显示真实 Goal、Run、Step 与可选 GoalPlan；没有已提交计划时不生成示例里程碑。实时内容须与已提交事实区分，流结束不能被当作 Run 完成。
- 浏览器在当前等待点分别提交结构化回答、任务提案批准或反馈、工具动作批准或拒绝；普通聊天文本不能代替审批。过期、重复或跨 Goal/Run 的操作不得改变状态或重复执行工具。
- 等待中的有效输入恢复当前 Run；已完成 Run 只有收到新任务输入才创建后续 Run。页面刷新或服务重启后依据已提交状态恢复，不重播已完成工具动作。
- 本次只允许本机浏览器访问；未获授权的写入和跨来源访问必须被拒绝，浏览器不得收到凭据或不应公开的执行内容。浏览器及事件连接故障不得破坏 Goal 的持久化事实。

### 风险与待确认

- 风险等级：high；理由：浏览器写入可以驱动模型与工具执行，跨越本机 HTTP 访问、工具授权和持久化恢复边界。
- 关键操作：后续真实工具动作可能修改工作区；验收使用隔离工作区和受控工具，本需求文档阶段不执行真实副作用。
- 风险：浏览器断线、旧审批请求和临时事件可能造成重复动作或错误状态展示；本机其他页面可能尝试调用写入入口。
- 待确认：无。

## 引言

当前 Goal 看板原型使用浏览器内存和模拟流，刷新后会丢失数据。本功能使其中一条会话链路反映真实后端状态，并以浏览器可观察的操作和恢复结果验证该链路，同时保留原型的主要看板与会话布局。

## 需求

### 需求 1：从真实看板进入单个 Goal 会话

**用户故事：** 作为使用者，我希望从看板创建或选择当前工作区的真实 Goal，以便在熟悉的界面中进入实际会话。

#### 验收标准

1. <a id="req-1-1"></a> 当用户打开看板时，系统必须列出当前工作区已持久化的 Goal，并以稳定身份、真实意图和当前 Run 状态区分条目；不得把原型示例 Goal 当作真实记录。
2. <a id="req-1-2"></a> 当用户提交非空的新 Goal 意图时，系统必须创建并持久化该 Goal，随后打开其真实会话；创建失败时必须显示错误，不得在看板中加入虚构条目。
3. <a id="req-1-3"></a> 当用户选择已有 Goal 时，系统必须显示该 Goal 最新已提交状态；Goal 不存在或记录不可读取时，必须显示可区分的错误，不得呈现旧的本地模拟状态。
4. <a id="req-1-4"></a> 当看板列出多个 Goal 时，本次浏览器会话只能推进当前选中的一个 Goal；切换查看对象不得暗中启动或继续其他 Goal。
5. <a id="req-1-5"></a> 当用户在宽屏或窄屏打开看板与会话时，界面必须保留原型的主要布局、会话打开方式及窄屏返回方式，并以真实状态替换原型的示例状态。

### 需求 2：区分已提交历史与实时进展

**用户故事：** 作为观察会话的使用者，我希望看到真实且有时间顺序的消息、步骤与当前活动，以便判断哪些工作已经保存、哪些仍在进行。

#### 验收标准

1. <a id="req-2-1"></a> 当打开真实会话时，系统必须按已提交顺序展示消息与执行步骤、当前 Run 状态，以及已存在的 GoalPlan；GoalPlan 不存在时不得生成示例里程碑或伪造完成比例。
2. <a id="req-2-2"></a> 当模型或工具正在运行时，系统可以显示实时进展，但必须让用户区分临时活动与已提交记录；属于其他 Goal、旧 Run 或已过期连接的活动不得覆盖当前会话。
3. <a id="req-2-3"></a> 当执行步骤成功提交时，系统必须将其作为稳定历史展示；实时活动与已提交记录不得形成重复步骤，刷新后也不得重复播放旧流。
4. <a id="req-2-4"></a> 当实时文本结束但 Run 尚未到达终态时，界面不得显示 Goal 或 Run 已完成；Run completed、failed、cancelled 和等待状态必须按真实状态呈现。

### 需求 3：在真实等待点完成用户交互

**用户故事：** 作为参与执行的使用者，我希望直接在会话中回答、审批或拒绝当前请求，以便安全地推进同一个 Run。

#### 验收标准

1. <a id="req-3-1"></a> 当当前 Run 等待 `ask_user` 回答时，界面必须展示当前问题及可选项，并将用户回答作为该请求的结构化回答提交；普通聊天文本不得被当作回答。
2. <a id="req-3-2"></a> 当当前 Run 等待任务提案审批时，界面必须展示当前提案及完成条件，并允许用户明确批准或提交反馈；“批准计划”不得通过发送普通聊天文本实现。
3. <a id="req-3-3"></a> 当当前 Run 等待工具动作审批时，界面必须展示待执行动作，并允许明确批准或附理由拒绝；批准前及拒绝后该动作不得执行，同一次批准只放行当前动作一次，后续恢复仍遵守该动作已有的重放规则。
4. <a id="req-3-4"></a> 当回答、批准、反馈或拒绝携带过期、重复、错误 Goal/Run 或不匹配的请求身份时，系统必须拒绝操作并显示最新状态，不得改写已提交事实或触发工具。

### 需求 4：按 Run 生命周期处理后续输入

**用户故事：** 作为持续使用一个 Goal 的使用者，我希望消息进入正确的 Run，以便等待恢复与新任务继续不会混淆。

#### 验收标准

1. <a id="req-4-1"></a> 当当前 Run 因可由普通消息解除的等待而暂停时，用户提交有效消息必须恢复同一 Run，不得创建新的 Run；需要结构化回答或审批的等待点仍须使用对应操作。
2. <a id="req-4-2"></a> 当当前 Run 已完成时，只有用户提交新的非空任务输入，系统才可为同一 Goal 创建后续 Run；剩余 GoalPlan 项不得自动启动新 Run。
3. <a id="req-4-3"></a> 当当前 Run 已失败或取消，或界面正在处理前一次命令时，不适用的新输入必须被拒绝并给出原因，不得由浏览器自行改写 Run 状态。

### 需求 5：刷新与服务重启后的恢复

**用户故事：** 作为长任务使用者，我希望重新打开浏览器或重启本机服务后仍看到同一会话的可靠状态，以便继续处理未完成的交互。

#### 验收标准

1. <a id="req-5-1"></a> 当页面刷新或本机服务重启后再次打开同一 Goal 时，界面必须从最新已提交状态恢复消息、步骤、当前 Run、等待请求与已存在的 GoalPlan，不得依赖刷新前的浏览器内存。
2. <a id="req-5-2"></a> 当刷新或重启发生在工具动作执行边界时，系统必须遵守该动作已有的恢复状态与重放规则；结果未知时必须呈现需处理的状态，不得自动重复执行。
3. <a id="req-5-3"></a> 当实时连接断开、重连或收到较旧事件时，界面必须以已提交状态重新建立历史，并只接收属于当前 Goal/Run 的后续活动；连接故障不得伪造终态或删除已提交记录。

### 需求 6：限制浏览器访问与信息暴露

**用户故事：** 作为在本机运行 LazyGoal 的使用者，我希望浏览器控制能力只提供给获准的本机页面，以便网页请求不会绕过现有工具权限或暴露敏感信息。

#### 验收标准

1. <a id="req-6-1"></a> 当浏览器会话服务启动时，它必须只接受本机回环访问，不得向远程网络接口开放 Goal 读取或写入能力。
2. <a id="req-6-2"></a> 当非获准页面、跨来源请求或缺少有效会话授权的客户端尝试读取受限会话信息或提交写入时，系统必须拒绝请求，且不得推进模型或工具。
3. <a id="req-6-3"></a> 当浏览器提交无效输入、身份或不适用于当前状态的命令时，系统必须返回可辨认的错误并保持已提交状态不变；浏览器请求不得绕过 Profile、Tool Policy 或动作审批。
4. <a id="req-6-4"></a> 当会话数据发送到浏览器时，系统不得提供 API 凭据、非公开推理内容或超出当前会话展示所需的原始执行数据；可见工具输出必须受限。

### 需求 7：可重复验证真实后端行为

**用户故事：** 作为维护者，我希望用可重复的浏览器场景核对 UI 与后端行为，以便明确判断接入是否可靠。

#### 验收标准

1. <a id="req-7-1"></a> 当在隔离工作区重复执行创建 Goal、显示真实进展、处理等待交互和刷新恢复的浏览器场景时，系统必须得到相同的已提交状态与可观察结果，且场景不依赖真实外部模型或工作区之外的副作用。
2. <a id="req-7-2"></a> 当浏览器场景覆盖过期审批、断线重连和服务重启时，系统必须证明非法操作未推进 Goal、已提交步骤未重复，且不可重放的受控工具动作不会因浏览器重连而再次执行。
3. <a id="req-7-3"></a> 当本功能接入后，现有 TUI、Runtime 的创建、审批与恢复行为必须保持可用；浏览器会话不得改变既有 CLI/TUI 的默认启动行为。
