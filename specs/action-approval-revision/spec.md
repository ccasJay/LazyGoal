# 工具审批参数修订与未知结果重执行 Spec

## 目标与范围

LazyGoal 允许用户或宿主在工具尚未执行的审批等待点修改同一工具的参数，审阅最终操作与权限范围后明确批准；直接工具调用和 PTC 程序内业务子调用具备相同能力。修改后重新校验输入、权限和沙箱范围，可以在明确确认后扩大范围。模型与 PTC 调用方获知参数被修订及实际执行的必要信息，原始模型调用、程序请求和历史事实保持不变。

本次同时区分首次执行批准与未知结果后的重执行授权：前者批准尚未开始的操作，后者明确允许原操作按最终获批参数再次执行，也可以拒绝再次执行。未知操作不能修改参数、授予持续权限或由人工直接宣称成功。

本 Spec 依赖已批准但尚未实现的 [streaming-session](../streaming-session/spec.md) 与 [human-interaction](../human-interaction/spec.md)。前者拥有统一受理、收据、提交协调、执行所有权、中断和恢复；后者拥有交互区域、问答／审批布局、宿主处理器和提交状态。本次扩展工具审批领域规则及对应交互能力，不重新实现会话、表单系统或授权引擎。

本次不提炼 SDK、不迁移默认装配，不允许替换工具、修改已经开始的调用或改写 PTC 父程序代码；不增加任意审批 Hooks、外部审批系统、工具热更新、并行 PTC、跨进程写入或旧开发数据迁移。权限匹配规则、授权期限、Profile／工具发现、Plan 只读门和中断有限收尾保持现有边界。拒绝原操作并反馈建议仍可用于要求模型换工具或重新决策。

## 需求与验收标准

### 需求 1：明确的修订资格与操作身份

作为审批者，我希望只能修改尚未执行的当前操作，并知道批准对应的确切版本。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当直接调用或 PTC 业务子调用处于首次审批等待、尚未开始执行时，应允许提交同一工具的新参数；工具身份、Goal／Run、PTC 程序及调用位置不能由修订请求替换。已批准、已启动、结果未知、已结算或失效等待应拒绝新修订。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当修订请求通过 Session、Web 或宿主入口到达时，应核验当前操作引用和审批基准；跨 Goal／Run、旧审批或参数身份失配不得改变当前等待、创建 Grant 或启动工具。普通聊天、问答回答与 Steer 不能直接修改或批准工具参数。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当保存批准时，应将原操作来源、最终执行参数及其修订身份关联到同一逻辑 Action；获批版本随后不可编辑，执行和恢复都使用它。原始模型／程序请求和 `action_staged` 事实不得被覆盖，不能通过复用 Action ID 隐藏实际参数变化。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当拒绝原操作并提供非空理由或替代建议时，应继续走现有拒绝与反馈路径，不将建议直接当成另一条工具调用执行；修订不放宽模式、发现、Profile 或中断收尾所允许的操作范围。

### 需求 2：只读审阅与最终授权范围确认

作为用户或宿主，我希望先知道修改后的真实操作、范围和限制，再决定是否批准。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当预检拟修订参数时，应经当前工具 Contract／语义准备、执行准入、权限和沙箱规划计算最终 canonical 参数、实际目标与能力需求；预检仅返回审阅结果，不保存批准、不暂存或激活 Grant、不解除等待、不调用业务工具。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当参数变化扩大或缩小文件／网络能力需求时，应展示重新计算的最终范围及与原请求的差异；允许明确批准扩大的合法范围，但不得沿用旧沙箱范围、旧输入匹配器或将此前批准视为覆盖新范围。策略拒绝不能由审批覆盖。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当确认修订时，应绑定所审阅的原操作基准、最终 canonical 参数、授权期限和最终能力范围；提交阶段应重新计算并比较，若与审阅内容不一致则明确拒绝并要求重新审阅，不能自动批准改变后的结果。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当参数无效、工具不可用、完整详情读取失败、授权规划失败或内容超出已有输入／传输限制时，应提供可定位字段或稳定原因，保留原等待及本地草稿，不隐式裁剪参数、降级权限或执行原操作作为回退。
- <a id="spec-req-2-5"></a>**验收标准 2.5**：当多个客户端预检不同修订时，应各自得到对应只读结果，不覆盖彼此草稿或持久化候选；其中一个决定提交后，其余旧确认应失效。编辑或预检本身不产生执行授权，也不隐式触发宿主审批回调。

### 需求 3：扩展现有批准与 Grant 事务

作为运行时维护者，我希望参数修订复用现有授权事务，避免批准、授权和实际执行指向不同操作。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当首次批准原参数或修订参数时，应只接受首次待审批状态，将批准种类、实际来源和最终执行版本与输入收据、批准事实及待执行指针共同提交；保存失败不得执行工具或激活持续授权，受理成功不能仅来自预检或内存通知。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当选择 Goal／工作区持续授权时，应根据最终已验证参数和能力范围生成既有匹配器，沿用 Grant pending → 批准快照保存 → Grant 激活 → 执行的顺序；单次批准不产生持续授权。匹配器继续遵守现有语义，例如写入类工具按目标路径匹配，不被重定义为只匹配本次正文。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当激活 Grant 或准入执行时，应核验 Grant 来源、最终参数及能力范围与已提交批准一致；重启后 pending Grant 的恢复激活应沿用同一获批版本，不激活旧参数授权，不借故重新请求模型生成替代 Action。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当修订确认与原样批准、拒绝、Interrupt 或其他确认竞争时，应由基础 Spec 的短提交边界决定唯一有效结果；相同 `inputId` 与载荷重试返回原收据，不重复激活授权或推进。参数准备涉及的读取完成后仍须在提交边界核验基准，不能持锁等待模型或工具。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当保存批准后、激活前或工具开始后崩溃时，应区分未执行的批准与可能已产生效果的调用，沿用既有恢复分流和显式恢复规则；修订不能新增自动重放许可或声称外部效果 exactly-once。
- <a id="spec-req-3-6"></a>**验收标准 3.6**：当 Grant 已暂存而批准保存未成功，随后对同一 Action 提交不同参数或期限的新决定时，应允许按新决定身份暂存授权而不被旧 pending 记录永久阻塞；旧记录不激活、不匹配新操作。原决定重试仍幂等复用自身记录，只有与已提交批准身份和最终内容完全匹配的 Grant 才能激活。

### 需求 4：独立的未知结果重执行决定

作为用户，我希望明确知道自己是在批准首次执行，还是允许一个可能已经发生的操作再次执行。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当 Action 进入 `outcome_unknown` 等待时，应提供与首次审批不同的恢复决定和当前恢复引用；普通首次批准不得消费此等待，重执行命令也不能用于尚未执行的审批。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当明确授权重执行时，应绑定当前 Action、最终执行版本及本次未知结果等待身份，只允许按该版本再次执行；不得携带新参数或 Goal／工作区持续授权，YOLO 或现有 Grant 不能代替本次明确决定。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当同一 Action 重执行后再次发生未知结果时，应记录新的尝试与恢复等待身份；原决定及其收据不能授权新一轮重执行。既有安全工具的有限暂时故障重试、PTC 与中断预算保持原规则，不以重执行重置已消耗的程序或收尾预算。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当用户拒绝再次执行时，应记录拒绝进一步执行的决定并保留此前效果未知的事实，按现有 Run／PTC 结算路径继续或停止；不得把原操作描述成未执行、已回滚或已成功。不存在“人工宣称成功”的结果填入入口。
- <a id="spec-req-4-5"></a>**验收标准 4.5**：当重执行决定与中断、拒绝、响应重试或服务关闭竞争时，应保持统一收据与真实提交顺序；旧恢复引用应明确失效。显式恢复只重建等待，不替用户授权再次执行，也不能恢复已被 Interrupt 禁止的原任务。

### 需求 5：PTC 的修订执行与确定性恢复

作为程序工具调用方，我希望获知实际执行参数，并在程序重建时得到相同结果，而不会重复产生副作用。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当修订 PTC 子调用时，应保留父程序、调用索引、逻辑 Action ID 和原始程序输入，关联最终执行版本；执行前准备、授权和沙箱计划应使用最终参数，不能继续使用由程序原始参数构造的旧 `prepared` 对象。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当 PTC 程序重建并再次发出原子调用请求时，应先用原请求校验重放身份，再关联其已提交修订和真实结果；已结算子调用仅返回保存结果，不因最终参数不同于原请求而误报重放失配，也不重复执行。原程序请求本身改变、记录不完整或关联不一致时仍应明确失败。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当修订子调用返回或被重放时，应在现有结果信封中提供一致的修订标记、实际参数必要信息及事实引用；不改写业务 Observation 的原有输出为另一种工具结果，程序可以据此调整后续逻辑，宿主不重写程序代码。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当统计程序调用、结果大小、帧大小、执行时间和父 Step 时，应将新增修订信息计入现有资源上限，保持调用顺序、已消费预算和父 Step 单次结算；子调用修订不产生额外模型 Step，不允许嵌套 PTC 或系统工具调用。
- <a id="spec-req-5-5"></a>**验收标准 5.5**：当 PTC 修订执行发生保存失败、审批后重启、写入结果未知或中断时，应恢复同一最终版本及真实结算位置；不能用旧参数重放、借修订跳过当前未知结果确认，或丢弃此前已提交子调用结果。

### 需求 6：审计、模型理解与后续决策

作为模型或审计者，我希望区分原请求、用户修订、批准和实际结果，以免把不同操作混作完成证据。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当接受参数修订时，应记录原请求引用、最终 canonical 参数／摘要、权限范围、修订来源及批准关联；原始 Provider 响应、原生工具调用 ID 与参数、程序源码和初次暂存事实保持不变，不能伪造模型曾提出新参数。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当直接修订操作结算后构造下一模型请求时，应明确提供实际执行的必要参数与原请求差异，并与真实 Observation 保持来源关联；原生模型历史继续保持调用／结果配对，不把新参数冒充原始调用，也不制造第二次工具成功。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当 PTC 子调用被修订时，应除向程序返回修订信息外，在下一个模型安全边界提供有界的修订说明，即使程序未显式返回该元数据；其余内部子调用事实仍不自动全量进入模型上下文，公开事件也不得广播任意完整参数或敏感正文。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当直接调用属于预先生成的 Action 批次时，修订操作结算后应使尚未执行的旧批次剩余项失效，让模型在知晓实际变化后重新决策；不能把这些项记为已执行或沿用原假设继续启动。PTC 则按冻结代码及返回的修订信息继续，不承诺程序一定使用该信息。
- <a id="spec-req-6-5"></a>**验收标准 6.5**：当历史查询、Activity 或完成证据解释修订操作时，应关联最终执行版本与真实结果，不能用修改后的操作证明原参数对应的目标已完成。例如写入目标由 A 改为 B，B 的成功不能被展示或校验为 A 已写入；原完成审查规则仍决定任务是否满足。

### 需求 7：Web 与宿主的修订审阅体验

作为用户或宿主，我希望在同一交互体系内完成编辑、审阅、批准与恢复，并准确理解授权后果。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当首次待审批操作允许修订时，新交互区域和宿主入口应提供读取原参数、编辑同一工具参数及预检能力；默认仍可原样批准／拒绝。Web 通过有校验反馈的 JSON 参数编辑覆盖自定义工具，不引入通用表单引擎；退出编辑不修改原操作。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当展示预检结果时，应清楚区分原参数、最终参数、实际目标、能力变化及单次／Goal／项目授权后果；最终批准按钮只能确认当前审阅内容。再次编辑会使旧审阅结果失效，迟到预检不得覆盖新草稿，详情或范围不完整时不得确认。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当提交修订批准、重执行或拒绝决定时，应复用 human-interaction 的身份冻结、提交核验、草稿保留与请求失效流程；不会因预检成功清空草稿或误报工具完成。等待中的独立停止保持可达，其他客户端结算后原编辑与确认不能继续使用。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当宿主程序化修订时，应显式调用同一预检能力后返回绑定审阅结果的决定；普通审批处理器不能自动消费恢复等待，只有已注册的恢复处理器可明确授权重执行。注册、读取和预检不触发历史任务执行或创建权限。
- <a id="spec-req-7-5"></a>**验收标准 7.5**：当显示未知结果时，应以独立恢复说明和 `Retry action`／拒绝重执行操作表达可能重复的外部效果，不提供参数编辑或持续授权；产品文案保持英文，桌面、320px 窄屏与键盘均能完成编辑、差异审阅及明确确认。

### 需求 8：故障验证与契约交付

作为维护者，我希望参数修订不会破坏现有权限、恢复和模型协议，并有可追溯的集成证据。

- <a id="spec-req-8-1"></a>**验收标准 8.1**：当验证修订事务时，应覆盖直接调用与 PTC、原样批准与修订批准、单次与持续授权、范围扩大／缩小／策略拒绝及两种提交先后；检查最终参数、匹配器、沙箱计划、收据及实际工具调用，而不只断言字段或按钮存在。
- <a id="spec-req-8-2"></a>**验收标准 8.2**：当验证恢复时，应以真实文件存储重建和确定性故障注入覆盖预检后变化、批准保存前后、Grant 激活前后、工具开始后崩溃、重复未知等待、PTC 重放和 Interrupt；原参数或旧恢复决定不得触发重复执行。
- <a id="spec-req-8-3"></a>**验收标准 8.3**：当验证消费方时，应通过正式无界面装配及真实 Web 服务／浏览器完成修订、审阅、确认、拒绝和未知结果流程，并检查当前三种模型协议的历史配对与下一请求、PTC 实际返回元数据及上下文修订说明；使用确定性模型和隔离工具，不要求真实付费 Provider。
- <a id="spec-req-8-4"></a>**验收标准 8.4**：当交付功能时，应同步变化所有者概览、语义表、公开中文 TSDoc 和宿主／Web 使用说明，通过文档、依赖和类型检查；现有首次／恢复混用命令及其旧消费方应被替换，不为开发期 wire／Snapshot 保留旧批准分支。

## 架构与核心决策

### 现有基础与相关 Spec

[GoalCoordinator 审批入口](../../packages/runtime/src/goal-coordinator.ts) 当前以 `approve_action` 同时接受 `awaiting_approval` 和 `outcome_unknown`，按原 `pendingAction.action.input` 生成授权，再保存批准、激活 Grant 并调度。[状态转换](../../packages/runtime/src/transition.ts) 同样混合两种等待，并保留原 Action 参数。这些入口与转换必须修改；保留的是事务顺序和领域边界，不是整段审批分支。

[Grant 激活复核](../../packages/runtime/src/goal-coordinator.ts) 已验证来源、范围和输入匹配器，[Permission](../../packages/permission/notes/overview.md) 已拥有授权匹配；扩展时继续复用。PTC 当前在 [Runner](../../packages/runtime/src/runner.ts) 中按 `programId`／`callIndex` 分配 Action，恢复时比较原暂存输入，因此必须区分原请求与实际执行版本，不能直接覆盖输入后删除重放校验。

本次使用 [streaming-session 的受理与提交契约](../streaming-session/spec.md#持久化与提交顺序) 及 [human-interaction 的交互协议](../human-interaction/spec.md#请求与响应协议)。两者的职责保持不变，本 Spec 在工具审批分支新增只读预检、参数修订确认和独立重执行决定，并扩展现有工具交互区域／处理器。human-interaction 单独交付时保留原恢复命令的基线；集成本 Spec 后消费方切换到新的明确分支，不维持两套运行时语义。不修改前两份已批准文件，也不以本次批准授权联合执行三份 Spec。

### 组件与所有权

```text
Web 参数编辑 / 宿主处理函数
          │ 当前操作引用 + 拟修订参数
          ▼
   Runtime 只读审批预检
   工具准备 → 准入 → 权限／沙箱范围 → 审阅指纹
          │ 明确确认最终操作与期限
          ▼
   Session respond → Goal 短提交边界
   重算与核验 → Grant pending → 批准版本／收据保存
          ▼
   Grant 激活复核 → Runner 使用最终版本执行
          ├─ 真实结果 + 修订说明 → 模型／PTC
          └─ 结果未知 → 独立恢复决定 → 原版本重执行或拒绝
```

Runtime 拥有修订资格、只读预检编排、确认语义、最终执行版本、恢复等待身份和状态转换；Permission／Sandbox／Tool Core 继续拥有匹配、能力和参数准备规则。Storage 编解码当前状态与已提交事实，模型上下文模块构造必要修订说明，Sandbox 的 PTC 传输承载有界元数据。现有应用组合根只接线；Browser 负责授权 wire，Goal Board 负责编辑和审阅，不自行计算授权范围或拼装批准状态。不增加审批包、事件数据库或影子 Action 队列。

### 原请求与最终执行版本

保留同一逻辑 `actionId` 及原始 `action_staged`，避免破坏 PTC 固定调用位置和父 Step 归属。在当前 `pendingAction` 中按需扩展最终执行版本关联：原请求引用、最终 canonical 输入、审阅／修订身份、实际批准种类及权限范围。未修订操作直接使用原版本，不重复保存一份等价正文；修订历史和真实效果由已提交 Trajectory 关联，不改写原始模型响应。

批准后 Runner 通过一个明确的执行版本选择入口取得实际 Action，所有直接执行、PTC、授权激活、沙箱计划、失败／未知结果和恢复路径使用相同选择。不能出现授权匹配新参数、`executeToolAndObserve` 仍执行旧 `prepared.action` 的分叉。已批准版本不得再次编辑；已知结果与未知结果均指向实际执行版本。修订本身不是一次工具调用或成功结果。

首次审批引用绑定原操作的稳定来源；最终版本绑定输入和权限范围的审阅身份。未知结果使用独立 `recoveryRef`，由本次已提交未知结果／尝试身份派生，跨重启稳定，后续再次未知时变化；不能仅以 `actionId` 或进程内计数标识所有恢复等待。Session `inputId` 是决定的幂等身份，不代替这些目标身份。

### 两阶段审阅：只读预检与持久化确认

在现有内部会话／管理 Port 增加只读审批预检，输入为当前操作引用、拟修订参数和拟授权期限，输出为原参数／最终 canonical 参数、目标及能力变化、允许或拒绝理由和审阅指纹。预检受现有详情读取的访问边界保护，处理函数也使用该入口。预检只进行参数与路径元数据等必要准备，不执行工具、不调用模型，不保存候选、不预留 Grant；各客户端草稿互不覆盖。

审阅指纹绑定原审批基准、最终 canonical 输入、Tool／Profile／模式准入所需的实际版本和最终授权／沙箱范围。它是内容一致性引用，不是新的认证令牌；访问权限继续由现有宿主／wire 边界控制。确认请求包含拟执行输入、审阅引用和期限，不能只凭客户端声称的 scope 放行。提交时重做必要准备并对比，环境／路径身份／策略变化造成审阅结果变化则返回重新审阅，不把变化静默并入批准；无关队列写入不应仅因 Goal 提交修订增加就使相同审批对象失效。

预检前后可用的既有范围规划和元数据读取不跨越长时间 Gate；进入最终提交时读取最新状态并核验当前审批及审阅依赖。准入执行前仍执行既有路径与沙箱检查，不承诺文件系统在批准到系统调用之间完全不变化，也不通过放宽沙箱解决变化。拟修订参数扩大能力时允许生成新的合法范围供确认，Profile、模式与策略的拒绝不可被用户选项绕过。

编辑／预检结果不持久化为新 pending 状态，避免每次键入形成请求版本和回调重投递。最终确认才提交实际修订身份；重启前未确认的编辑不提供执行许可，恢复仍展示原等待。界面可复用 human-interaction 的页面草稿保留规则，不承诺跨刷新保存参数草稿。

### 明确的决定分支与授权事务

下列名称表示新增领域语义，最终类型在实现时整合到现有 `SessionInput.kind = "respond"` 联合，不另建控制传输通道。

| 决定 | 目标等待 | 提交内容与后果 |
| --- | --- | --- |
| `approve_action` | 首次未执行审批 | 原版本及其当前批准范围；不再消费未知结果。 |
| `approve_action_revision` | 首次未执行审批 | 同一工具最终参数、审阅引用、期限；提交修订与批准，再执行。 |
| `reject_action` | 首次未执行审批 | 非空理由／建议，原操作不执行，继续原拒绝反馈流程。 |
| `retry_unknown_action` | 当前未知结果等待 | `recoveryRef` 与最终版本，明确允许再执行；无改参或持续权限字段。 |
| `decline_unknown_action_retry` | 当前未知结果等待 | 拒绝再次执行及理由，保留原未知效果；不将其记作从未执行的普通拒绝。 |

保留现有事务顺序：根据最终内容暂存需要的 Grant → 在 Snapshot 提交批准、修订、收据及对应事实边界 → 复核并激活 Grant → 唤醒执行所有者。单次批准没有持久化 Grant。Grant 来源仍能关联逻辑 Action，激活时必须同时核验批准冻结的最终输入／范围；不能只因为来源 Action ID 相同就接受不同匹配器。已批准后的参数冻结使同一 Action 不会生成多个互相竞争的有效批准。

当前 Tool／Sandbox Grant Store 仅按 Goal／Run／Action 判定来源唯一，旧 pending 还不能通过普通撤销接口移除；因此只增加最终参数字段不足以支持保存失败后换参数再次批准。本次将 Grant 的事务来源扩展为包含稳定批准输入身份 `approvalInputId`，并在获批状态保存同一关联，两个账本及激活复核共同使用。匹配规则和期限不变。同一决定同内容重试复用暂存记录；不同决定的未提交 pending 可以保留，但不可作为有效权限，只激活被 Snapshot 批准引用的那一条。读取或提交结果不明时先按原身份核验，不能用新决定绕过已生效批准；不新增自动删除授权账本的清理流程。

不在 Permission 重新实现领域事务，也不把 Grant Store 与 Goal Store 宣称为分布式原子事务。pending Grant 在批准快照前不可匹配；批准保存后而激活前重启，沿用既有可恢复激活顺序。执行是否开始仍由既有调用记录、replayPolicy 和未知结果规则判断，修订不扩大自动重试许可。原始批准、修订确认和恢复决定都通过基础短提交与输入账本；旧决定的同载荷重试优先返回原收据，不因当前已变为另一等待而再次执行。

恢复拒绝记录“未获准再次执行”，保留之前的失败／未知结果来源；按现有 Run 或 PTC 规则提供真实结算信息，不能追加伪造成功结果或将原动作改写为普通未执行拒绝。收尾中的合法审批继续受中断目的与剩余预算约束，新的明确恢复决定也不能重启已被中断的原任务。

### PTC 与模型历史

PTC 在 `(programId, callIndex, actionId)` 上保留原调用身份及原始 canonical 参数，另关联最终执行版本。程序重建时仍验证原代码发出的调用与原暂存请求一致，再选择已批准的最终版本或返回已提交结果。原请求失配继续失败；不能通过允许任意最终参数来弱化重放校验。每个逻辑子调用仍只有一个原暂存记录和一个已结算 Observation，修订与恢复尝试以关联事实表达，不新增同 ID 的第二条 `action_staged` 来绕过旧检查。

PTC 的结果信封在现有 `observation`、`sourceReferences` 外按需增加修订元数据，说明实际版本、必要参数信息及来源引用；业务工具输出本身不换形。恢复返回同样的修订信息，新增字节计入原结果／帧限额，父程序的预算和结果统计同步遵循最终编码内容。程序可使用元数据调整后续逻辑，Runtime 不修改冻结代码，也不保证程序一定采取调整。

直接调用的下一模型请求和 PTC 父程序后的下一模型请求均包含有界、明确来源的修订说明。原生历史保留原调用参数与 ID，结果仍配对同一调用；真实结果与修订说明共同解释实际操作，不重写 Provider 原文。历史查询、Activity 与 Evidence 的动作解释也沿同一最终版本关联，不从旧 `action_staged` 参数单独推断完成目标。PTC 修订说明是本次明确的上下文扩展，不把其他内部子调用明细自动暴露到 Hot／Warm、检索或原生历史。参数必要信息按现有模型可见性与预算投影，截断须明确并保留事实引用；普通公开订阅只提供安全摘要，完整内容通过现有授权详情边界读取。

对直接 Action 批次，修订结算后清除未开始的旧批次剩余决策，并以实际参数说明回到模型边界；原结果、已执行兄弟调用与审计链不删除。这样避免模型尚未看到修改就按旧假设启动后续动作。PTC 后续调用由程序收到实际结果后产生，继续沿用原串行准入和审批，不套用直接批次的丢弃方式。

### Web 与宿主适配

复用 human-interaction 新交互区域增加“编辑参数 → 预检 → 原／最终参数和范围对比 → 明确批准”的流程。JSON 编辑器覆盖业务工具输入，提供字段路径与解析／语义错误；不是根据任意 Schema 自动生成表单。只编辑 input，工具名称与 PTC 归属只读。修改工具或程序代码仍通过拒绝并反馈重新决策。

预检展示原样批准与修订批准的差异、实际目标／沙箱能力、授权期限和既有匹配范围含义；再次编辑或期限变化使旧预检失效。持久化授权不得暗示“只允许本次相同正文”，现有路径型 Grant 的广度必须保留说明。预检中的新请求取消旧网络读取，迟到结果不得覆盖当前编辑。无效／过期确认保留草稿并要求重新审阅，不执行原操作作为补偿。

宿主审批函数通过同一只读预检确认最终范围后，返回修订决定；不将 `updatedInput` 直接交给执行器。未知结果只投递到 human-interaction 已单独注册的恢复函数，结果使用新的恢复决定；类型化同进程值不额外套不可信解析，wire、排队和持久化边界正常校验。

未知恢复视图明确显示此前可能已执行、实际获批参数及重执行后果；禁用编辑与持续授权，拒绝文案说明是不允许再次执行。独立停止与结果核验沿用前置 Spec；界面只在收据确认后显示决定已受理，真实成功／失败仍来自工具结算。主题、英文文案、窄屏和键盘语义沿用 human-interaction，不再次整体重写布局。

## 曾考虑的备选方案

- **扩展现有 Coordinator 事务**：选择保留 Grant 暂存、批准保存、激活和调度顺序，修改决定分支和最终版本关联。备选另建审批引擎会重复等待、权限和恢复规则；完全原样保留则无法区分改参和未知重执行，均不采用。
- **同一 Action 的不可变执行版本**：选择保留原请求和逻辑身份，批准时冻结最终版本。备选覆盖 `pendingAction.input` 会失去原始来源并破坏 PTC 重放；所有修订都换 Action ID 则需要改写程序固定调用身份和结果归属，故不采用。
- **只读预检、确认时重算**：选择客户端各自编辑，预检不写状态，最终确认校验所见内容。备选每次预检持久化候选会引入协同编辑冲突和处理器重投递；单次提交任意参数并直接执行不能确保审批者看过新的能力范围，故不采用。
- **扩大范围须重新审阅并明确确认**：按用户确认允许同工具的合法范围扩大。备选仅允许缩小会限制修订用途；自动继承旧批准会错误授权未审阅能力，均不采用。
- **独立未知结果决定**：选择明确重执行或拒绝重执行，绑定本次恢复等待。备选继续复用 `approve_action` 会混淆首次执行和重复效果；允许人工填写成功结果会把不可核验声明变成工具证据，不纳入本次范围。
- **同时支持直接调用与 PTC**：按已确认范围保证能力一致，并保留两种路径不同的批次／重放规则。备选只覆盖直接调用会让程序内相同工具无法修订；跳过 PTC 输入一致性校验会破坏恢复身份，均不采用。
- **告知真实参数修订**：选择模型与程序获得必要说明，原生记录保持原文。备选只在审计中记录会让调用方按原参数解释不同结果；直接改写模型调用则伪造来源，故不采用。

## 风险与否定性保证

- **风险等级：high**。修订可能改变写入目标、命令和网络范围；授权／执行参数失配、恢复身份复用及 PTC 重放错误会产生未批准或重复的外部效果。验证需覆盖最终参数、权限范围、真实调用、持久化恢复和模型历史，不只覆盖类型或页面。
- **关键操作**：实现修改 Coordinator／transition 的首次与恢复分流、最终执行版本、Grant 复核、PTC 结果信封和模型上下文。设计批准不授权真实危险命令、付费模型、用户数据迁移／删除或 SDK 发布；测试使用隔离目录、确定性适配器和受控工具。
- **授权不变量**：只有同一工具的尚未执行待审批操作可修订；原批准不覆盖新范围；预检不产生权限；审批不能覆盖 Profile／模式／策略拒绝；Grant 与真正执行的参数／范围必须一致；未知结果不能改参或持续授权。
- **身份与恢复不变量**：原调用和暂存事实不可改写；批准版本不可变；旧恢复决定不能授权下一次未知等待；收据重试不重复执行；只读打开、注册和预检不自动恢复历史任务；不把拒绝重执行描述为原操作未发生。
- **PTC 与证据不变量**：原请求重放校验不弱化，已提交子调用不重复执行，实际参数与结果来源可追溯；父 Step 和已有预算不重置。模型修订说明不成为虚构工具成功，也不把未知效果当成完成证据；程序可能忽略元数据是明确限制。
- **竞争与故障验证**：覆盖预检与确认之间的范围变化、同一操作的不同决定、批准／Grant／工具开始的崩溃边界、恢复重试和 Interrupt。发布丢失不撤销已提交决定，关闭未确认结算不报告成功；不承诺跨进程写入或外部效果 exactly-once。
- **兼容与写集**：按开发期政策更新当前契约及测试数据，不增加旧 wire／Snapshot 解析回退、不自动清理用户 Home。本阶段仅生成本 Spec，不修改前两份已批准 Spec／Plan，不生成本 Spec 的 Plan、不开始实现，也不写入项目记忆。
