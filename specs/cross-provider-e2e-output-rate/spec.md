# 跨 Provider 端到端输出速率 Spec

## 目标与范围

让 LazyGoal 对不同模型 Provider 使用统一口径记录和展示输出速率。速率以应用观察到的模型请求端到端耗时为时间基准，覆盖流式与非流式适配器；Goal 卡片、指标摘要和详情弹窗统一用它替换现有的 Generation 指标。

一次模型调用完成并写入指标事实后，运行中的指标视图立即纳入该调用。仍在进行的调用不提供临时估值；Run 结束时展示同一口径下的最终汇总。

本指标回答“每秒端到端请求耗时对应多少 Provider 确认的输出 token”，包含 Provider 等待、首 token 等待和响应传输耗时。它不代表 Provider 内部解码速度，也不代表整个 Run 的墙钟吞吐量。

## 需求与验收标准

### R1. 记录统一的模型请求耗时

1. <a id="spec-req-1-1"></a>当 Agent 调用任一模型适配器时，系统必须用单调时钟测量从适配器请求开始到完整响应被消费结束的耗时，并把该耗时作为模型调用完成事实的一部分持久化。
2. <a id="spec-req-1-2"></a>对流式适配器，计时从调用流式请求前开始，至流结束并完成消费后结束；对非流式适配器，计时从调用生成方法前开始，至生成调用返回后结束。
3. <a id="spec-req-1-3"></a>计时不得包含 Prompt 构造、调用事实写入、Agent 响应解析、工具执行或后续业务处理。
4. <a id="spec-req-1-4"></a>计时应在请求抛错时仍能反映已观测到的适配器请求耗时；失败调用不能因此被纳入成功输出速率。
5. <a id="spec-req-1-5"></a>计时值必须为有限且大于零的毫秒数。若适配器未完成、运行时无法取得有效耗时或事实未能持久化，该调用不得伪造计时值。

### R2. 按 Provider 确认的用量计算端到端输出速率

1. <a id="spec-req-2-1"></a>一次调用只有在调用成功、Provider 用量明确包含有效输出 token 数、用量来源为 Provider 确认，且存在有效请求耗时时，才可计入已测量输出速率。
2. <a id="spec-req-2-2"></a>聚合速率必须按以下公式计算：

   `sum(已纳入调用的 Provider 输出 token 数) / sum(这些调用的请求耗时秒数)`

3. <a id="spec-req-2-3"></a>聚合值必须由 token 总数除以耗时总数得到；不得对单次调用速率作不加权算术平均。
4. <a id="spec-req-2-4"></a>调用缺少 Provider 输出用量、有效耗时或成功结果时，必须排除在速率计算之外，并计入未测量调用数；不得估算 token、把缺失值视为零，或用 Trace、Run 总耗时、首 token 解码耗时补齐。
5. <a id="spec-req-2-5"></a>若没有可纳入的调用，速率必须显示为不可用而不是 `0 tok/s`。速率测量覆盖率必须独立于 token 用量覆盖率展示和解释。

### R3. 运行期间逐调用更新

1. <a id="spec-req-3-1"></a>当一条模型调用完成事实成功持久化后，运行中的指标投影必须可以包含该调用，无须等待整个 Run 完成。
2. <a id="spec-req-3-2"></a>当前尚未完成的模型调用不得进入已测量分子、分母或计数，也不得显示基于部分 token 或部分耗时的速率估值。
3. <a id="spec-req-3-3"></a>Run 完成后的汇总必须使用与运行期间相同的纳入规则和聚合公式。

### R4. 替换现有 Generation 指标展示

1. <a id="spec-req-4-1"></a>Goal 卡片、指标摘要栏和指标详情弹窗必须使用端到端输出速率替换现有 Generation 速率，不再把首个非空文本 delta 到请求结束的解码耗时作为该展示值。
2. <a id="spec-req-4-2"></a>展示应使用清楚表明输出速率的标签和 `tok/s` 单位；无有效调用时显示不可用标记，并保留已测量与未测量调用数。
3. <a id="spec-req-4-3"></a>指标详情必须说明这是应用观察到的端到端 Provider 请求速率，包含 Provider 等待及响应传输时间，不代表 Provider 内部解码速度。
4. <a id="spec-req-4-4"></a>现有 token 用量、缓存命中、上下文余量及用量覆盖信息保持各自语义，不因输出速率口径变更而改变。

### R5. 保持历史事实诚实可读

1. <a id="spec-req-5-1"></a>新请求耗时是模型调用完成事实中的可选字段，以便不含该字段的既有指标事实仍可读取。
2. <a id="spec-req-5-2"></a>既有事实没有请求耗时时必须继续作为未测量调用处理；不得通过历史 Trace 或旧的解码耗时推导并写入请求耗时。
3. <a id="spec-req-5-3"></a>现有的首 token 解码耗时（`decodeDurationMs`）不得作为新输出速率的回退来源。

## 架构与核心决策

### D1. 在通用适配器调用边界计时

由 Agent 的统一模型调用执行路径在调用 Provider 适配器前启动单调计时，并在整个请求或流消费结束时停止。这样 `.generate()` 和 `.stream()` 都能使用同一契约，无须要求每个 Provider 新增专属计时实现或改变其流式协议。

耗时字段表达应用观察到的完整 Provider 请求生命周期。它包含网络、Provider 排队/处理、首 token 等待和响应接收；不包含本地调用前准备及 Agent 对响应的后续处理。它不是模型服务端的纯生成阶段计时。

### D2. 以完成事实承载耗时

在模型调用完成事实中新增可选 `requestDurationMs`。持久化边界继续校验事实结构；旧事实因字段可选而可读，新事实没有该字段时不会被估值。保留原有 `decodeDurationMs` 事实字段以读取和保留已有采集语义，但投影和展示不得用它计算新的输出速率。

### D3. 速率投影采用耗时加权聚合

Session Metrics 投影只将成功调用、Provider 确认的输出 token 数和有效 `requestDurationMs` 配对。分子是纳入调用的输出 token 总和，分母是对应请求耗时总和。DTO 的速率数值和覆盖计数字段可维持现有形状，但其定义及 TSDoc 必须改为端到端输出速率。

该聚合表示按请求耗时加权的调用速率；并发请求的独立耗时分别累加。因此它不宣称是跨并发请求按 Run 墙钟时间计算的吞吐量。

### D4. 完成调用后实时刷新，不估算进行中的调用

沿用现有指标事实持久化与实时观察链路：每个完成事实写入后更新指标投影。正在执行的 Provider 调用在完成前不贡献临时 token、耗时或速率；不新增按 token delta 持续猜测最终用量的机制。

### D5. 替换 Generation 展示

按用户选择，Goal 卡片、摘要栏与详情弹窗用端到端输出速率替换 Generation 展示，不并列保留旧解码速率。旧 `decodeDurationMs` 可继续作为事实中的观测字段，但不作为该 UI 指标的计算输入。

## 曾考虑的备选方案

1. **只统计流式首 token 后的解码耗时**：排除非流式 Provider，并掩盖首 token 等待和响应传输差异；与跨 Provider 统一比较的目标不符。
2. **由各 Provider 实现各自的速率计时**：计时边界会随适配器实现不同，增加 Provider 接入成本，难以保证口径一致。
3. **同时展示端到端与解码速率**：用户已选择替换现有 Generation 指标；并列展示会让核心摘要变复杂，而且解码速率仍无法覆盖非流式调用。
4. **先对每次调用求速率，再计算算术平均**：短请求和长请求权重相同，会偏离按总输出 token 和总请求耗时计算的速率，因此采用总量相除。
5. **从旧 Trace 或旧解码耗时回填请求耗时**：这些数据没有证明新计时边界，回填会把估值混入实测结果，因此旧调用保持未测量。

## 风险与否定性保证

- **风险等级：中。** 改动跨越 Runtime 指标事实、Storage JSONL 校验、Session Metrics 投影、Web DTO 和 Goal Board 展示；错误字段传播或不一致的口径会导致指标误报。通过在事实源定义边界并由投影统一筛选来控制。
- 不新增 Provider 特定流式协议或强制 `.stream()` 支持；非流式 `.generate()` 调用也可以纳入测量。
- 不把 Provider 内部解码速度、整个 Run 墙钟吞吐量或工具执行速度描述为本指标。
- 不推测未报告的 token 用量，不将缺失值按零计算，不用旧 Trace 或旧解码计时伪造请求耗时。
- 不改变 token、缓存、上下文余量及用量覆盖率的事实来源和计算语义。
- 本 Spec 修订了既有 Generation 速率定义。Session Metrics 的速率展示统一采用端到端 Provider 请求耗时。
