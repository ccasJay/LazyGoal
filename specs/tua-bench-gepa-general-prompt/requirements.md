# TUA-Bench 驱动的通用 Prompt 进化需求

## 审批摘要

### 目标

以本机 default Agent Profile 的 `systemPrompt` 和 `instructions` 为种子，用 TUA-Bench 驱动 GEPA 生成通用 Prompt 候选，并通过独立任务和其他 LazyGoal 环境检验其迁移表现。

### 范围

- 包含：TUA-Bench 候选评测与官方评分；按任务族覆盖的训练、GEPA 验证和最终预留任务；两个 Prompt 字段的变异；评分信息隔离；候选产物、跨环境对照和审阅报告。
- 不包含：自动覆盖本机 default Profile、写入未来内置默认值、模型权重训练、仅凭 TUA-Bench 分数认定通用性。

### 核心行为

- 每次运行从明确指定的 default Profile 冻结完整 Prompt；候选只能改变 `systemPrompt` 和 `instructions`，不得改变工具授权、执行协议或其他 Profile 字段。
- TUA-Bench 训练与 GEPA 验证使用互不重叠的任务；最终预留任务在候选确定后才参与评估。Agent 和反思反馈不得接触验证器私有内容、标准答案或预留任务信息。
- TUA-Bench 候选以官方验证器的数值 reward 评分，保留部分得分；任务失败、评分故障、基础设施故障和取消必须区分。真实运行须先展示数据、模型、预算、联网任务和费用影响，再经当次明确确认启动。
- 同一候选与种子使用可比条件评估 TUA 预留任务以及 GAIA 和 ALFWorld；报告分别展示任务族和环境结果、运行成本、Prompt 改动与证据不足之处。
- 无论优化成功、失败、停止或恢复，本功能都只保存已产生的候选与报告，不自动修改本机或仓库中的默认 Prompt；未证实净收益时不得建议晋升。

### 风险与待确认

- 风险等级：high；理由：可信评分可能需要调整容器内验证器的可见边界，真实运行涉及付费模型、容器及部分联网任务，候选未来可能影响所有默认任务。
- 关键操作：启动真实 GEPA 运行前，必须基于当次预检摘要明确确认模型和容器费用、预算及联网任务范围。
- 风险：公开任务与验证器信息可能造成过拟合；少量或不可比试次可能夸大提升；[TUA-Bench 官方仓库](https://github.com/facebookresearch/TUA-Bench)标注 CC BY-NC，未来商业内置用途需单独核对授权范围。
- 待确认：无。

## 引言

本功能把现有 TUA-Bench 隔离评测接入 GEPA Prompt 进化流程，以 default Profile 的两个 Prompt 字段形成候选，再用未参与优化的终端任务和其他任务环境检验表现，交付供人工审阅的候选与对照证据。

## 需求

### 需求 1：独立且可追溯的任务集合

**用户故事：** 作为 Prompt 优化者，我希望明确训练与验证使用哪些任务，以便识别任务泄漏并复现候选表现。

#### 验收标准

1. <a id="req-1-1"></a> 当准备一次 TUA-Bench 优化时，系统必须要求调用方明确提供数据来源和任务范围，并记录数据来源版本、任务 ID、任务族及各任务所属集合。
2. <a id="req-1-2"></a> 当形成训练集、GEPA 验证集和最终预留集时，三者的任务 ID 必须互不重叠；验证集与预留集均须覆盖本次训练纳入的每个任务族，预留集在候选确定前不得参与变异、反思或选择。
3. <a id="req-1-3"></a> 如果任务缺失、重复、所属任务族不明、运行资源缺失，或无法满足上述独立性与覆盖要求，系统必须在调用模型前拒绝运行并指出具体问题。

### 需求 2：完整 Prompt 候选与冻结约束

**用户故事：** 作为 default Profile 的维护者，我希望 GEPA 同时改进总体说明和逐条指引，以便评估真正会交付给用户的完整 Prompt。

#### 验收标准

1. <a id="req-2-1"></a> 当优化开始时，系统必须从明确指定的本机 default Profile 冻结 `systemPrompt` 和完整 `instructions`，并将该快照作为种子候选和后续对照基线。
2. <a id="req-2-2"></a> 当 GEPA 产生候选时，候选可以变异 `systemPrompt` 与 `instructions`，但不得改变 Profile 身份、工具列表、授权边界、Prompt Bundle、模型输出契约或完成证据规则。
3. <a id="req-2-3"></a> 当候选进入任一任务评测时，执行中的 Agent 必须实际接收该候选的两个 Prompt 字段；候选与种子的其他执行条件必须保持一致。
4. <a id="req-2-4"></a> 如果候选包含具体任务的标准答案、验证器私有内容或仅对已知任务有效的硬编码解法，系统不得将其标记为可晋升候选，并必须在报告中说明排除原因。

### 需求 3：可信的 TUA-Bench 评分与反馈

**用户故事：** 作为评测审阅者，我希望候选分数只反映实际完成任务的程度，以便不把验证器泄漏或运行故障误认为 Prompt 改进。

#### 验收标准

1. <a id="req-3-1"></a> 当 TUA-Bench 任务结束时，候选评分必须来自该任务官方验证器返回的数值 reward；合法的部分得分不得被压成零，模型的完成声明不得替代官方评分。
2. <a id="req-3-2"></a> 当 Agent 仍可执行任务操作时，它不得读取或修改仅供评分使用的验证器脚本、标准答案及其私有产物；若这一隔离条件无法满足，该任务不得产生可用于 GEPA 的有效分数。
3. <a id="req-3-3"></a> 当失败信息进入 GEPA 反思时，反馈必须保留任务状态与有界诊断，同时排除验证器脚本、标准答案、验证器原始输出和最终预留任务信息。
4. <a id="req-3-4"></a> 当 reward 缺失或无效，或容器、Worker、模型调用、产物回收发生故障时，系统必须将该任务归为评分或基础设施故障，不得把它作为零分任务继续优化；正常完成但 reward 较低的任务仍须作为领域结果保留。
5. <a id="req-3-5"></a> 当运行被取消时，系统必须将未完成任务标记为取消，且不得把取消记为候选的领域零分。

### 需求 4：有界运行与仅保存候选

**用户故事：** 作为运行发起者，我希望在了解真实资源影响后启动优化，并保留人工决定是否采用候选的权利。

#### 验收标准

1. <a id="req-4-1"></a> 当请求预检时，系统必须在不启动容器、调用模型或修改 Profile 的情况下展示任务集合、Working LM、Reflection LM、评测预算、可能联网的任务和预期副作用。
2. <a id="req-4-2"></a> 当请求启动或恢复真实优化时，系统必须要求针对当次预检内容的明确确认，并在预先声明的评测预算与任务时限内运行；取消后不得再启动新任务。
3. <a id="req-4-3"></a> 无论运行成功、失败、停止还是恢复，本功能都必须保留已完成的有效评测和已产生的候选产物，且不得自动覆盖本机 default Profile 或仓库中的未来内置默认值。

### 需求 5：未见任务与跨环境验证

**用户故事：** 作为未来默认 Prompt 的审阅者，我希望看到候选在训练任务以外的表现，以便判断它是否只适合 TUA-Bench。

#### 验收标准

1. <a id="req-5-1"></a> 当 GEPA 确定最佳候选后，系统必须在未参与优化的 TUA-Bench 预留任务上，将该候选与种子在同一任务、模型配置、运行预算和试次条件下比较。
2. <a id="req-5-2"></a> 当评估通用性时，系统必须将同一完整候选与种子分别用于 GAIA 和 ALFWorld 的指定任务，保持各环境原有工具授权和评分规则，并分别报告结果。
3. <a id="req-5-3"></a> 如果 GAIA 或 ALFWorld 缺少可用任务、无法应用同一候选，或对照条件不一致，系统必须标明跨环境验证未完成，不得以其他环境结果补称其表现或推荐晋升。

### 需求 6：可审阅的对照报告

**用户故事：** 作为人工审阅者，我希望得到完整候选及其证据，以便决定是否另行推进内置默认 Prompt。

#### 验收标准

1. <a id="req-6-1"></a> 当优化结束或停止时，系统必须提供可读取的完整候选、两个 Prompt 字段相对种子的改动、候选与种子身份、数据集合及版本、模型配置、评测预算和产物定位信息。
2. <a id="req-6-2"></a> 当生成对照报告时，系统必须分别展示 TUA-Bench 各任务族及预留集、每个非 TUA 环境的种子与候选结果，并列出原始 reward、通过状态、有效试次数、任务/评分/基础设施故障及可取得的用量与成本。
3. <a id="req-6-3"></a> 如果 TUA 预留集平均得分不高于种子，或 GAIA、ALFWorld 任一组平均得分低于种子，报告必须标记不建议晋升；如果有效样本或试次少于预先声明的对照计划，报告必须标记证据不足。报告不得自动将候选写入默认 Prompt。
4. <a id="req-6-4"></a> 当报告包含任务诊断时，面向审阅者的汇总不得泄露凭据、验证器私有内容或标准答案，并必须明确哪些 LazyGoal 场景尚未覆盖。

### 需求 7：验证与副作用边界

**用户故事：** 作为仓库维护者，我希望日常回归能验证接入契约，而真实评测只在显式请求下执行，以便控制成本与外部副作用。

#### 验收标准

1. <a id="req-7-1"></a> 当运行默认自动化回归时，任务集合校验、候选冻结、评分映射、故障分类、信息隔离及报告检查必须无需真实模型、Docker 或外部数据服务即可完成。
2. <a id="req-7-2"></a> 当显式执行真实端到端验收时，系统必须能证明候选 Prompt 实际进入 TUA-Bench 隔离任务、官方 reward 被回收、有效与无效评分可区分、最佳候选能在预留及跨环境任务中对照，且本机 default Profile 保持不变。
