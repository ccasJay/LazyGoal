# Prompt 基础指令与动态上下文分层需求

## 审批摘要

### 目标

让 LazyGoal 在长期 Goal 中保持更完整、稳定的基础指令，并按状态变化向模型提供完整、准确的动态上下文，减少重复内容且不损害恢复能力。

### 范围

- 包含：从当前 `dev` 实现由模型请求 Think 的按需阶段决策及 Think 输出恢复；扩充内置 system prompt 的固定行为指令并与动态上下文分层；动态内容的身份、来源和消息角色；首版对 Run 模式、已批准任务、GoalPlan、授权工具和 Working Memory 分别进行 section diff；区分比较状态、模型可见更新和恢复记录；历史裁剪和恢复后的当前状态重建。
- 不包含：模型专属消息目录、供应商协议扩展、Runtime 工具授权或审批规则改动，以及新增项目指令发现机制。

### 核心行为

- 当前任务、GoalPlan、Run 模式、授权工具等状态变化不得改写长期稳定的基础指令；现有 Profile 指令的有效语义必须保留。
- 内置基础指令与固定阶段说明在单阶段参考请求中应达到约 2,000–3,000 `o200k_base` tokens，覆盖目标理解与持续推进、工具和证据边界、失败恢复、用户沟通、等待与完成等行为；不得靠重复内容凑篇幅，也不得把动态状态计入该目标。
- diff 比较同一推理阶段中，动态 section 的当前模型可见投影与保留历史里最近有效的模型可见投影：首次可见时提供完整内容，投影未变化时不追加，变化时追加必要更新，移除时明确失效。已有模型可见历史不得被原地改写。
- Working Memory 与 GoalPlan 分别作为动态 section；比较状态、发给模型的语义更新和恢复所需的已提交记录必须区分。各 section 可按自身语义选择完整替换或局部更新，不把内部状态差异记录直接发送给模型。
- Step 执行状态、上一轮结果、pending Action、checkpoint、Hot/Warm 和 Lookup 结果按每次请求提供；这些本轮输入不得因状态 section 未变化而被省略。
- 当相关历史被裁剪、Context Epoch 切换或 Goal 恢复时，各推理阶段的请求仍须呈现当前有效状态；相同已提交状态、阶段及阶段输入生成相同请求，超出上下文预算时保持现有失败边界。
- 每个 Step 先尝试 Decide：模型可提交有效决策，也可提出带明确目标的 Think 请求；Think 使用 `prompt_only` 并接收该目标，其后的 Decide 仍可按需再次请求 Think，直到取得有效决策或被现有失败、中止边界打断。请求 Think 与 Think 输出都不单独推进 Step；首版不新增每 Step 的 Think 次数或累计 token 预算。Decide 在支持原生 strict 的供应商上使用 `strict`，其余现有供应商使用带结构指引的 `prompt_only` 与相同的本地校验；再次 Decide 必须显式获得所需当前状态及已提交的 Think 结果，并保留其模型来源语义。
- 当 Think 输出已成功提交、后续 Decide 失败或被取消时，当前 Step 保持可恢复，恢复后复用该输出并只重试 Decide；未提交的输出不得成为恢复依据。
- 分层不得放宽 Prompt Bundle 版本约束、工具授权、审批、模型输出校验及证据校验；未获批 Plan Run 的“先提案”顺序仍是模型行为要求，不新增 Runtime 业务工具硬门控；来自用户或外部内容的文本不得因分层获得更高指令权限。

### 风险与待确认

- 风险等级：high；理由：变更影响所有模型请求的指令优先级、长任务恢复和模型可见授权信息。
- 关键操作：无。
- 风险：增量消息与保留历史或阶段交接不一致时，模型可能遗漏现行约束或继续遵循已撤销的状态；需要覆盖恢复、裁剪、阶段交接和权限边界。
- 风险：扩充固定指令会提高请求的输入量，并可能影响上下文预算与缓存命中；需核对新增规则与现有协议一致，避免相互矛盾或重复。
- 风险：Think 中间文本将成为持久化数据；Decide 的 `prompt_only` 路径缺少供应商原生结构约束，必须保持本地解析、授权和证据校验，恢复时防止跨 Goal、Run 或 Step 复用旧输出。
- 风险：同一 Step 可反复请求 Think 且不新增调用预算，模型调用费用、延迟和持久化内容可能持续增长；现有取消与失败边界仍须生效。
- 实施基线：当前 `dev`；其配置已接受 `two_stage`，但 Agent 执行器仍按单次模型请求运行，本 Spec 包含补齐由模型请求 Think 的按需阶段调用。
- 待确认的需求决策：无。

## 引言

本需求从当前 `dev` 出发，补齐由模型请求 Think 的按需阶段调用及 Think 后的恢复点，扩充内置固定行为指令，将混合在单条 system 消息中的稳定规则与运行状态区分，并引入按动态 section 比较的增量注入行为；实现方案由后续 Design 确定。

## 需求

### 需求 1：稳定的基础指令

**用户故事：** 作为长任务使用者，我希望基础执行规则在任务推进时保持稳定，以便模型持续遵循同一行为契约。

#### 验收标准

1. <a id="req-1-1"></a> 当系统构造模型请求时，必须将长期适用的执行规则与当前运行状态区分，并使基础指令不依赖本轮 Step、当前任务、GoalPlan、Run 模式或授权工具列表的变化。
2. <a id="req-1-2"></a> 当上述动态状态发生变化而基础规则未变时，后续请求中的基础指令必须保持字符级一致。
3. <a id="req-1-3"></a> 当 Goal 使用冻结的 Profile 指令和 Prompt Bundle 时，分层后的模型请求必须继续体现这些指令及其版本约束，不得静默替换为当前默认版本。
4. <a id="req-1-4"></a> 当同一步中的 Think 与 Decide 需要不同的阶段说明时，这些说明不得改变两个阶段共享的长期基础指令。
5. <a id="req-1-5"></a> 当系统在默认 Profile、无授权业务工具、无任务与 GoalPlan 的参考场景中构造任一阶段的单次请求时，内置基础指令与该阶段固定说明的模型可见文本按 `o200k_base` 估算必须处于 2,000–3,000 tokens；统计不包含 Profile 文本、动态 section、Conversation、Working Context、Shape Guide 或工具 schema，也不合并两阶段的 token 数。
6. <a id="req-1-6"></a> 当内置固定指令扩充后，两个阶段都必须获得与其职责相符的目标理解与持续推进、工具使用与授权、证据驱动验证、失败恢复、用户沟通、等待及完成行为要求；新增文本不得通过重复、空泛填充或与现有协议冲突的规则满足篇幅目标。

### 需求 2：有身份与来源的动态上下文

**用户故事：** 作为 Prompt 维护者，我希望每段运行时上下文都能识别来源和作用，以便检查模型在某轮实际接收了哪些信息。

#### 验收标准

1. <a id="req-2-1"></a> 当任务、GoalPlan、Working Memory、Run 模式、授权工具或其他模型决策所需的运行状态进入请求时，系统必须按稳定身份区分各动态 section，并能检查其来源和模型消息角色；Working Memory 必须与 GoalPlan 分属不同 section。
2. <a id="req-2-2"></a> 当来自 Conversation、Tool Observation、历史检索或其他外部内容的文本进入动态上下文时，系统不得把该文本提升为基础指令或授予高于其来源的指令权限。
3. <a id="req-2-3"></a> 当相同的已提交状态被重复投影时，各 section 的内容、身份和排列顺序必须一致；模板变量中的文本不得被二次执行。
4. <a id="req-2-4"></a> 当 Step 执行状态、上一轮结果、pending Action、checkpoint、Hot/Warm 或 Lookup 结果存在且属于本次推理所需输入时，系统必须在该次请求中提供，不得因可 diff 的当前状态 section 未变化而省略，也不得把已提交的历史事实当成可由状态更新覆盖的 section。

### 需求 3：按 section 变化增量注入

**用户故事：** 作为长任务使用者，我希望模型只收到需要更新的状态说明，以便减少重复输入，同时始终依据现行状态决策。

#### 验收标准

1. <a id="req-3-1"></a> 当某个动态 section 尚未出现在当前推理阶段保留的模型可见历史中时，系统必须提供该 section 的完整当前模型可见投影。
2. <a id="req-3-2"></a> 当系统判断动态 section 是否变化时，必须以同一推理阶段保留历史中最近有效的模型可见投影为基线，只依据该 section 的模型可见差异决定是否更新；比较状态可以是该投影的等价摘要，不得以完整 Runtime 状态或渲染后的整条 Prompt 文本作为比较对象。
3. <a id="req-3-3"></a> 当两份投影一致或只有未投影的 Runtime 字段变化时，系统不得追加该 section 的重复状态消息；当投影变化时，必须追加足以让模型理解新状态的更新。
4. <a id="req-3-4"></a> 当先前可见的 section 被移除或失效时，系统必须明确告知模型该状态不再有效，不得让旧内容继续充当当前状态。
5. <a id="req-3-5"></a> 当系统注入动态变化时，必须保留已提交的真实 Conversation 和 Trajectory 事实，不得通过原地改写历史消息来实现差异更新。
6. <a id="req-3-6"></a> 当 Working Memory 的模型可见投影未变化时，系统不得重复注入该 section；当投影变化时，必须明确传达当前有效内容及旧内容的替换或失效关系，允许按 section 语义完整替换或局部更新。
7. <a id="req-3-7"></a> 当系统计算并注入动态 section 的变化时，必须区分用于判断变化的比较状态、模型可见的语义更新与恢复比较基线所需的已提交记录；不得把内部状态差异记录直接当作模型消息发送。

### 需求 4：裁剪与恢复后的状态完整性

**用户故事：** 作为可恢复 Goal 的使用者，我希望增量上下文在暂停、重启或历史裁剪后仍准确，以便任务不会因缺少先前消息而误判状态。

#### 验收标准

1. <a id="req-4-1"></a> 当 Context Epoch 切换或历史裁剪使先前的动态 section 不再模型可见时，下一次请求必须补齐决策所需的当前有效状态，不能仅依赖已经丢失的差异基线。
2. <a id="req-4-2"></a> 当 Goal 从已提交的 Snapshot 与 Trajectory 恢复时，系统必须能够重建当前模型可见状态，并重建或识别缺失的后续比较基线；基线缺失时必须提供完整当前状态，不得依赖供应商连接、未持久化的进程内差异缓存，或仅靠反解析先前发给模型的自然语言更新来恢复当前状态。
3. <a id="req-4-3"></a> 当相同的已提交边界、推理阶段及该阶段输入被重新执行时，系统必须产生相同的模型请求；上下文无法在现有预算内完整表达时，必须沿用明确失败行为，不得静默遗漏有效状态。
4. <a id="req-4-4"></a> 当同一步先由 Decide 请求 Think、再执行一次或多次 `prompt_only` Think 与后续 Decide 时，系统必须分别依据各阶段实际保留的模型可见历史确定动态 section 的比较基线；每次后续 Decide 必须显式包含其决策所需的当前有效状态和已提交的 Think 结果，不得假定其他请求的内容会自动成为该请求的模型可见历史。

### 需求 5：保留执行与验证边界

**用户故事：** 作为 Goal 执行与审计者，我希望上下文分层只改变模型接收信息的方式，以便既有授权和结果验证继续可靠。

#### 验收标准

1. <a id="req-5-1"></a> 当模型依据分层请求发起 Tool 调用时，Runtime 必须继续按冻结 Profile、Tool Policy、Action 审批及工具输入契约执行现有检查；模型可见说明不得自行授予权限。
2. <a id="req-5-2"></a> 当模型提交决策、GoalPlan 更新或完成声明时，系统必须继续执行现有输出契约、状态转换和已提交证据校验；Working Memory 的增量更新不得使记忆条目充当已提交 Tool/Observation 证据。
3. <a id="req-5-3"></a> 当 Prompt Bundle 不受支持、必需上下文缺失或动态 section 无法可靠比较时，系统必须在产生不完整的模型请求前失败，不得回退到含有过期状态的请求。
4. <a id="req-5-4"></a> 当 Plan Run 尚未批准任务时，分层后的模型指令必须继续要求模型先提交任务提案；Runtime 对业务工具调用仍按现有冻结 Profile、Tool Policy 和 Action 审批规则处理，不得仅因任务未批准而新增硬门控。

### 需求 6：从当前 dev 接入按需阶段决策

**用户故事：** 作为 Goal 使用者，我希望模型在尝试决策时按需请求思考，以便获得当前上下文后提交符合输出契约的最终决策。

#### 验收标准

1. <a id="req-6-1"></a> 当当前 `dev` 执行器需要模型为一个 Step 作出决策时，系统必须先调用 Decide，允许模型直接提交决策，或输出经本地验证的 Think 请求；仅在收到该请求后调用 `prompt_only` Think，再调用 Decide。后续 Decide 仍可请求 Think；首版不得设置额外的每 Step Think 次数或累计 token 预算，持续调用直到取得有效 AgentDecision 或现有失败、中止边界生效。Decide 在 OpenAI、Google 与 OpenAI-compatible 上使用带原生严格输出约束的 `strict`，在 Anthropic、OpenRouter 与 DeepSeek 上使用带结构指引的 `prompt_only`；两种供应商路径都必须通过本地输出校验，仅将有效的最终 AgentDecision 提交给 Runtime 执行。
2. <a id="req-6-2"></a> 当模型请求 Think 时，请求必须包含非空、明确的思考目标，系统必须将该目标传给本次 Think；该请求不得被当作已完成的 Step、Tool Action 或用户指令。后续 Decide 必须接收此前已提交的 Think 输出及其决策所需的当前有效状态。Think 目标与输出必须保留模型生成内容的来源语义，不得被当作新的用户意图或 Runtime 授权指令。
3. <a id="req-6-3"></a> 当任一阶段失败或被取消时，系统不得把未完成的阶段链结果作为有效决策提交；现有输出解析、工具授权和证据校验边界必须继续适用。
4. <a id="req-6-4"></a> 当模型请求 Think 时，系统必须先将每次 Think 输出与所属 Goal、Run、Step 的输入边界可靠提交，再发起后续 Decide；如果提交失败，不得发起后续 Decide。当已提交输出对应的 Decide 失败或被取消时，当前 Step 必须保持可恢复；恢复时复用该 Step 已提交的 Think 输出并只重试该 Decide，不得重新调用此前已完成的 Decide 或 Think，也不得使用未提交或身份不匹配的输出。
5. <a id="req-6-5"></a> 当模型请求 Think 或已有 Think 成功但最终 Decide 尚未提交有效结果时，系统不得增加 `stepCount`、生成已完成 Step 记录或执行 Tool；直接 Decide 与多轮 Think 后的有效 Decide 均只按有效决策及现有 Runtime 规则推进 Step。
