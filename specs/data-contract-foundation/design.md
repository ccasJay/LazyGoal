# 数据契约设计参考

> 本文保存双核心架构的数据契约终态设计，作为[渐进迁移路线](../contract-migration/README.md)的参考，不再作为一个整体交付或审批单元。下文验收条目是后续小 Spec 的设计素材，不要求某一步完成全部条目；实施范围以当步独立 Spec 为准。当前从[在线模型列表响应](../ts-provider-models-contract/spec.md)开始。

## 目标与范围

将 LazyGoal 的契约层重构为“数据契约 + 执行契约”双核心。数据契约回答载荷包含什么、字段意味着什么、数据本身必须满足哪些约束；[执行契约](../execution-contract-foundation/design.md)回答谁能推进任务、何时允许副作用、如何提交、失败与恢复。两者共同构成 Agent 架构基础，不要求各自对应一个集中存放全部领域类型的大包。

本参考 以原生 TypeScript `interface/type` 和必要 JSDoc 约束作为自有数据契约的主要定义来源，替换当前 Contract DSL、AST、`InferContract`、手写通用 Parser 和通用 JSON Schema 编译器。覆盖模型载荷、工具输入及跨边界结果、Web/进程消息、配置解析后的数据和持久化 DTO；普通类型化接口不因此次重构增加运行时校验。

允许重设当前开发协议，不提供旧协议兼容层。协议调整限于本文明确的数据表示、生成机制、校验和提取规则；执行、授权、审批、恢复、关闭的可观察语义遵循执行契约参考。本文不新增通用置信度评分、迁移框架、远程 Agent 调度系统或新的传输方式。

### 六个内部设计维度

六层是双核心内部的设计和验收维度，不建立六套定义语言、注册中心或独立生命周期。本表是两份参考 的维度归属说明。

| 维度 | 数据契约的职责 | 执行契约的职责 |
| --- | --- | --- |
| 结构 | 字段、值域、联合分支、可序列化表示与读取结果。 | 消费类型化命令和结果，不重复定义载荷结构。 |
| 语义 | 字段定义、单位、身份含义和仅依赖当前载荷的数据不变量。 | 命令效果、前后条件、副作用和依赖当前运行状态的业务规则。 |
| 执行 | 动作、审批、授权决定等载荷的形状。 | 权限、执行准入、审批绑定和副作用顺序。 |
| 状态 | 状态值和快照的表示及数据内部一致性。 | 状态所有权、合法转换、并发、超时、重试、恢复与关闭。 |
| 可信度 | 现有来源、证据引用和候选标记的表示与含义。 | 核验证据、采信结果和接受完成声明；不把结构合法等同于事实可信。 |
| 演进 | 生成物、发布版本、Schema 方言和兼容范围。 | 版本变化时的恢复、授权及在途结果处理，保持当前执行保证。 |

## 需求与验收标准

### 需求 1：以原生 TS 维护结构

作为契约维护者，我希望只维护一份自有数据结构定义，以避免 TS 类型、运行时校验和跨系统 Schema 漂移。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当新增或修改自有数据契约时，维护者应当通过所属模块的 TS 类型和必要 JSDoc 表达结构与字段约束；系统从这些源生成边界制品，不要求同步编辑 DSL、Zod/Pydantic 定义或手写字段 Schema。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当类型使用泛型、联合、映射、交叉、递归或可选属性时，系统应当在需要导出契约的具体类型上解析其结构；若生成器无法正确解析，应当在生成阶段定位并失败，不得静默放宽为 `any`、空 Schema 或跳过校验。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当生成跨 Agent 或其他 JSON 边界的契约时，系统应当要求其 wire 表示由 JSON 标量、数组、对象、字典及其组合组成；函数、进程句柄、流、循环对象和类实例不得被当作普通 JSON 载荷导出。确需传输的日期、大整数或二进制数据应当由所有者明确其字符串、数字、数组或引用表示及编解码。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：当本参考 完成时，生产消费者应当不再依赖原 Contract 构造器、AST 节点检查、`InferContract` 和自研通用解析/编译实现；仍有消费者的 canonical JSON、对象守卫和深冻结等独立原语应当保留单一实现。

### 需求 2：明确字段语义与数据约束

作为数据消费者，我希望类型合法的数据也满足其声明的字段约束，并能够区分数据错误和执行拒绝。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当 TS 基础类型不足以表达数值范围、整数、字符串模式或长度、数组长度时，系统应当从受支持的 JSDoc 约束生成校验；出现未知、拼错、不支持或不适用于目标类型的约束注解时应当生成失败。文档标签与约束标签应当明确区分。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当仅依赖本次载荷的数据关系需要校验时，例如区间顺序、身份唯一或快照内部引用一致性，系统应当调用所属模块的命名纯函数；该函数不得读取 Runtime 当前状态、执行工具或更改持久化状态，也不得重复维护字段类型表。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当字段省略、为 `null`、为空字符串或为错误类型时，读取器应当分别按照 TS 与约束处理；不得自动补默认值、将字符串转换为数字、删除非法已知字段以通过校验，或将 `null` 普遍视作省略。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当迁移现有数值及文本约束时，系统应当保留安全整数、有限数值和字段已声明的长度语义；JSON Schema 的字符长度与现有 UTF-16 展示上限不同的规则应当由各自所有者明确校验，不得因更换生成器而静默改变单位。

### 需求 3：宽容读取并提取已知字段

作为边界调用方，我希望无害的字段扩展不阻断处理，同时能够发现实际类型错误与发送端漂移。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当自有对象声明 `runId: string` 并收到 `{ runId: "r-1", debug: true }` 时，读取器应当成功返回 `{ runId: "r-1" }`，并产生定位到 `debug` 的未知字段诊断；缺少 `runId` 或其值为数字时应当失败，不向下游返回可执行的部分数据。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当对象嵌套于对象、数组或递归结构时，读取器应当递归提取已知字段；提取结果与诊断不得与输入共享可变子对象，且原始输入不得被修改。JSON 键应当按自有属性处理，不得因复制特殊键改变对象原型。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：当 TS 显式声明索引签名、`Record` 或 `JsonValue` 扩展载荷时，读取器应当校验并保留该开放范围内的合法值，不把字典键当作未知字段删除；使用任意 JSON 表示时不得接受非 JSON 值。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当读取联合类型时，系统应当基于未修改输入进行分支判定，再按匹配结构提取；未知判别值和无匹配分支应当失败。多个匹配分支若产生相同提取结果，应当合并诊断后成功；若产生不同结果，应当报告明确的联合歧义错误，不得按分支排列顺序任意删除字段或选择结果。
- <a id="spec-req-3-5"></a>**验收标准 3.5**：当产生未知字段诊断时，边界适配器应当记录契约身份、版本及有界字段路径，并标识诊断截断；不得默认记录字段值或完整原始载荷。未知字段诊断或其旁路记录失败不得把合法数据改判失败，不触发模型纠错或执行重试。
- <a id="spec-req-3-6"></a>**验收标准 3.6**：若载荷触发现有明确禁止的敏感字段或其他安全语义规则，系统应当按所属边界的规则拒绝；字段提取不得先删除这些字段并使禁止规则失效。此例外限于明确的禁止规则，不恢复默认严格对象策略。

### 需求 4：分层验证与稳定错误

作为 Runtime 和适配器维护者，我希望验证只发生在信任边界，并返回足够定位问题的数据。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当框架内部直接传递受 TS 检查保护的值时，系统应当依赖静态接口，不因其是“契约对象”而重复解析；模型输出、外部工具响应、配置解析结果、队列读取、文件/持久化数据和跨进程/传输消息应当在进入可信调用链前验证。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当读取成功或失败时，数据读取器应当分别返回类型化的提取结果或结构化问题，并将未知字段诊断与拒绝原因分开；问题应当包含稳定类别、字段/数组路径和安全英文消息，不暴露底层库错误对象或依赖消息正文分类。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：当外部工具响应穿过进程或第三方边界时，适配器应当验证响应信封及已声明结果结构；显式开放的结果只能宣称 JSON 合法，不得把它标记为已通过未声明的业务结果验证。库替换后现有模型、工具及持久化边界的外层错误分类应当保持可识别。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当输入超过所属边界的大小、深度或诊断预算，或包含循环/非 JSON 数据时，系统应当有界失败或截断诊断；不得因宽容读取而取消现有资源限制，亦不得在失败后继续执行。

### 需求 5：复用类型并隔离 wire 投影

作为工具与模型协议维护者，我希望相同载荷在注册、传输和模型声明之间共用定义，同时保留系统间真实的表示差异。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当注册自有工具时，输入类型、生成读取器及输入 Schema 应当关联同一契约入口；工具实现使用原生输入类型，不再通过 AST 推导。结果在需要穿越外部边界时同样关联其结果类型或显式 `JsonValue` 约定。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当按请求选择阶段决策或工具声明时，模型适配层应当组合已有生成制品及当前请求绑定；Runtime 仍应当独立判断工具是否获授权、可见及允许执行。Schema 中出现某个分支不授予执行权。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当 Provider 要求必填可空字段、封闭对象或受限 Schema 子集时，模型适配层应当从生成制品派生专用 wire 表示并在本地转换为 canonical 载荷；不能支持的结构应当在请求准备阶段明确失败，不得生成无约束占位 Schema。已接受并提交的原生续接字段、签名及 Part 顺序应当按第三方协议保真，不交给通用字段剥离器改写，也不作为可信执行参数直接复用。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当处理第三方协议或另一进程提供的 Schema 时，适配器应当识别其权威来源并限定支持范围；自有生产者应当从其 TS 类型生成并发布制品，不由消费者再维护一份同形状 TS/Schema。非 TS 系统的外部定义仅在该协议边界使用，不成为第二套 LazyGoal 内部结构定义。

### 需求 6：可复现生成与发布身份

作为契约发布者，我希望生成制品可以核对来源，并使消费者能够确定使用的 Schema 版本。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当运行数据契约生成或发布构建时，系统应当固定契约标识、Schema 版本、实际 Schema 方言、生成工具版本及制品内容摘要；类型、读取器、Schema 和读取策略应当来自同一输入集。相同输入重复生成的制品应当一致。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：当 TS、约束、生成设置或投影规则改变但提交制品未更新时，生成一致性检查应当失败；开发、回归和浏览器入口应当消费可直接加载的同一批制品，不依赖忽略目录下的 `dist/lib/build` 或运行时 TS transformer。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当对外发布契约时，系统应当在构建中固化对应版本与制品摘要；不同内容不得静默覆盖同一已发布身份。字段扩展可被宽容读取不等于任意语义变化都兼容；不支持的版本应当在协议入口明确拒绝。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当开发期调整当前协议时，系统应当只保留当前实现，不为旧本地 Goal、Snapshot 或协议添加迁移、回退和版本并行分支，也不因单纯实现变化递增版本。固定发布制品不要求现在增加每条消息的版本信封或提供在线版本协商。

### 需求 7：完成替换与交叉验证

作为框架维护者，我希望双核心落地后仍可验证实际边界行为，而不是仅完成类型替换。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当完成迁移时，模型文本/原生调用、工具准备与远程响应、Web 输入/输出、进程消息、配置及 Snapshot/Trajectory 的实际边界应当使用相应类型驱动制品与所属语义校验；删除旧实现及其生产导出，不保留新旧引擎回退。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当核对生成质量时，应当通过正常、缺失、错误类型、未知字段、开放字典、可空/可选、递归、联合歧义、错拼注解和超限样本，验证类型源、发布 Schema、读取策略与提取结果的对应关系；Node 与真实浏览器消费者应当通过相同代表性样本。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当两份参考 集成时，宽容读取后的输入应当进入执行契约规定的身份、授权和提交路径；无效数据与未知字段诊断应当分别证明不会触发副作用与额外执行。所属模块的 README、概览、语义表及公共 TSDoc 应当同步反映最终职责。

## 架构与核心决策

### 定义、生成与读取

数据类型保留在语义所有者处：模型载荷由 `model-contracts`、工具载荷由各工具、Web DTO 由 `web-contracts`、持久化表示由 `storage` 维护。执行状态的类型和合法值由执行领域拥有，数据层仅为需要序列化的表示生成制品。公共类型不能在两个核心各声明一份同义结构。

`contracts` 收敛为通用读取结果、诊断、JSON 原语及标准校验库的薄适配；编译器与构建依赖留在生成入口，不进入浏览器运行时依赖图。契约入口登记仅描述导出类型位置、契约身份、版本和生成目标，不允许登记字段表、约束表达式或执行策略。

生成路径为：**TS 与 JSDoc → 标准 JSON Schema → 标准库校验制品 → 类型化读取器与发布清单**。生成物置于所属模块可直接消费的 `src/generated/` 并纳入版本控制，由显式生成和只检查差异的命令维护，不手改生成物。

基线采用已做局部验证的 `ts-json-schema-generator`、Ajv standalone 及必要的 ESM 打包。固定实际验证过的依赖版本；生成器当前输出的 draft-07 按真实方言声明，不把它重新标记为 2020-12。Provider 使用其专用受限投影，不将“方言升级”作为更换引擎的附带需求。[生成器文档](https://github.com/vega/ts-json-schema-generator#cli-usage)、[Ajv standalone 文档](https://ajv.js.org/standalone.html)分别说明生成选项和独立校验代码的运行约束。

原生 TS 与约束注解是维护源；生成 Schema、读取器和发布清单属于派生物。JSDoc 初始约束范围覆盖数值上下界与 `multipleOf`、字符串长度/模式、数组项数；整数同时明确安全范围。字段单位与跨字段关系由 TSDoc 和命名纯函数补足，不另造表达式 DSL。生成检查必须发现被库静默忽略的约束注解。

读取接缝为 `DataReader<T>`，以 `unknown` 接收边界值并返回 `DataReadResult<T>`：成功分支携带 `ok: true`、`data: T` 和 `diagnostics`，失败分支携带 `ok: false`、`issues` 和 `diagnostics`，不携带部分 `data`；问题和诊断各自报告是否截断。此接缝不暴露生成库类型，具体所属模块的读取函数可直接包装它，不强制引入全局注册表。

默认不强制转换、不补值、不修改输入。只为实际跨界的类型生成读取器，不让 `Tool<Input>` 等同进程泛型接口为了满足 JSON 字典约束而强迫普通 `interface` 添加索引签名。数据定义中的 `readonly` 负责静态约束；不因此对每次同进程调用自动深冻结或深复制，边界读取的隔离保证按验收标准 3.2 执行。

### 宽容读取与 Schema 的对应关系

发布制品明确区分同源派生的两种用途：描述提取后载荷的值 Schema，以及描述接收规则的 reader Schema/读取策略。reader 只放宽固定对象的未知字段，不放宽必需字段、已知值约束、判别字段或显式字典的值约束。发布清单固定读取策略，不能让接收方误认为“严格拒绝额外字段”和“提取后继续”是相同行为。

校验使用纯验证模式。字段提取适配只负责按生成结构复制已知字段、保留开放范围和收集诊断；分支是否满足约束由标准校验器判定，禁止另写 TS AST Parser、标量约束解释器或公共投影 AST。对象形状不同的跨 Agent 消息优先采用判别联合；无判别联合按验收标准 3.4 处理歧义。不得把 Ajv 全局 `removeAdditional` 当作完整实现，其在联合分支试探期间可能修改待验证数据，[官方说明](https://ajv.js.org/guide/modifying-data.html#removing-additional-properties)要求对此组合特别处理。

语义禁止字段在提取前检查；仅依赖保留字段的关系在提取后检查。成功数据完成必要的 wire→canonical 转换后才进入可信调用链。工具准备结果、授权输入、审批展示和摘要计算共用同一 canonical 载荷；具体时序归执行契约参考。

### 协议调整与保留边界

| 现有设计 | 本次目标 |
| --- | --- |
| AST 维护结构，TS 通过 `InferContract` 推导。 | 原生 TS 维护结构，库生成 Schema 与校验制品。 |
| 自有对象分别使用严格或开放节点，后者可能保留未知字段。 | 固定对象宽容读取并剥离未知字段；字典与扩展载荷在 TS 显式开放。 |
| Contract Parser 同时校验并复制，错误包含 AST 定义分类。 | 标准库校验与提取适配分工；保留公共边界错误分类，定义错误在构建阶段暴露。 |
| wire 转换和请求组合遍历 Contract AST。 | 从生成结构派生专用 wire 投影并组合制品；模型协议绑定留在适配层。 |
| 自研编译器统一生成 2020-12 Schema。 | 清单与 `$schema` 使用实际方言，Provider 投影单独校验。 |

除本表和验收标准明确的变化外，不附带重命名业务字段、替换全部身份格式、改变 Snapshot 提交模型或添加通用消息信封。确需进一步改变 wire 形状时，应当在实施前修订本参考，给出具体前后表示并审阅，不能借“允许重设协议”自行扩大变化。

### 渐进实施边界

数据读取结果、诊断、生成入口、Tool 输入泛型对 AST 的解除以及 wire/持久化 Codec 替换属于数据方向；读取成功之后的受理、授权、审批、提交和恢复属于执行方向。模型提议类型保持由模型协议所有者维护，其是否能被接受由 Runtime 判断。

这些方向不再组成两次整体实施。每个小 Spec 仅替换一个契约族及其真实消费者，并说明它从本参考采用哪些规则。迁移期间允许未迁移契约继续使用原 AST；同一契约不保留双定义，不通过 TS→旧 AST 转换伪装替换，也不在新读取失败后回退旧解析器。执行接口只在完成当前迁移所必需的接缝上调整，其余保留现状。已迁移契约的旧节点应当随该步删除，最终无消费者时再删除引擎。

当前行为核对入口为[通用契约](../../packages/contracts/notes/overview.md)、[模型协议](../../packages/model-contracts/notes/overview.md)、[Web DTO](../../packages/web-contracts/notes/overview.md)、[持久化边界](../../packages/storage/notes/overview.md)和[执行契约参考](../execution-contract-foundation/design.md)。当前文档中的严格读取和 AST 说明属于迁移前基线，不视作本文已实现。

## 风险与否定性保证

- **风险等级：高。** 替换横跨模型、工具、持久化和权限相关载荷的边界；字段剥离、联合分支或编解码错误可能改变授权目标或恢复事实。关键操作是切换生产读取器、更新持久化 Codec、替换工具准备与模型 wire 投影。切换前必须完成验收标准 7 的真实路径验证，不能只证明生成文件可编译。
- **工具链风险。** 已完成的隔离验证覆盖 26 个基础样本及打包后 ESM 的 Node 加载，不证明宽容提取、全仓类型或真实浏览器入口通过。生成器的编译器版本与仓库 TS 版本存在差异；实施先验证具体泛型/映射类型、注解检查、递归与联合提取，再迁移消费者。若必须改变本参考 的类型书写方式或核心生成路线，应当修订设计，不静默引入第二套引擎。
- **资源与诊断风险。** 宽容处理仍需有界；被剥离字段不得回流为 canonical 执行参数、快照 DTO、授权摘要或模型视图。原生续接按验收标准 5.3 保真，既有原始输入记录按其受控边界保存，均不得作为绕过提取的参数来源。显式开放载荷按其声明处理，不能扩大为任意对象免验证。
- **否定性保证。** 数据读取不管理任务状态、不决定超时重试、不授予权限、不保存 Goal、不执行工具；禁止规则、执行身份和证据采信不能由类型断言或 Schema 成功替代。诊断不是恢复来源。
- **兼容边界。** 当前开发数据可以不兼容，但实施不得自动删除用户工作区或历史数据来掩盖读取失败；仅更新本次测试需要的 fixture。本文不批准真实数据清理或协议迁移操作。
