# React Ink TUI 需求

## 引言

本功能为 LazyGoal 提供基于 React Ink 的交互式终端入口，使使用者能够创建或发现一个非终态 Goal，在同一界面完成准备、执行、审批与恢复交互，并在中断程序时保留最近成功持久化的检查点。

## 需求

### 需求 1：命令入口与单 Goal 会话

**用户故事：** 作为 CLI 使用者，我希望通过简短且稳定的 `lazygoal` 命令进入目标会话，以便快速创建或继续工作。

#### 验收标准

1. <a id="req-1-1"></a> 当 LLM 配置有效且使用者执行不带参数的 `lazygoal` 时，系统必须启动交互式 TUI 并进入新 Goal 的 intent 输入流程，不得自动恢复已有 Goal。
2. <a id="req-1-2"></a> 当使用者执行 `lazygoal -c` 时，系统必须直接恢复最近更新的非终态 Goal；如果不存在候选项，系统必须输出英文错误并以非零状态退出，且不得创建新 Goal。
3. <a id="req-1-3"></a> 当使用者执行 `lazygoal resume` 时，系统必须打开可交互的 Goal 选择界面，并在使用者确认选择后恢复该 Goal。
4. <a id="req-1-4"></a> 当任一命令已创建或选定 Goal 后，当前程序必须只允许该 Goal 成为活跃会话，退出前不得并行驱动其他 Goal。

### 需求 2：模型配置与默认身份

**用户故事：** 作为 CLI 使用者，我希望通过环境变量完成模型配置，以便启动 TUI 时无需在界面中输入敏感凭据。

#### 验收标准

1. <a id="req-2-1"></a> 当程序启动时，系统必须从 `LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL` 读取 `OpenAICompatible` 所需配置。
2. <a id="req-2-2"></a> 当创建新 Goal 且模型配置完整时，系统必须使用应用提供的默认 Agent Profile，且不得要求使用者在 TUI 中选择 Provider 或输入模型凭据。
3. <a id="req-2-3"></a> 如果任一必需环境变量缺失或去除空白后为空，系统必须指出缺失的变量并以非零状态退出，且不得创建、恢复或修改任何 Goal。
4. <a id="req-2-4"></a> 当模型连接、鉴权或响应失败时，系统必须在 TUI 中显示可识别的英文错误，并保留失败发生前最近成功保存的 Goal 快照。

### 需求 3：可发现的恢复候选项

**用户故事：** 作为返回已有工作的使用者，我希望看到按最近活动排序的可恢复 Goal，以便准确继续目标会话。

#### 验收标准

1. <a id="req-3-1"></a> 当 Goal 的最新快照成功创建或更新时，系统必须使该 Goal 能够按其最近成功更新时间被后续命令发现。
2. <a id="req-3-2"></a> 当系统查找恢复候选项时，必须只返回 Run 状态不是 `completed`、`failed` 或 `cancelled` 的 Goal，并按最近成功更新时间倒序排列。
3. <a id="req-3-3"></a> 当 `lazygoal resume` 展示候选项时，每一项必须至少显示可区分的 `goalId`、intent 摘要、当前 workflow phase、Run 状态和最近成功更新时间，并允许通过键盘选择和确认。
4. <a id="req-3-4"></a> 如果多个候选项具有相同的最近成功更新时间，系统必须使用稳定且可重复的次级顺序；`lazygoal -c` 必须选择该完整排序中的第一项。

### 需求 4：新 Goal 与 Preparation 交互

**用户故事：** 作为 Agent 使用者，我希望在 TUI 中提交意图并完成执行前交互，以便 Agent 只执行经过我确认的任务。

#### 验收标准

1. <a id="req-4-1"></a> 当 TUI 请求新 Goal 的 intent 时，系统必须允许使用者编辑并提交文本；如果内容去除空白后为空，系统必须保持输入状态并显示英文校验提示。
2. <a id="req-4-2"></a> 当使用者提交合法 intent 时，系统必须创建并保存新 Goal、显示其 `goalId`，然后推进到首个等待点或执行终态；重复提交不得创建多个 Goal。
3. <a id="req-4-3"></a> 当 Goal 等待 `gathering_context` 问题回答时，TUI 必须显示 Agent 问题，并将使用者提交的非空文本作为对应的 `message` 操作恢复同一 Goal。
4. <a id="req-4-4"></a> 当 Goal 等待 `planning` 批准时，TUI 必须显示当前任务提案，并允许使用者批准提案或提交非空修改意见。
5. <a id="req-4-5"></a> 当创建或恢复操作尚未结束时，TUI 必须显示进行中状态并阻止重复提交会造成的并发推进。

### 需求 5：执行、Action 与终态交互

**用户故事：** 作为 Agent 使用者，我希望在 TUI 中理解执行进度并处理阻塞或风险 Action，以便对真实执行保持控制。

#### 验收标准

1. <a id="req-5-1"></a> 当 executing Goal 因 Agent `blocked` 等待输入时，TUI 必须显示等待原因，并将使用者提交的非空文本作为 `message` 操作恢复同一 Goal。
2. <a id="req-5-2"></a> 当 Goal 等待 Action 批准时，TUI 必须显示对应的 `actionId`、`toolId` 和结构化输入，并允许使用者批准该 Action 或提供非空理由拒绝该 Action。
3. <a id="req-5-3"></a> 当 Goal 恢复到结果未知的 Action 时，TUI 必须明确标识恢复风险，并只允许针对同一 `actionId` 执行批准重试或带理由拒绝。
4. <a id="req-5-4"></a> 当 Goal 活跃时，TUI 必须展示按原顺序排列的真实会话消息，以及当前 workflow phase、Run 状态、`stepCount` 和存在时的 checkpoint。
5. <a id="req-5-5"></a> 当 Run 进入 `completed`、`failed` 或 `cancelled` 时，TUI 必须停止接收推进输入，并显示终态、最终摘要或可用的停止原因。

### 需求 6：保留检查点的程序退出

**用户故事：** 作为需要随时中断工作的使用者，我希望按下 `Ctrl+C` 后程序完整退出且 Goal 保持可恢复，以便不会留下驻留进程或破坏已保存进度。

#### 验收标准

1. <a id="req-6-1"></a> 当任一 TUI 界面收到第一次 `Ctrl+C` 时，系统必须进入关闭流程，停止接受用户输入，并不得启动新的模型调用、Tool 调用或 Goal 推进。
2. <a id="req-6-2"></a> 当关闭流程开始时，系统不得把 Run 转换为 `cancelled`，不得回滚快照，也不得把尚未成功提交的内存状态保存为新快照；最近成功持久化的检查点必须保持有效，包括其中已有的 `pendingAction`。
3. <a id="req-6-3"></a> 当中断发生在未完成的模型调用期间时，后续恢复必须从最近持久化的检查点重新推进；当快照包含 `pendingAction` 时，后续恢复必须继续遵守该 Action 已有的安全重放或人工确认规则。
4. <a id="req-6-4"></a> 当关闭流程执行时，系统必须恢复终端状态并终止由当前程序拥有的输入监听、网络请求、计时器和子进程；清理超过有限等待时间时，系统必须强制结束剩余的受管资源。
5. <a id="req-6-5"></a> 当 `Ctrl+C` 关闭完成时，父程序及其受管子进程必须全部退出，程序必须返回退出码 `130`，并且最近成功保存的 Goal 必须能够在下一次启动时恢复。

### 需求 7：英文反馈与失败可见性

**用户故事：** 作为终端使用者，我希望所有状态和错误都清晰一致，以便理解当前会话以及失败后是否可以恢复。

#### 验收标准

1. <a id="req-7-1"></a> 当 TUI 显示标签、提示、操作、Agent 消息、状态或错误时，所有面向使用者的信息必须使用英文，代码标识与原始 Tool 数据除外。
2. <a id="req-7-2"></a> 当 Goal 不存在、快照损坏、状态与操作不匹配或 Runtime 返回业务失败时，TUI 必须显示可识别的错误信息，停止本次无效推进，并且不得静默创建替代 Goal。
3. <a id="req-7-3"></a> 当一次交互失败且最近快照仍可恢复时，TUI 必须保持错误可见，并允许使用者退出；再次启动恢复命令时必须仍以最近成功保存的快照为准。
