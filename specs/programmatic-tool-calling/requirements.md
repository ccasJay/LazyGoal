# PTC 程序化工具调用需求

## 审批摘要

### 目标

让 Agent 用 JavaScript 编排业务工具，并在沙箱内处理大量中间数据，只向模型返回结论，减少模型往返与上下文占用。

### 范围

- 包含：默认可用、通过一个专用 Tool 触发且由 Prompt 引导按需选择的 PTC；保留直接工具调用；覆盖获授权的读取、检索、文件修改和 Bash；内部调用审批、持久化记录与中断续跑。
- 不包含：厂商托管 PTC、绕过业务工具的任意宿主访问、外部系统副作用的 exactly-once 保证，以及历史开发数据的迁移或兼容。

### 核心行为

- Agent 必须通过专用 PTC Tool 提交 JavaScript 来发起程序执行；系统不得从普通模型文本或代码块中自动提取并执行程序。程序结束后，该 Tool 返回程序的显式返回结果或有界失败反馈。
- 每个程序使用干净、独立的 Node.js 沙箱进程；程序可按工具结果执行循环、分支和数据处理，不能直接取得宿主文件、网络、凭据或进程启动能力。隔离无法建立时不得执行程序。
- 正常完成时，只有可序列化的显式 `return` 值进入模型上下文；中间结果和 stdout/stderr 不自动进入后续模型历史。无有效返回、程序错误、工具拒绝或资源超限必须可辨别，诊断有界且不携带完整中间数据。
- 每次内部工具调用均遵守现有 Profile、输入校验、Permission、持续授权与 Sandbox 边界；审批展示实际操作，等待期间暂停程序推进，批准后继续，拒绝不得执行。授权撤销约束尚未开始的调用，不能用一次程序批准放行未来未知操作。
- 内部调用意图、已提交结果、审批等待和程序结算必须可持久化审计。审批或进程重启后恢复同一程序的逻辑进度，复用已保存结果；已确认完成的操作不得重复执行，结果未知且可能产生副作用的调用须等待用户处理，不因原工具允许重放而直接重跑。
- 执行时间、内存、工具调用次数与输出大小有界；取消后停止程序推进和新工具调用，并向正在执行的工具传递取消，不能将取消等同于副作用回滚。

### 风险与待确认

- 风险等级：高；涉及模型代码执行、宿主权限、写操作及跨进程恢复。
- 关键操作：程序内需要审批的 Tool 或 Sandbox 请求，仍须按现有有效授权范围取得批准；本阶段仅编写需求，不执行程序或业务操作。
- 风险：独立 Node.js 进程本身不构成安全隔离；恢复不能依赖旧进程内存，错误重放可能重复副作用；持久化记录与模型输出需区分，避免重新引入中间数据或泄漏宿主凭据。具体隔离与恢复机制在 Design 中确定。
- 待确认：无需求决策待确认。

## 引言

PTC（Programmatic Tool Calling）让 Agent 在保留直接工具调用的同时，通过专用 Tool 提交 JavaScript，完成多个业务工具的组合和中间数据处理。本需求定义按需选择、独立 Node.js 沙箱、结果返回、权限审批及可恢复执行的可观察行为。

## 需求

### 需求 1：专用 Tool 触发与按需选择

**用户故事：** 作为 LazyGoal 使用者，我希望 Agent 根据任务选择直接调用或程序编排，以便简单操作保持直接，批量处理减少模型往返。

#### 验收标准

1. <a id="req-1-1"></a> 当默认 Agent 处理 Goal 时，系统必须在可调用工具中提供一个专用 PTC Tool，并保留其原有直接工具调用与业务决策能力；用户无需通过专用命令逐次启用 PTC。
2. <a id="req-1-2"></a> 当系统向 Agent 提供执行指引时，Prompt 必须说明批量调用、可用确定规则衔接的多步骤操作及大量结果的过滤汇总适合 PTC；少量简单操作或需要模型逐步理解结果的任务可直接调用工具。
3. <a id="req-1-3"></a> 当 Agent 选择某种调用方式时，系统必须执行该显式决策，不得依据累计调用次数将直接调用自动改写为程序，也不得在程序失败后隐式改为直接工具执行。
4. <a id="req-1-4"></a> 当 Agent 通过专用 PTC Tool 提交 JavaScript 时，系统必须以该工具请求发起一次程序执行，并通过该 Tool 的结果返回程序结论或失败反馈；普通模型文本或代码块不得单独触发执行。

### 需求 2：独立且受限的 Node.js 执行

**用户故事：** 作为项目使用者，我希望模型生成的 JavaScript 在独立沙箱中运行，以便程序计算不会获得宿主的任意访问能力。

#### 验收标准

1. <a id="req-2-1"></a> 当新的 PTC 程序开始执行时，系统必须使用干净、独立的 Node.js 沙箱进程运行 JavaScript，不得继承其他程序的内存变量、未完成异步任务或私有结果。
2. <a id="req-2-2"></a> 当程序尝试访问宿主文件、网络、凭据、环境敏感值或启动进程时，系统必须阻止其绕过获授权业务工具直接访问；内部工具的实际访问仍受该工具既有能力边界约束。
3. <a id="req-2-3"></a> 当运行环境无法建立所需隔离时，系统必须拒绝启动程序并返回明确失败，不得降级为在宿主或仅有普通子进程隔离的环境执行。
4. <a id="req-2-4"></a> 当程序完成或执行终止时，系统必须释放其沙箱进程及执行资源，且保留恢复或审计所需的持久化记录；恢复时不得把旧进程仍存活作为必要条件。

### 需求 3：业务工具组合与中间数据处理

**用户故事：** 作为 Agent 使用者，我希望一个程序可以根据工具结果继续操作，以便循环、分支与聚合无需每步重新请求模型。

#### 验收标准

1. <a id="req-3-1"></a> 当程序请求调用业务工具时，系统必须支持当前 Goal 获授权的读取、检索、文件修改与 Bash 工具；PTC 不得扩大工具集合或替代任务完成、等待用户等业务决策的既有授权规则。
2. <a id="req-3-2"></a> 当内部工具正常返回成功或领域失败结果时，系统必须把可区分的结果交给运行中的程序，允许程序通过 JavaScript 的循环、分支和数据处理决定后续操作。
3. <a id="req-3-3"></a> 当程序执行多个无需模型介入的工具调用时，系统必须允许其在同一次程序执行中继续，不得为每个内部调用强制增加模型推理；需要用户介入时必须进入相应等待流程。

### 需求 4：显式返回与模型上下文隔离

**用户故事：** 作为处理大量数据的使用者，我希望模型只接收程序返回的结论，以便原始中间数据不会占据后续上下文。

#### 验收标准

1. <a id="req-4-1"></a> 当程序正常完成并显式 `return` 可序列化结果时，系统必须将该结果作为模型可见的业务输出，不得把程序的局部变量、完整内部工具结果或 stdout/stderr 附加到该输出。
2. <a id="req-4-2"></a> 当系统组装后续模型历史或上下文时，PTC 内部调用的持久化记录不得自动展开为逐条模型工具结果；模型可见历史必须保留程序级请求、返回结果及必要的状态反馈。
3. <a id="req-4-3"></a> 当程序没有有效显式返回、结果不可序列化或出现语法及执行错误时，系统必须返回可辨别的有界失败诊断，不得把日志或任意最后一个工具结果当作成功返回，也不得自动泄漏完整中间数据。
4. <a id="req-4-4"></a> 当核验批量读取、检索或汇总场景时，系统必须能够证明中间数据在程序内处理、模型接收显式返回结果，且不因后续历史组装再次加载全部中间结果；不要求所有任务均取得固定比例的耗时或 Token 节省。

### 需求 5：逐调用权限与可恢复审批

**用户故事：** 作为审批者，我希望程序中的每个操作遵守真实授权，以便批准一段程序不会无意放行它未来生成的所有操作。

#### 验收标准

1. <a id="req-5-1"></a> 当任一内部工具调用准备执行时，系统必须按当前 Goal 的 Profile、工具注册、输入契约、Permission 和 Sandbox 边界判断该调用；模型代码、工具返回内容或程序级批准均不得代替实际授权。
2. <a id="req-5-2"></a> 当内部调用需要用户审批且没有匹配有效授权时，系统必须在执行前保存等待状态并暂停程序推进，向用户展示实际 Tool 输入和申请的能力范围，并沿用现有审批期限与范围规则。
3. <a id="req-5-3"></a> 当用户对匹配的待审调用批准或拒绝时，批准必须使同一程序继续处理该调用；拒绝必须不执行该调用且不得产生授权，并将可辨别的拒绝结果提供给程序；错配或过期答复不得推进程序。
4. <a id="req-5-4"></a> 当授权在程序运行或等待期间被撤销或不再匹配时，尚未开始的后续调用必须重新判断权限；程序恢复、已有单次批准或项目模式不得自动扩大授权范围，也不得把撤销描述为撤回已发生的副作用。

### 需求 6：持久化续跑与副作用保护

**用户故事：** 作为长期 Goal 的使用者，我希望审批和进程中断后继续原程序，以便已完成操作无需重做且副作用不会因恢复重复发生。

#### 验收标准

1. <a id="req-6-1"></a> 当程序发起内部调用时，系统必须在实际执行前可靠保存调用意图，并在向程序交付结果前可靠提交结果；调用顺序、输入、结果、等待状态和程序结算必须关联到同一 Goal、Run 与程序执行，供恢复及审计使用。
2. <a id="req-6-2"></a> 当审批等待期间或工具调用之间发生进程退出后恢复时，系统必须继续同一程序的逻辑进度、复用已提交结果，不得要求模型重新生成程序或重新执行已确认完成的操作；恢复允许重建纯计算过程，不要求保留原 Node.js 内存。
3. <a id="req-6-3"></a> 当恢复发现调用已经开始但结果未可靠提交，且该调用可能产生副作用时，系统必须保存结果未知状态并等待用户处理，不得自动重复调用；原工具的重放声明、程序批准或项目模式均不得单独消除该等待。
4. <a id="req-6-4"></a> 当恢复数据缺失、损坏或与当前程序及 Goal/Run 身份不匹配时，系统必须明确报告恢复失败并阻止后续工具执行，不得猜测结果、丢弃未知调用后从头执行，或复用其他程序的结果；持久化提交失败时不得继续推进。
5. <a id="req-6-5"></a> 当用户处理未知结果后，系统必须依据明确处理结果继续或终止程序，并保留该决定及实际执行记录；无论审批、恢复或重复提交如何发生，已确认完成的操作和程序结算不得被重复计为新完成，且系统不得宣称外部副作用具有 exactly-once 保证。

### 需求 7：资源边界与取消

**用户故事：** 作为项目使用者，我希望程序的执行资源可控且能够停止，以便错误循环或海量结果不会无限占用宿主资源。

#### 验收标准

1. <a id="req-7-1"></a> 当程序执行时，系统必须对执行时间、内存、内部工具调用次数和模型可见输出大小施加有限上限；超过任一上限时必须停止程序推进，报告可辨别的超限原因，不得将截断的结果伪装为完整返回。
2. <a id="req-7-2"></a> 当用户取消程序或当前执行收到取消信号时，系统必须停止程序推进及新工具调用，向正在执行的工具传递取消，并释放程序资源；已开始且不能确认结果的副作用必须保留结果未知状态。
3. <a id="req-7-3"></a> 当程序失败、取消或超限时，系统必须保留已提交的调用结果及待处理副作用，不得宣称已回滚既有修改，也不得隐式重启程序继续执行。
