# Goal 阶段与决策索引及分层检索 Spec

## 目标与范围

在同一 Goal 内建立跨 Run 的工作历史入口，让 Agent 先了解做过什么、重要决策、用户强调信息及剩余问题，再沿稳定引用读取阶段详情和原始来源。目录减少查找成本，不承担执行调度、任务授权或完成证明。

本功能基于 [Run 内阶段审查与上下文投影](../run-stage-review-and-context-projection/spec.md) 的阶段身份、修订、结果和提交事实构建。前置功能与本功能已在联合编排下共同交付并完成双向验证。

范围包括阶段目录、带来源的重要决策与用户强调信息、跨 Run 的有效记录投影、普通模型请求的有界导航、目录查询与来源展开，以及索引存储、失效重建和 context benchmark 回归。复用现有 Goal Snapshot、Trajectory、Context Lookup 和 Retrieval Index Sidecar，不建立 Task 聚合、独立阶段调度或完整历史的第二份权威状态。

首期不迁入前置 Spec 的原生历史去重、阶段审查和 Web 折叠 UI；不新增目录编辑 UI、独立摘要模型、后台整理 Agent、Warm Sidecar、向量库、跨 Goal 检索或项目长期记忆自动写入；不修改工具权限、沙箱、模型默认配置、现有纠错和执行预算。Run 仍仅由既有用户入口开启，阶段切换不创建 Run。

## 需求与验收标准

### 需求 1：整个 Goal 的阶段导航

作为 Agent，我希望能定位当前及历史阶段，而不必重放全部执行过程。

- <a id="spec-req-1-1"></a>**验收标准 1.1**：当读取 Goal 目录时，系统应当汇总当前及已归档 Run 的已提交阶段，返回稳定阶段身份、来源 Run、目标、最新修订、实际状态、可用结果摘要和详情引用；重名阶段不得合并。
- <a id="spec-req-1-2"></a>**验收标准 1.2**：当阶段仍在执行、审查拒绝、Run 等待或终止时，目录应当区分阶段接受结果与实际执行状态；未通过阶段不得显示为完成，失败或取消 Run 中的已接受局部结果不得表示整体成功。
- <a id="spec-req-1-3"></a>**验收标准 1.3**：当阶段修订或前一 Run 归档时，目录应当保持原阶段身份和可定位历史，更新其有效投影；续接的新 Run 不得继承旧 Run 的活动阶段或调用权限。
- <a id="spec-req-1-4"></a>**验收标准 1.4**：若目录尚无已接受结果，系统应当明确表达该状态；系统不得生成虚构工作总结、从 Todo 完成状态推断阶段接受，或把缺少目录条目解释为历史工作不存在。

### 需求 2：重要信息及其来源

作为使用者，我希望关键决策和明确强调的信息在长任务中能够找回。

- <a id="spec-req-2-1"></a>**验收标准 2.1**：当模型提出重要信息记录时，系统应当校验类别、简短内容、来源和可选关联阶段，在接受相应决策的提交边界保存记录；类别限定为重要决策和用户强调信息，记录不作为 Fact、Tool Observation 或授权。
- <a id="spec-req-2-2"></a>**验收标准 2.2**：当记录用户强调信息时，系统应当要求真实已应用用户消息引用及可核对的原文片段；标签和简述应当标记为模型提取，不能声称是用户逐字表达或替代原消息。未提取的信息仍应当能通过原会话检索找回。
- <a id="spec-req-2-3"></a>**验收标准 2.3**：当记录重要决策时，系统应当保存决定内容、简短理由和其发生来源，区分用户明确决定与 Agent 采用的方案；不得保存内部思维过程，或把决策理由当作实际执行成功的证据。
- <a id="spec-req-2-4"></a>**验收标准 2.4**：当修正或替代重要信息记录时，系统应当要求当前记录修订和替代来源，原子提交变化并保留旧记录；Agent 不得以自己的新决定替代用户明确要求。重复提交和恢复不得生成重复记录，过期修订或非法来源仍走现有严格纠错。

### 需求 3：提交与存储

作为 Runtime，我希望导航能力复用现有持久化边界并能安全重建。

- <a id="spec-req-3-1"></a>**验收标准 3.1**：当保存阶段历史及重要信息时，系统应当把权威记录留在已提交 Trajectory，用户原文留在 Goal messages；Snapshot 仅保存既有阶段恢复状态和必要提交指针，不复制整个 Goal 的目录及阶段正文。
- <a id="spec-req-3-2"></a>**验收标准 3.2**：当生成 Goal 级索引时，系统应当按当前 Snapshot 确定的每个 Run 提交边界和消息来源构建；索引应当记录来源摘要及构建版本，任何未提交 tail 或其他 Goal 的记录不得进入结果。
- <a id="spec-req-3-3"></a>**验收标准 3.3**：若派生索引不存在、损坏、落后或来源身份失配，系统应当从合法权威来源重建；缓存保存失败不改变已提交结果，也不允许使用已判失效的缓存回答。权威来源读取或校验失败应当明确报错，不返回不完整目录冒充完整结果。
- <a id="spec-req-3-4"></a>**验收标准 3.4**：当进程在记录提交或索引替换期间退出时，恢复应当只呈现 Snapshot 纳入的记录，重建后结果与正常读取一致；删除派生索引应当不丢失阶段、决策或用户来源。索引写入不推进 Run、Step、Memory revision 或执行提交边界。

### 需求 4：目录、详情与原文的检索

作为 Agent，我希望先找到相关工作，再读取足以继续执行或核验的内容。

- <a id="spec-req-4-1"></a>**验收标准 4.1**：当查询 Goal 工作历史时，系统应当支持有界目录浏览和按阶段目标、结果、决策、用户强调内容检索；结果保留 Run/阶段身份、命中类别、原始来源和可继续展开的引用，并明确是否还有未返回条目。
- <a id="spec-req-4-2"></a>**验收标准 4.2**：当请求展开有效目录引用时，系统应当直接定位相应阶段详情、信息记录或原始消息/轨迹，无须模型猜测事件序号；请求受当前 Goal、各 Run 提交边界和原权限限制，非法或失效引用应当明确失败。
- <a id="spec-req-4-3"></a>**验收标准 4.3**：若目录或阶段详情不足以支持当前问题，系统应当允许继续检索原会话与执行历史；目录未命中不能阻断该路径。展开的大结果应当遵循有界输出、截断标记及继续读取规则，不静默丢失剩余正文。
- <a id="spec-req-4-4"></a>**验收标准 4.4**：当返回历史信息时，系统应当统一标记其为 Goal 历史，并保留实际结果与时效范围；索引、阶段接受、决策记录和 lookup 结果均不能直接作为当前 Run 的完成证据。需要当前环境事实时，仍使用授权业务工具。

### 需求 5：每轮模型请求的导航

作为 Agent，我希望恢复和阶段切换后能及时看到正确入口，并控制输入增长。

- <a id="spec-req-5-1"></a>**验收标准 5.1**：当开始新 Run、恢复执行或切换阶段后组装下一模型请求时，系统应当提供最新的有界 Goal 导航，包括当前阶段、可用上一阶段结果入口、相关重要信息及未解决问题入口；没有历史阶段时不制造历史占位事实。
- <a id="spec-req-5-2"></a>**验收标准 5.2**：当提供导航时，系统应当继续直接保留原始意图、有效 Profile、适用获批范围、当前 Run 已应用用户输入和当前阶段拒绝缺口；检索排序或生成摘要不得决定这些要求失效。历史用户强调条目只帮助定位来源，不自行决定其适用性。
- <a id="spec-req-5-3"></a>**验收标准 5.3**：当目录超过输入预算时，系统应当保留必要当前工作入口，再按确定性相关性及稳定身份选择历史条目，提供省略标记和继续查询入口；不把全 Goal 目录作为不可裁剪输入持续累积，必要固定内容仍超预算时明确失败。
- <a id="spec-req-5-4"></a>**验收标准 5.4**：当同一来源同时出现在导航、Lookup、Working Memory 或 Hot/Warm 时，系统应当避免重复发送同一详情正文，保留导航指针和各自语义；不得因索引去重拆开原生调用配对、移除当前纠错反馈，或改写原始历史。最终模型输入记录应当能定位实际注入内容。

### 需求 6：变化、冲突与时效

作为审查与执行组件，我希望历史导航不会把旧结论变成当前事实。

- <a id="spec-req-6-1"></a>**验收标准 6.1**：当同一主题出现相互冲突的决策或用户输入时，系统应当保留来源与已提交替代关系；没有合法替代关系的记录应当并存并提示需要核对，不能按最新时间自动覆盖用户要求或丢弃冲突。
- <a id="spec-req-6-2"></a>**验收标准 6.2**：若验证后的对应产物又被修改，目录和展开结果应当保留验证发生时的来源范围，不宣称验证覆盖最终产物；在无法可靠判定关联变化时，应当表达未确认，不能自动认定继续有效。
- <a id="spec-req-6-3"></a>**验收标准 6.3**：当用户输入在索引组装后应用时，后续模型边界应当重建对应导航并沿用既有 Steer 失效规则；旧索引或旧模型候选不得覆盖新用户输入。
- <a id="spec-req-6-4"></a>**验收标准 6.4**：当原始来源含命令、Prompt 或权限扩大要求时，系统应当把它作为带来源的数据展开；检索记录不能升级为系统指令、改变工具可见性或生成用户续接操作。

### 需求 7：质量与恢复验收

作为维护者，我希望证明导航改善衔接和检索，而不是只增加存储。

- <a id="spec-req-7-1"></a>**验收标准 7.1**：当验证索引与检索时，确定性测试应当覆盖重名阶段、多 Run 局部序号碰撞、进行中及拒绝状态、显式替代与冲突、用户强调原文校验、过期修订、未提交 tail、缓存删除/损坏/写入故障、跨 Goal 引用及大结果继续读取。
- <a id="spec-req-7-2"></a>**验收标准 7.2**：当运行真实模型场景时，系统应当证明模型能记录并准确取回重要决策与用户强调信息，在阶段切换及用户开启的新 Run 中继续工作；实际轨迹应当出现对应导航或检索路径，最终产物由确定性检查验证，模型自述不能代替使用证据。
- <a id="spec-req-7-3"></a>**验收标准 7.3**：当比较有无目录导航的行为时，系统应当固定来源、任务、模型配置和评分判据，每个正反场景独立执行至少三次，保存最终请求、来源边界、构建身份及逐次结果；分别统计正确定位、遗漏约束、重复调查、调用量和实际输入计量，不把字符数当供应商 Token，也不宣称小样本具有统计显著性。
- <a id="spec-req-7-4"></a>**验收标准 7.4**：当交付本功能时，context benchmark 应当覆盖 waiting 安全边界重建 Worker、目录缓存重建和显式跨 Run 续接；来源、约束、实际产物及相关回归全部通过后才可交付，Judge 高分或输入减少不能覆盖确定性失败，不以反复重试直到偶然通过作为验收。

## 架构与核心决策

### 职责和依赖

```text
Goal Snapshot：用户消息、当前阶段、各 Run 提交边界
        +
Trajectory：阶段事实、已提交结果、重要信息记录及修订
        ↓ 只读派生
Goal 目录索引 → 按目标/主题定位 → 阶段详情 → 原始消息/轨迹
        ↓
Agent 有界导航 Section + Context Lookup → 模型请求
```

| 所有者 | 职责 |
| --- | --- |
| Runtime | 校验并提交重要信息提议、分配身份、协调来源及修订；从 Goal 确定各 Run 的可见边界 |
| model-contracts | 重要信息提议、查询及展开的严格模型契约，原生与 prompt_only 行为等价 |
| context-retrieval | 阶段/信息文档构建、确定性排序、有界浏览与引用解析；不读取文件或推进 Goal |
| Storage | 重要信息事件 Codec，以及 Goal 级派生索引的验证、原子替换和删除 |
| Agent | 只读导航投影、必要内容优先的预算与重复正文消除；不拥有持久化状态 |
| 宿主与 context benchmark | 复用 Composition Root 接线，保存实际输入、恢复与行为验证证据 |

前置 Spec 拥有阶段执行与审查状态，本功能只消费其已提交结果。GoalPlan 继续拥有用户 Todo，Working Memory 继续拥有 Facts/Hypotheses/Blockers，三者均不从目录反向更新。

### 记录与更新

阶段目录的最小条目为 `(goalId, runId, stageId)`、当前修订、目标、实际状态、结果摘要及来源引用。摘要复用已接受阶段候选，不额外调用摘要模型。未接受阶段展示目标和已发生状态，不能生成接受结果。

重要信息记录包括 Runtime 身份及 revision、类别、简短内容、来源、可选关联阶段、可选简短决策理由和替代关系。用户强调来源包含消息位置、内容摘要校验值及精确原文片段；决策来源区分用户决定和 Agent 方案，引用原始消息、已提交阶段事实或相关执行事实。来源身份必须携带 Run，禁止将不同 Run 的相同 sequence 合并。Think 和公开 reasoning 不能直接成为重要决策记录的正文。

主模型在既有决策中附加有界重要信息提议，不引入专用记录模型或独立调度操作。Runtime 在业务执行前校验提议；合法记录在对应接受结果的既有提交边界落盘，最终候选的记录须等审查接受后提交。结构合法只说明记录来源和形状成立，不证明其归纳准确或业务结果成功。提取质量由正反行为案例验证。

修正以新 revision 追加，不改写旧事件。阶段修订、用户明确替代和 Agent 改变自身方案各有原始来源；模型不能通过改标签使用户要求失效。检索同时保留有效项及可访问旧版本。条目复用稳定身份、预期 revision 和原执行来源，接受后的重放不再次创建同一记录。

### 存储与恢复

默认使用 [Workspace Home](../../packages/config/src/home.ts) 的 `goals/`、`trajectories/` 和 `context-sidecars/`。阶段及重要信息正文仅保存于权威 Trajectory，Goal Snapshot 保存真实用户消息和前置功能已有恢复指针；不增加整个 Goal 的完整阶段历史数组。

派生 Goal 索引放在同一 `context-sidecars/<encoded-goal-id>/` 下，与既有 Run 检索索引区分。索引包含每个来源 Run 的提交边界、消息来源摘要、文档来源摘要和构建标识，不以不同 Run 的最大 sequence 充当统一边界。Runtime 提供来源信封，Storage 不自行推导执行状态。复用现有索引设施扩展 Goal 级视图，不另建 Warm 缓存、后台进程或新的持久化平台。

权威记录提交先于缓存更新。索引可删除，失配即重建；重建过程中按同一来源边界完成整次查询，避免混用旧目录与新详情。缓存更新失败可以使用本次合法重建结果并记录诊断，权威记录失败则沿现有失败路径停止。索引仅适配当前开发期契约，不为旧试验 Goal 增加迁移、虚构阶段或协议版本分支。

### 查询与模型输入

复用 `system_context_lookup` 所在的历史查询协议，增加目录浏览/检索与引用展开的明确操作，保留原有三类历史需要及查询入口；具体字段和系统函数投影由 Plan 对齐当前契约。目录结果返回有界条目及继续查询游标，详情引用支持直接读取而非再次关键词排名。游标绑定来源摘要，来源改变时要求重新查询，不沿过期游标混合历史。

分层读取是能力，不强制每次历史查询先查目录。已知原始来源可直接展开；目录未命中仍能查询原会话和执行历史。详情保留截断、失败和被替代状态，工具输出不能由索引简述替换。跨 Run 信息可指导后续工作，但完成 Evidence 继续服从当前 Run 门禁。

Agent 使用现有动态 Section 机制提供有界 Goal 导航。每轮根据已提交来源重建或验证索引；新 Run、恢复、阶段转换和用户输入变化自然触发最新投影。选择优先级为必要当前阶段及缺口入口、上一结果入口、明确依赖，再按当前用户请求和阶段目标的确定性排序选择历史项；同分按稳定来源身份排序。未选项仍可查询，不因索引排名改变用户要求。

导航使用摘要和引用，原文只在实际需要时展开。固定必需输入按前置 Spec 保留；所有选择、工具声明和输出契约计入现有输入预算。普通输入消除相同来源的重复正文，但不把目录当作原生工具结果替代物；`runtime_feedback` 仍在请求末尾。历史信息是否仍适用需要依据原用户输入和当前产物核对，索引不维护第二套事实有效性裁决器。

### 验收与设计参考

验证先覆盖确定性记录、检索和存储边界，再通过既有 context benchmark 验证真实模型使用、等待恢复和显式跨 Run 衔接。固定正反任务包含找回旧决策、遵守跨阶段用户强调、区分被替代方案、旧测试后修改产物、目录未命中但原文存在。对照只切换本功能导航与查询能力，保持前置阶段实现、历史材料和现有预算一致。模型配置、Docker 构建及判据由 Plan 显式列明；不改全局 default。

## 曾考虑的备选方案

- **只依赖现有 BM25 历史查询**：不新增目录，实现最小。落选原因：原始事件没有稳定阶段导航，也没有明确组织关键决策和用户强调信息，模型仍需猜测关键词及历史位置。原查询作为补充保留。
- **把全部历史与重要信息写进 Goal Snapshot**：读取简单。落选原因：复制 Trajectory 正文，增加双份历史一致性和 Snapshot 增长；采用权威事件加可重建索引。
- **只在阶段接受时记录信息**：提交规则简单。落选原因：等待、失败或取消前的重要决定也需要找回；采用随合法决策提交的记录，并明确阶段尚未通过。
- **扩展 Working Memory 为统一阶段记忆**：可复用 Patch。落选原因：导航记录与已证据支持的 Fact、当前 Blocker 职责不同，跨 Run 目录不应成为新 Fact 通道或另一条 Memory revision 链。
- **自由编辑单个进度 Markdown**：接近成熟 harness 的简单做法。落选原因：难以保持 Run/阶段身份、来源、修订和提交一致性；采用 Runtime 校验的记录与结构化派生目录。
- **每轮重写全 Goal 摘要或后台 LLM 整理**：可生成更自然的总结。落选原因：新增成本、延迟和摘要漂移，且本功能已有阶段结果可复用；首期使用主模型有界提议及确定性索引。
- **全目录永久常驻 Prompt，或强制目录优先检索**：入口容易发现。落选原因：前者随历史增长占用输入，后者增加已知来源读取的调用成本；采用有界相关导航和可直接展开的来源。
- **只缓存模型生成记录**：写入少。落选原因：缓存删除后无法恢复重要信息；模型记录先提交到 Trajectory，缓存只持有派生内容。

## 风险与否定性保证

- **风险级别：medium**。变更涉及模型契约、Runtime 提交、Storage、检索与模型输入，影响长任务衔接及恢复；不增加权限或外部发布。必须验证跨模块提交故障、来源门禁和真实模型使用。
- **前置依赖**：Run 阶段契约未交付前，不能用虚构阶段或旧数据兼容层声称本功能可用；实施计划应当明确依赖顺序。本 Spec 不取消或修改前置审批。
- **提取误差**：模型可能遗漏重要信息或归纳错误。保留原文及提取标记，以固定正反例验证；本功能不保证自动识别所有自然语言强调或任意矛盾。
- **增长与成本**：权威历史可以增长，模型输入与单次查询始终有界。初次重建仍可能扫描较多历史；记录冷构建与缓存读取开销，不以新增后台生命周期掩盖性能问题。
- **历史时效**：成功测试只支持当时产物；可靠变化关联不足时保留未确认状态。历史决策不能扩大当前权限，旧 Run Evidence 不自动提升为当前证明。
- **否定性保证**：不自动新建 Run、不创建 Task 聚合、不自动改 Todo、不保存内部思维过程、不用索引替代用户原文、不静默覆盖冲突、不接受未提交 tail、不以目录命中证明任务完成、不以目录未命中证明历史不存在、不自动写入项目长期记忆。
