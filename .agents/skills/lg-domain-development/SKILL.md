# LazyGoal 领域开发

让术语、规则和状态变更各有明确所有者，并用可观察行为检验结果。本 Skill 适用于领域行为的需求分析、设计、实现与审查；不替代 `using-lazyspec` 的阶段与审批流程。

## 确认术语和边界

1. 读取适用的 `AGENTS.md`，从项目根 `README.md` 进入相关模块的 `README.md`、`notes/overview.md` 和 `notes/semantics.md`，再核对目标源码、测试和实际调用方。Spec 描述获批需求或设计，不自动代表当前实现。
2. 对本次涉及的概念确认它在所属上下文中的名称与含义，以及状态、业务规则和持久化分别由谁拥有。只记录本次变更需要澄清的术语；不要在本 Skill 中维护全局词汇表或模块清单。
3. 当同一词在不同上下文含义不同，或同一概念需要不同名称时，在跨边界契约与适配处写清映射。包依赖检查只能证明导入方向，仍需核对规则和状态的实际归属。

## 封装领域行为

- 先写清行为的前置条件、合法状态转换、不变量、拒绝结果与可观察后果，再决定修改位置。
- 将校验、计算和状态转换放在状态所有者提供的行为函数或 reducer 中。外层负责授权、输入转换、调用编排和持久化，不在多个调用方复制领域判断，也不绕过行为入口直接拼接新状态。
- 用现有代码风格表达封装；不可变数据配合纯函数或 reducer 可以承载完整领域行为，不要求引入实体类、getter/setter 或新的抽象层。
- 区分领域不变量与输入信任边界：按 `AGENTS.md` 在模型、工具、持久化、进程和 wire 等边界校验；不要仅为同进程已类型化的值重复加防御校验。
- 若规则跨多个所有者，明确由哪个边界协调、每一方负责什么，以及失败时哪些状态已经提交；不要让表示层或存储层自行裁决领域规则。

## 用行为验证

1. 在实现前列出足以判定行为的正常、拒绝和边界场景；涉及状态流转时覆盖旧状态不被错误改写。按改动风险选择有意义的测试，不按函数数量机械补测试。
2. 优先在规则所有者附近验证领域行为。若改动穿过持久化、恢复或模块边界，再覆盖对应的真实调用路径与失败结果。
3. 从当前项目脚本和相关 Spec 发现适用检查；领域代码变更同时核对依赖方向。架构或公开契约变化时，按 `AGENTS.md` 同步相应文档和 TSDoc。

## 与其他流程协作

- 需求、设计、任务和实施审批继续交给 `using-lazyspec`；本 Skill 只补充领域建模与实现判断，不自动创建或修改 Spec。
- 文档位置与验证遵循 [lg-doc-standards](../lg-doc-standards/SKILL.md)，文本契约与措辞遵循 [lg-prose-standard](../lg-prose-standard/SKILL.md)。不要在此复制它们的规则。
- 审查或讨论请求只报告有证据的术语歧义、规则泄漏、绕过封装和验证缺口；用户要求实施时才在授权范围内修改文件。
