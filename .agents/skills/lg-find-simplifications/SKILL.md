# LazyGoal 简化审计

把“看起来复杂”转化为有调用证据、边界分析和验收条件的简化候选。保持判断力：优先提出少量能够真正删除或合并生产代码的候选，不要为了凑数量而罗列风格偏好。

## 先建立仓库上下文

按以下顺序读取和核对信息：

1. 读取 `AGENTS.md`，遵守其用户授权、提交、TSDoc、架构文档和 `//TODO` 约束。
2. 按“从项目文档加载架构边界”一节定位当前设计意图，再以源码和实际调用关系核验已实现事实。
3. 只按该节的路由读取相关 project-memory，了解为什么当前边界存在以及哪些历史替代方案已经被否决；本 Skill 不读取其他设计材料。
4. 先检查 `git status`、当前分支和用户已有 diff。保留未提交修改，不把 `.lazygoal/` 中的运行时快照当作源码，也不要在审计过程中修改或删除它们。

## 从项目文档加载架构边界

不要在本 Skill 中维护模块职责、状态流转或生命周期不变量的副本。先从项目文档定位候选所属边界，再用源码和实际调用关系验证当前实现：

- 先读 `docs/architecture/README.md`，确认跨模块关系、主流程、跨模块不变量和模块文档入口。
- 涉及 Goal/Run、状态转换、Preparation、调度、Tool 授权、持久化、恢复、中止或关闭时，读 `docs/architecture/runtime.md`。
- 涉及 Working Context、Prompt、响应协议或 Executor 职责时，读 `docs/architecture/agent.md`。
- 涉及供应商无关接口、Adapter、消息映射或供应商错误时，读 `docs/architecture/llm.md`。
- 涉及 CLI、Composition Root、`SessionController`、React Ink、Ctrl+C 或进程退出时，读 `docs/architecture/tui.md`。
- 需要理解架构决定的历史理由时，先读 `project-memory/index.md`，再只读取与候选直接相关且状态有效的 `project-memory/features/*.md`。

架构文档表达当前设计意图，源码和生产调用关系表达已实现事实。两者冲突时，记录为文档漂移并降低候选置信度；不要自行选择其中一方来证明简化安全。不得把功能 Spec 当作当前架构事实来源，也不要把文档中的“当前限制”误判为已经实现的能力。

## 什么算强简化候选

只有在候选能移除、合并或降级真实的维护面，并且有证据证明当前成本大于收益时，才将其列为强候选：

- 公共方法、事件、配置项、注册表通知、导出类型或 helper 没有生产消费者。
- 只有测试、文档或旧示例引用，且该行为不是已批准需求、持久化格式、CLI 契约或安全边界的一部分。
- 多份状态表达同一个事实，例如重复的 transient 标记、重复的错误包装或跨层复制的生命周期信号；合并后仍能保留持久化恢复所需的信息。
- 多个 readiness Promise、布尔标记、disposer 或回调共同表达同一异步生命周期事实；可以由一个明确的 owner 或事务取代。
- 独立包、适配层或支持脚本只服务于测试/demo，增加依赖、发布或类型维护成本，却没有产品消费者。
- 为未来需求预留的泛化能力（多 Session、并发恢复、历史快照、队列/租约、流式 LLM、统一重试、复杂 UI 扩展点等）没有当前产品 owner、project-memory 记录或生产调用。
- 手写协议解析、路径处理、匹配、重试或其他基础设施与 Node 内置能力或健康的依赖完全重叠，并且替换后能删除实现、专用测试和文档，而不是只把复杂度搬到 wrapper。

“代码比较长”“有两个类似文件”“测试数量很多”“将来可能用到”本身不是证据。供应商 Adapter、Tool 授权、持久化迁移和关闭闸门等已记录的 seam 默认视为有意设计，除非新的调用和产品证据足以推翻其理由。

## 进行广度足够的调查

不要只看第一个明显的未使用符号。优先查看生产代码变更最大的区域，再覆盖所有边界：

- Runtime：Goal/Run 转换、Coordinator/Runner、Store/Catalog、Scheduler、Checkpoint Gate、Shutdown 和中止传播。
- Agent/LLM/Tools：Prompt/响应协议、Adapter、Tool Definition/Registry/Policy、输入校验和执行错误。
- TUI/CLI：参数路由、Composition Root、Controller 命令、ViewModel、屏幕状态、Ctrl+C 和退出清理。
- 测试、脚本、project-memory 和架构文档：判断它们是生产入口、历史依据，还是已经过时的叙述；不要为了补充背景而打开其他设计材料。

使用 `rg` 做精确检索，并阅读上下文而不是只看命中数量。至少检查：

1. 符号、方法、事件名、配置键、包名和持久化字段的定义与所有导入。
2. 同名方法的 `.name(` 和 `name(` 两种调用形式，以及动态字符串、反射或注册表访问。
3. CLI/bin、跨进程测试和 loader/config 路径等静态检索容易漏掉的入口。
4. `git log`、`git blame` 和 project-memory，了解是否存在明确的兼容或安全理由。

将引用分为三类：

- **生产消费者**：`packages/*/src`、`bin/`、运行时脚本、CLI/loader/config 路径以及真实 workspace 入口。
- **非生产消费者**：单元测试、文档、project-memory、快照期望值和注释。
- **歧义消费者**：示例、smoke test、辅助脚本；必须读完调用路径后再归类。

如果用户要求全面扫描，可以按边界分工并最后统一证据标准；不能因并行调查而重复建议或跳过跨层调用检查。

## 审计信任边界和异步生命周期

对每一个拷贝、冻结、校验器和 callback capture，说明值从哪里来、下一步由谁拥有：

- 同进程、类型安全的服务调用通常借用 readonly 数据；解析器、LLM/Tool JSON、队列、持久化文件、子进程和 wire boundary 必须负责校验或复制。
- 不要因为测试能构造恶意 getter、修改已传对象或替换 callback，就自动保留同进程接口的防御代码；先确认该攻击面是否属于真实边界。
- 对复杂异步逻辑画出 owner/transition 关系，逐一对应 sentinel、readiness Promise、取消路径、disposer 和状态标记。
- 当多个机制镜像同一个 liveness 或 settlement 事实时，优先提议单一生命周期控制器；但保留同步发布回滚、callback 隔离、首个终态仲裁、进程所有权、Gate 冻结和 dispose-to-quiescence 等有独立语义的机制。

## 评估“改用依赖”

把引入依赖视为一种合法的简化方式，但必须证明净收益：

1. 阅读手写实现，列出候选依赖真正覆盖的精确行为和未覆盖的剩余语义。
2. 检查 Node.js 20+ 运行基线下是否已有内置能力；优先使用内置能力。
3. 核对依赖维护状态、采用情况、transitive footprint、许可证和包边界。
4. 计算净删除量：实现 + 专用测试 + 文档，减去适配胶水、配置和新增维护成本。
5. 保留 LazyGoal 的错误语义、路径安全、取消传播和持久化契约；一个只迁移复杂度的 wrapper 不算简化。

## 证明或否决每个候选

在写建议前，为每个符号或行为完成以下分类：

- 找到所有生产调用方，确认删除后没有动态或跨进程入口。
- 检查是否由当前架构文档、project-memory、持久化 schema、CLI 行为或安全策略明确要求。
- 判断候选是否真的减少公共 API、状态、包、生命周期分支、测试或文档，而不是只移动文件。
- 说明将放弃的能力、未来重新引入的条件、迁移/兼容成本和可验证的终态。

拒绝或降级候选的情况包括：

- 存在生产调用方，且删除会改变产品行为，而不是局部清理。
- 候选由 project-memory、持久化迁移或安全边界明确支撑，新增证据不足以推翻它。
- 只能减少一处 typo、一次 `knip` 命中、一个局部变量或纯格式样式；这类问题可在确有价值时记录为小范围 TODO。
- 删除会引起无关的大范围 churn，却没有减少可理解的公共面或维护责任。
- 想法本身合理，但需要产品选择（例如取消多模型、多 Tool、历史快照或恢复能力）；先报告 trade-off，不要擅自实现。

## 输出简化建议

默认只输出审计结果，不改代码、不改项目文档、不删除分支或快照。每个有价值候选使用以下结构：

```markdown
### 候选：<动作导向标题>

- 现状：<当前实现和边界>
- 生产消费者：<调用方或明确无调用方>
- 证据：<相对路径、符号、必要的调用关系和 project-memory/历史依据>
- 建议：<删除、合并、降级、迁移或改用内置/依赖>
- 净收益：<具体减少的代码、状态、接口、包、测试或文档>
- 放弃与风险：<能力损失、兼容性、未来需求和安全影响>
- 验收条件：<可观察的最终状态和必须通过的检查>
- 置信度：<高/中/低，以及仍缺少的证据>
```

先按“收益 × 证据强度”排序，再说明明确保留的相似设计以及原因。不要把调查报告伪装成已获批准的实现计划。

## 记录和实施边界

- 只有用户明确要求实施或批准后，才修改生产代码；实施时使用 `apply_patch`，保留用户已有 diff。
- 简化改变模块责任、状态所有权、跨模块数据流、生命周期、不变量或当前限制时，同步更新对应 `docs/architecture/*.md`，并在源码新增/扩展的公共 TypeScript 接口中补齐中文契约级 TSDoc 和最小示例。
- 不读取、新建或修改功能设计材料；需要持久化简化决策时，先由用户指定记录位置和格式。
- 仅适合局部、低风险清理时，使用短小且可执行的 `TODO(simplify-...)`、`FIXME(simplify-...)` 或 `XXX(simplify-...)`，写明为何安全以及要删除/合并什么。
- 保留任何 `//TODO N` 任务标记，不替换、删除或改写；本 Skill 默认不主动打开任务文件。
- 不要创建或照搬 DeepSeek Harness 的 `.agents/notes`、Agent Note 树、供应商专用路径或不存在的项目文档；LazyGoal 的简化提议先留在审计报告，持久化记录由用户指定位置。

## 验证和收尾

按改动风险选择最小但足够的验证：

- Skill 或文档变更：运行 `git diff --check`，并检查 Markdown、frontmatter、相对链接和示例路径。
- TypeScript 代码变更：运行 `npx tsc --noEmit`，再运行受影响包的 `npx tsx --test packages/<pkg>/test/*.test.ts`；必要时执行跨包回归测试。
- Runtime/Agent/TUI 生命周期变更：覆盖快照保存顺序、恢复、Action 状态、abort、Ctrl+C、资源清理和退出码 130，不只验证成功路径。
- LLM 适配器变更：优先使用 fake adapter 或本地 fake server；不要把 `npm run llm:agent-smoke` 当自动化测试，它会产生真实请求和费用。
- 依赖替代：记录包版本、许可证、依赖树影响、删除量和行为等价性；没有这些证据就否决候选。

结束时报告调查范围、提出/保留/否决的候选数量、关键证据、运行的检查和仍未解决的风险。若没有达到证据门槛，明确写“未形成可执行简化候选”，不要用猜测填充结果。
