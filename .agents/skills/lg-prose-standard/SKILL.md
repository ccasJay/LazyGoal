# LazyGoal 文本规范

写到足以保存完整契约，再删除推理过程、重复和装饰。契约是调用方、实现者、生产者或消费者依赖的义务、不变量、前置条件、后置条件或兼容承诺。

本 Skill 负责文本覆盖范围和编辑判断；文档的放置、层级、导航及链接治理使用 [lg-doc-standards](../lg-doc-standards/SKILL.md)。把本 Skill 当作判断指南，不要当作机械删字脚本或固定检查清单。

## 输入与权限边界

要求用户提供显式 `scope`，例如文件、目录或明确的变更集合。缺少 scope 时，说明需要的输入并停止；不要推断全仓库审计范围，也不要开始逐步访谈来替用户构造范围。

接受 `mode: automatic | interactive`，默认使用 `automatic`。只有用户明确要求提问、校准或比较版本时才进入 `interactive`。

mode 只控制边界案例的沟通方式，不扩大写权限：

- 审查、审计或建议任务只报告发现，不修改文件。
- 明确要求编写、修复、恢复或精简时，才在 scope 内实施清晰改动。
- 涉及产品行为、公开契约或范围外所有者时，先报告影响，不借文本任务擅自改变实现。

开始前读取仓库根及目标路径适用的 `AGENTS.md`、`.gitignore` 和用户已有 diff。候选发现应遵守当前忽略规则，不进入依赖、构建产物、运行时数据或其他被忽略路径；用户显式指定的新文件仍属于 scope。不要沿符号链接越出 scope 或仓库边界。

将生成文件、快照和 fixture 视为派生表面。先定位并修改权威所有者，再按仓库当前机制更新派生产物；无法确认所有者时报告缺口，不直接猜测。

## 保留完整命题

编辑前识别段落中的每个命题，并保留仍与 scope 相关的：

- 主体和动作；
- 条件、时机和顺序；
- 必须、可以、禁止等强制程度；
- 否定保证、例外和兼容边界；
- 所有权、副作用、失败方式和后果。

只有在所有事实从句都保留且表达更清楚时，才删除修饰、重复或叙述。字数减少本身不算改进。

在使用点保留调用者或维护者必须就地知道的行为、失败、所有权和后果。架构、历史、算法、扩展示例和长期理由应链接到其权威所有者，避免维护多份解释；必要的局部契约事实可以重复。

当删除理由可能导致误用或错误简化时，保留非显然理由。否则说明可观察后果，并把扩展理由链接到其所有者。

## 按文本表面判断覆盖

不要把精简当作单向删除。代码、类型和结构无法表达必要契约时，应补充或恢复文本；事实已在局部显而易见时，不要新增注释。

- **公共 TSDoc：** 先读取适用 `AGENTS.md` 的当前契约要求，再覆盖调用方可见但类型无法完整表达的返回差异、错误、副作用、所有权、时机、取消和持久性语义。
- **内部注释：** 只解释非局部结构、关键不变量、竞态顺序、所有权、安全边界和意外失败行为；删除控制流旁白和代码复述。
- **测试说明：** 只解释非显然的 fixture、断言、平台兼容、真实入口或间接观测为何必要；删除测试步骤复述和覆盖清单。
- **Markdown：** 保留目标读者完成查询或操作所需的契约、前置条件、限制和可观察结果；位置和层级交给 `lg-doc-standards` 判断。
- **Skill 与 Agent 指令：** 写明行为护栏、输入、权限和明确限制，保持工作流简洁，并通过路径读取会变化的规则。
- **示例与配置说明：** 解释访问限制、非显然接线或加载顺序、安全立场、恢复行为、例外和常见误用；不要逐项朗读配置。
- **Prompt 与可见字符串：** 把措辞视为行为。阅读生成路径和消费方，保留模型或用户依赖的格式、强制程度和可观察含义。
- **诊断：** 指出失败主体或路径、被违反的规则，以及不明显时的纠正方式；删除内部执行过程叙述。

术语不是禁词。使用“契约”“边界”“状态”“协议”等抽象词之前，先确认更精确的规则、接口、字段、时机或失败状态是否更清楚；当术语确实指向精确技术对象时保留。

## 工作流

1. 确认显式 scope、mode、写权限、工作树状态和适用的 `AGENTS.md`；不检查无关分支或 scope 外文件。
2. 阅读文本的权威所有者、相邻实现、测试和真实消费入口，再判断文本是否完整或冗余。
3. 覆盖整个 scope，不只查看最大文件。搜索和统计只用于发现候选，每个候选都必须进行语义判断。
4. 将候选分类为保留、补充、精简、恢复、重构或暂缓。获得写权限后只实施清晰改动，不为满足删除数量而制造修改。
5. 先更新权威所有者，再处理派生表面；从一个案例学到新规则后，复查 scope 内的同类文本。
6. 从当前 manifest、配置、脚本和 CI 定义发现与改动相关的验证。Prompt、诊断或 CLI/TUI 文案变化必须运行实际存在的行为测试，或说明为什么没有适用测试。
7. 运行 `git diff --check` 并检查最终 diff，确认没有修改 scope 外内容、被忽略路径或用户无关改动。
8. 报告检查范围、清晰改动、刻意保留、暂缓案例、实际运行的检查和剩余风险。

## 边界案例

只有当至少两个版本都保留完整命题、但在已接受原则之间存在真实取舍，而且本 Skill 没有给出明确答案时，才算边界案例。存在唯一命题完整改法的普通重写不属于边界案例。

在 `automatic` 模式中，获得写权限后实施清晰改动；对真正的边界案例给出推荐与取舍，但不提问、不削弱命题以推进任务。

在 `interactive` 模式中，把同类案例按支配原则分组，提供两到三个完整可行版本，推荐其中一个，并说明事实或结构差异。不要提供明显较差的干扰选项。用户决定后，把选定原则应用到 scope 内所有同类文本；除非用户明确指定持久化位置，不要创建示例库或把评审过程写入仓库。

## 避免参考仓库泄漏

- 不复制参考仓库的专属目录、文档类型、双语流程、预算工具、生成器或检查命令。
- 不假设固定 package manager、测试脚本或 CI gate；每次从当前仓库入口发现。
- 不在本 Skill 中维护模块职责、架构事实或 TSDoc 细则的副本；按目标路径读取权威来源。
- 不主动修改 durable memory、功能 Spec 或其他历史材料；只有用户明确授权相应专用流程后才写入。
