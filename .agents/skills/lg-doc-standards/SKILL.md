# LazyGoal 文档工作流

把本 Skill 当作文档工作的路由器，而不是规则副本。每次任务都从仓库中的权威入口加载当前规则和事实；不要把模块清单、架构状态、验证命令或篇幅限制固化在本文件中。

## 加载当前权威来源

按任务范围逐步读取，不要一次性加载整个文档树：

1. 从仓库根目录开始，读取根 `AGENTS.md`，并检查目标文件路径上是否存在更近的 `AGENTS.md`。以后者补充或收紧适用于目标文件的规则。
2. 涉及当前架构时，从 `docs/architecture/README.md` 进入，只沿其中的导航读取与任务相关的架构文档。不要在本 Skill 中维护模块文件、职责或生命周期清单。
3. 需要了解已完成特性的背景或既有决定时，先读 `project-memory/README.md` 获取当前本地契约，再从生成的 `project-memory/index.md` 选择相关且状态有效的记录。不要扫描全部 memory 来寻找可能相关的材料。
4. 涉及需求、设计、实施任务或功能演进时，定位相关 `specs/<feature>/`，按该目录和适用 Skill 的流程读取。不要把 Spec 中的未来设计当成当前实现事实。
5. 阅读目标源码、相邻测试和真实调用方，核验文档描述的行为、接口和限制。文档与实现冲突时，记录漂移，不要用其中一方静默覆盖另一方。

路径不存在、导航失效或权威来源互相冲突时，先报告缺口并缩小结论范围。不要为了继续流程而虚构替代规则、文件或命令。

## 先决定结构和归属

编辑句子之前，先明确文档的受众、主题、直接子主题和使用方式：

- 根据当次读取到的仓库规则，区分当前架构、源码契约、功能演进和 durable memory，并把内容留在其权威所有者处；在其他位置用链接代替复制。
- 从读者意图判断文档类型，不只看目录或标题。教程应从明确前置条件推进到可观察结果；参考文档应支持在清晰范围内独立查询。
- 私下检查教程概念的依赖顺序。把尚未建立前置知识的内容后移，把可选深层细节放到更合适的教程或参考文档。
- 小范围混合内容可用清晰小节隔开；两种用途都占较大篇幅时拆分，并指定一个权威入口。
- 父级文档只保留理解导航所需的摘要；深入行为放到其所有者处。不要建立需要多层跳转才能发现的说明链。

## 编写、移动与审查

1. 先检查工作树、目标文件及其上下文，识别用户已有修改并保持改动范围。
2. 用 `rg` 搜索目标路径、标题、锚点和有辨识度的短语，查找 Markdown、源码注释、字符串及其他可能的入站引用。
3. 移动或重命名时，在同一改动中完成旧位置处理、目标位置更新和全部入站引用修复。生成内容应修改其来源或生成器，不要直接编辑生成结果；`project-memory/index.md` 必须通过当前仓库声明的生成入口更新。
4. 先修正文档层级、主题归属和阅读顺序，再处理措辞、格式和篇幅。
5. 逐项用源码、测试、配置和实际入口验证行为陈述。对无法证明的陈述标记不确定性或删除，不把推断写成事实。
6. 若改动影响其他权威材料，按当前 `AGENTS.md` 和相关入口给出的同步要求处理；不要在本 Skill 中预设同步清单。

审查或精简时，重点识别：

- 同一事实存在多个维护副本，且没有明确权威所有者。
- 推理过程、实施流水账、评审过程或已经失效的状态记录泄漏到长期文档。
- 手写目录、接口清单、测试清单或配置清单能够从更权威的源码、配置或导航生成或查询。
- 文档只重复类型签名、代码控制流或测试步骤，没有补充契约、理由或使用边界。
- 当前实现、历史设计和未来计划混在一起，使读者无法判断哪些已经生效。

保留承载非显然契约、安全或兼容边界、长期适用理由以及必要操作结果的内容。长度本身不是缺陷；优先删除重复和无所有者内容，不为压缩而丢失约束。

## 避免引入不存在的机制

- 不从参考仓库复制专属目录、文档类型、翻译流程、预算工具、生成器或检查脚本。
- 不假设固定 package manager、测试命令、文档预算或 CI gate。读取当前 manifest、配置、脚本和 CI 定义，选择实际存在且与改动相关的验证。
- 不在本 Skill 中复述 `AGENTS.md` 的语言、提交、TSDoc 或架构同步细则；执行时读取并遵守其当前版本。
- 不主动创建或修改 `project-memory/`。只有用户明确要求 distillation 或既有 Capsule 维护，并通过适用流程的证据、预览和授权门槛后，才写入 durable memory。
- 保留用户已有改动和任务标记；具体处理规则以目标路径适用的 `AGENTS.md` 与 Spec 工作流为准。

## 行为边界与输出

- 用户要求审查、审计或建议时，默认只报告问题、证据、建议位置和验证方式，不修改文件。
- 用户明确要求编写、移动或修订时，才实施对应文档改动；不要借文档任务改变未获授权的产品行为。
- 报告文档漂移时，分别指出文档陈述、实现证据和需要产品或设计决策的差异，不自行把历史材料提升为现行规范。
- 输出优先按影响排序，并为每个结论提供可定位的仓库路径或符号。说明已读取的权威入口、实施或建议的改动、运行的检查以及尚未解决的缺口。

## 验证

从当前仓库发现验证方式，而不是复用本 Skill 中的陈旧命令：

1. 检查目标路径适用的 `AGENTS.md`、项目 manifest、配置、脚本和 CI 定义，选择与改动范围匹配的检查。
2. 验证 Markdown 结构、代码围栏、相对链接、标题锚点和移动后的入站引用。
3. 文档包含代码示例或行为契约时，使用当前源码与相关测试核验；不要运行会产生费用或外部副作用的检查，除非用户明确授权。
4. 运行 `git diff --check`，再检查最终 diff，确认没有改写用户无关内容或复制动态规则。
5. 如仓库没有适用的自动化检查，明确记录已完成的人工验证和未覆盖风险，不虚构通过结果。
