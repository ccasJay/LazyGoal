# LazyGoal 功能分支集成

把已完成的功能分支或 Spec worktree 交接到指定目标分支。先证明源分支的验收结果适用于当前提交，再验证合并后的代码，最后更新目标分支。`lg-spec-worktree-execution` 负责逐任务实现与提交；本 Skill 从其交接状态开始。

## 判断请求与权限

- “检查能否合入”“审查合入准备”是只读请求：报告结论，不改 Git 引用或文件。只有用户明确要求合入时才更新目标分支；之前的 Spec 执行授权不等于合入授权。
- 从用户请求、当前 worktree 和 Git 引用确定源分支与目标分支。目标不明确且不能从明确的交接上下文唯一确定时，先核对目标，不猜测 `dev` 或 `main`。尊重用户指定的分支与合并方式。
- 合入授权不包括 push、建 PR、删除源分支或源 worktree，也不包括写入 Project Memory；这些操作各自需要明确请求。不要 stash、丢弃或提交他人的未提交改动来清理现场。

## 建立可合入事实

1. 读取仓库根及相关 worktree 适用的 `AGENTS.md`。有对应 Spec 时，读取其 `requirements.md`、`design.md`、`tasks.md`，包括 `Feature Verification` 的 Planned Checks 和 Latest Result；fast plan 则读取对应 `plan.md`。没有 Spec 时，以用户明确的验收条件、分支交接记录和当前实现测试为依据，不虚构 Spec 状态。从当前 `package.json` 和脚本发现验证命令，不沿用 Skill 中的历史命令。
2. 用 `git worktree list`、`git status`、`git merge-base`、`git log` 和源/目标差异确认两个引用的当前提交、工作树是否干净、源分支是否已经合入，以及是否包含尚未合入的父分支。源或目标工作树有未提交改动时，不把这些改动混入集成；无法隔离时报告阻塞。
3. 有 Spec 时，检查全部要求的 TODO 已完成，且 Feature Verification 对当前源提交及验收合同为 `passed`、`current`。没有 Spec 时，对照约定的验收条件检查当前源提交的可归属证据。复选框、单项测试通过或旧提交上的通过记录不能单独证明就绪。对于过期或缺失的证据，按适用的 Feature Verification 流程完成受影响的检查；用户只要求只读就绪审查时，只报告证据缺口。需要人工验收或真实环境检查而尚未完成时，按实际状态报告，不写成通过。
4. 对堆叠分支核对父子关系和目标已有提交。若源分支带有未获本次合入授权的父分支改动，先报告依赖并确认合入顺序；不通过 cherry-pick、rebase 或隐式合入父分支改变范围。已合入的源分支报告当前目标提交，不重复制造合并提交。

## 验证候选合并

1. 获得合入授权且就绪条件满足后，从目标提交建立临时候选集成分支或 worktree，在那里合并源分支。目标分支在候选验证完成前保持不变。使用用户指定的合并方式；未指定时根据仓库现有历史选择能保留可审查来源的方式，不重写源分支历史。
2. 合并冲突先按当前已批准的行为合同解决。若冲突要求改变需求、设计、验收标准，或引入未获授权的其他功能，停在候选分支并报告具体差异；不要凭冲突解决过程替用户作产品决定。
3. 在候选提交上运行当前仓库的完整确定性回归入口，并核对合并范围的差异与文档。若合并本身改变了实现或验收合同，更新受影响的 Feature Verification 证据，再执行相关检查。失败时诊断并在授权范围内修复，保留目标分支不变；不得跳过、缩小或改名失败用例来宣称通过。
4. 更新目标前重新确认它仍指向构建候选时的提交。只有候选检查通过、目标未前进且工作树干净时，才将已验证的候选提交快进到目标；否则重新评估合并与验证，不强制更新引用。核对目标最终提交和工作树状态。

## 交接

报告源与目标的分支名和提交、实际合并方式、候选及目标最终提交、运行的检查与结果、未完成的人工或真实环境验收，以及仍需处理的冲突或阻塞。检查相关 Project Memory 索引中的影响候选，但不自动生成或修改 Capsule。保留源分支和源 worktree，除非用户另行要求清理。
