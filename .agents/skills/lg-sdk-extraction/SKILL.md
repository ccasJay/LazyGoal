# LazyGoal SDK 提炼

将已有执行能力封装为无界面、状态可控、可嵌入的运行时库。库负责内部执行复杂度，宿主通过明确契约提供任务、扩展能力、控制交互并观察结果。

## 范围与事实来源

- 从用户指定的入口、package、组件或嵌入场景开始；未指定位置时，先只读定位能完成该场景的最小调用链，不扩展成全仓库重构。
- 读取适用的 `AGENTS.md`，从根 `README.md` 定位相关模块说明，再核对公开导出、源码、相邻测试、真实消费者和依赖检查规则。区分现有能力、契约缺口与建议设计。
- 分析、讨论和审查请求只报告发现。实现以用户授权及适用 Spec 为边界；需要进入 Spec 流程时使用 `using-lazyspec`，本 Skill 不替代其阶段规则。
- 涉及领域状态与跨模块契约时使用 [lg-domain-development](../lg-domain-development/SKILL.md)；文档归属与文本按 [lg-doc-standards](../lg-doc-standards/SKILL.md)、[lg-prose-standard](../lg-prose-standard/SKILL.md) 处理。

## 从真实嵌入场景确定边界

先描述宿主如何创建运行时、提交任务、接收活动、处理交互并释放资源；可恢复场景还需描述重建实例后如何重新关联原 Goal。用最小调用方代码草图验证接口是否足够，而不是先罗列 SDK 功能。

沿调用链区分三类内容，并为状态和副作用指定所有者：

| 内容 | 提炼目标 |
| --- | --- |
| 宿主职责 | 用户界面、输入来源、HTTP 或 CLI 传输、进程信号与退出决策留在应用边界。 |
| 运行时机制 | 模型和工具执行、上下文管理、重试、检查点、恢复及自有资源管理由库内实现协作完成。 |
| 扩展契约 | 仅暴露当前消费者需要替换的工具、策略、存储等接口，并提供适合真实场景的默认装配。 |

SDK 门面可以在外层组合既有模块。保留领域规则的现有所有者，检查依赖方向，避免让核心反向依赖应用或 SDK。共享装配从真实消费者的共同职责提炼，应用差异留在适配层；不因代码相似就强行合并。

## 对外契约与内部封装

- 先区分创建与恢复、同一 Run 恢复与后继 Run、到达等待点与终态。顶层操作复用现有领域入口，不在 SDK 复制状态判断或直接拼接状态。
- 明确宿主配置、Goal 持久化配置和调用级控制的作用范围。说明恢复时哪些值来自快照、哪些需重新注入；凭据、函数、连接和进程句柄不直接进入可恢复快照。
- 将默认装配细节收进库内，调用方无需自行组合执行器、上下文组装器或提交器。内部仍保留诊断能力，公开结果应表达等待、失败、取消和完成等可观察后果。
- 公开入口只承诺调用方所需的操作、类型和扩展点，不把内部对象全集重新导出。优先复用适合公开的既有类型；仅在确有边界差异时增加映射层。
- API 名称、SDK 目录和打包方式由实际消费方式决定。不预设必须采用 `query()`、新建 `sdk` 包、跨进程封装或支持所有运行环境；单语言嵌入不要求先建立进程协议。

## 控制、事件与扩展

- 控制命令与观察订阅分别定义生命周期。异步迭代可以观察执行；解除订阅、订阅故障、背压与执行中断的关系必须明确，避免由观察者消费速度隐式决定状态推进。
- 实时活动与恢复事实分清来源。需要重连或重启恢复时，使用现有持久化边界；不将临时事件或模型增量当成已提交结果。
- 扩展按用途定义权限：观察回调说明失败是否隔离；策略接口返回受限决策，由 Runtime 应用；人工审批复用可持久化等待与恢复命令，不能仅靠悬挂回调保存等待关系。
- 对可能阻塞或改变执行的扩展，说明调用时机、取消、异常后果及恢复后是否重复调用；不提供可任意修改内部状态的通用 Hook。
- 区分工具可见范围、自动批准规则和执行授权；不要仅凭参考 SDK 的字段名推断语义。模型切换等控制继续遵守领域安全点与持久化规则。

## 资源、隔离与恢复

- 为运行时创建和宿主注入的资源分别说明所有权与关闭责任；定义实例关闭对活动执行、等待状态和后续恢复的影响。嵌入式关闭只处理约定资源，进程退出由宿主决定。
- 环境与工作区通过实例配置传递；核对隐式配置读取、共享可变模型绑定、授权、持久化命名空间和中止信号。配置对象本身不构成并发或租户隔离保证，按目标场景声明支持范围。
- 重试、看门狗和协议握手可以封装在库内，但不能隐藏副作用结果未知的情况。保持既有提交顺序和重放规则，禁止将未知结果操作当作安全重试。
- Runtime 状态恢复与外部文件回滚分别定义保证。递归调用执行入口只能复用引擎；子代理的身份、父子恢复、权限、预算和取消传播应在明确需求下单独设计，不随 SDK 提炼自动引入。

## 最小实施与验证

获授权实现时，先完成一个贯穿创建、执行与关闭的嵌入切片，再按场景补齐交互和恢复，并接入一个现有消费者验证契约。保持既有领域行为，不同时重写执行循环、增加插件平台或扩大公开承诺。

按本次承诺选择可观察验证，从当前仓库脚本发现适用检查：

- 独立调用方通过约定入口完成任务与自定义扩展，无需启动界面、绑定端口或手动装配内部执行对象。
- 涉及审批与恢复时，覆盖等待后重建实例、关联原 Goal 并恢复推进，核对已提交操作的重放行为。
- 涉及订阅与关闭时，覆盖解除订阅、显式中断和资源释放，确认宿主进程仍可继续工作；关闭语义与契约一致。
- 承诺多实例并发时，验证配置、模型、授权、中止与持久化作用范围；未验证的能力不得报告为已支持。
- 对受影响消费者运行相关回归，并执行适用的依赖与文档检查。分析请求只给出验证建议，不把未执行检查写成通过。

报告时列出有源码依据的边界问题、建议的最小提炼位置、公开契约及明确限制。实施后报告调用方得到的行为、实际验证与剩余缺口；不以新增包或导出函数数量作为 SDK 化完成的证据。
